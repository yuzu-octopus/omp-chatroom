# Angle
Prompt caching and cache-stable context for multi-agent systems

## Claims (claim / source URL / fetch date / confidence per item — confidence: primary > secondary > speculative)

### Anthropic prompt caching (cache_control, TTL, prefix matching)
- **Claim:** Prompt caching is a prefix match; any byte change anywhere in the prefix invalidates everything after it. Render order is `tools` -> `system` -> `messages`. A breakpoint on the last system block caches tools + system together. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Two ways to enable: automatic caching (top-level `cache_control` field) or explicit cache breakpoints (`cache_control` on individual content blocks). Up to 4 cache breakpoints per request. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Default TTL is 5 minutes (refreshed on cache hit at no extra cost); lifetime measured from request start (generation time counts). Optional 1-hour TTL available at higher cost (`"ttl": "1h"`). For 1-hour, cache writes cost 2× base input; reads still 0.1×. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Cache reads cost 10% of base input (or 2.5% for Claude Fable 5.1/Mythos 5.1, 5% for Opus 5.5/Sonnet 5.5). Cache writes cost 25% more than base for 5-minute TTL. Breakpoints themselves have no cost. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Lookback window is up to 20 blocks when walking backward to find prior writes; a run of consecutive tool_use/tool_result blocks counts as one position. Writes only occur at breakpoints; the system does not auto-cache behind a breakpoint. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Caches isolated by workspace (Claude API/Platform/AWS Foundry) or by organization (Bedrock/Google Cloud managed); never shared across organizations. Exact byte match required including all text/images up to breakpoint. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** When mixing TTLs, entries with longer TTL must appear before shorter TTLs in the prompt. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary

### OpenAI prompt caching
- **Claim:** Prompt caching reuses KV states for unchanged prompt prefixes; caches model's full rendered context including OpenAI-provided instructions, developer messages, tool definitions, conversation history. Cached states are KV tensors (not tokens). | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** For GPT-5.6+, explicit/implicit caching supported; cache writes cost 1.25× for 30-minute TTL (default), or 2.5× for 12-hour TTL via `prompt_cache_options.ttl`. Reads cost 0.1× on most GPT-5.6+ models (0.05× on GPT-6.1 Sol). Prefix must meet minimum cacheable length (1024+ tokens for GPT-5.6+, varies for earlier models). | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Implicit caching places breakpoints automatically at eligible message endings; explicit mode via `prompt_cache_options.mode: "explicit"` with `prompt_cache_breakpoint` markers gives control, up to 4 cache writes per request. Content after last selected breakpoint not cached. | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Cache reuse requires entire rendered prefix to match; changes to model, tools, schemas, ordering, parallel_tool_calls, reasoning.effort, text.format affect cached prefix. Caches stored on machines, not shared across orgs/regions; routing affected by prompt hash and optionally `prompt_cache_key` (less critical on GPT-5.6+). | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Earlier models only support implicit caching; caches typically cleared after 5-10 min inactivity, removed within 1 hour of last use (default behavior varies). | **Source URL:** https://openai.com/index/api-prompt-caching/ | **Fetch date:** 2026-10-26 | **Confidence:** primary

### What makes a prefix cache-stable
- **Claim:** Prefix cache-stable means byte-identical prefix across requests; any byte change at position N invalidates everything after. Must control ordering (render order fixed), eliminate per-request/per-turn volatile values from early positions, keep JSON key order stable. | **Source URL:** https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/prompt-caching.md | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Classify inputs by stability (never changes -> early; per-session -> middle; per-turn -> end; per-request like timestamps/UUIDs -> eliminate or move to very end). Put breakpoints at stability boundaries. | **Source URL:** https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/prompt-caching.md | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** For shared prefix varying suffix, put breakpoint at end of shared portion (not whole prompt) or you'll write distinct cache entries every request. | **Source URL:** https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/prompt-caching.md | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Tool definitions must remain identical (names, descriptions, schemas, ordering) across cached turns - changing them breaks prefix. | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary

### Multi-agent systems maintaining cache hits when injecting shared context
- **Claim:** Move volatile/live state out of system prompt into tail (e.g., user message/end of request) so byte-stable prefix survives; append-only pattern preserves cache. Example: move "changed files", browser tabs to `<runtime_state>` at end of messages. | **Source URL:** https://github.com/bitsky-tech/bridgic-agent/pull/11 | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** For forked/subagent fan-out, keep byte-identical prefix across workers and vary only final instruction block to share cached prefix. | **Source URL:** https://blog.ax0x.ai/prompt-cache-is-architecture | **Fetch date:** 2026-10-26 | **Confidence:** secondary (blog post analyzing implementation pattern)
- **Claim:** In multi-agent pipelines sharing context, put shared prefix in stable position with breakpoint; if shared state mutates frequently between steps, cache writes invalidate and cost crossover occurs. Closed-form arithmetic over published multipliers (write 1.25× 5-min / 2× 1h, read 0.1×), NOT a measurement: for a 3-step pipeline, crossover ≈0.67 mutation rate (5-min TTL); 1h TTL ≈0.21 from the higher write cost; longer pipelines drift into the high 0.70s. Savings % are of shared-prefix input cost only (per-step unique input + all output cancel out, which is why the crossover rate is robust). From an OPEN community PR (contributor @hipvlady, opened 2026-06-13, still open, execution of the one live-API cell pending maintainer run). | **Source URL:** https://github.com/anthropics/claude-cookbooks/pull/707 | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** When evolving state must be shared across agents, options are composable: keep in prefix paying mutation cost, externalize to retrieval layer (pull relevant context), and/or coordinate/version for currency. Externalizing attacks broadcast cost; coherence is separate concern. | **Source URL:** https://github.com/anthropics/claude-cookbooks/issues/596#issuecomment-2966806244 | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Routing A2A/volatile context through tail/runtime-context message (not system prompt) preserves byte-stable prefix across sources; injecting volatile content into system prompt ahead of history/tools invalidates prefix on every change. | **Source URL:** https://github.com/openclaw/openclaw/issues/112986 | **Fetch date:** 2026-10-26 | **Confidence:** primary

### Cost of cache misses
- **Claim:** Cache miss means full price for tokens; cache hit much cheaper. Anthropic: read 10% of base, write 125% of base (5-min). OpenAI GPT-5.6+: read 10% (or 5%), write 125% (30-min) or 250% (12-hr). Net depends on reuse count and TTL. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching, https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Anthropic break-even framing: 5-min caching pays for itself after one cache read (1.25x write + 0.1x read = 1.35x vs 2x for two uncached). 1-hour needs at least two reads (2x + 0.2x = 2.2x vs 3x uncached). | **Source URL:** https://technspire.com/en/blog/anthropic-prompt-caching-pricing-mechanics | **Fetch date:** 2026-10-26 | **Confidence:** secondary
- **Claim:** Cache miss cost is especially high in multi-agent fan-out if prefixes not shared; sharing identical prefix across workers/forks avoids N× cost. | **Source URL:** https://blog.ax0x.ai/prompt-cache-is-architecture | **Fetch date:** 2026-10-26 | **Confidence:** secondary
- **Claim:** If shared prefix mutates on >~67% of steps (3-step, 5-min cache; closed-form over published multipliers, not a measurement), not caching can be cheaper than repeatedly rewriting cache. | **Source URL:** https://github.com/anthropics/claude-cookbooks/pull/707 | **Fetch date:** 2026-10-26 | **Confidence:** primary

### Patterns that maximize cache hit rate
- **Claim:** Keep byte-stable prefix first (tools/system/stable context), put volatile content last (user tail/runtime state). Render order: tools -> system -> messages. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching, https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/prompt-caching.md | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Use append-only conversation history (don't rewrite earlier turns); avoid mid-conversation reloads of cached-layer content. | **Source URL:** https://github.com/NousResearch/hermes-agent/issues/13631, https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Keep tool definitions/schemas stable and ordered; structured output schema in prefix affects caching. | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching, https://community.openai.com/t/prompt-caching-not-applied-when-schema-changes/967577 | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** For multi-turn, place breakpoint on last block of growing conversation (automatic) or manage explicitly; earlier breakpoints remain valid. For shared static content varying per request, breakpoint at end of shared portion. | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching, https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/prompt-caching.md | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Use appropriate TTL based on request cadence (5-min for frequent <5min gaps; 1-hour for longer gaps but higher write cost). | **Source URL:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching, https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** For multi-agent fan-out, share byte-identical prefix across workers; route volatile/runtime context to tail; consider external shared state + retrieval when shared context mutates often. | **Source URL:** https://blog.ax0x.ai/prompt-cache-is-architecture, https://github.com/anthropics/claude-cookbooks/pull/707, https://github.com/bitsky-tech/bridgic-agent/pull/11 | **Fetch date:** 2026-10-26 | **Confidence:** primary
- **Claim:** Avoid changing reasoning effort, model, parallel_tool_calls mid-way in ways that break prefix; use mechanisms that don't rewrite prefix when possible. | **Source URL:** https://developers.openai.com/api/docs/guides/prompt-caching | **Fetch date:** 2026-10-26 | **Confidence:** primary

## Gaps
- **Quantitative multi-agent benchmarks:** Limited primary benchmarks on cache hit rates/cost in large multi-agent swarms; most data comes from implementation PRs/issues and cookbooks rather than controlled studies.
- **Cross-provider cache coherence semantics:** No single primary source comparing exact behaviors across all providers in multi-agent contexts; behavior inferred from provider docs.
- **Long-running agent sessions:** Cache eviction behavior over very long sessions (hours) and interaction with context compaction not fully specified in primary docs.
- **Provider-side routing effects:** Exact hashing/routing internals not fully documented; impact on cache reuse in distributed/multi-instance deployments unclear.
