## Addendum — what an extension CAN observe of peer traffic

- Incoming IRC messages are delivered as a `custom`-role message (`customType: "irc:incoming"`) and routed through `agent.emitExternalEvent({type:"message_start"|"message_end"})`, which the session forwards to extension `message_start`/`message_end` handlers. So a plugin CAN observe incoming peer messages in the session that hosts it, by filtering `message.role === "custom" && message.customType === "irc:incoming"`. | src/session/agent-session.ts:1170-1182; src/extensibility/extensions/lifecycle-mirror.ts:137-153; src/session/agent-session.ts:4812-4831 | primary
- There is NO dedicated `irc_message` extension event: `extensionEventFromSessionEvent` maps only 19 session-event types (agent/turn/message/tool-exec/auto-compaction/retry/ttsr/todo/goal) and returns `null` for everything else, including `irc_message`. The session-level `irc_message` event exists for UI/RPC subscribers, not extensions. | src/extensibility/extensions/lifecycle-mirror.ts:83-119; src/extensibility/extensions/types.ts:1204-1234 | primary
- Outbound peer messages are visible as an ordinary `tool_call`/`tool_result` on the `write` tool with `path: "agent://<id>"` (or `xd://`-dispatched variants), so a plugin can intercept/annotate outbound sends through the standard tool hooks. | src/internal-urls/agent-protocol.ts:170-200; omp://extensions.md (tool_call/tool_result) | primary

## Addendum 2 — the decisive architectural facts for a plugin blueprint

Four facts together determine whether an in-process room plugin is possible at all:

1. **Module-level state IS shared across the whole session tree.** Child sessions do not re-import the extension module; `bindPreparedExtensions` calls the SAME factory function object again with a fresh `ExtensionAPI` (`src/extensibility/extensions/loader.ts:490-520, 461-475`). Documented explicitly: "child sessions reuse imported factories but bind fresh APIs and extension registrations; module-level variables remain shared across those sessions" (`omp://extensions.md`, Runtime model). A plugin can therefore hold ONE process-global room store in module scope, shared by every agent in the tree. | primary
2. **A fresh, per-session `ExtensionAPI` is bound per child**, so `pi.sendMessage`/`pi.sendUserMessage` inside the factory closure always targets the session that owns that binding — but the closure can also capture the per-session `ctx` handed to handlers/tools. The shared store and the per-session delivery API are both available. | src/extensibility/extensions/loader.ts:490-520; omp://extensions.md | primary
3. **`AgentRegistry` IS a public package export** (`src/sdk.ts:898`, re-exported by `src/index.ts`), and `AgentRef.session` is the live `AgentSession` with public `sendCustomMessage`, `steer`, `followUp`, `sendUserMessage`, `deliverIrcMessage`, `drainPendingIrcInboxMessages`, `waitForIrcReplies`, `setIrcWakeTurnObserver`, `emitIrcRelayObservation` (`src/session/agent-session.ts:7829,7852,8324,8518,10380-10420`). A plugin can therefore enumerate every agent in the process AND push a custom message into a SIBLING session's context directly — the one thing the missing `IrcBus` export would otherwise block. `IrcBus` itself is NOT exported (`src/index.ts` has no `irc/*`; `sdk.ts` does not export it), so a plugin cannot use the bus's mailbox/waiter machinery, but it does not need to: `AgentSession.sendCustomMessage` is the supported per-session injection path and `AgentRegistry` is the supported directory. | primary
4. **The shared `EventBus` is per top-level session and forwarded to children** (`src/sdk.ts:1632`; `src/task/structured-subagent.ts:653` `eventBus: session.eventBus`), giving a plugin a cross-agent in-process notification channel with no bus API of its own. Note it is NOT process-global across independent top-level sessions. | primary

Consequence for the brief's central question: an omp plugin CAN implement a persistent in-process room (shared log, claim board, blackboard) spanning main + subagents + nested subagents, with real push delivery, without any new omp API — by combining shared module state, `AgentRegistry` for the roster and cross-session injection, the shared `EventBus` for wake signals, and `appendEntry`/`local://` for durability. The irreducible native gaps are the ROOM SEMANTICS (topic addressing, shared durable log, claims/locks, read cursors, bounded room context), not the transport. | [INFERENCE] from 1-4 | primary-derived

Limits a plugin cannot escape: it is in-process only (no cross-process room); it cannot reach restricted/plan-mode children's tool sets (`src/task/structured-subagent.ts:604,674-676`); `AgentSession.sendCustomMessage` returns `false` when the target cannot own a turn, and idle targets without `triggerTurn` get context without a turn; and a message injected into a sibling is attributed to that sibling's own transcript, so the room log must be the plugin's own store, not a transcript.
