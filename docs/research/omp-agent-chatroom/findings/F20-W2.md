# F20-W2: Does any multi-agent / shared-log system compress a shared log hierarchically?

## Angle

Find or disprove: a system where the *shared* multi-agent log (not per-agent memory) is compressed
by a *hierarchical* structure (tree of summaries, recursive aggregation), so a late joiner gets a
bounded view instead of a gap. Search CRDT-summarised logs, epoch/generation summarisation, MAS
frameworks (AutoGen/CrewAI/LangGraph/MetaGPT/CAMEL/AgentVerse/ChatDev), memory layers
(Letta/MemGPT/Mem0/Zep/Graphiti), academic communication-compression, and OptMem/OptChat limits.

**Terminology used throughout:** *per-agent memory compression* = one agent's own history or notes
summarised for its own context (ubiquitous). *Shared-log hierarchical compression* = ONE shared
transcript of multiple agents, compressed into a multi-level summary structure that any agent (incl.
a late joiner) reads at bounded cost and can descend. The question is the second.

## Claims

### A. The verdict (negative evidence is the deliverable)

- [W2.1] **No system found that compresses a shared multi-agent log hierarchically.** Across
  framework docs/source (AutoGen, LangGraph, CrewAI, CAMEL, MetaGPT, AgentVerse, ChatDev, Agno,
  Letta, OpenAI Swarm), production memory layers (Letta, Mem0, Zep/Graphiti), MAS-memory papers
  (G-Memory, MIRIX, HMARS, DeALOG, DeLM, Agentsensus, AOI, Ensemble QSP, AutoWorldBuilder), and the
  agent-context-compression survey (EMNLP 2026), every deployed *shared* log is either (a) unbounded,
  (b) bounded by flat rolling/one-shot summarisation, or (c) compressed by a non-hierarchical
  mechanism (dedup, graph selection, KV/latent compression). — sources: see B–F below; survey
  https://github.com/YerbaPage/Awesome-Agent-Context-Compression (fetched 2026-10-06) — confidence: high
- [W2.2] The **only** hierarchical-summary-tree-over-a-transcript design found is OptChat/OptMem, and
  it is **single-writer, single-agent, single-chat**. OptChat: "One writer: two processes on the same
  chat would corrupt it. Hold a lock for the life of the process."; the memory is "the chat" of one
  user, not a shared multi-agent log. — source: https://gist.github.com/VictorTaelin/91837951a5ce5b38f341ec1ba1df6449 §2 (fetched 2026-10-06); /tmp/OptMem/README.md:100-106 — confidence: high
- [W2.3] The nearest *shared-log* analogue, OptMem's own rule, **forbids the multi-agent case**: "A
  subagent must never run `memo`, because it cannot judge what is already known, and its notes would
  arrive duplicated and incorrectly." The tree is therefore a single-judge structure by design. —
  source: /tmp/OptMem/README.md:100-106; /tmp/OptMem/memo:536-541 (fetched 2026-10-06) — confidence: high
- [W2.4] A 2026 survey of 89 LLM-agent papers on collective memory states plainly that commutative
  merge of natural-language memory **fails**: "semantic summarization is order-dependent and
  non-associative", so CRDT convergence "does not transfer without an equality relation over
  natural-language state". This is the theoretical reason no CRDT+summarisation shared tree is
  deployed. — source: https://github.com/xiaoqi-7/Multi-Agent-Memory-Survey (fetched 2026-10-06) — confidence: high
- [W2.5] The same survey codes **global scope in 0 of 89 papers** (widest scope: individual 53.9%,
  team 25.8%); 80/89 papers do not state who controls memory operations. No paper in the corpus
  implements a single globally-visible hierarchically-compressed shared log. — source: same (fetched 2026-10-06) — confidence: high

### B. MAS frameworks — shared state exists, hierarchical shared-log compression does not

- [W2.6] **AutoGen**: shared memory = "pass the same memory instance to multiple agents"; the
  documented memory API is store/retrieve, "**not itself a built-in conversation summarizer**".
  Model-context limiting is buffer/head-tail/token-limit selection, "not semantic summarization". —
  source: https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html (fetched 2026-10-06) — confidence: high
- [W2.7] **LangGraph**: shared state is a user-defined `messages` list; summarisation is an explicit
  pattern the *application* implements ("you decide when to summarize"), plus a documented warning
  that checkpoints grow unboundedly and must be pruned manually. — source: https://docs.langchain.com/oss/python/langgraph/persistence ; F6-blackboard-claimboard.md:29 (fetched 2026-10-06) — confidence: high
- [W2.8] **CrewAI / MetaGPT**: CrewAI's collaboration model "is not itself a guaranteed rolling
  group-transcript summarizer"; MetaGPT basic memory "stores messages and retrieves all or the most
  recent k by recency" — no semantic rolling summarisation. — sources: https://docs.crewai.com/core-concepts/Agents ; https://docs.deepwisdom.ai/main/en/guide/tutorials/use_memories.html (fetched 2026-10-06) — confidence: high
- [W2.9] **CAMEL**: shared state = per-agent `AgentMemory`; "No global board". Bounding is
  `ScoreBasedContextCreator(token_limit)`, not summarisation. — source: F6-blackboard-claimboard.md:50-51 (fetched 2026-10-06) — confidence: high
- [W2.10] **ChatDev 1.0**: global `ChatEnv` dict, but memory is bounded "by SEGMENTATION not
  truncation": short-term = utterances within one phase; long-term = only extracted solutions from
  prior phases (`M~^i = τ(M^j)`). One flat extraction step per phase — not a hierarchy. — source: F6-blackboard-claimboard.md:59-61; https://arxiv.org/abs/2307.07924 (fetched 2026-10-06) — confidence: high
- [W2.11] **AgentVerse**: `BasicEnvironment.last_messages: List[Message]` bounded by `max_turns`;
  no compression. **Semantic Kernel / Swarm**: no shared board at all (Swarm: "does not store state
  between calls"). — sources: F6-blackboard-claimboard.md:78-93 (fetched 2026-10-06) — confidence: high
- [W2.12] **AgentScope**: `MsgHub` broadcasts into a shared history; `MultiAgentFormatter` combines
  speakers, but "if that formatted history exceeds the token limit, built-in formatters truncate
  older messages; that is not summarization." Compression is a **per-agent** `ReActAgent` memory
  feature. — source: https://doc.agentscope.io/tutorial/task_agent.html ; .../task_prompt.html (fetched 2026-10-06) — confidence: high
- [W2.13] **Group-chat pattern catalogues** list the token blow-up as a *known pitfall* and prescribe
  "a rolling summary window ... last K messages or a compressed narrative of earlier turns" — i.e. a
  flat rolling summary, explicitly not a hierarchy. — source: https://multiagentsystems.sites.markushanses.de/en/pattern/group-chat/ ; https://github.com/Hovborg/multi-agent/blob/main/docs/patterns/group-chat.md (fetched 2026-10-06) — confidence: high

### C. Memory layers (Letta/MemGPT, Mem0, Zep/Graphiti) — per-agent or flat, never shared-hierarchical

- [W2.14] **Letta/MemGPT**: compaction summarises a conversation's in-context history (modes `all`,
  `sliding_window`, self-compaction); old messages remain retrievable but the summary is a **flat
  replacement**. Shared blocks are "update once, visible everywhere" memory, explicitly a different
  mechanism from summaries; "shared memory lets multiple agents access common information; it doesn't
  mean their conversation threads are merged." — sources: https://docs.letta.com/api/resources/conversations/subresources/messages/methods/compact ; https://docs.letta.com/guides/agents/multi-agent-parallel-execution/ ; https://docs.letta.com/v1-sdk/memory/shared-memory (fetched 2026-10-06) — confidence: high
- [W2.15] **Zep**: "There is one summary per thread, and it is persisted ... generated and updated
  automatically as new messages arrive." One flat summary per thread; summaries are an *extra* context
  type, not a tree, and there is no hierarchical roll-up of thread summaries into higher levels. —
  source: https://help.getzep.com/thread-summaries (fetched 2026-10-06) — confidence: high
- [W2.16] **Mem0 / Graphiti**: extract facts → dedup → store in vector/SQL/graph; Graphiti's third
  layer (Communities) has "optional groups/summaries" but the primary artefact is a bi-temporal
  entity/fact graph, not a summary tree over a shared transcript. — sources: F7-bounded-context-compression.md:174-188 (fetched 2026-10-06) — confidence: high

### D. MAS-memory papers — hierarchy exists, but over experience/retrieval, not the live shared log

- [W2.17] **G-Memory (NeurIPS 2025)**: "a hierarchical, agentic memory system for MAS ... a
  three-tier graph hierarchy: insight, query, and interaction graphs", retrieving "high-level
  generalizable insights" and "fine-grained, condensed interaction trajectories". Hierarchy is over
  **cross-trial collaboration experience**, retrieved by traversal; it is not a compression of the
  current shared transcript and does not give a late joiner a bounded tiled view. — source: https://arxiv.org/abs/2506.07398 ; https://github.com/bingreeky/GMemory (fetched 2026-10-06) — confidence: high
- [W2.18] **HMARS**: "Sub-agents maintain grounded access to bounded memory regions, mid-agents manage
  regional context and provide query-specific coordination, and a frontier model performs final
  reasoning over retrieved evidence pages." This is a **retrieval hierarchy** (region → mid → frontier),
  i.e. routing/expansion, not a merge tree of summaries over a shared log; regions are pre-existing
  documents/history, not merged. — source: https://arxiv.org/abs/2606.28349 (fetched 2026-10-06) — confidence: high
- [W2.19] **DeALOG**: "specialized agents ... communicate through a shared natural-language log as
  persistent memory." The shared log is real, but the paper "does not describe the log as a formally
  compressed or size-bounded memory" — the log is uncompressed; a Summarizing agent proposes an
  answer, it does not maintain a tree. — sources: https://arxiv.org/abs/2602.00996 (fetched 2026-10-06) — confidence: high
- [W2.20] **DeLM (Stanford)**: replaces the main agent with "a shared context and a task queue"; the
  shared context is "an append-only log of what agents learn" with typed entries (FACT/FAIL/DONE) that
  "stay brief and attach files by reference, so the log stays under 15K tokens even with four agents."
  Compression is a **flat per-entry gist**, bounded by authoring discipline — not a summary tree.
  Peer-status awareness and reuse are the contribution; the paper itself says "Coordination, not
  parallelism or CRDT-merge, bears the load." — sources: https://arxiv.org/abs/2606.10662 ; https://yuzhenmao.github.io/DeLM/ ; https://raw.githubusercontent.com/yuzhenmao/DeLM/main/board/shared_context.py (fetched 2026-10-06) — confidence: high
- [W2.21] **Agentsensus**: one unified long-term memory; "records of the same event merge into one
  owned by all its witnesses" (dedup/merge of duplicate memories), 22–44% fewer entries. Merging is
  **equality-based consolidation, not hierarchical summarisation**; no tree, no levels. — source: https://arxiv.org/abs/2609.32297 (fetched 2026-10-06) — confidence: high
- [W2.22] **AOI** (AIOps MAS): "hierarchical memory system with LLM-based context compression" —
  compresses operational context 72.4% preserving 92.8% diagnostic info, but it is an incident-response
  memory hierarchy (Observer/Probe/Executor roles), not a shared transcript tree. **Ensemble QSP**
  (three-layer hierarchical memory) similarly bounds *injected* context (median 301 tokens) by capping
  state categories and evicting completed work — eviction, not hierarchical summarisation. **AutoWorldBuilder**
  (4-layer context compression, ~90% token reduction) is task-schema layer budgeting, not a log tree. —
  sources: https://arxiv.org/abs/2512.13956 ; https://arxiv.org/abs/2607.07666 ; https://arxiv.org/abs/2607.09403 (fetched 2026-10-06) — confidence: medium
- [W2.23] **Learning to Share (LTS)** and **Gated-Memory Routing**: a *learned* gate decides which
  intermediate steps enter a **global memory bank** (LTS) / a learned execution memory (GMR). This is
  selective admission/pruning of a shared execution history — flat, learned, no hierarchy. — sources: https://arxiv.org/abs/2602.05965 ; https://arxiv.org/abs/2609.00237 (fetched 2026-10-06) — confidence: high

### E. Compression-side systems — flat, graph-based, or latent; never a shared summary tree

- [W2.24] **RAPTOR** builds a genuine recursive summary tree, but over a **static retrieval corpus**,
  not a live multi-agent shared log. **HAT** recursively aggregates *dialogue* context — single
  conversation, optimal-traversal retrieval, no shared/multi-agent dimension. — sources: https://arxiv.org/abs/2401.18059 ; https://arxiv.org/abs/2406.06124 (fetched 2026-10-06) — confidence: high
- [W2.25] **Toward a Theory of Hierarchical Memory** (ICLR 2026) formalises exactly the (extract,
  coarsen, traverse) pipeline, instantiating it on 11 systems. **None of the 11 is a shared multi-agent
  log**; the agent-trace instances (MemoBrain, StackPlanner, AgeMem, InfiAgent) are single-agent
  execution traces. The paper's own §4 notes "hierarchical organization of stored knowledge" and
  "three coupled hierarchies" remain open — it does not name a shared-log system. — source: https://arxiv.org/abs/2603.21564 (fetched 2026-10-06) — confidence: high
- [W2.26] **ReCAP**: "stores attention-derived importance scores and dependency links in a lightweight,
  persistent context graph" and selects messages per request. Graph selection, not a summary tree;
  single coding-agent history. **Parallel Context Compaction** summarises *blocks in parallel* for
  predictable volume — flat blocks, not hierarchical. — sources: https://arxiv.org/abs/2609.40118 ; https://arxiv.org/abs/2605.23296 (fetched 2026-10-06) — confidence: high
- [W2.27] **DebateOCR** compresses *shared* multi-agent debate histories cross-modally (to images,
  >92% token cut) and proves diversity across agents recovers omitted info — but it is a single-shot
  cross-modal encoding of the debate trace, **not hierarchical**, and not descendable node-by-node. —
  source: https://arxiv.org/abs/2602.00454 (fetched 2026-10-06) — confidence: high
- [W2.28] **KV-cache / latent sharing** (KVCOMM, LatCom, KVCMAS, Latent Briefing, Q-KVComm): compress
  the *representation* of a shared context across agents. These are not text-summary hierarchies and
  have no `zoom`-style descent; they solve redundant prefill, not bounded-view-for-a-late-joiner. —
  sources: https://arxiv.org/abs/2510.12872 ; https://arxiv.org/abs/2609.37017 ; https://arxiv.org/abs/2609.34060 (fetched 2026-10-06) — confidence: high
- [W2.29] **Compaction-as-projection (Apache Maka)** and **Union-Find compaction (provenance-preserving)**:
  both explicitly *reject* a summary tree — Maka keeps one rolling checkpoint with coverage metadata
  ("rolling checkpoints: do not repeatedly summarize the entire world"); union-find builds a forest of
  source-backed clusters. Maka's rolling checkpoint is the closest deployed design to "bounded view",
  but it is flat (one checkpoint + raw tail) and single-session. — sources: https://github.com/apache/maka/blob/main/docs/architecture/llm-compaction-events-log-projection-draft.md ; https://june.kim/provenance-preserving-compaction (fetched 2026-10-06) — confidence: high

### F. CRDT / epoch angles — proposed, not built

- [W2.30] **crdt-merge** (patented, BSL-1.1): two-layer CRDT agent state (LWWMap facts, ORSet tags,
  PNCounter) with a `ContextMerge` that dedups and budget-caps memory lists. It provides *convergence*,
  not hierarchical summarisation; its `ContextBloom` is O(1) dedup. No summary tree. — source: https://github.com/mgillr/crdt-merge/blob/main/docs/guides/convergent-multi-agent-ai.md (fetched 2026-10-06) — confidence: high
- [W2.31] **agentcrdt**: LWW + semantic rule engine over content-addressed `WorldFact`s; contradiction
  events for audit. Convergent *facts*, no summarisation at all. **AgentRoom** (CRDT-backed shared
  workspace) merges *files*, not a log; its finding is "Coordination, not parallelism or CRDT-merge,
  bears the load." — sources: https://github.com/sandeep-alluru/agentcrdt ; https://arxiv.org/abs/2608.23740 (fetched 2026-10-06) — confidence: high
- [W2.32] **Epoch/generation-based shared summarisation**: no system found. Epochs appear as *fencing/
  scheduling* (Kleppmann fencing tokens, ZooKeeper/etcd leader epochs, SAGA scheduling epochs), not as
  a shared-summary tree; the only epoch-vs-tree discussion found is F20-W4's own extrapolation, which
  concludes epoch/fencing can serialise compaction but does not create hierarchy. — sources: F20-W4.md:35-41 (fetched 2026-10-06); no primary system found — confidence: medium
- [W2.33] **Conversation Tree Architecture** (2026) is a tree of *context-isolated conversation
  branches* with parent/child context flow — a tree of contexts, not a compressed summary tree over a
  shared log; it is a design proposal, and "extends naturally to multi-agent settings" only as future
  work. — source: https://arxiv.org/abs/2603.21278 (fetched 2026-10-06) — confidence: high

### G. OptMem/OptChat limits and follow-ups (as requested)

- [W2.34] OptChat repo does **not** exist on GitHub (`https://github.com/VictorTaelin/OptChat` → HTTP
  404; GitHub search returns 0 items for `user:VictorTaelin OptChat`). OptChat is a gist spec only. —
  source: curl + GitHub API (fetched 2026-10-06) — confidence: high
- [W2.35] OptMem's stated limits (open issues): scoped/per-project memories (#9), split-memory merge
  (#19), transient status-log pollution (#14), torn-TREE-record handling (#10), separator bug (#12),
  no license (#8). None concerns multi-agent or shared-log hierarchy. — source: https://github.com/VictorTaelin/OptMem/issues (fetched 2026-10-06) — confidence: high
- [W2.36] **18 public replications of the OptChat spec** exist (GitHub search `optchat`, 2026-10-06),
  incl. `ericjuta/omp-optchat` (10★, OMP extension), `jonaslsaa/pi-optchat` (7★),
  `samoylenkodmitry/optchat` (MCP server, multi-machine), `Dinkum/Hermes-OptChat-Plugin`,
  `AodhanHayter/optchat-rs`. **All remain single-user**: `samoylenkodmitry/optchat` is the closest to
  multi-agent and still states "One memory for the Claude Code and Codex agents **of one user**" and
  "The machines share one memory through a folder" — replication across machines, not across agents;
  its subagent compactor is a *worker* for the same chat, not a peer. — sources: GitHub search API; https://github.com/samoylenkodmitry/optchat ; https://github.com/ericjuta/omp-optchat (fetched 2026-10-06) — confidence: high
- [W2.37] `ericjuta/omp-optchat` (an OMP port) confirms the single-writer boundary is deliberate and
  host-enforced: "Run just one enabled session per chat directory"; the lock "uses an OS-owned abstract
  Unix socket ... A second writer in the same network namespace fails." — source: https://github.com/ericjuta/omp-optchat (fetched 2026-10-06) — confidence: high
- [W2.38] OptChat explicitly **rejected** the two-region "raw hot tail" design that a shared-log variant
  would want: "Showing recent messages whole (and only older ones summarized) ... breaks everything",
  because "one 30 KB tool output entering the view forces dozens of merges among old lines, which are
  never split back". It also rejected hybrid raw blocks (§11 #15). The spec is therefore a *pure*
  summary tree, not the two-region design in this project's brief. — source: gist §5.3, §11 (fetched 2026-10-06); F20-W1.md:66-74 — confidence: high

## Conflicting evidence

- **"Hierarchical memory for MAS" is claimed by several papers** (G-Memory, HMARS, AOI, Ensemble QSP)
  but in every case the hierarchy organises *retrieval / experience / state categories*, not a merge
  tree over the live shared transcript. A keyword search for "hierarchical memory multi-agent" returns
  these and can mislead; the distinction must be checked per paper (see W2.17–W2.22).
- **DeLM's "shared context" is genuinely a shared append-only log** (the strongest shared-log hit), but
  its compression is a flat per-entry gist with a <15K-token budget — it is not hierarchical and has no
  descent. Treat DeLM as "shared log, non-hierarchical compression".
- **Zep's per-thread summary is "incrementally updated"**, which reads like progressive summarisation;
  the docs confirm it is one flat summary per thread with no level above it, and thread summaries are
  not merged upward. Not hierarchical.
- **The OptChat spec is sometimes described as multi-agent** because §9 defines `spawn`/`tell`; but
  subagents "stay in their own session, NOT in the main log", and the subagent prompt forbids `memo`.
  Multi-agent *use* of a single-writer tree, not a shared tree.
- **F20-W4 argued a CRDT multi-value register could in principle make a shared summary tree
  convergent**; the 2026 survey (W2.4) gives the counter-reason it is not done: summarisation is
  order-dependent and non-associative, so commutative merge has no equality relation to converge on.

## Gaps

- No source directly measures a *shared-log* hierarchical compression system because none was found;
  this is an absence claim backed by ~20 searches + ~40 primary fetches, not a proof across all code.
- AutoGen's `Memory` protocol, LangGraph's checkpointer, and Letta's compaction were verified from
  docs/API reference, not by tracing their full source for any hidden summariser.
- HMARS (2606.28349), AOI (2512.13956), Ensemble QSP (2607.07666) and AutoWorldBuilder (2607.09403)
  were verified from abstracts only (paywalled/HTML not fetched in full); their "hierarchical" labels
  are the authors' and the internal structure was not confirmed line-by-line.
- GitHub code search (`/search/code`) returned 401 (unauthenticated), so the search for a shared binary
  summary tree implementation rests on repo search + web search, not a code-level sweep.
- OptChat's gist comments (`?show=comments`) returned the same document body — no comment thread was
  retrievable, so no author statement on multi-agent limits beyond §9 was obtained.
- gossip.py HN/Reddit/arXiv adapters returned empty result sets for every query tried, so forum
  chatter contributed no evidence.
