# F21-W4: Invalidation and divergence detection

## Angle
Can a node be wrong? What if two compactors disagree? Is the tree content-addressed (hash of children)? How is divergence detected and resolved? What happens when a compressed node must be invalidated? OptMem's forget: exact semantics.

---

## Claims

### OptMem `forget` semantics

**Claim 1:** `memo forget <lo>-<hi>` calls `tree_drop(d, lo, hi)` which truncates every level file at or above the block's level back to the block's position, invalidating the target block and all its descendants. The log is never touched.
- **Source:** `/tmp/OptMem/memo:372-389` (`tree_drop`), `/tmp/OptMem/memo:718-728` (`cmd_forget`)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 2:** `tree_drop` iterates `size` from `hi-lo` up to `log_len(d)`, and at each level truncates the file at offset `k * TREE_REC` where `k = lo // size`. This removes the target block and all blocks built from it at every higher level.
- **Source:** `/tmp/OptMem/memo:379-386`
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 3:** After `forget`, the forgotten blocks appear in `pending()` and are rebuilt in order by `memo nap`. The rebuild starts from the smallest (oldest) forgotten block. The log is the sole source of truth — summaries are a rebuildable cache.
- **Source:** `/tmp/OptMem/memo:437-449` (`pending`), `/tmp/OptMem/memo:489-494` (`next_nap`), `/tmp/OptMem/memo:666-692` (`cmd_nap`)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 4:** `forget` prints "Forgot N summaries, from lo-hi up. Run: memo nap" — it reports the count of invalidated summaries and the range, then instructs the agent to rebuild.
- **Source:** `/tmp/OptMem/memo:727-728`
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 5:** OptMem uses a lock file (`fcntl.flock` on Unix, `msvcrt.locking` on Windows) to serialize all writes. Only one process writes at a time. The lock is held for the duration of each write operation (`log_append`, `tree_put`, `tree_drop`).
- **Source:** `/tmp/OptMem/memo:302-332` (`locked`), `/tmp/OptMem/memo:335-350` (`log_append`), `/tmp/OptMem/memo:353-369` (`tree_put`), `/tmp/OptMem/memo:372-389` (`tree_drop`)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 6:** OptMem is NOT content-addressed. Blocks are identified by position (offset in TREE/<size> file), not by hash of children. There is no hash comparison anywhere in the codebase.
- **Source:** `/tmp/OptMem/memo:68-73` (position IS identity), `/tmp/OptMem/memo:279-292` (`tree_get` — seek by offset)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 7:** OptMem has NO divergence detection. If two compactors disagree on a summary, there is no mechanism to detect or resolve it. The lock serializes writes, but there is no validation that a summary is "correct" — it is whatever the LLM produced. A bad summary can only be detected by a human or agent reading it and calling `forget`.
- **Source:** `/tmp/OptMem/memo` (entire file — no hash, no validation, no comparison logic)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 8:** OptMem's `tree_get` detects corruption: if a summary record is blank (empty after rstrip), it dies with "The summary of #lo-hi is corrupt. Run: memo forget lo-hi". This is the only "validation" — a blank record is treated as corrupt.
- **Source:** `/tmp/OptMem/memo:288-292`
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 9:** OptMem's `nap_prompt` also detects missing halves: if a child summary is `None` when building a parent, it dies with "The summary of #a-b is blank. Run: memo forget a-b". This is a build-time check, not a divergence check.
- **Source:** `/tmp/OptMem/memo:469-475`
- **Fetch date:** 2026-10-06
- **Confidence:** primary

### OptChat compactor validation

**Claim 10:** OptChat enforces size on compactor output: TRIES=5 attempts to get under NODE=512 bytes. Shows the line cut at 512 bytes with a visual marker. Keeps the shortest try. A stubborn node keeps its shortest try, a few bytes over.
- **Source:** gist §4.3 (lines ~280-300 of fetched content)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 11:** OptChat has NO semantic validation. There is no check that a summary is "correct", "consistent" with its children, or "equivalent" to the source. The only validation is size. A bad summary is stored and used until a human notices.
- **Source:** gist §4.3 (size enforcement only), gist §4.4 (compactor prompt — no validation step)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 12:** OptChat retries failed nodes forever: RETRY=10s wait, then retry. Only the first failure is reported. "Don't use long exponential backoff: the next turn waits for these summaries, so the compactor must catch up as fast as possible."
- **Source:** gist §4.1
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 13:** OptChat's `settle()` waits until all view parts are built before starting a turn. No call ever sees an unbuilt placeholder. The placeholder `(not summarized yet: zoom it)` exists only for display and as a fail-safe.
- **Source:** gist §6
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 14:** OptChat is NOT content-addressed. Nodes are identified by `(l, i)` coordinates (level, index), not by hash of children. The `busy` set prevents concurrent builds of the same node. There is no hash comparison.
- **Source:** gist §3 (addressing: `id+n` where `id` = first message, `n` = 2^l), gist §4.1 (`busy` set)
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 15:** OptChat has a single-writer lock: "two processes on the same chat would corrupt it. Hold a lock for the life of the process. The reference uses a Unix socket." No PID files, no timeouts.
- **Source:** gist §2

- **Confidence:** primary

**Claim 16:** OptChat's compactor rule 3 ensures messages are compressed one at a time, in order: "every line of the current view that lies before the node's end is a built summary." The compactor never sees a line that isn't a summary.
- **Source:** gist §4.1
- **Fetch date:** 2026-10-06
- **Confidence:** primary

### Content-addressing and divergence detection

**Claim 17:** Neither OptMem nor OptChat is content-addressed. Both use positional identity. This means:
- No hash comparison to detect divergence
- No way to verify a summary is "correct" without re-computing it from the log
- Divergence can only be detected by re-reading the log and re-computing
- A bad summary is indistinguishable from a good one without external judgment
- **Source:** `/tmp/OptMem/memo:68-73`, gist §3
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 18:** In a content-addressed Merkle tree, divergence detection works by: compare root hashes → if different, descend into children → skip matching child hashes → recurse into differing branches. This pinpoints WHERE divergence occurred, not WHAT is correct.
- **Source:** https://docs.datastax.com/en/cassandra-oss/3.x/cassandra/operations/opsRepairNodesManualRepair.html, https://cassandra.apache.org/doc/latest/cassandra/managing/operating/repair.html
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 19:** In Git's Merkle-DAG, a changed parent hash tells you THAT something changed, not WHICH child changed. To locate divergence, decode both parent blocks and compare corresponding entries. Correspondence depends on the data structure (name-keyed vs positional).
- **Source:** https://github.com/ipld/docs, https://ipld.io/docs/intro/primer/
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 20:** Merkle trees detect divergence but do not resolve it. Resolution requires the system's conflict-resolution policy: version vectors, timestamps, application-specific merge logic, or CRDT semantics.
- **Source:** https://docs.datastax.com/en/cassandra-oss/3.x/cassandra/operations/opsRepairNodesManualRepair.html
- **Fetch date:** 2026-10-06
- **Confidence:** primary

### CRDT tree invalidation and concurrent compaction

**Claim 21:** In CRDT systems, safe reclamation of compacted history requires version vectors. A deletion is causally stable once `stableVV[A] >= deletion_counter` for every eligible peer. Only then can the tombstone be collected.
- **Source:** https://yorkie.dev/docs/internals/crdt-concepts, https://github.com/marcschier/crdt/blob/main/docs/architecture.md
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 22:** Concurrent compaction in CRDT systems: treat a compacted tree as a snapshot that incorporates a specific causal frontier. Build from consistent local state, record covered version vector, publish atomically, delete only log entries the snapshot includes. If two replicas compact concurrently, keep both snapshots or merge their covered histories.
- **Source:** https://automerge.org/docs/reference/under-the-hood/storage/
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 23:** LWW (last-writer-wins) is safe for scalar fields where losing one concurrent value is acceptable, but does NOT establish causality or prove that replicas have seen a deletion. For tree structure, use CRDT-specific deterministic rules (stable IDs, tie-breaks for concurrent insertions).
- **Source:** https://github.com/marcschier/crdt/blob/main/docs/architecture.md, https://automerge.org/docs/reference/documents/conflicts/
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 24:** Offline replicas make safe reclamation impossible without a bound: an offline replica could send an edit anchored to a removed node. Solutions: retain tombstones until every registered replica acknowledges, expire replicas after a lease/epoch, or reject operations older than the compaction frontier.
- **Source:** https://yorkie.dev/docs/internals/crdt-concepts
- **Fetch date:** 2026-10-06
- **Confidence:** primary

### Multi-agent room implications

**Claim 25:** Neither OptMem nor OptChat supports multi-writer. OptMem has a per-operation lock (serialized writes, no concurrent compaction). OptChat has a single-writer lock for the life of the process. For a multi-agent room, a single-writer compaction service is the simplest correct design.
- **Source:** `/tmp/OptMem/memo:302-332`, gist §2
- **Fetch date:** 2026-10-06
- **Confidence:** primary

**Claim 26:** In a multi-agent room with a single-writer compaction service, agents never compact — they only read the view and append to the log. The compaction service is the only writer of tree nodes. This eliminates divergence by construction: there is only one compactor.
- **Source:** [INFERENCE] from OptMem's subagent rule ("A subagent must never run memo") and OptChat's single-writer lock
- **Fetch date:** 2026-10-06
- **Confidence:** speculative

**Claim 27:** If multiple compactors are allowed (e.g., different agents compact different regions), content-addressing enables divergence detection: each node is a hash of its children, so two compactors that disagree produce different hashes. The divergence is detected by hash comparison, and resolved by re-computing from the log.
- **Source:** [INFERENCE] from Merkle tree literature applied to the room log
- **Fetch date:** 2026-10-06
- **Confidence:** speculative

**Claim 28:** In a multi-agent room, one agent's compaction can conflict with another's read if the read sees a stale view. OptChat's `settle()` prevents this by waiting for all view parts to be built. In a room, MVCC (each read gets a consistent snapshot) or a versioned view (each view is immutable once built) would prevent this.
- **Source:** [INFERENCE] from gist §6 (`settle()`), CRDT literature on snapshots
- **Fetch date:** 2026-10-06
- **Confidence:** speculative

## Conflicting evidence

**Conflict 1:** OptMem's X post says "nothing is ever deleted" but the `forget` command exists and drops summaries.
- **Resolution:** The log is never deleted — only summaries. Raw memories are permanent. Summaries are a rebuildable cache. "Nothing is ever deleted" refers to the log, not the tree.
- **Source:** `/tmp/OptMem/memo:719-721` ("The log is untouched, so nothing is ever actually lost"), X post 2081453432318132603

**Conflict 2:** OptMem's README says "426-token prompt" but the actual TEMPLATE in source is longer by most tokenizers.
- **Resolution:** 426 may be from an earlier version or a specific tokenizer. Not relevant to invalidation/divergence.
- **Source:** `/tmp/OptMem/memo:499-542` (TEMPLATE), README.md:3

**Conflict 3:** OptChat's spec says "the tree is a cache in principle (rebuildable from the log), but it costs model calls to rebuild, so it is stored and never recomputed." This suggests the tree is NOT rebuilt in practice, unlike OptMem where `forget` + `nap` is the rebuild path.
- **Resolution:** OptChat's tree is rebuilt only on corruption or manual intervention, not as a routine operation. OptMem's `forget` is a routine operation. The difference is that OptMem's summaries are cheap to rebuild (one LLM call per block), while OptChat's are expensive (one LLM call per node, with 64k token context).
- **Source:** gist §2, `/tmp/OptMem/memo:718-728`

## Gaps

1. **No content-addressing in either system.** Neither OptMem nor OptChat uses hashes to identify nodes. This is the biggest gap for divergence detection. A content-addressed tree would enable: (a) automatic divergence detection by hash comparison, (b) verification that a summary is "correct" by re-computing it, (c) deduplication of identical subtrees.

2. **No semantic validation.** Both systems validate size (OptChat) or blankness (OptMem), but neither validates that a summary is a faithful compression of its children. A summary that drops critical information or hallucinates is stored and used.

3. **No multi-writer support.** Both systems are single-writer. The multi-agent room use case requires either a single-writer compaction service or a CRDT-style approach with version vectors.

4. **No divergence resolution mechanism.** If two compactors disagree, there is no automatic resolution. The lock prevents concurrent writes, but if a compactor produces a bad summary, it stays until a human notices.

5. **OptChat has no `forget` equivalent.** OptMem has `forget` to drop a bad summary. OptChat has no documented way to invalidate a bad node. The only recovery is manual file editing or re-importing the log.

6. **No MVCC or snapshot isolation.** Neither system supports concurrent reads during compaction. OptChat's `settle()` blocks reads until compaction catches up. In a room, this would block agents from reading while compaction runs.

7. **No measurement of compaction quality.** Neither system measures whether summaries are "good" — whether they preserve critical information, whether they are consistent with children, whether they degrade over time. The only feedback is size (OptChat) or blankness (OptMem).

8. **CRDT tree literature is about operational transforms, not summary trees.** The CRDT tree literature (Automerge, Yjs, Yorkie) deals with concurrent edits to a shared document, not concurrent compaction of a summary log. The analogy is imperfect: compaction is a many-to-one merge, not a one-to-one edit.

9. **Merkle tree literature is about data synchronization, not summary trees.** Merkle trees are used to detect divergence in replicated data (Cassandra, Git, IPFS), not to validate that a summary is a faithful compression of its children. The tree structure is similar, but the semantics are different.

10. **No primary source for multi-agent summary trees.** No paper or system was found that addresses the specific problem of multiple agents compacting a shared summary log. This is an open research question.
