# F21-W5: Cost budget and invariants

## Angle
Compaction is LLM calls. Bound it: batch size, concurrency, max spend. What happens when compaction can't keep up? Invariants: tree rebuildable from log; no agent blocked on compaction; raw log stays authoritative; gap semantics when a tree exists. OptChat's JOBS=8: what's the right number for a room? OptMem's nap model: cost per node, total cost for N messages.

Fetch date: 2026-10-06.

## Claims

### Q1: OptMem cost model — nap cost per node, total cost for N messages

- [W1.1] **Each nap is one LLM call made by the agent itself.** `nap_prompt` (memo:463-486) generates a prompt; the agent runs `memo nap <lo>-<hi> "<summary>"` to write the summary. There is no background compactor. — source: `/tmp/OptMem/memo:463-494,666-692` — confidence: high
- [W1.2] **Cost per nap = one LLM call with the block's raw text or children's summaries as input.** For blocks ≤ RAW_MAX (16), the prompt body is the raw memories from `log_slice` (memo:464-465). For larger blocks, the body is the two halves' summaries from `tree_get` (memo:466-477). Output is one line of ≤ 280 bytes. — source: `/tmp/OptMem/memo:463-486` — confidence: high
- [W1.3] **Total naps for N messages = O(N).** Each block in the tree needs exactly one nap. A binary tree over N leaves has N-1 internal nodes, so total naps ≈ 2N (N level-0 blocks + N-1 merge blocks). But blocks ≤ RAW_MAX compress directly from raw log (one nap per block), and larger blocks compress from children's summaries (one nap per block). The total is bounded by the number of aligned power-of-two blocks covering [0,N), which is at most 2N. — source: `/tmp/OptMem/memo:82-131,437-449` — confidence: high
- [W1.4] **No explicit cost budget.** OptMem has no token budget, no concurrency limit, no max-spend cap. The only bound is `WAKE_LINES=96` (the wake output size) and `ENTRY_CHARS=280` (per-memory size). The agent decides when to nap. — source: `/tmp/OptMem/memo:50-65` — confidence: high
- [W1.5] **The agent is the compactor — compaction competes with the agent's own work.** `cmd_note` (memo:654-663) and `cmd_wake` (memo:584-651) print nap prompts. The agent must do the compression before its next action (TEMPLATE:523). This means compaction latency is added to the agent's critical path. — source: `/tmp/OptMem/memo:523,654-663,584-651` — confidence: high
- [W1.6] **Subagents must never run `memo`.** The TEMPLATE (memo:536-541) explicitly says: "A subagent is not: it must never run `memo`, because it cannot judge what is already known, and its notes would arrive duplicated and incorrectly." — source: `/tmp/OptMem/memo:536-541` — confidence: high

### Q2: OptChat cost model — JOBS=8, cost per node, total cost for N messages

- [W2.1] **JOBS=8 concurrent compactors.** The pump (optchat.md:192-204) scans all levels and starts every node that is not built, not running, has its sources, and has its context summarized. Up to JOBS=8 run at once. — source: `/tmp/optchat.md:89,192-204` — confidence: high
- [W2.2] **Cost per node = one LLM call with ~64k tokens of cached context.** Each compactor call sees the current view's lines up to the node, wrapped in `<chat>` tags (optchat.md:224-228). The context is ~64k tokens but is the same prefix across calls, so it is prompt-cached. Output is one line of ≤ 512 bytes. — source: `/tmp/optchat.md:218-267,636-693` — confidence: high
- [W2.3] **Total cost for N messages ≈ 2N compactor calls (amortized).** The spec says "about two calls per message (one compress + one merge, amortized)" (optchat.md:754-756). Each message becomes a level-0 node (one call), and each merge of two children into a parent is one call. A binary tree over N leaves has N-1 internal nodes, so total ≈ 2N calls. — source: `/tmp/optchat.md:754-756` — confidence: high
- [W2.4] **Free nodes cost nothing.** If the source already fits in NODE bytes, it IS the node with no model call (optchat.md:150-155). Level 0: short messages stay verbatim. Level > 0: if `childA + "\n" + childB` fits, no call. — source: `/tmp/optchat.md:150-155` — confidence: high
- [W2.5] **TRIES=5 attempts per node, RETRY=10s between retries.** A failed node waits 10s and is tried again, forever; only its first failure is reported (optchat.md:211-214). The spec says "Don't use long exponential backoff: the next turn waits for these summaries, so the compactor must catch up as fast as possible." — source: `/tmp/optchat.md:211-214,269-292` — confidence: high
- [W2.6] **The compactor uses a cheap model.** The reference uses Claude Sonnet at medium effort (optchat.md:218-219). The master can be any model; switching models mid-chat costs nothing since every turn is fresh. — source: `/tmp/optchat.md:218-219,752-756` — confidence: high
- [W2.7] **No explicit cost budget.** OptChat has no token budget, no max-spend cap. The only bounds are VIEW=128,000 bytes (view size) and NODE=512 bytes (per-node size). JOBS=8 bounds concurrency but not total spend. — source: `/tmp/optchat.md:83-96` — confidence: high

### Q3: What happens when compaction can't keep up

- [W3.1] **OptMem: `wake` refuses with exit 1.** If a block needed for the view is not yet compressed, `cmd_wake` prints "Cannot wake: the memory context needs #lo-hi, which is not compressed yet" and the nap prompt, then `sys.exit(1)` (memo:609-622). The agent cannot proceed without doing the compression first. — source: `/tmp/OptMem/memo:609-622` — confidence: high
- [W3.2] **OptMem: the view does not grow unbounded.** `cover(T, WAKE_LINES)` always returns at most WAKE_LINES=96 blocks. If T ≤ budget, everything is raw (memo:112-113). If T > budget, the tiling compresses older blocks. The view size is bounded by WAKE_LINES regardless of how far behind compaction is. — source: `/tmp/OptMem/memo:105-131` — confidence: high
- [W3.3] **OptChat: `settle()` blocks the turn loop.** An agent turn waits until every line of the view is a summary before starting (optchat.md:497-506). "This takes seconds (one or two compactor calls for the previous turn's last messages). The user can cancel the wait; their message then stays in the log, unanswered." — source: `/tmp/optchat.md:497-506` — confidence: high
- [W3.4] **OptChat: the view can exceed VIEW bytes temporarily.** If no parent is built yet, `fit()` breaks and "the view stays over budget until one is" (optchat.md:443-445). In practice the compactor keeps up in seconds. — source: `/tmp/optchat.md:443-445` — confidence: high
- [W3.5] **OptChat: unbuilt parts show as placeholders.** A part whose node isn't built renders as `id+1|(not summarized yet: zoom it)` (optchat.md:490-492). No call ever sees that placeholder — the compactor can't (rule 3), and agent turns wait for settle(). — source: `/tmp/optchat.md:490-508` — confidence: high
- [W3.6] **Degradation mode: the agent blocks, it does not see partial data.** Both OptMem and OptChat refuse to show unsummarized content. OptMem exits 1; OptChat waits. The alternative — showing cut text — is explicitly rejected: "The agent then acts on half a message. Never show cut text." (optchat.md:477-479) — source: `/tmp/OptMem/memo:609-622`, `/tmp/optchat.md:477-479,497-506` — confidence: high

### Q4: Invariants

- [W4.1] **Tree is rebuildable from the log.** OptMem: "The tree is a cache in principle (rebuildable from the log), but it costs model calls to rebuild, so it is stored and never recomputed." (optchat.md:126-127). OptMem's `forget` command drops summaries but never touches LOG.txt (memo:718-728). The raw log is never edited or deleted. — source: `/tmp/optchat.md:126-127`, `/tmp/OptMem/memo:718-728` — confidence: high
- [W4.2] **Raw log stays authoritative.** OptMem: "Never edit or delete anything in these files. The log is history." (optchat.md:129). OptMem's `tree_drop` truncates tree files but never the log (memo:372-389). — source: `/tmp/optchat.md:129`, `/tmp/OptMem/memo:372-389` — confidence: high
- [W4.3] **No agent blocked on compaction (OptChat).** `settle()` blocks the turn loop, but the user can cancel the wait. The compactor runs in the background with JOBS=8. The agent's turn starts only when the view is ready. — source: `/tmp/optchat.md:497-506` — confidence: high
- [W4.4] **OptMem: the agent IS blocked on compaction.** `wake` exits 1 if a needed summary is missing. The agent must compress before waking. This is by design: "The ONLY reason to refuse: this document cannot be written without that summary." (memo:612-615) — source: `/tmp/OptMem/memo:609-622` — confidence: high
- [W4.5] **Gap semantics when a tree exists.** The tree is a cache over the log. If the tree is missing a node, the log still has the raw data. `zoom` can descend from any built node down to raw messages (memo:762-782). A gap in the tree is a cache miss, not a data loss. — source: `/tmp/OptMem/memo:762-782`, `/tmp/optchat.md:126-127` — confidence: high
- [W4.6] **PLAN §5.2: gap record on overflow.** When retention (5000 records or 7 days) must pass the minimum live cursor, append a `gap` record with `reason: "retention"` and notify affected agents. Drop-oldest for the log tail; never silently below the minimum live cursor. Over-quota producers get drop-newest (coalesce the new post). — source: `PLAN-build.md:496,507-509` — confidence: high

### Q5: Multi-agent room — right concurrency

- [W5.1] **OptChat's JOBS=8 is for a single-agent chat.** The compactor builds nodes for one chat log. In a multi-agent room, the log is shared but the compaction workload is the same (one tree over the room log). JOBS=8 is reasonable for one room's tree. — source: `/tmp/optchat.md:89,192-204` — confidence: medium
- [W5.2] **For 10 agents in one room: JOBS=8 is still adequate.** The compaction workload is determined by the message rate, not the agent count. 10 agents posting at the PLAN's rate limit (1 post/2s per agent) = 5 posts/s = 18,000 posts/hour. At 2 calls per message, that's 10 compactor calls/s. JOBS=8 with each call taking ~1-2s would be saturated. — source: [INFERENCE] from `/tmp/optchat.md:89,754-756` + `PLAN-build.md:493` — confidence: medium
- [W5.3] **For 100 agents: JOBS=8 is insufficient.** 100 agents at 1 post/2s = 50 posts/s = 100 compactor calls/s. JOBS=8 would fall behind. The degradation mode is `settle()` blocking — agents wait for summaries. — source: [INFERENCE] from `/tmp/optchat.md:89,497-506` — confidence: medium
- [W5.4] **The right concurrency depends on message rate, not agent count.** The formula is: `JOBS ≥ message_rate × avg_compactor_latency`. At 1 post/2s per agent with 1s latency, JOBS ≥ 0.5 × agent_count. For 10 agents: JOBS ≥ 5. For 100 agents: JOBS ≥ 50. — source: [INFERENCE] — confidence: medium
- [W5.5] **OptMem's model doesn't scale to multi-agent.** OptMem has no background compactor — the agent does compressions itself. In a multi-agent room, every agent would need to run `memo nap`, which is wasteful and racy. OptChat's background compactor is the right model for a room. — source: `/tmp/OptMem/memo:654-692` vs `/tmp/optchat.md:192-204` — confidence: high

### Q6: Cost of a compaction LLM call

- [W6.1] **OptMem nap call: input = block text (≤ 16 raw memories or 2 summaries), output = 1 line ≤ 280 bytes.** At ~280 bytes per memory, a RAW_MAX block is ~4.5 KB input. A merge block is ~560 bytes input (2 × 280). Output is ~280 bytes. Total per nap: ~1-5 KB input, ~280 bytes output. — source: `/tmp/OptMem/memo:463-486` — confidence: high
- [W6.2] **OptChat compactor call: input = ~64k tokens of cached context + node text, output = 1 line ≤ 512 bytes.** The context is prompt-cached across calls, so the marginal cost is the cache read (~64k tokens at cache-read price) + the node text + 512 bytes output. — source: `/tmp/optchat.md:218-267,636-693` — confidence: high
- [W6.3] **omp compaction: input = conversation history up to threshold, output = summary.** The threshold is `max(floor(contextWindow × 0.15), 16384)` tokens. For a 200k window, that's 30k tokens. The summary replaces the summarized region. — source: `omp://compaction.md` — confidence: high
- [W6.4] **Snapcompact and shake cost no LLM calls.** Snapcompact is local deterministic archival (PNG frames). Shake is inline local reduction (artifact references). Both are free of model/API cost. — source: `omp://compaction.md` — confidence: high
- [W6.5] **Remote compaction uses provider-native endpoints.** OpenAI Responses compact, Anthropic compaction beta. The cost is borne by the provider; the harness sends the history and receives a compaction item. — source: `omp://compaction.md` — confidence: high
- [W6.6] **Latency: OptChat settle() takes "seconds" (one or two compactor calls).** OptMem adds nap latency to the agent's critical path. omp's async compaction hides latency by speculatively summarizing before the threshold is crossed. — source: `/tmp/optchat.md:497-506`, `omp://compaction.md` — confidence: high

### Q7: omp compaction cost bounding

- [W7.1] **`compaction.reserveTokens` = `max(floor(contextWindow × 0.15), 16384)`.** This is the threshold below which compaction triggers. For a 200k window: 30k tokens. For a 128k window: 19,200 tokens. For a 100k window: 16,384 tokens (the floor). — source: `omp://compaction.md` — confidence: high
- [W7.2] **`compaction.keepRecentTokens` = 20000.** The most recent 20k tokens are never summarized. — source: `omp://compaction.md` — confidence: high
- [W7.3] **Async (speculative) compaction hides latency.** When context enters the pre-threshold band `[threshold − lead, threshold)` (lead = `clamp(threshold × 0.125, 8192, 32000)`), background summarization starts off a branch snapshot. The armed result is committed instantly when the threshold is crossed. — source: `omp://compaction.md` — confidence: high
- [W7.4] **Method order: `["remote", "snapcompact", "handoff", "shake", "soft"]`.** The cheapest methods are tried first. Snapcompact and shake are free (no LLM). Soft (LLM summarization) is the fallback. — source: `omp://compaction.md` — confidence: high
- [W7.5] **No explicit max-spend cap.** omp has no budget for total compaction cost. The bounds are: reserveTokens (threshold), keepRecentTokens (protected tail), method order (preference), and async lead (speculation window). — source: `omp://compaction.md` — confidence: high

### Q8: Gap semantics when a tree exists

- [W8.1] **PLAN §5.2: gap record on retention overflow.** When the log exceeds 5000 records or 7 days, the oldest records are dropped — but never below `min(cursor)` (the minimum live cursor across all agents). When retention must pass a live cursor, a `gap` record is appended with `reason: "retention"` and the affected agents are notified. — source: `PLAN-build.md:496,507-509` — confidence: high
- [W8.2] **Gap record schema.** `{ v: 1, seq: number; ts: number; kind: "gap"; id: string; from: string; skipped: number; reason: "retention" }`. The `skipped` field tells the reader how many records were dropped. — source: `PLAN-build.md:219` — confidence: high
- [W8.3] **Interaction with a tree.** If a tree exists over the log, a gap means the tree's leaf nodes covering the dropped range are now invalid (their source messages are gone). The tree nodes should be rebuilt from the remaining log. The gap record preserves the fact that messages were dropped, so agents know there's a hole. — source: [INFERENCE] from `PLAN-build.md:219,507-509` + `/tmp/OptMem/memo:372-389` — confidence: medium
- [W8.4] **Drop-oldest vs drop-newest.** The log tail is drop-oldest (evict history). Over-quota producers get drop-newest (coalesce the new post) rather than evicting history. This prevents a flood from destroying the room's memory. — source: `PLAN-build.md:507-509` — confidence: high
- [W8.5] **omp's compaction has no gap record.** omp's compaction replaces old history with a summary — the summary IS the gap record. The `CompactionEntry` has `firstKeptEntryId` and `tokensBefore`/`tokensAfter`. There is no explicit "these messages were dropped" record; the summary is the record. — source: `omp://compaction.md` — confidence: high

## Conflicting evidence
- **OptMem vs OptChat on blocking.** OptMem's `wake` exits 1 (hard block); OptChat's `settle()` waits (soft block with cancel). Both refuse to show partial data, but the mechanism differs. For a room, OptChat's model is better — agents can cancel and retry. — source: `/tmp/OptMem/memo:609-622` vs `/tmp/optchat.md:497-506`
- **OptMem vs OptChat on raw blocks.** OptMem compresses blocks ≤ 16 directly from raw log; OptChat is purely binary. OptChat explicitly rejected OptMem's approach: "That had no real justification and made the structure confusing; OptChat dropped it." (optchat.md:145-148) — source: `/tmp/OptMem/memo:65,463-477` vs `/tmp/optchat.md:145-148`
- **OptChat's "64k tokens for 50 years" claim vs no measurement methodology.** The X post claims "I can keep talking to the agent for years and years and it never uses more than ~64k tokens of its context." The VIEW=128,000 bytes ≈ 62-64k tokens is consistent, but "50 years" has no measurement methodology. — source: `/tmp/optchat.md:88,483-486` + X post
- **omp's compaction.reserveTokens vs PLAN's log retention.** omp reserves 15% of context window for compaction; PLAN caps the room log at 5000 records or 7 days. These are different bounds — omp's is per-session context, PLAN's is the room's shared log. They don't conflict but they interact: the room log feeds into the session context, so the room log cap indirectly bounds the compaction input size. — source: `omp://compaction.md` vs `PLAN-build.md:496`

## Gaps
- **No cost measurement for OptMem/OptChat with real LLMs.** Both are specs/implementations without published cost benchmarks. The "2 calls per message" figure is from the spec, not a measurement.
- **No multi-agent OptMem/OptChat testing.** Both are single-agent designs. The brief's room log use case (multiple agents writing to one log) is untested.
- **No formula for JOBS as a function of message rate.** The spec says JOBS=8 but doesn't derive it. The inference that JOBS ≥ message_rate × latency is untested.
- **No measurement of compaction latency's effect on room real-time requirements.** OptChat says settle() takes "seconds" but there's no SLA for a room where agents expect sub-second response.
- **Gap record + tree interaction is inferred, not specified.** The PLAN says to append a gap record on retention overflow, but doesn't say what happens to tree nodes that covered the dropped range. The inference that they should be rebuilt is untested.
- **No total cost budget in any of the three systems.** OptMem, OptChat, and omp all lack a max-spend cap for compaction. A room that runs for days could accumulate unbounded compaction costs.
- **OptChat's "free nodes" are not counted in the 2 calls/message figure.** If many messages are short enough to fit in 512 bytes, the actual cost is lower than 2N. The spec doesn't quantify this.
