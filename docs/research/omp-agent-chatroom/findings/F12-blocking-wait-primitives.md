# F12 blocking / wait primitives for agents

## Angle

Blocking-wait primitives, exactly as specified. Four questions, in order:

1. **Agent protocols** — MCP (`2025-11-25` + `2026-07-28`), A2A 1.0.0, ACP v1/v2, AG-UI 1.0. Does any of them define a *server→client long-poll* / blocking primitive, and what is the exact spec form of the ones they do define (long-running tools, tasks, progress, `notifications/cancelled`, `subscriptions/listen`, sampling/elicitation, MRTR, `tasks/subscribe`, push config, cancellation, timeout guidance)?
2. **Harness prior art** — Codex `wait_agent` (exact signature + timeout semantics from source), Claude Code agent teams, LangGraph `interrupt`/`Command(resume=)`, AutoGen, OpenAI Agents SDK, CrewAI, Temporal, Erlang/OTP, Akka.
3. **Infrastructure primitives** — SQS long polling, Redis blocking commands, Kafka `poll`, NATS JetStream pull, RabbitMQ, HTTP long polling, SSE, WebSocket, gRPC, and how each handles *a message arriving during the block*.
4. **Abort/interrupt mid-wait** — how cancellation propagates, and what should happen when a peer message arrives while a wait is blocking.

Plus an angle-specific section: **`## Candidate tool shapes`** — concrete shapes for `wait_for_agent`, `wait_for_message`, `wait_for_claim`, with a block-vs-return-immediately recommendation per tool.

Format per item: `<claim> | <source URL or file:lines> | <fetch date> | <confidence>`. `[primary, aggregated]` marks a claim carried from a sibling round-1 findings file whose own sources were read there. Everything else was opened in this pass. omp source = installed v18.6.1 at `~/.bun/install/global/node_modules/@oh-my-pi/`.

**Headline for the chatroom design:** every mature blocking primitive in this survey is (a) bounded by an explicit timeout, and (b) *abort-and-return* when the awaited event arrives mid-wait — the queue-and-keep-waiting pattern exists only where the waiter is a stateless worker pool, not an agent. omp's native `wait` already implements exactly this shape. The one protocol that deliberately deleted its blocking primitive (MCP `tasks/result`) did so for **HTTP-intermediary and statelessness reasons that do not apply to an in-process tool call**.

#### 1.7 MCP Multi Round-Trip Requests (2026-07-28) — deliberately NOT blocking

#### 1.8 MCP — **KEY QUESTION: no server→client long-poll primitive exists**

- **Definitive answer: No.** MCP defines no primitive in which a server-side operation blocks awaiting an external event and surfaces that wait to the client as a distinct pending operation. The complete interaction-pattern set in 2026-07-28 is exactly three: "1. **Request and Response** ... 2. **Multi Round-Trip Requests (MRTR)** ... 3. **Subscribe and Notify**: A client subscribes to a stream of notifications from the server, which are sent as they occur." | https://modelcontextprotocol.io/specification/2026-07-28/basic/index#message-patterns | 2026-10-06 | primary
- Direction is hard-restricted at both pattern and transport level (quoted in §1.6). | https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/index ; .../basic/transports/streamable-http | 2026-10-06 | primary

### 8. Abort / interrupt semantics mid-wait — cross-mechanism comparison

| Mechanism | What it cancels | Cooperative? | What happens to an event arriving during the wait |
|---|---|---|---|
| MCP `notifications/cancelled` | one in-progress request by `requestId`, same direction | Yes — receiver **SHOULD** stop/free and **MUST NOT** reply; **MAY** ignore if already done | Race documented: cancellation "may arrive after request processing has completed"; sender **SHOULD** ignore the late response |
| MCP `tasks/cancel` (2025-11-25) | a task-augmented request | Yes — **MUST** transition to `cancelled` before responding; terminal → `-32602` | Task state machine absorbs it; a blocked `tasks/result` returns because the task reached terminal |
| MCP `tasks/cancel` (2026-07-28 ext) | a task | Cooperative and weaker: "not obligated to actually stop the work"; eventual `cancelled` not guaranteed | Polling `tasks/get` continues independently |
| MCP `subscriptions/listen` | one long-lived stream | Yes — client closes SSE (HTTP) or sends `notifications/cancelled` (stdio) | Notifications keep flowing until closed; server **MUST NOT** send requests on it |
| A2A `CancelTask` | one Task by id | Yes — "success is not guaranteed"; server "attempts" | Task state reflects the result; messages to terminal tasks → `UnsupportedOperationError` |
| A2A stream close | one SSE stream | N/A | "Closing one stream MUST NOT affect other active streams for the same task" |
| ACP `session/cancel` | one prompt turn | Yes — agent SHOULD stop LLM requests + abort tool calls, **MUST** reply with `cancelled` stop reason | Pending updates MUST be sent before the prompt response |
| ACP `$/cancel_request` | one request by id | Yes — MAY cancel; MUST answer with a valid response or `-32800` | "The calling side MAY implement graceful cancellation processing by waiting for the response" |
| AG-UI | one run, by run **termination** | Producer-reported only | Consumer abandoning a stream = "truncated", explicitly **not** cancelled |
| gRPC | one RPC stream | Yes at handler level; library cannot interrupt the handler | Wire = `RST_STREAM CANCEL(8)` = "immediate full-closure" |
| Temporal | one Workflow Execution or scope | Yes — Cancelled Failure; cleanup needs a disconnected scope | Signal/Update is recorded and processed on the next Workflow Task; cancel on a Paused Workflow is deferred until Unpaused |
| Erlang `gen_server:call` | one caller's wait | N/A (caller-side) | **Abort-and-return**: a matching reply ends the wait; non-matching messages stay queued |
| Akka `ask` | one Future | N/A | Future fails with `TimeoutException`; "the receiving actor does not know and may still process it to completion" |
| **omp native `wait`** | one tool call's block | Yes — abort signal | **Abort-and-return**: the peer message ends the wait and is returned as the result; `details.interrupted = true` |
| **Codex `wait_agent` V2** | one tool call's block | Yes | **Abort-and-return** on steer: `"Wait interrupted by new input."` |

- **The three classic patterns, with primary sources:**
  1. **Abort the wait and return the event** — Erlang selective receive resolves on the matching message; `gen_server:call` resolves on the reply; Redis multi-key `BLPOP` returns as soon as any key is non-empty; SQS returns "sooner than `WaitTimeSeconds`" if a message is available; Codex V2 returns on any mailbox activity or steer; omp `wait` returns the message.
  2. **Queue and keep waiting** — Redis documents the helper-key pattern where `BRPOP helper_key` is only a wake-up signal while real elements live elsewhere; unreturned SQS messages simply remain in the queue; Kafka records not returned stay in the log; Erlang leaves non-matching messages in the mailbox; Akka `stash` buffers up to `capacity`.
  3. **Deliver as a separate event on an open stream while the wait continues** — SSE (server→client only, `Last-Event-ID` resumption), WebSocket (full-duplex, control frames mid-stream), gRPC server streaming, NATS `consume()` with `idle_heartbeat`, MCP `notifications/progress` on the request's SSE stream, A2A `SubscribeToTask` event stream.
- **Where the two blocking-wait tools that ship in agent harnesses land:** both omp `wait` and Codex `wait_agent` V2 use pattern (1) — abort-and-return — and both express it as a *distinct string in the result* rather than a silent success (`"Wait interrupted by message."` vs `"Wait interrupted by new input."`). | `src/tools/wait.ts:164-169` ; `multi_agents_v2/wait.rs:146` | 2026-10-06 | primary
- **Why (1) is right for an agent, argued from sources:** a queue-and-continue wait holds the agent's turn open for a message it already has, and omp's own code comment names the opposite failure — "waiting on peers can park both sides for good" | `src/tools/wait.ts:43-48` | 2026-10-06 | primary. Akka's `ask` caveat is the mirror image: on timeout "the receiving actor does not know and may still process it to completion" — a timed-out wait does not cancel the work. | https://doc.akka.io/libraries/akka-core/current/typed/interaction-patterns.html | 2026-10-06 | primary

## Candidate tool shapes

Three tools, not one tool with an op discriminator. Rationale and shapes below.

### Why three tools, not one

- **Precedent is unanimous.** Codex ships `wait_agent` as its own top-level tool with its own schema per version (`multi_agents_spec.rs:287-312`). MCP splits `tasks/get` / `tasks/update` / `tasks/cancel` into separate methods. ACP separates `session/cancel` from `$/cancel_request`. omp itself ships `wait` and `vibe_wait` as two tools rather than one tool with an op (`src/tools/wait.ts:50`; `src/tools/vibe.ts:134`).
- **The tool name is the model's affordance.** `loadMode: "discoverable"` tools surface via BM25 search on `name` + `summary` + `description` (`src/extensibility/extensions/types.ts:669-744`). A discriminator field hides the three intents behind one name and forces the model to read the schema to discover them.
- **`interruptible` is per-tool, resolved before execute.** The agent loop reads `tool?.interruptible` (`agent-loop.ts:3269`), so a per-tool boolean is the natural declaration. A discriminator would need the function form, which is supported (`agent-loop.ts:3271-3279`) but is an untyped extra property on `ToolDefinition` (`types.ts:669-744`) — more machinery for no gain. `wait_for_claim` also wants a *different* interrupt policy from the other two (see below), which a single tool cannot express cleanly.

### `wait_for_agent`

```ts
parameters: {
  "agents?":   string[]   // registry ids; omit = every live agent in this session tree
  "timeout?":  number     // seconds; default 30, min 1, max 1800
  "require?":  "'any' | 'all'"  // default 'any'
}
```

- **Default 30 s** mirrors Codex's `DEFAULT_WAIT_TIMEOUT_MS = 30_000` (`multi_agents_common.rs:23`) and `vibe_wait`'s documented default of 30 (`src/tools/vibe.ts:47`).
- **Min 1 s, max 1800 s (30 min)** — the cap equals omp's own `WAIT_MAX_MS = 30*60_000` (`src/tools/wait.ts:25`). Codex's own cap is 1 h (`config/mod.rs:265`); staying at omp's existing ceiling keeps one number in the codebase rather than two. **Do not use Codex's 10 s minimum** — a 1 s floor is useful for a quick "is anything moving" probe and the min exists in Codex to stop busy-polling, which is a different concern here.
- **Return — event:** `{ op: "wait_for_agent", outcome: "event", agents: [{ id, status, summary?, resultUri? }], timedOut: false }`. Codex V1 returns `{status: {<id>: AgentStatus}, timed_out}` (`multi_agents_spec.rs:519-536`); mirror that, but attach `resultUri` pointing at the published artifact (`agent://<id>`) rather than inlining the result — Codex V2 explicitly refuses to return content ("Does not return the content", `multi_agents_spec.rs:306`).
- **Return — timeout:** `{ op: "wait_for_agent", outcome: "timeout", agents: [...], timedOut: true }` plus text "Wait window elapsed; re-issue to keep waiting" (the `vibe_wait` phrasing, `src/tools/vibe.ts:202`).
- **Return — abort:** `{ op: "wait_for_agent", outcome: "aborted", interrupted: true, ... }` with `useless: true`, matching the native `wait` contract exactly (`src/tools/wait.ts:164-169`; `pi-tui/src/tools/wait.ts:132-133`).
- **Block or return immediately? → BLOCK by default, bounded.** Sources: Codex `wait_agent` blocks in both versions; A2A's `SendMessageConfiguration.return_immediately: false` is the **default** and "MUST wait until the task reaches a terminal state ... or an interrupted state" (`specification.md:446`); Temporal `wait_condition` blocks; Erlang `gen_server:call` blocks. MCP's deletion of `tasks/result` is not counter-evidence: SEP-2663's stated reasons are HTTP intermediaries, SSE streams, and session removal (`seps/2663-tasks-extension.md`) — an in-process omp tool has none of those.

### `wait_for_message`

```ts
parameters: {
  "from?":     string     // registry id; restrict to one sender
  "mention?":  boolean    // default false; only wake on an @-mention of this agent
  "timeout?":  number     // seconds; default 30, min 1, max 1800
}
```

- **Block or return immediately? → BLOCK, bounded, and it should be the *short* one.** omp already has the mechanism: `IrcBus.wait(agentId, {from}, timeoutMs, signal)` with `timeoutMs <= 0` meaning wait forever (`src/irc/bus.ts:188-201`), and the native `wait` calls it with `0` bounded by `WAIT_MAX_MS`. Codex V2 blocks on any mailbox activity (`multi_agents_v2/wait.rs:181-205`). Use a shorter default (30 s) than `wait_for_agent` would need for a long-running peer, because the arrival of a message is a low-latency event — the caller can re-issue cheaply.
- **Return — event:** `{ op: "wait_for_message", outcome: "event", waited: IrcMessage }` — reuse the existing `CoordinationDetails.waited?: IrcMessage | null` field (`pi-tui/src/tools/wait.ts:126-127`) so the TUI renderer works unchanged.
- **Return — timeout:** `{ op: "wait_for_message", outcome: "timeout", waited: null }`. The existing bus already returns `null` on timeout (`src/irc/bus.ts:222-223`).
- **Return — abort:** `{ op: "wait_for_message", outcome: "aborted", interrupted: true }`, `useless: true`.
- **Delivery rule — this is the load-bearing one.** A parked waiter consumes the message directly, bypassing inbox and injection: "A pending `wait` from the recipient consumes the message directly — it is returned from their irc tool call and never hits the inbox or the session injection path" (`src/irc/bus.ts:155-163`). Therefore the tool **MUST NOT** also inject the message — otherwise the agent sees it twice. Call `IrcBus.wait(...)` and nothing else; do not combine it with `deliverIrcMessage`.
- **Ordering:** the bus resolves the **OLDEST** matching waiter (`src/irc/bus.ts:296-305`). If a plugin parks more than one waiter for the same agent, the older one wins — so the tool should refuse to park a second concurrent waiter for the same agent (the bus itself has no such guard).

### `wait_for_claim`

```ts
parameters: {
  "resource":  string     // the claim key, e.g. "task:F7" or "file:src/foo.ts"
  "timeout?":  number     // seconds; default 20, min 1, max 300
  "ttl?":      number     // seconds; lease length if acquired; default 300
}
```

- **Block or return immediately? → BLOCK with a SHORT bound, and always return `acquired` explicitly.** This is the one tool where blocking is bounded tightly and where "not acquired" is a normal outcome, not an error.
  - **20 s default** mirrors SQS's hard maximum long-poll of 20 s ("The maximum long polling wait time is 20 seconds", `sqs-short-and-long-polling.html`) — the largest wait a well-behaved request/reply primitive in this survey will hold.
  - **300 s cap** is deliberately far below `wait_for_agent`'s 1800 s. A claim waiter that blocks for 30 min parks an agent with no work; omp's own comment names this failure: "a peer owes no message ... so waiting on peers can park both sides for good" (`src/tools/wait.ts:43-48`). F6 records that no surveyed framework ships a first-class claim primitive, so there is no prior art to copy — the closest analogues are lease-based (`SQS VisibilityTimeout`, `BullMQ lockDuration`, `NATS AckWait`) and all of them are *bounded*.
  - **Do not use `timeoutMs = 0` (wait forever).** Redis `BLPOP` supports 0 = indefinite (`redis.io/docs/latest/commands/blpop/`) and Erlang `receive...after infinity` exists, but both are *stateless worker* patterns. An agent that blocks forever on a claim has no other work and cannot be steered except by the interrupt path.
- **Return — acquired:** `{ op: "wait_for_claim", outcome: "event", acquired: true, resource, holder: "<agentId>", expiresAt: <epoch ms> }`.
- **Return — timeout (NOT an error):** `{ op: "wait_for_claim", outcome: "timeout", acquired: false, resource, holder?: "<currentHolder>" }` plus text naming the holder so the agent can decide whether to message them. This is the SQS/Redis "empty result" shape, not a failure: SQS returns "an empty list instead of a Null object" on timeout; Redis returns nil/Null.
- **Return — abort:** `{ op: "wait_for_claim", outcome: "aborted", acquired: false, interrupted: true }`.
- **`ttl` is required in spirit.** Every real claim mechanism in F6 is a lease with an expiry (SQS visibility timeout max 12 h; BullMQ `lockDuration` + renewal at ~half; NATS `AckWait` triggers redelivery) — F6's own summary: "No classical system provides exactly-once semantics; all modern queues are at-least-once." A claim without a TTL deadlocks the moment the holder dies. Return `expiresAt` so the holder knows when to renew.

### `interruptible` policy per tool

| Tool | `interruptible` | Why |
|---|---|---|
| `wait_for_agent` | `true` | A peer message or steering should cut the wait short — that is the designed wake path (`agent-loop.ts:3232-3234`: "interruptible waits are always cut short, since a pure wait has nothing to finish and would otherwise sit out its full window with a message already queued"). |
| `wait_for_message` | `true` | Same. And it is the tool whose *whole purpose* is to receive that message. |
| `wait_for_claim` | `(args) => args.mention === true`-style narrow, or `false` | **Different policy on purpose.** Aborting a claim wait on an unrelated room message would drop the waiter's place in the queue and could livelock a hot claim. Only a *relevant* event (an explicit mention, or a claim-release notice for the same resource) should abort. Because the loop supports the function form (`agent-loop.ts:3271-3279`) but a plain `false` is simpler and always safe, start with `false` and widen only if the room proves noisy. |

Note: an extension sets `interruptible` as an **extra own property** on the `ToolDefinition` — it is not in the TS interface (`types.ts:669-744`). It works because `applyToolProxy` copies own keys through `RegisteredToolAdapter` and `ExtensionToolWrapper` (`tool-proxy.ts:6-35`; verified empirically this pass). Until it is added to the interface, the plugin needs a cast or a declaration merge.

### Return-shape convention (all three)

Discriminate on an explicit `outcome` field, never on the presence of other fields:

```ts
type WaitOutcome = "event" | "timeout" | "aborted";
interface WaitToolDetails extends CoordinationDetails {
  op: "wait_for_agent" | "wait_for_message" | "wait_for_claim";
  outcome: WaitOutcome;
  interrupted?: boolean;   // set iff outcome === "aborted"
}
```

- omp already distinguishes these two non-event paths — timeout returns `details: { op: "wait", jobs: [] }` with no `interrupted`, abort returns `details.interrupted = true` (`src/tools/wait.ts:164-185`) — but it infers "timeout" from the *absence* of a flag. An explicit `outcome` is one field and removes the inference.
- Codex does the same thing with `timed_out: boolean` plus a human-readable `message` (`multi_agents_v2/wait.rs:132-158`); the discriminated union is the stronger form.
- Set `useless: true` on `timeout` and `aborted` results so compaction can elide them once consumed — the field exists for exactly this ("safe for compaction to elide once consumed (e.g. zero matches, wait timeout)", `pi-agent-core/src/types.ts:1003`). Note the native `wait` already sets `useless: true` on the abort path but **not** on timeout; the plugin should set it on both.

### Non-goals for these tools

- **No polling loop inside the tool.** All three park on a promise/waiter and return on the first settle. A poll loop would reproduce the busy-wait that every source in this survey warns against (Codex: "Prefer longer waits (minutes) to avoid busy polling", `multi_agents_spec.rs:900-905`; omp: "Results and messages auto-deliver. NEVER poll while work remains", `src/prompts/tools/wait.md:4`).
- **No `block: boolean` parameter.** omp's whole design is that blocking is the *only* mode of a wait tool and returning-immediately is what every other tool does. A `block: false` flag would make the tool a no-op wrapper around a state read that the room's own read tools should provide.
- **No unbounded wait.** `timeout` is required in spirit and capped on all three; `timeoutMs <= 0` (wait forever, `src/irc/bus.ts:190-191`) must not be reachable from the model.

Carry the 2026-07-28 rule for that revision and the 2025-11-25 rule for that revision. | https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation ; https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation | 2026-10-06 | primary

## Gaps

- **MCP:** the full SEP-2322 / SEP-2575 / SEP-2567 proposal texts and the complete `schema/2026-07-28/schema.ts` notification list were not exhaustively enumerated (the 2026-07-28 method list came from the ext-tasks schema and core changelog, not a schema grep). `subscriptions/listen` and MRTR were read from the published spec pages, which is the normative surface, so the gap is depth of the change-record rather than the rules.
- **MCP:** `tasks/update` semantics when a client never sends `inputResponses` and the task has no `ttlMs` (unlimited TTL) are undefined. No `pollIntervalMs` default value is specified anywhere.
- **MCP:** the ext-tasks repo exposes a two-generation TypeScript surface (`packages/ext-tasks` with `/core/v1` and `/core/v2` entry points) that the spec itself does not document.
- **A2A:** no polling interval, backoff, or client-side rate limit exists anywhere in the spec — this is a proven absence (exhaustive grep), but it means there is no authoritative number to cite for a client polling loop. No disable/expiry semantics for a push-notification config are defined beyond "MAY stop attempting delivery". No client-side rule for "task already terminal" beyond the error table; the spec never states a client MUST stop polling.
- **A2A:** whether the blocking `return_immediately: false` path has any server-side implementation guidance beyond "MUST wait" — no timeout is given, so a server could hold a connection indefinitely.
- **ACP:** no timeout, heartbeat, or idle limit exists in v1 or v2 (verified by exhaustive per-page grep). ACP v2's Streamable HTTP transport is an empty stub, so no resumption mechanism is specified there.
- **AG-UI:** no timeout or heartbeat is specified; only the informational `maxExecutionTime` capability declaration. `docs/spec/draft/` was diffed against 1.0 on `EventType` and `$defs` keys only.
- **Codex:** `agent/control/watch.rs` (the v1 status-subscription wake path) was not opened; the V1 wake mechanism is cited from handler usage of `subscribe_status` + `FuturesUnordered` rather than from the subscription implementation. Codex's mailbox queue is in-memory with no durable file located, so whether unloaded-session mail survives a process restart is unverified.
- **Claude Code:** closed source; the agent-teams and cross-session claims rest on first-party docs, not source. No source-level confirmation of the inbox read/injection point.
- **OpenAI Agents SDK:** the absence of a blocking wait primitive is a proven negative over the `Runner`/`Agent`/handoff surface, but proving a negative is inherently weaker than citing a positive API.
- **Temporal:** the Python SDK's public `workflow.py` could not be fetched from the raw paths tried; `wait_condition` semantics rest on `temporalio/workflow/_context.py` plus docs.temporal.io.
- **Akka:** the typed Stash capacity is caller-specified with no documented default constant (the sample uses 100).
- **CrewAI:** fetched from the PyPI sdist `crewai-1.15.23`, not repo HEAD (GitHub raw returned 404 on the branch guesses tried).
- **Erlang:** `gen_server:call` timeout semantics verified from the OTP docs and `gen_server.erl`; the exact `exit` term shape (`{Reason, Location}`) is from the docs, not traced through a runtime.
- **omp:** `IrcBus` is reachable via the wildcard subpath export but is **not** in the package's public API surface (not re-exported from `index.ts`/`sdk.ts`), so a plugin depending on `@oh-my-pi/pi-coding-agent/irc/bus` is relying on a deep import that could change without a semver signal. `interruptible` is likewise absent from `ToolDefinition`, so opting in requires an untyped own property. Both are load-bearing for the candidate tool shapes and both are currently undocumented extension contracts.
- **omp:** the 250 ms IRC interrupt poll (`STEERING_INTERRUPT_POLL_MS`) means an interruptible wait can take up to ~250 ms to observe a peer message that arrives after the wait has parked — the direct-consumption path in `IrcBus.#deliver` resolves a waiter immediately, but the *abort* path (steering, background completion) is polled. Which path a given wake takes was not traced end to end.
- **Not covered here (owned by siblings):** the room's own storage/log design, attention/budget mechanics, and the envelope/mention grammar. This file covers only the blocking-wait surface.
