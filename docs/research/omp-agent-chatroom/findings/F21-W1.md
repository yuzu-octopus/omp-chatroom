## Claims

### OptMem RAW_MAX=16 and the raw/compressed boundary

- **RAW_MAX = 16 is the nap-prompt rendering threshold, not the wake rendering threshold.** In `nap_prompt()` (line 464), `if hi - lo <= RAW_MAX:` decides whether a block's compression prompt shows the raw log lines (`log_slice`) or the two half-summaries (`tree_get` on each half). Blocks of size ≤16 are rendered raw; larger blocks are rendered as two compressed halves. | `/tmp/OptMem/memo:65,464` | 2026-10-06 | primary
- **In `wake`, the raw/compressed boundary is block size 1, not RAW_MAX.** `cmd_wake` (line 604-606) iterates `cover(T, WAKE_LINES)` and checks `if hi - lo == 1:` — only singleton blocks are rendered as raw memories (`log_get`); all larger blocks are rendered as tree summaries (`tree_get`). RAW_MAX=16 does not appear in `wake` at all. | `/tmp/OptMem/memo:604-606` | 2026-10-06 | primary
- **The cover() algorithm: `_cover(T, alpha)` tiles [0,T) with aligned power-of-two blocks, keeping a block whole iff `size ≤ alpha × (T - lo)` (age).** Bigger alpha = coarser = fewer lines. The binary search in `cover(T, budget)` finds the smallest alpha such that the number of blocks ≤ budget (WAKE_LINES=96). Then remaining budget is spent by splitting the largest block (most recent detail). | `/tmp/OptMem/memo:82-131` | 2026-10-06 | primary
- **The boundary is a sliding window that shifts on every new message.** `cover(T, budget)` is called with T = current log length. As T grows, the binary search finds a new alpha, and the tiling changes. Recent memories stay verbatim (small blocks near T); ancient ones collapse (large blocks near 0). The boundary is not fixed — it moves forward as the log grows. | `/tmp/OptMem/memo:105-131,584-604` | 2026-10-06 | primary
- **At T ≤ budget (96), nothing is compressed.** `cover(T, budget)` returns `[(i, i+1) for i in range(T)]` — every memory is a singleton raw block. | `/tmp/OptMem/memo:112-113` | 2026-10-06 | primary
- **At T=100, the boundary is near the end.** cover(100, 96) must compress slightly. The binary search finds alpha such that the tiling yields ≤96 blocks. The most recent ~96 memories stay as singletons or small blocks; the oldest few are merged into larger blocks. | `/tmp/OptMem/memo:105-131` | 2026-10-06 | primary [inference]
- **At T=5000, the boundary is deep in the past.** cover(5000, 96) produces 96 blocks tiling [0,5000). The most recent ~16-32 memories are singletons (raw); the oldest are in blocks of size ~512-1024 (compressed). The raw/compressed boundary sits somewhere around T-32 to T-64, depending on the alpha found. | `/tmp/OptMem/memo:105-131` | 2026-10-06 | primary [inference]
- **The tree is a rebuildable cache over the log.** `tree_drop` (line 372-389) truncates level files back to a point; the log is never touched. `forget` drops a bad summary and everything built on it; the next `nap` rebuilds. The raw log is the source of truth; the tree is derived state. | `/tmp/OptMem/memo:372-389,718-728` | 2026-10-06 | primary

### Kafka: log retention vs consumer offsets

- **Kafka retention is time/size based and ignores consumer position.** `retention.ms` default 604800000 (7 days); `retention.bytes` default -1 (no limit); `cleanup.policy` default `delete`. Retention is enforced at whole-segment granularity (`segment.ms` default 604800000, `segment.bytes` default 1073741824). | https://kafka.apache.org/42/configuration/topic-configs/ | 2026-10-06 | primary
- **When a consumer's committed offset falls below the log-start-offset (because segments were deleted), the offset is "out of range."** The consumer cannot read the deleted records. `auto.offset.reset` controls the response: `earliest` (resume at earliest remaining offset), `latest` (skip to log end), `none` (throw `OffsetOutOfRangeException`). Default is `latest`. | https://kafka.apache.org/42/configuration/consumer-configs/ | 2026-10-06 | primary
- **The boundary between retained and deleted is the log-start-offset, which advances as segments are deleted.** The log cleaner runs every `log.retention.check.interval.ms` (default 300000 = 5 min). When a segment's age exceeds `retention.ms` or the partition exceeds `retention.bytes`, the segment is deleted and the log-start-offset advances. | https://kafka.apache.org/42/configuration/broker-configs/ | 2026-10-06 | primary
- **Slow-consumer retention pinning is NOT a thing in Kafka.** A consumer whose committed offset falls below the log-start-offset loses those records. This is the core "drop under a slow reader" behaviour. The Java client surfaces this as `OffsetOutOfRange`. | https://kafka.apache.org/42/configuration/topic-configs/ ; https://kafka.apache.org/42/configuration/consumer-configs/ | 2026-10-06 | primary (inferred from documented behaviours; the docs do not name the exception)
- **The committed group offset and the log start offset are different things.** The group's commit can remain at 500 even after the partition's available data starts at 800; the problem becomes apparent when a consumer attempts to fetch from the stale position. | https://github.com/apache/kafka/blob/trunk/core/src/main/scala/kafka/cluster/Partition.scala | 2026-10-06 | primary
- **A reset is a recovery choice, not data recovery.** `earliest` means earliest *still retained*, not the original beginning of the topic. `latest` can skip retained backlog too. | https://kafka.apache.org/42/configuration/consumer-configs/ | 2026-10-06 | primary

### NATS JetStream: retention and consumer semantics

- **Stream limits `MaxMsgs`, `MaxBytes`, `MaxAge` work separately and all are active at once.** "Whichever one is reached first triggers a discard." `DiscardOld` (default) evicts the oldest stored message; `DiscardNew` rejects the publish. | https://docs.nats.io/learn/jetstream/shaping-the-stream | 2026-10-06 | primary
- **Retention policies: `Limits` (default), `Interest`, `WorkQueue`.** "Limits don't ask" whether a consumer is done. `LimitsPolicy` retains according to stream limits, irrespective of acknowledgements. | https://docs.nats.io/learn/jetstream/retention-policies | 2026-10-06 | primary
- **A consumer's ack floor tracks acknowledged progress, NOT the oldest message still retained.** If a message is removed by a limit before a consumer acknowledges it, the consumer can no longer receive or redeliver that message. The ack floor does not pin old messages in the stream. | https://docs.nats.io/learn/jetstream/ ; https://github.com/nats-io/nats-server/blob/main/server/consumer.go | 2026-10-06 | primary
- **The ack floor can point to a sequence that has already been evicted.** Messages deleted by stream limits cannot be delivered or redelivered. A fresh or reset consumer can only process what the stream still retains. | https://github.com/nats-io/nats-server/blob/main/server/consumer.go | 2026-10-06 | primary
- **Even `WorkQueuePolicy` and `InterestPolicy` still enforce stream limits.** Those limits can remove messages before acknowledgment. | https://docs.nats.io/learn/jetstream/retention-policies | 2026-10-06 | primary

### The boundary over time: sliding window dynamics

- **In OptMem, the boundary shifts on every new message.** `cover(T, budget)` is recomputed each time `wake` is called with the current T. The binary search finds a new alpha, and the tiling changes. The boundary is a function of T and budget, not a fixed offset. | `/tmp/OptMem/memo:105-131,584-604` | 2026-10-06 | primary
- **In Kafka, the boundary (log-start-offset) advances as segments are deleted.** It does not advance on every message — it advances when the log cleaner runs (every 5 min by default) and finds a segment eligible for deletion. The boundary moves in segment-sized steps, not per-message. | https://kafka.apache.org/42/configuration/broker-configs/ | 2026-10-06 | primary
- **In NATS, the boundary (oldest retained sequence) advances as messages are discarded.** With `DiscardOld`, each new publish beyond `MaxMsgs` evicts the oldest. The boundary moves per-message once the limit is reached. With `MaxAge`, the boundary moves as messages expire. | https://docs.nats.io/learn/jetstream/shaping-the-stream | 2026-10-06 | primary
- **The two-region design (raw hot tail + compressed cold tail) maps to OptMem's cover() output.** The raw tail is the singleton blocks near T; the compressed tail is the larger blocks near 0. The boundary is where block size exceeds 1 (in wake) or exceeds RAW_MAX=16 (in nap_prompt). | `/tmp/OptMem/memo:604-606,464` | 2026-10-06 | primary
- **PLAN §5.2 retention: 5000 records or 7 days, never below min(cursor).** When retention must pass the minimum live cursor, append a `gap` record and notify affected agents. This is the Kafka OffsetOutOfRange / NATS ack-floor-below-window situation made explicit rather than silent. | `PLAN-build.md:496,507-508` | 2026-10-06 | primary
- **omp's compaction boundary is `firstKeptEntryId`.** The LLM sees a summary of entries before `firstKeptEntryId` plus raw entries from `firstKeptEntryId` onward. The display transcript keeps all entries; only the LLM context resets at the compaction boundary. | `omp://compaction.md` | 2026-10-06 | primary

## Conflicting evidence

- **RAW_MAX=16 is not the wake boundary.** The assignment brief says "RAW_MAX=16: how does this map to a room log?" but in the source, RAW_MAX=16 only appears in `nap_prompt` (the compression prompt), not in `wake` (the reading path). In `wake`, the raw/compressed boundary is block size 1. This is a naming mismatch: RAW_MAX controls what the LLM sees when compressing, not what the agent sees when reading. | `/tmp/OptMem/memo:65,464,604-606` | 2026-10-06 | primary
- **Kafka's `auto.offset.reset` default is `latest`, not `earliest`.** The F14 findings note this. For a room log, `latest` means a late joiner skips all retained backlog — the opposite of what a bounded-view design wants. The PLAN's "never below min(cursor)" rule is a deliberate departure from Kafka's default. | https://kafka.apache.org/42/configuration/consumer-configs/ ; `PLAN-build.md:507-508` | 2026-10-06 | primary
- **NATS `LimitsPolicy` (default) does not protect slow consumers.** The ack floor does not pin messages. This conflicts with the PLAN's "never silently below the minimum live cursor" rule. The PLAN's gap-record mechanism is a layer above NATS's retention, not a NATS feature. | https://docs.nats.io/learn/jetstream/retention-policies ; `PLAN-build.md:507-508` | 2026-10-06 | primary

## Gaps

- **No primary source measures the exact cover() output at T=100 or T=5000.** The inferences about boundary position at those sizes are derived from the algorithm, not from running it. A quick Python evaluation of `cover(100, 96)` and `cover(5000, 96)` would confirm the exact block sizes.
- **The relationship between RAW_MAX=16 and WAKE_LINES=96 is not documented.** Why 16? Why 96? The source has no comment explaining the ratio. The inference is that 16 is small enough to read verbatim in a compression prompt, while 96 is the total wake budget.
- **The PLAN's 5000-record retention has no direct OptMem analogue.** OptMem's log is unbounded (append-only, never truncated). The 5000-record cap is a room-log policy that would need to be implemented as a separate retention layer over the tree, not as a tree feature.
- **No primary source addresses the interaction between the tree and a retention cap.** If the log is truncated at 5000 records, what happens to the tree? The tree is a cache over the log; if the log is truncated, the tree must be rebuilt. This is not addressed in the OptMem source.
- **The "gap record" in PLAN §5.2 has no OptMem analogue.** OptMem's `recall` searches the whole log by regex; there is no gap concept. The gap is a room-log semantic that would need to be implemented above the tree.
