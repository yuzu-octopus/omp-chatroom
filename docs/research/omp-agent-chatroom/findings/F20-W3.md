# F20-W3: Merkle trees, content-defined chunking, transparency logs — what transfers to an LLM-summarised append-only log

## Angle
Primary-source survey of Merkle/append-only trees (RFC 6962/9162, Trillian, Go `tlog`, Sigstore/Rekor, transparency.dev), content-defined chunking (FastCDC, restic, borg, IPFS), content-addressed mutable state (IPLD/CID/IPNS/MFS), and the Git object model — then an explicit verdict on (a) whether content-addressing can verify LLM-generated summaries given non-determinism, and (b) whether CDC applies to fixed-width records. Cross-referenced against OptMem `/tmp/OptMem/memo` and OptChat `/tmp/optchat.md`.

## Claims

### Q1 — Divergence detection and repair in a Merkle/append-only tree

- [W3.1] MTH definition: `MTH({}) = SHA-256()`, `MTH({d0}) = SHA-256(0x00 || d0)`, `MTH(D[n]) = SHA-256(0x01 || MTH(D[0:k]) || MTH(D[k:n]))` with `k` the largest power of two < n. Leaf and interior hashes use different prefixes (0x00 vs 0x01); this domain separation is required for second-preimage resistance. — source: https://www.rfc-editor.org/rfc/rfc6962.txt §2.1 (fetched 2026-10-06); restated verbatim in https://www.rfc-editor.org/rfc/rfc9162.txt §2.1.1 (fetched 2026-10-06) — confidence: high
- [W3.2] Detection is by cascade: "If any record is modified, its hash changes. This cascades up all the levels, resulting in a different tree head." The tree head is a snapshot; a full audit recomputes every hash and compares to a stored historical tree head. — source: https://transparency.dev/verifiable-data-structures/ (fetched 2026-10-06) — confidence: high
- [W3.3] Localisation: a Merkle audit (inclusion) path recomputes the root from one leaf plus `ceil(log2(n))+1` sibling hashes; a consistency proof shows a later tree is an extension of an earlier one. "As soon as two conflicting Signed Tree Heads for the same log are detected, this is cryptographic proof of that log's misbehavior." — source: https://www.rfc-editor.org/rfc/rfc6962.txt §2.1.1, §2.1.2, §7.3 (fetched 2026-10-06) — confidence: high
- [W3.4] Reference verification code: `CheckRecord` / `CheckTree` recompute node hashes with `NodeHash = SHA256(0x01||left||right)` and return `errProofFailed` on root mismatch. `StoredHashes` appends "at most 1 + log₂ n hashes, but … averages just under two per call" for records 1..k. — source: https://raw.githubusercontent.com/golang/mod/master/sumdb/tlog/tlog.go (fetched 2026-10-06) — confidence: high
- [W3.5] Repair: transparency logs never repair in place — they are append-only and MUST NOT be edited. The repair *recipe* that does transfer is recompute-from-children: every node is a pure function of its children, so a bad node is fixed by recomputing it, and if leaves are authoritative the subtree is rebuilt. — source: [INFERENCE] from W3.1/W3.2 + https://www.rfc-editor.org/rfc/rfc6962.txt §7.3 (fetched 2026-10-06) — confidence: high
- [W3.6] OptMem already implements exactly that repair recipe, but with *ad-hoc* detection, not hashes: `forget [lo,hi)` → `tree_drop` truncates each level file from `lo//size` upward, dropping the block and every ancestor; the next `nap` rebuilds them; the log is never touched. Detection of a bad node is by `UnicodeDecodeError` ("The summary of #a-b is corrupt. Run: forget") or a blank record, not by a hash mismatch. — source: /tmp/OptMem/memo:372-389, 288-292, 624-628, 718-728; /tmp/OptMem/test.py:492-506, 562-571 (fetched 2026-10-06) — confidence: high
- [W3.7] Compact ranges (the modern transparency.dev model): a node is *perfect* if its subtree is a perfect binary tree; perfect nodes are immutable, *ephemeral* nodes are modified on each append until they become perfect. A compact range is the minimal set of perfect nodes covering `[L,R)`; size `O(log(R-L))`, always unique, and mergeable. This is the structure that makes "old" hashes stable while the tail changes — the same property OptMem's per-size level files approximate positionally. — source: https://raw.githubusercontent.com/transparency-dev/merkle/main/docs/compact_ranges.md (fetched 2026-10-06) — confidence: high

### Q2 — Does CDC help when records are fixed-width but messages are variable-size?

- [W3.8] CDC chunks the *byte stream*, not records: fixed-size chunking (FSC) suffers the boundary-shift problem (one inserted byte shifts every later cut-point); CDC declares cut-points from a rolling hash of the content, so unchanged regions re-align. Sizes are bounded by min/avg/max (LBFS: 8 KB avg, 2 KB min, 64 KB max). FastCDC is ~10× faster than Rabin-based CDC and ~3× faster than Gear/AE at ~equal dedup ratio. — source: https://www.usenix.org/system/files/conference/atc16/atc16-paper-xia.pdf (FastCDC, USENIX ATC '16) (fetched 2026-10-06) — confidence: high
- [W3.9] restic: "data from each file is split into variable length Blobs cut at offsets defined by a sliding window of 64 bytes. The implementation uses Rabin Fingerprints for implementing this Content Defined Chunking (CDC). An irreducible polynomial is selected at random and saved in `config` … so that watermark attacks are much harder. Files smaller than 512 KiB are not split, Blobs are of 512 KiB to 8 MiB … aims for 1 MiB … For modified files, only modified Blobs have to be saved … even works if bytes are inserted or removed at arbitrary positions." — source: https://raw.githubusercontent.com/restic/restic/master/doc/design.rst (Backups and Deduplication) (fetched 2026-10-06) — confidence: high
- [W3.10] borg ships *both* a CDC chunker (`buzhash`) and a fixed-size chunker, and recommends `--chunker-params=fixed,4194304` for "block devices (like disks, partitions, LVM LVs) or raw disk image files" — i.e. when the content is already block-aligned, content-defined boundaries buy nothing. — source: https://borgbackup.readthedocs.io/en/stable/usage/notes.html (--chunker-params) (fetched 2026-10-06) — confidence: high
- [W3.11] IPFS exposes the same choice: chunking strategy is `fixed size` or `rabin`; "Chunking strategy balances retrieval overhead against sync efficiency: large chunks mean fewer blocks for bulk downloads, small chunks mean less data to transfer when syncing deltas." — source: https://docs.ipfs.tech/concepts/file-systems/ and https://docs.ipfs.tech/concepts/content-addressing/ (fetched 2026-10-06) — confidence: high
- [W3.12] CDC is not free: keyed CDC schemes deployed in Borg, Bupstash, Duplicacy, Restic and Tarsnap are all broken by key-recovery attacks from known/chosen plaintext; chunk-length patterns leak content. — source: https://eprint.iacr.org/2025/558.pdf (Truong et al., "Breaking and Fixing Content-Defined Chunking", 2025) (fetched 2026-10-06) — confidence: high
- [W3.13] **Verdict — CDC does not apply to OptMem's fixed-width log.** Records are `LOG_REC=320` bytes, "position IS identity", every lookup is one seek, and the log is *append-only at the tail*. The boundary-shift problem CDC exists to solve requires insertions/deletions in the middle; there are none. The variable-size thing is the *text inside* the record, which is padded to fixed width — chunking that text by content would destroy O(1) offset addressing and the aligned power-of-two block invariant (`block [lo,hi)` at `k*TREE_REC` of `TREE/<size>`) that `cover()`/`zoom()` depend on. — source: /tmp/OptMem/memo:68-73, 78-102, 213-214, 279-292, 762-782 (fetched 2026-10-06) — confidence: high
- [W3.14] Corollary: CDC is only relevant if the store were a *variable-size byte stream* (e.g. OptChat's `chat/main/YYYY-MM-DD.jsonl`, one JSON object per line) **and** cross-version dedup were a goal. For an append-only log where every message is unique and the tree is index-addressed (`node(l,i)` covers `[i·2^l,(i+1)·2^l)`), content-defined boundaries would make node membership non-deterministic and break the "free node" and merge rules. — source: /tmp/optchat.md:100-113, 139-148 (fetched 2026-10-06) + [INFERENCE] — confidence: medium

### Q3 — Git's incremental sharing vs OptMem's `forget` cascade

- [W3.15] Git is content-addressed: a blob's name is `SHA-1("blob <len>\0" + content)`; a tree object lists `(mode, hash, name)` for each blob or subtree; a commit names exactly one top-level tree plus its parents. — source: https://git-scm.com/book/en/v2/Git-Internals-Git-Objects (fetched 2026-10-06) — confidence: high
- [W3.16] Changing one leaf: "although you added only a single line to the end of a 400-line file, Git stored that new content as a completely new object." The changed file becomes a new blob, so every tree on the path to the root is rewritten (it names the child by hash); unchanged sibling subtrees are shared because their hashes are unchanged. — source: https://git-scm.com/book/en/v2/Git-Internals-Git-Objects and .../Git-Internals-Packfiles (fetched 2026-10-06) — confidence: high
- [W3.17] **Count:** one leaf change rewrites the leaf plus its ancestors — `O(depth)`, i.e. `O(log_F N)` tree objects for fan-out F (Git's tree fan-out is the directory's entry count). The changed *file* is stored whole initially; delta compression against a sibling is a later pack-time storage optimisation (`git verify-pack -v` shows the first version as a 9-byte delta on the second, stored intact). — source: https://git-scm.com/book/en/v2/Git-Internals-Packfiles (fetched 2026-10-06) — confidence: high
- [W3.18] **Contrast with `tree_drop`:** OptMem's level files are *dense prefixes*, so `forget [lo,hi)` cannot leave a hole — it truncates each level at `lo//size` from `size=hi-lo` upward, dropping the target **and every later block at those levels**, which are then rebuilt. Git invalidates exactly the ancestor path and shares all siblings by hash; OptMem invalidates a positional *suffix* per level. — source: /tmp/OptMem/memo:372-389, 718-728 vs https://git-scm.com/book/en/v2/Git-Internals-Git-Objects (fetched 2026-10-06) — confidence: high
- [W3.19] Cost trade-off: OptMem's positional identity needs no hash and no index (O(1) seek); a content-addressed store needs a hash→location index (restic keeps one mapping plaintext hash → pack/offset, rebuildable from pack headers) and pays hash computation. OptMem therefore gets no dedup of identical subtrees, and coarser invalidation; Git gets dedup and precise invalidation, and pays the index. — source: /tmp/OptMem/memo:68-73 vs https://raw.githubusercontent.com/restic/restic/master/doc/design.rst (Indexing) (fetched 2026-10-06) — confidence: high

### Q4 — Can content-addressing make an LLM-generated summary *verifiable*?

- [W3.20] LLM output is non-deterministic even under maximal control. OpenAI: setting `seed` and all parameters and matching `system_fingerprint` gives outputs that "will mostly be identical. There is a small chance that responses differ even when request parameters and `system_fingerprint` match, due to the inherent non-determinism of our models." Determinism "is not guaranteed". — source: https://developers.openai.com/cookbook/examples/reproducible_outputs_with_the_seed_parameter (fetched 2026-10-06) — confidence: high
- [W3.21] **Therefore hashing a summary text proves integrity of *that artifact*, not reproducibility and not correctness.** Two honest compactors given identical children will produce different text and therefore different hashes; a hash difference carries no signal about which is right. Content addressing can only *record that they disagreed* (two distinct node objects) and preserve both. — source: [INFERENCE] from W3.20 + W3.15 (fetched 2026-10-06) — confidence: high
- [W3.22] What content-addressing **does** buy: bind each summary to the exact child hashes and generation metadata (model, prompt hash, decoding params), then commit it into a Merkle log. That yields tamper-evidence ("this exact summary was produced from these exact inputs by this signer") and non-repudiation — not semantic faithfulness. This is precisely the pattern in the recent literature: MemLineage = RFC-6962 Merkle log over Ed25519-signed per-principal entries plus a weighted derivation DAG; VCT = branch-level hash chains → session Merkle roots → account Merkle root with joint user+server signatures and gossip to detect view forks; Portable Agent Memory = content-addressable entries linked by a Merkle-DAG provenance graph. — source: https://arxiv.org/abs/2605.14421, https://arxiv.org/abs/2606.23003, https://arxiv.org/abs/2605.11032 (fetched 2026-10-06) — confidence: high
- [W3.23] Split-view/consistency detection (the "two compactors disagree" analogue) requires a **deterministic** tree: RFC 6962 consistency proofs and gossip assume the same leaf set yields the same root for everyone. Non-deterministic leaves mean two compactors can never produce a shared root, so the gossip mechanism cannot prove disagreement — it can only observe two incomparable roots. — source: [INFERENCE] from https://www.rfc-editor.org/rfc/rfc6962.txt §7.3 + W3.20 (fetched 2026-10-06) — confidence: medium-high
- [W3.24] The practical substitute for a hash is *provenance*, not verification: Traceable Text links passages of a generated summary to source passages and "markedly improved correctness of answers in cases where there were hallucinations in the summaries." A hash chain proves a summary is unchanged; only source links let a reader check it. — source: https://arxiv.org/abs/2409.13099 (fetched 2026-10-06) — confidence: high

### Q5 — IPLD/IPFS: how mutable state is expressed

- [W3.25] A CID = cryptographic hash + multicodec (how to interpret bytes) + multibase (string encoding). Merkle DAG: a node's id = hash of its payload **and its children's ids**; nodes are immutable, so "any change in a node would alter its identifier and thus affect all the ascendants … essentially creating a different DAG." — source: https://docs.ipfs.tech/concepts/content-addressing/, https://docs.ipfs.tech/concepts/merkle-dag/ (fetched 2026-10-06) — confidence: high
- [W3.26] Mutable state = a signed pointer, not a mutable node: IPNS name = hash of a public key; the IPNS record contains the target content path, a `sequence` number, a `validity`/TTL, and a signature. Mental model: `IPFS = immutable *Pointer => content`, `IPNS = **Pointer => content`. Consistency (DHT, latest sequence) vs availability (PubSub, cached older record) is an explicit trade-off. — source: https://docs.ipfs.tech/concepts/ipns/ (fetched 2026-10-06) — confidence: high
- [W3.27] MFS is the "hide the hash rewriting" layer: "you can add, remove, move, and edit MFS files and have all the work of updating links and hashes taken care of for you." — source: https://docs.ipfs.tech/concepts/file-systems/ (fetched 2026-10-06) — confidence: high
- [W3.28] IPLD Patch = RFC 6902-like declarative ops (`add`, `replace`, `remove`, `copy`, `move`, `test`) applied linearly over the IPLD Data Model; "any operation erroring results in the entire patch not being applied." — source: https://ipld.io/specs/patch/ (fetched 2026-10-06) — confidence: high
- [W3.29] DAG-CBOR is the recommended codec for hash-consistent representations: binary, length-delimited, "canonical DAG-CBOR should always use length prefixes" (no indefinite-length mode) so the same data hashes the same. — source: https://ipld.io/docs/codecs/known/dag-cbor/ (fetched 2026-10-06) — confidence: high

### Q6 — Has any of this been applied to LLM context/memory compression?

- [W3.30] No primary source found that combines Merkle trees or CDC with **LLM hierarchical-summarisation compression** (the OptMem/OptChat shape). The recent work found splits the two concerns: integrity/provenance (VCT, MemLineage, Portable Agent Memory) vs hierarchical compression (Hierarchical Aggregate Tree, arXiv:2406.06124) — none does both. — source: searches listed below; https://arxiv.org/abs/2406.06124 (fetched 2026-10-06) — confidence: medium
- [W3.31] Closest integrity-side work: VCT (verifiable LLM transcripts, 3-tier Merkle), MemLineage (RFC-6962 log + derivation DAG, zero ASR on its harness), Portable Agent Memory (Merkle-DAG provenance, 54 tests). Closest compression-side: Hierarchical Aggregate Tree (recursive aggregation of dialogue, no integrity layer). — source: https://arxiv.org/abs/2606.23003, https://arxiv.org/abs/2605.14421, https://arxiv.org/abs/2605.11032, https://arxiv.org/abs/2406.06124 (fetched 2026-10-06) — confidence: medium

### Q7 — Mapping to the two-region chatroom (inference)

- [W3.32] Content-addressing adds three things to a two-region store: (a) *divergence detection* — a node built from the wrong child has a hash that does not match; (b) *provenance* — "which summary was built from which children, by which model/prompt"; (c) *dedup* — identical subtrees share one object. It adds **none** of: semantic correctness, determinism, or repair. — source: [INFERENCE] from W3.2, W3.5, W3.21, W3.22 — confidence: high
- [W3.33] The raw log stays authoritative and the tree stays rebuildable regardless (OptMem's own property: `forget` never touches the log). A content-addressed tree would make that invariant *checkable* rather than merely intended — but at the cost of hash computation and a hash→location index, and it would change node identity from position (`[lo,hi)`) to content, which breaks OptMem's O(1) `tree_get` seek. — source: /tmp/OptMem/memo:68-73, 279-292, 718-728 + [INFERENCE] — confidence: high
- [W3.34] CDC is the wrong tool for the boundary between raw tail and cold tree: the correct analogue is the aligned power-of-two index range (OptMem `_cover`/`cover`, OptChat `node(l,i)`), which is *offset*-defined and keeps `zoom(lo,hi)` addressable; CDC would define boundaries by content and make both the tiling and `zoom` non-deterministic. — source: /tmp/OptMem/memo:78-131, /tmp/optchat.md:139-148 + [INFERENCE] — confidence: high
- [W3.35] A `gap` hole a late joiner sees is **not** filled by content addressing: an inclusion proof proves that what is present is in the tree; it cannot prove the absence of what is missing. Bounding a late joiner's view needs the summary tree itself; *verifying* it needs a signed checkpoint (RFC 6962 STH / tlog-tiles checkpoint, Ed25519-signed). — source: [INFERENCE] from https://www.rfc-editor.org/rfc/rfc6962.txt §3.5, https://c2sp.org/tlog-tiles (fetched 2026-10-06) — confidence: high

## Conflicting evidence
- **Repair semantics.** Merkle/CT literature treats the tree as strictly append-only and never edits a node — "repair" is detection plus out-of-band correction (RFC 6962 §7.3). OptMem *does* edit/truncate tree nodes (`tree_drop`), treating the tree as a rebuildable cache. Both are consistent because OptMem's tree is explicitly a cache over an authoritative log; a CT log has no underlying authoritative source, so it cannot truncate. A chatroom store is in OptMem's camp (the raw log is authoritative), so `forget`-style repair is legitimate there.
- **CDC applicability.** CDC vendors (restic, FastCDC) present CDC as universally superior to FSC; borg and IPFS both document fixed-size chunking as the *correct* choice for already-aligned content. For a fixed-width, tail-append-only log the second position is the applicable one.
- **"Verifiable summary".** Transparency-log sources use "verifiable" to mean *tamper-evident inclusion/consistency* of deterministic data; the LLM-provenance papers use it to mean *signed provenance of a non-deterministic artifact*. These are different guarantees; conflating them is the central trap in applying Merkle trees to LLM summaries.

## Gaps
- **No source combines Merkle/CDC with LLM hierarchical-summarisation compression.** Stated as W3.30; verified across 7 searches. The design space (OptMem/OptChat + content addressing) appears unstudied.
- **No published measurement of whether a hash-pinned summary tree actually detects compactor divergence in practice.** W3.23 is an inference from RFC 6962's determinism assumption, not a cited experiment.
- **Git object-rewrite count is derived, not measured here**: W3.17's `O(depth)` follows from the object model (Git book); no benchmark was run and none was cited.
- **CDCs on records**: the "record-aware chunking" recommendation in W3.13 comes from a search summary rather than a fetched primary spec; the primary sources (FastCDC §2, restic) only state that CDC cuts the byte stream.
- **borg `buzhash` polynomial details** were not read from source (only the user-facing notes); restic's Rabin details were.
