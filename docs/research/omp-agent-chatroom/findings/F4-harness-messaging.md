# F4 harness messaging (Claude Code / Codex / Cursor)

## Angle
Do shipped coding harnesses give agents peer messaging? For each: tool/API name, transport, delivery semantics, persistence, in-process vs cross-process. Deep on Claude Code, Codex CLI, Cursor. One-line verdict for 15 more harnesses. Report-only.

## Claims

### Claude Code — SHIPS peer messaging (3 tiers)

**Tier 1: subagents (in-session)**
- Subagent = `Agent` tool call → isolated context window, returns summary to caller. `sub-agents` doc: "Subagents work within a single session." | https://code.claude.com/docs/en/sub-agents | 2026-10-06 | primary | no peer channel by default; caller-mediated
- Claude may pass `name` param on Agent call → subagent becomes *addressable*: "Claude can message or resume it by name". | https://code.claude.com/docs/en/sub-agents (line ~925) | 2026-10-06 | primary | names auto-generated by Claude without user asking
- Sibling roster: a system-reminder injected into a named subagent lists `main` + every other named agent in the session, "each a valid `to` value for SendMessage". Requires v2.1.206+. Snapshot at subagent start. | https://code.claude.com/docs/en/sub-agents (line ~1067) | 2026-10-06 | primary | → named subagents CAN message each other, not only parent
- Resume: `SendMessage` with agent ID/name resumes a completed subagent in background without a new Agent invocation; keeps tool set + prompt cache. A subagent with SendMessage can send too; resumed agent reports back to the resumer. | https://code.claude.com/docs/en/sub-agents (lines ~1091,1103-1105) | 2026-10-06 | primary | SendMessage does NOT require agent teams
- Name-collision guard: SendMessage verifies a name still maps to same agent; refuses if a newer agent took the name. | https://code.claude.com/docs/en/sub-agents (line ~1113) | 2026-10-06 | primary | scoped to current conversation

**Tier 2: agent teams (experimental, opt-in)**
- Gate: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in settings.json env; disabled by default; interactive session only (`-p`/SDK can't spawn teammates). | https://code.claude.com/docs/en/agent-teams | 2026-10-06 | primary | "experimental"
- Model: lead session + N teammates, each its own context window; teammates "communicate directly with each other"; lead assigns names; any teammate messages any other by name. | same | 2026-10-06 | primary |
- Mailbox transport: each agent's mailbox = JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`. Team name = `session-` + first 8 chars of session ID. Team config `~/.claude/teams/{team-name}/config.json` (members array); task list `~/.claude/tasks/{team-name}/`. | same | 2026-10-06 | primary | file-backed, not socket
- Delivery: "Automatic message delivery — when teammates send messages, they're delivered automatically to recipients. The lead doesn't need to poll." Idle teammate finishing notifies lead + includes final answer. | same | 2026-10-06 | primary | push, not pull
- Structured protocol messages: `shutdown_request`, `plan_approval_response` — team-only (cross-session is plain text only). Write succeeds only when mailbox write succeeds; disk-full/missing dir → error, nothing sent. | same + https://code.claude.com/docs/en/cross-session-messaging (Limitations) | 2026-10-06 | primary |
- Persistence: team config dir removed at session end; task list dir persists locally (never uploaded), governed by `cleanupPeriodDays`. Mailbox malformed entries validated+removed. | https://code.claude.com/docs/en/agent-teams | 2026-10-06 | primary |
- Limitations: no session resumption for in-process teammates (`/resume`,`/rewind` don't restore them); one team per session; no nested teams; lead fixed; teammate can't spawn background subagent. | same | 2026-10-06 | primary |
- Task list = shared coordination (TaskCreate/Get/List/Update) with file locking for claim races; agents lacking Task tools coordinate via messages instead. | same | 2026-10-06 | primary |

**Tier 3: cross-session messaging (session↔session)**
- Tools: `SendMessage` (send) + `ListAgents` (discover; backs `/list-agents` also aliased `/peers`). Permission-gated by bare tool name (`permissions.deny: ["SendMessage","ListAgents"]`). Requires v2.1.224+ (macOS/Linux/WSL2), v2.1.234+ native Windows. | https://code.claude.com/docs/en/cross-session-messaging | 2026-10-06 | primary | bare names, no specifier
- Transport: same machine → per-session Unix domain socket (`/tmp/cc-socks-<uid>` fallback), named pipe on Windows; "never through Anthropic servers". Cross-machine / cloud → through Anthropic servers over Remote Control. Socket path in `/status` `Peer address` (`uds:` prefix); env `CLAUDE_CODE_MESSAGING_SOCKET` + `CLAUDE_CODE_MESSAGING_TOKEN`; auth line `{"type":"auth","token":...}` (optional macOS/Linux, required Windows). | same | 2026-10-06 | primary | cross-process by design
- Delivery: "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message." | same (Message delivery) | 2026-10-06 | primary | turn-boundary inject / wake-idle
- Inbound controls: `crossSessionInbound` = accept|hold|refuse; default derived from permission modes (bypass vs prompting class). Held msgs → approval dialog; at most 100 held, oldest dropped. | same | 2026-10-06 | primary |
- `notify_when_idle` input on SendMessage: one notice when watched session goes idle/exits (v2.1.236+), 12h expiry, only main conversation, only same-machine. | same | 2026-10-06 | primary |
- Persistence: none for messages (transient); sessions bind inbox socket while alive; `claude -p` binds socket unless bare mode. | same | 2026-10-06 | primary |
- Limits: plain text only; same-machine size cap ~1M serialized chars; rapid-burst refusal; loop throttle + drop identical repeats; queue ≤50 accepted messages per receiver. | same (Limitations) | 2026-10-06 | primary |
- Security: incoming msg can't approve prompts, can't change config/CLAUDE.md, commands in text don't execute; auto-mode classifier reviews each agent message before delivery. | same + agent-teams | 2026-10-06 | primary |
- Memory: CLAUDE.md = always-on context loaded every session (not a message bus); `.claude/agents/` = subagent defs. | https://code.claude.com/docs/en/features-overview | 2026-10-06 | primary |

## Conflicting evidence
- Claude Code marketing summary ("subagents don't normally message one another") vs docs: `sub-agents` doc + `agent-teams` comparison both state *named* subagents can message each other via sibling roster. Nuance: unnamed/ordinary subagents cannot; naming is required and Claude may name them unprompted.
- Codex CLI: official docs (learn.chatgpt.com) describe subagents as spawn→collect summaries and never name `send_message`/`followup_task`; the shipped tool schemas in `multi_agents_spec.rs` explicitly implement peer messaging. Docs lag implementation.
- Cursor: "Cursor has custom subagents" (staff) could read as multi-agent, but staff explicitly disclaim sibling messaging; Projects adds human↔agent direct messaging + shared files, still coordinator-relayed. Absence confirmed by repeated staff "not available out of the box yet".
- Amp: docs say subagents "can't communicate with each other", but the June 2026 Plugin API release enables thread↔thread messaging — contradiction is scope (built-in vs plugin-authored custom agents).
- Codex V2: feature works but has a provider-compat regression (encrypted spawn schema 400s) reported in issues; not removed, just gated/fragile.

## Gaps
- Codex CLI: exact on-disk location/schema of mailbox persistence not located — mailbox.rs shows in-memory `HashMap` with eviction transferring mail; no durable mailbox file found. Whether unloaded-session mail survives process restart unverified.
- Codex CLI: no official prose doc for `send_message`/`followup_task` delivery-boundary semantics beyond the tool schema strings; sampled-boundary behavior ("while sampling") not further specified in source read.
- Claude Code: mailbox JSON file format/schema for team inboxes not enumerated (only path + validation described). Whether cross-session `SendMessage` can address a *subagent* of another session (vs that session's main) not stated.
- Cursor: no official docs page for any agent-to-agent API; verdict rests on staff forum replies + docs absence. Projects internals (how coordinator "keeps in the loop", shared-context file format) undisclosed.
- Cline SDK Teams: `mailbox.json` schema and delivery semantics (push vs poll) not documented in the reference file read; only tool names + persistence paths.
- Warp: message-bus wire protocol (transport type, persistence store) not specified; only "durable, server-backed".
- Devin/Manus/Jules: no public peer-messaging protocol; verdicts rest on docs absence — could exist internally.
- Dates: all fetches 2026-10-06; Cursor changelog entries dated 2026-04-02..09-10; Codex source = `main` branch snapshot.
