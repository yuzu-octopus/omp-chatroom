# F20-W4: Is single-writer fundamental to hierarchical summarisation?

## Angle

Whether the single-writer constraint in OptMem and OptChat is a fundamental property of hierarchical LLM summarisation, or an incidental implementation choice tied to their specific storage model. Examines CRDT convergence, epoch/fencing serialisation, and the CALM theorem.

## Claims

### Q1: Is OptMem's single-writer requirement enforced or incidental?

- [W4.1] OptMem enforces mutual exclusion via `fcntl.flock(LOCK_EX)` in `locked()` (lines 302-332), acquired by `log_append` (line 339), `tree_put` (line 357), and `tree_drop` (line 377). This is a real filesystem-level lock, not a convention. — source: `/tmp/OptMem/memo:302-332,339,357,377` (fetched 2026-10-06) — confidence: high
- [W4.2] The lock's primary purpose is **log integrity**: fixed-width records (LOG_REC=320) mean "position IS identity" (lines 68-73); a torn append misaligns every later record. The lock serialises appends so ids are assigned atomically (line 338: "two sessions noting at the same moment must not be handed the same id"). — source: `/tmp/OptMem/memo:68-73,335-350` (fetched 2026-10-06) — confidence: high
- [W4.3] The lock also enforces **nap ordering**: "Blocks are built in order, so this only ever appends one record to one level file" (line 354-355). `tree_put` checks `count(p, TREE_REC) != lo // size` and refuses to write out of order (line 361). This is about tree structural integrity, not summariser uniqueness per se. — source: `/tmp/OptMem/memo:353-369` (fetched 2026-10-06) — confidence: high
- [W4.4] The TEMPLATE (line 538) says "Parallel sessions on this machine are all you, and may all write memories" — but this refers to the agent's own concurrent sessions coordinating via the lock, not to parallel summarisers. The subagent rule (line 539: "it must never run `memo`") is a policy against duplicate notes, not a concurrency mechanism. — source: `/tmp/OptMem/memo:536-542` (fetched 2026-10-06) — confidence: high
- [W4.5] **Verdict for Q1**: The single-writer lock is **enforced** (flock) but **incidental to summarisation** — it exists because the storage format (fixed-width append-only log + ordered tree files) requires serialised writes. A different storage model (e.g., content-addressed, CRDT-based) would not need it. — source: `/tmp/OptMem/memo:302-332` (fetched 2026-10-06) — confidence: high

### Q2: OptChat's 'One writer' lock — log integrity or summariser uniqueness?

- [W4.6] OptChat's lock (lines 120-125) is explicitly about **log integrity**: "two processes on the same chat would corrupt it." The mechanism is a Unix socket lock held for the life of the process. — source: `/tmp/optchat.md:120-125` (fetched 2026-10-06) — confidence: high
- [W4.7] The tree is "a cache in principle (rebuildable from the log), but it costs model calls to rebuild, so it is stored and never recomputed" (lines 126-127). This makes the lock also about **summariser uniqueness**: if two processes built different summaries for the same node, the tree would be incoherent and rebuilding is expensive. — source: `/tmp/optchat.md:126-127` (fetched 2026-10-06) — confidence: high
- [W4.8] The distinction: **log integrity** = the append-only message log must not be corrupted (torn lines, misaligned ids). **Summariser uniqueness** = at most one process should produce the summary for a given node, because LLM summarisation is non-deterministic and the tree is not recomputed. The lock solves both, but they are separable concerns. — source: `/tmp/optchat.md:120-127` (fetched 2026-10-06) — confidence: high
- [W4.9] OptChat's `settle()` (lines 503-506) and the pump's rule 3 (lines 176-184) ensure no read sees an unbuilt placeholder, but they assume a single compactor. With two compactors, `settle()` could pass on one writer's summary while the other writer's summary for the same node is still pending. — source: `/tmp/optchat.md:176-184,503-506` (fetched 2026-10-06) — confidence: medium

### Q3: Can a summarised node be treated as a CRDT value?

- [W4.10] **State-based CRDTs** (CvRDTs) require a join-semilattice: states partially ordered, join is associative/commutative/idempotent, updates monotonic. Two replicas converge by joining states. — source: Shapiro et al., "Conflict-free Replicated Data Types," INRIA RR-7687 (2011), https://www.lip6.fr/Marc.Shapiro/papers/RR-7687.pdf (fetched 2026-10-06) — confidence: high
- [W4.11] **Operation-based CRDTs** (CmRDTs) require concurrent operations to commute, with reliable causally-ordered broadcast. — source: Shapiro et al., RR-7687 (2011), https://www.lip6.fr/Marc.Shapiro/papers/RR-7687.pdf (fetched 2026-10-06) — confidence: high
- [W4.12] LLM summarisation is **non-deterministic**: two calls with the same input produce different text. This means the "state" of a summary node is not a function of its input range — it is a function of (range, model, prompt, temperature, time). A CvRDT join of two different summaries for the same range would need a **multi-value register** (retain both), not a last-writer-wins register. — source: `/tmp/optchat.md:218-244` (fetched 2026-10-06) — confidence: high
- [W4.13] The view tiles `[0, T)` with **exactly one part per range** (line 389-390: "a list of tree nodes that tiles the whole chat"). A multi-value register would break this: the view would need a policy to pick one summary (e.g., latest by epoch), which reintroduces a single-writer assumption at read time. — source: `/tmp/optchat.md:389-390,422-435` (fetched 2026-10-06) — confidence: high
- [W4.14] **What breaks downstream**: if two compactors write different summaries for node `(l, i)`, the view could render different text depending on which write landed last. This is a **divergence problem** (different reads see different summaries), not a **correctness problem** (the log is still the source of truth; the tree is a cache). But divergence undermines the cache's value: the agent cannot trust that a summary is stable. — source: `/tmp/optchat.md:126-127,389-390` (fetched 2026-10-06) — confidence: medium
- [W4.15] **Verdict for Q3**: A summarised node **cannot** be a simple CRDT value (LWW register) because LLM non-determinism means two writers produce different text. It **could** be a multi-value register, but the view's tiling invariant (one part per range) forces a read-time policy that is equivalent to single-writer. — source: `/tmp/optchat.md:389-390`; Shapiro et al., RR-7687 (fetched 2026-10-06) — confidence: medium

### Q4: Epoch/fencing — can compaction be serialised by a monotonic epoch?

- [W4.16] **Fencing tokens** (Kleppmann): each lock acquisition gets a strictly increasing number; the protected resource remembers the greatest token accepted and rejects lower ones. This prevents a stale holder from committing writes after a new holder has taken over. — source: Kleppmann, "How to do distributed locking" (2016-02-08), https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html (fetched 2026-10-06) — confidence: high
- [W4.17] **Epoch as fencing token**: a monotonic epoch on the log length `T` (or on block index) serialises compaction. At most one compactor owns each block at a given epoch. A compactor with epoch `e` writes node `(l, i)` with token `e`; the store rejects writes with token `< e`. This is exactly Kleppmann's fencing pattern applied to tree nodes. — source: Kleppmann (2016), https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html (fetched 2026-10-06) — confidence: high
- [W4.18] **Kafka log compaction** serialises by key: each key has a latest value, and compaction retains only the latest. This is LSM-based, not tree-based, but the principle (monotonic epoch per key, stale writes rejected) is the same. — source: Kafka documentation, https://kafka.apache.org/documentation/#compaction (fetched 2026-10-06) — confidence: medium
- [W4.19] **ZooKeeper/etcd leader epochs**: each leader election produces a higher epoch; writes from older epochs are rejected. This is the same fencing pattern. — source: Kleppmann (2016), https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html (fetched 2026-10-06) — confidence: high
- [W4.20] **CALM theorem** (Hellerstein & Alvaro): monotone computations can be implemented consistently without coordination; non-monotone computations generally need coordination. LLM summarisation is **non-monotone** (adding a message can change the summary of an earlier range, because the new message provides context that changes what is salient). This means summarisation is **not** coordination-free under CALM. — source: Hellerstein & Alvaro, "Keeping CALM: When Distributed Consistency Is Easy," https://arxiv.org/abs/1901.01930 (fetched 2026-10-06) — confidence: high
- [W4.21] **Verdict for Q4**: Epoch/fencing **can** serialise compaction (Kleppmann's pattern applies directly), but it requires the store to enforce token checks, and it does not solve the divergence problem (two compactors still produce different summaries; fencing just ensures only one lands). — source: Kleppmann (2016), https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html (fetched 2026-10-06) — confidence: high

### Q5: Verdict — MUST a summariser be single-writer by construction?

- [W4.22] **Strongest argument for "fundamental"**: The view tiles `[0, T)` with exactly one part per range. LLM summarisation is non-deterministic. Therefore, if two compactors can write summaries for the same range, the view can diverge (different reads see different summaries). Since the view is the agent's only context, divergence is a correctness problem for the agent's behaviour, not just a cache inconsistency. Single-writer is the simplest way to guarantee the view is stable. — source: `/tmp/optchat.md:389-390,422-435` (fetched 2026-10-06) — confidence: medium
- [W4.23] **Strongest argument for "incidental"**: The tree is a rebuildable cache over the log. If the tree were content-addressed (hash of summary text) and the view used a deterministic selection policy (e.g., lexicographically smallest summary, or latest by epoch), two compactors could write different summaries and the view would still be deterministic. Single-writer is a policy choice that trades simplicity for the cost of serialisation. — source: `/tmp/optchat.md:126-127` (fetched 2026-10-06) — confidence: medium
- [W4.24] **Judgement call**: Single-writer is **incidental to the concept** of hierarchical summarisation but **practically necessary** given (a) LLM non-determinism, (b) the view's one-part-per-range invariant, and (c) the cost of rebuilding the tree. A CRDT-based design is theoretically possible but would require a multi-value register + deterministic read policy, which is more complex than the current single-writer lock and would still need epoch/fencing to avoid unbounded growth of the register. — source: `/tmp/optchat.md:126-127,389-390`; Shapiro et al., RR-7687 (fetched 2026-10-06) — confidence: medium
- [W4.25] **CALM implication**: Because LLM summarisation is non-monotone (new context can change what is salient in an old summary), it is **not** coordination-free under the CALM theorem. This means some form of serialisation (single-writer, epoch/fencing, or consensus) is required for a shared tree. The choice is which mechanism, not whether to have one. — source: Hellerstein & Alvaro, https://arxiv.org/abs/1901.01930 (fetched 2026-10-06) — confidence: medium

## Conflicting evidence

- OptMem's TEMPLATE (line 538) says parallel sessions "may all write memories," which could be read as endorsing multi-writer. But the `flock` in `locked()` (lines 302-332) serialises all writes, so the TEMPLATE refers to the agent's sessions coordinating via the lock, not to lock-free parallel writes. No true conflict, but the wording is ambiguous.
- OptChat's tree is "a cache in principle (rebuildable from the log)" (line 126), which suggests single-writer is not fundamental. But the same sentence says "it costs model calls to rebuild, so it is stored and never recomputed," which makes single-writer practically necessary. The design is internally consistent but the "cache" framing understates the serialisation requirement.

## Gaps

- No primary source found that directly addresses CRDT convergence for LLM-produced summaries. The argument in W4.12-W4.15 is an inference from CRDT theory + observed LLM non-determinism, not a cited result.
- No primary source found that applies epoch/fencing specifically to tree-structured summarisation. W4.17-W4.21 extrapolate from Kleppmann's general fencing pattern and Kafka/ZooKeeper epoch mechanisms.
- The CALM theorem's application to LLM summarisation (W4.20, W4.25) is an inference: CALM addresses logical monotonicity of queries, and LLM summarisation is not a query in the database sense. The argument that summarisation is "non-monotone" is plausible but not formally proven in the CALM framework.
