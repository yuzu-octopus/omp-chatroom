# F20-W1: OptMem and OptChat as a two-region design

## Angle
Re-read OptMem (`/tmp/OptMem/memo`) and OptChat (`/tmp/optchat.md`) to understand how each implements a two-region view (raw near the present, compressed far from it), what mechanisms enforce the boundary, and what OptChat explicitly rejected.

## Claims

### Q1: OptMem's `cover(T, budget)` as a two-region view

- [W1.1] `_cover(T, alpha)` tiles `[0,T)` with aligned power-of-two blocks, keeping a block whole iff its size ≤ `alpha * (T - lo)` (its age). Larger alpha = coarser = fewer lines. — source: `/tmp/OptMem/memo:82-102` — confidence: high
- [W1.2] The bisection: `cover(T, budget)` binary-searches alpha in `[0, 1]` for 60 iterations, calling `_cover(T, mid)` each time. If the tiling exceeds `budget`, `lo = mid` (need coarser); else `hi = mid`. Final tiling uses `hi`. — source: `/tmp/OptMem/memo:114-121` — confidence: high
- [W1.3] The "spend what is left on the present" loop: after bisection, if `len(out) < budget`, it repeatedly finds the largest block (`max` by size) and splits it in half, until the budget is reached or no block > 1 remains. This ensures the most detail is spent near the present. — source: `/tmp/OptMem/memo:122-131` — confidence: high
- [W1.4] The two-region property: near T, blocks are small (size 1 = raw memories); far from T, blocks are large (compressed summaries). The `size <= alpha * (T - lo)` rule means a block is kept whole only if it is small relative to its age — recent blocks pass, ancient blocks are forced to split. — source: `/tmp/OptMem/memo:95` — confidence: high
- [W1.5] If `T <= budget`, everything is raw: `[(i, i+1) for i in range(T)]`. No compression at all. — source: `/tmp/OptMem/memo:112-113` — confidence: high

### Q2: `RAW_MAX=16` and the raw/compressed boundary

- [W2.1] `RAW_MAX = 16` (line 65): "blocks up to this many memories compress from the raw log." — source: `/tmp/OptMem/memo:65` — confidence: high
- [W2.2] In `nap_prompt` (line 463): if `hi - lo <= RAW_MAX`, the prompt body is the raw memories from `log_slice(d, lo, hi)` — each memory printed verbatim. — source: `/tmp/OptMem/memo:464-465` — confidence: high
- [W2.3] If `hi - lo > RAW_MAX`, the prompt body is the two halves' summaries from `tree_get(d, a, b)` — each half rendered as `#a-b <summary>`. — source: `/tmp/OptMem/memo:466-477` — confidence: high
- [W2.4] Implication: blocks of ≤ 16 memories are compressed directly from raw log entries (the model sees the original text). Larger blocks are compressed from their children's summaries (the model sees already-compressed text). This creates a two-level compression: raw → ≤16-summary → larger summaries. — source: `/tmp/OptMem/memo:463-477` — confidence: high
- [W2.5] The raw/compressed boundary is at 16 memories. Below: model sees raw. Above: model sees summaries-of-summaries. This is a quality tradeoff — larger blocks lose more detail per compression step. — source: `/tmp/OptMem/memo:65,463-477` — confidence: medium

### Q3: `nap` lazy model — triggers and blocking behaviour

- [W3.1] `next_nap(d, T)` (line 489) finds the first pending block (smallest, via `pending(d, T, limit=1)`) and returns a prompt for it, or `None` if nothing is pending. — source: `/tmp/OptMem/memo:489-494` — confidence: high
- [W3.2] `cmd_note` (line 654): after appending a memory, calls `next_nap(d, i + 1)` and prints the prompt if one exists. The agent is told "If `memo note` asks a compression: do it before your next action" (TEMPLATE line 523). — source: `/tmp/OptMem/memo:661-663,523` — confidence: high
- [W3.3] `cmd_wake` (line 584): after printing the memory context, calls `next_nap(d, T)` and prints the prompt if one exists (lines 649-651). — source: `/tmp/OptMem/memo:649-651` — confidence: high
- [W3.4] `cmd_nap` (line 666): after saving a block (or if no args), calls `next_nap(d, T)` and prints the next prompt (lines 688-692). — source: `/tmp/OptMem/memo:688-692` — confidence: high
- [W3.5] Blocking behaviour: `cmd_wake` refuses with exit 1 when a block needed for the view is not yet compressed (lines 609-622). It prints "Cannot wake: the memory context needs #lo-hi, which is not compressed yet" and the nap prompt, then `sys.exit(1)`. This is the ONLY reason wake refuses. — source: `/tmp/OptMem/memo:609-622` — confidence: high
- [W3.6] The comment at line 612-615: "The ONLY reason to refuse: this document cannot be written without that summary. Work that the document does not need is handed over after the read instead, costing no round trip." — source: `/tmp/OptMem/memo:612-615` — confidence: high
- [W3.7] Compaction is non-blocking in the sense that `wake` does not itself compress — it delegates to the agent. But it IS blocking in that the agent cannot proceed without doing the compression first (exit 1). — source: `/tmp/OptMem/memo:609-622` — confidence: high
- [W3.8] A parallel session may have paid the pending block between the check and the exit: line 623 re-checks `tree_get` after the exit path. — source: `/tmp/OptMem/memo:623` — confidence: high

### Q4: `zoom(lo,hi)` and `forget(lo,hi)` semantics

- [W4.1] `cmd_zoom` (line 762): parses a block id, computes `mid = (lo + hi) // 2`, then for each half `(lo, mid)` and `(mid, hi)`: if the half is a single memory (`b - a == 1`), prints it raw via `log_get`; otherwise prints the summary via `tree_get` (or "not compressed yet" if `None`). — source: `/tmp/OptMem/memo:762-782` — confidence: high
- [W4.2] `cmd_forget` (line 718): calls `tree_drop(d, *block_id(args[0]))` which truncates every level file from that block onward, then prints how many summaries were forgotten. The log is never touched. — source: `/tmp/OptMem/memo:718-728` — confidence: high
- [W4.3] `tree_drop` (line 372): cascades upward — for each level `size` from `hi - lo` up to `log_len(d)`, it truncates the level file at position `lo // size`. This drops the target block AND every block built from it (all ancestors). Later blocks at those levels also go and are rebuilt. — source: `/tmp/OptMem/memo:372-389` — confidence: high
- [W4.4] The cascade: `while size <= log_len(d)` iterates through all levels, truncating each at the target position. `gone` collects all dropped blocks for reporting. — source: `/tmp/OptMem/memo:379-387` — confidence: high

### Q5: Single-writer assumption in OptMem

- [W5.1] OptMem does NOT enforce a single writer. The `locked(d)` function (line 302) uses `fcntl.flock` (or `msvcrt.locking` on Windows) to serialise individual operations (append, tree_put, tree_drop), but multiple processes may hold the lock sequentially. — source: `/tmp/OptMem/memo:302-332` — confidence: high
- [W5.2] The TEMPLATE explicitly acknowledges multi-writer: "Parallel sessions on this machine are all you, and may all write memories." (line 538) — source: `/tmp/OptMem/memo:538` — confidence: high
- [W5.3] The lock is per-operation, not per-process: `log_append` opens the lock, writes, closes it (lines 339-350). Between operations, another process can acquire it. — source: `/tmp/OptMem/memo:339-350` — confidence: high
- [W5.4] Id assignment is inside the lock: "Ids are assigned INSIDE the lock: two sessions noting at the same moment must not be handed the same id." (line 337-338) — source: `/tmp/OptMem/memo:337-338` — confidence: high
- [W5.5] The single-writer assumption is incidental, not enforced. Multiple sessions are expected to write; the lock only prevents corruption of individual operations. — source: `/tmp/OptMem/memo:302-350,538` — confidence: high

### Q6: The subagent rule

- [W6.1] TEMPLATE lines 536-541: "If you're a subagent: skip everything above. Parallel sessions on this machine are all you, and may all write memories. A subagent is not: it must never run `memo`, because it cannot judge what is already known, and its notes would arrive duplicated and incorrectly. When you spawn one, write: `You are a subagent. Don't run memo.`" — source: `/tmp/OptMem/memo:536-541` — confidence: high
- [W6.2] The stated reason: a subagent cannot judge what is already known (it lacks the full context of the parent's memory), so its notes would be duplicated and incorrect. — source: `/tmp/OptMem/memo:539-540` — confidence: high
- [W6.3] The distinction: parallel sessions of the SAME agent are "all you" and share the same identity/context. A subagent is a different agent with different context, so its notes would pollute the parent's memory. — source: `/tmp/OptMem/memo:538-540` — confidence: high

### Q7: OptChat's `fit()` serialisation and the process-level lock

- [W7.1] OptChat's `fit()` (§5.2, line 422): on each new message, appends `part(0, i)` to the view, then repeatedly finds the most-due adjacent pair (same level, even index, parent built) and merges them, until the view fits `VIEW` bytes. — source: `/tmp/optchat.md:414-435` — confidence: high
- [W7.2] "Most due" = oldest relative to size: `due = (T - start) / 2^(l+2)`. The pair with the largest `due` is merged first. — source: `/tmp/optchat.md:429-431` — confidence: high
- [W7.3] "Never split" (line 441): once merged, a part stays merged. The view only appends at the end and coarsens. This is what makes the view cacheable. — source: `/tmp/optchat.md:441-442` — confidence: high
- [W7.4] The process-level lock (§2, lines 120-125): "One writer: two processes on the same chat would corrupt it. Hold a lock for the life of the process. The reference uses a Unix socket: the process listens on `lock`; a second process that can connect to it exits; a socket that refuses connections is stale (the OS frees it when the owner dies), so it is deleted and taken over." — source: `/tmp/optchat.md:120-125` — confidence: high
- [W7.5] The lock is for the LIFE OF THE PROCESS (not per-operation like OptMem). This is a stronger guarantee: only one process ever writes to a chat. — source: `/tmp/optchat.md:121` — confidence: high
- [W7.6] `fit()` serialises concurrent compaction in ONE process: the compactor runs up to `JOBS=8` background workers (line 89), but `fit()` is called synchronously after each node is built (line 419-420) and after each new message (line 417). The `settle()` function (§6, line 503) blocks the turn loop until all view parts are built. — source: `/tmp/optchat.md:89,414-420,503-506` — confidence: high
- [W7.7] The relationship to multi-writer: OptChat's lock is process-level and exclusive — a second process exits immediately. This is fundamentally different from OptMem's per-operation lock that allows multiple writers to interleave. — source: `/tmp/optchat.md:120-125` vs `/tmp/OptMem/memo:302-350` — confidence: high

### Q8: OptChat's rejection of "showing recent messages whole" (§5.3)

- [W8.1] The exact passage (§5.3, lines 470-476): "**Showing recent messages whole** (and only older ones summarized). This breaks everything. A message can be any size: one 30 KB tool output entering the view forces dozens of merges among old lines, which are never split back, so a few big messages permanently erase old detail. And a long last turn could be 200k tokens. With summaries only, every line is ≤ ~512 bytes, so the budget is stable and the math works. The cost is a zoom when the agent needs exact text, which is cheap." — source: `/tmp/optchat.md:470-476` — confidence: high
- [W8.2] The rejection is specific to OptChat's constraints: (a) the view must be cacheable — whole messages of arbitrary size would cause cache misses; (b) the view must be stable in size — a 30 KB message would blow the 128 KB budget; (c) "never split" means merges are permanent — big messages would force irreversible merges of old lines. — source: `/tmp/optchat.md:470-476,441-442` — confidence: high
- [W8.3] The rejection is NOT general — it is specific to OptChat's design where the view is the ONLY context, must be cacheable, and must be size-bounded. In a design where raw messages are kept in a separate region (like OptMem's log), the "show recent whole" approach works because the raw region is not part of the compressed view. — source: `/tmp/optchat.md:470-476` vs `/tmp/OptMem/memo:82-131` — confidence: medium
- [W8.4] OptChat's alternative: "The cost is a zoom when the agent needs exact text, which is cheap." The agent zooms to get the full message when needed. — source: `/tmp/optchat.md:476` — confidence: high
- [W8.5] The checklist (§11, line 762) reiterates: "Putting whole messages in the view (big messages wreck old memory)." — source: `/tmp/optchat.md:762` — confidence: high
- [W8.6] OptChat also rejected "hybrid trees (raw blocks of 16, etc.)" (§11, line 777): "Keep it purely binary." This is a direct rejection of OptMem's `RAW_MAX=16` approach. — source: `/tmp/optchat.md:777` — confidence: high
- [W8.7] The §3 tree description (lines 145-148) explains why OptChat dropped OptMem's raw blocks: "OptMem built small blocks of up to 16 memories straight from the raw notes, and only bigger ones from two halves. That had no real justification and made the structure confusing; OptChat dropped it. Every parent comes from exactly its two children." — source: `/tmp/optchat.md:145-148` — confidence: high

## Gaps
- OptMem's `RAW_MAX=16` is not configurable via `config` (it is a module-level constant, not in `KNOBS`). This means the raw/compressed boundary is fixed at 16 and cannot be tuned per-memory. — source: `/tmp/OptMem/memo:50-65` — confidence: high
- OptMem does not have a `settle()` equivalent — it relies on the agent to do compressions when prompted. There is no background compactor. — source: `/tmp/OptMem/memo:584-692` — confidence: high
- OptChat's `fit()` is O(n) in view size per call (scans all adjacent pairs). With ~500 lines, this is 500 iterations per message. The spec does not discuss this cost. — source: `/tmp/optchat.md:422-435` — confidence: medium
