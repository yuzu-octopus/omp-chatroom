# F21-W3: zoom(lo,hi) semantics and addressing

## Angle
How does zoom address a range when a node covers N messages? What is the exact signature: zoom(lo, hi) or zoom(seq, span)? How does zoom interact with the raw tail? What does zoom return: raw messages, or a sub-tree? OptMem's zoom: exact semantics from source.

---

## Claims

### Q1: OptMem `memo zoom` — exact signature, return value, descent

- [W3.1] **Signature**: `memo zoom <lo>-<hi>` — a single string argument, inclusive at both ends (e.g. `zoom 16-31`). Parsed by `block_id()` at `/tmp/OptMem/memo:407-418`. The parser converts to exclusive: `lo, hi = int(m.group(1)), int(m.group(2)) + 1`. — source: `/tmp/OptMem/memo:407-418,762-769` — confidence: high

- [W3.2] **Validation**: `block_id()` enforces three constraints: (a) `n = hi - lo >= 2` (cannot zoom a single memory), (b) `n & (n-1) == 0` (must be a power of two), (c) `lo % n == 0` (must be aligned). Fails with "not a block. Copy the id printed by wake, like 16-31." — source: `/tmp/OptMem/memo:411-417` — confidence: high

- [W3.3] **Return value**: prints exactly two lines — the two halves of the node. For each half `(a, b)` where `mid = (lo + hi) // 2`: if `b - a == 1` (single memory), prints the raw log entry via `log_get(d, a)` in format `#<id> <date> <text>`; otherwise prints the tree summary via `tree_get(d, a, b)` in format `#<a>-<b-1> <summary>`, or `#<a>-<b-1> not compressed yet` if the summary doesn't exist. — source: `/tmp/OptMem/memo:774-782` — confidence: high

- [W3.4] **Descent**: zoom opens ONE level only — a single node into its two children. It does NOT recursively descend. The agent calls zoom repeatedly to walk down to raw memories. The docstring: "One node of the tree, opened: its two halves, each rendered as wake renders it — a summary, or the raw memory once a half is single. The navigating intelligence is the agent's; the tool only reads." — source: `/tmp/OptMem/memo:763-765` — confidence: high

- [W3.5] **Boundary check**: if `lo >= T` (the memory count), zoom dies with "beyond the memory". If a half extends past T (`a >= T`), that half is silently skipped ("the future: no memories there yet"). — source: `/tmp/OptMem/memo:770-777` — confidence: high

### Q2: OptChat `zoom(id, n)` — exact signature, return value, view interaction

- [W3.6] **Signature**: `zoom(id, n)` — two arguments: `id` = first message id (must be aligned), `n` = span (must be a power of 2). Validation: `n` must be power of 2, `id % n == 0`, `id + n <= T`. — source: OptChat gist §7.1 (fetched 2026-10-06 from `gist.github.com/VictorTaelin/91837951a5ce5b38f341ec1ba1df6449`) — confidence: high

- [W3.7] **Return value**: if `n == 1`: returns the whole message text: `id + "+0|" + kind + ": " + message text` (newlines kept). If `n > 1`: returns the two children lines, each rendered as `id+n|text`. If invalid: returns `"No line id+n."`. — source: OptChat gist §7.1 — confidence: high

- [W3.8] **Children always exist**: "Zoom returns the children's current text, which exists because a parent is only built after its children." This is guaranteed by the compactor's ordering (§4.1 rule 2: a node is built only when both children are built). — source: OptChat gist §7.1 — confidence: high

- [W3.9] **Descent cost**: "Zooming from the view down to a message takes `log2(n)` calls; in practice the agent finds things in 3-5." — source: OptChat gist §7.1 — confidence: high

- [W3.10] **View interaction**: zoom does NOT modify the view. The view is built by `fit()` (§5.2) which appends and merges. zoom is a pure read tool that descends from any view line to its children. The agent reads `2184+8` in the view and calls `zoom(2184, 8)` to open it. — source: OptChat gist §3, §5.2, §7.1 — confidence: high

### Q3: Addressing — (lo, hi) vs (id, span)

- [W3.11] **OptMem uses (lo, hi)**: inclusive range as a string `"16-31"`. The `+1` conversion to exclusive happens inside `block_id()`. This matches how wake prints blocks (`#16-31 <summary>`), so the agent copies the id directly from wake output. — source: `/tmp/OptMem/memo:407-418,629` — confidence: high

- [W3.12] **OptChat uses (id, n)**: `id` = first message, `n` = span = `2^l`. The node name `id+n` (e.g. `2184+8`) encodes both. This is equivalent to `(lo, hi)` where `lo = id` and `hi = id + n`. — source: OptChat gist §3 — confidence: high

- [W3.13] **Tradeoffs**: (lo, hi) is more readable for humans and matches wake output format. (id, n) is more natural for the tree structure — `n` directly encodes the level (`l = log2(n)`), and `id` is the permanent message index. Both require alignment validation. Neither is strictly superior; the choice depends on whether the primary interface is the rendered view (OptChat: `id+n`) or the command output (OptMem: `#lo-hi`). — source: [INFERENCE] from both systems — confidence: medium

### Q4: Zoom interaction with the raw tail

- [W3.14] **OptMem zoom CAN return raw messages**: when a half has `b - a == 1`, zoom reads from LOG.txt via `log_get()` and prints the raw memory. This is the base case of the descent. — source: `/tmp/OptMem/memo:778-779` — confidence: high

- [W3.15] **OptChat zoom CAN return raw messages**: when `n == 1`, zoom returns the whole message text with kind prefix. This is the base case. — source: OptChat gist §7.1 — confidence: high

- [W3.16] **Both systems mix raw and compressed in a single zoom**: when zooming a block of size > 2, one half may be size 1 (raw) and the other size > 1 (compressed). Both handle this naturally — each half is checked independently. — source: `/tmp/OptMem/memo:775-782`, OptChat gist §7.1 — confidence: high

- [W3.17] **OptMem's raw tail is separate from the tree**: raw memories live in LOG.txt (fixed-width 320-byte records), tree summaries live in TREE/<size> (fixed-width 288-byte records). Zoom reads from both. The raw tail is the authoritative source; the tree is a rebuildable cache. — source: `/tmp/OptMem/memo:68-73,255-292` — confidence: high

- [W3.18] **OptChat's raw tail is also separate**: messages live in `chat/main/YYYY-MM-DD.jsonl`, tree nodes in `tree/YYYY-MM-DD.jsonl`. Zoom reads from both. — source: OptChat gist §2 — confidence: high

### Q5: Zoom composition with cover/wake

- [W3.19] **OptMem zoom does NOT re-run cover**: zoom is a pure read operation. It takes a block id, splits it, and prints the two halves. It does not compute a tiling, does not check budgets, and does not interact with `cover()` or `wake()`. The agent first runs `wake` to get the view, then runs `zoom` on any block it wants to open. — source: `/tmp/OptMem/memo:762-782` — confidence: high

- [W3.20] **OptChat zoom does NOT re-run fit**: zoom is a pure read. The view is maintained incrementally by `fit()` on each new message and each node built. zoom descends from any view line without modifying the view. — source: OptChat gist §5.2, §7.1 — confidence: high

- [W3.21] **The agent orchestrates the descent**: in both systems, the agent (not the tool) decides when to zoom. OptMem's TEMPLATE says: "every `#a-b` line wake prints is one node of it. `memo zoom <a-b>` opens a node into its two halves, down to the raw memories." OptChat's VIEW_DOC says: "zoom(id, n) opens line id+n into the two lines of n/2 messages it was made from; zoom(id, 1) gives message id in full." — source: `/tmp/OptMem/memo:531-534`, OptChat gist §7.2 — confidence: high

### Q6: Edge cases

- [W3.22] **Zoom on a raw message (OptMem)**: impossible — `block_id()` requires `n >= 2`. The smallest zoomable block covers 2 memories. To read a single raw memory, the agent uses `recall <regex>` or reads it from wake output (where size-1 blocks are printed raw). — source: `/tmp/OptMem/memo:411-417` — confidence: high

- [W3.23] **Zoom on a raw message (OptChat)**: `zoom(id, 1)` returns the whole message. This is the base case and the most common zoom target. — source: OptChat gist §7.1 — confidence: high

- [W3.24] **Zoom spanning raw and compressed (both systems)**: handled naturally. Each half is checked independently: if size 1, read raw; else read tree. A zoom of `0-7` produces `0-3` (tree) and `4-7` (tree); a zoom of `0-1` produces `#0` (raw) and `#1` (raw); a zoom of `0-3` produces `0-1` (tree) and `2-3` (tree). — source: `/tmp/OptMem/memo:774-782` — confidence: high

- [W3.25] **Zoom on a range larger than the view (OptMem)**: no explicit check against the view. zoom reads the tree directly. If the block's summary doesn't exist, `tree_get` returns `None` and zoom prints "not compressed yet". The agent must run `nap` to compress it first. — source: `/tmp/OptMem/memo:781-782` — confidence: high

- [W3.26] **Zoom on a range larger than the view (OptChat)**: the `id + n <= T` check prevents zooming beyond the log. But there is no check against the view — the agent can zoom any valid node, even one not currently in the view. The children's text exists because the compactor builds all nodes in order. — source: OptChat gist §7.1 — confidence: high

- [W3.27] **Zoom on an unbuilt node (OptMem)**: prints "not compressed yet" for that half. The agent must run `memo nap` to compress it. This is the same mechanism as wake's refusal. — source: `/tmp/OptMem/memo:781-782` — confidence: high

- [W3.28] **Zoom on an unbuilt node (OptChat)**: impossible by construction — a parent is only placed in the view after it's built (§5.2: "Parents not built yet are passed over"). And zoom on any node returns children that are already built (§7.1: "a parent is only built after its children"). — source: OptChat gist §5.2, §7.1 — confidence: high

- [W3.29] **Zoom on a future range (OptMem)**: if `lo >= T`, zoom dies. If a half extends past T, that half is silently skipped. This handles the case where the tree has been built for a range larger than the current log (e.g. after a parallel session appended memories that wake hasn't seen yet). — source: `/tmp/OptMem/memo:770-777` — confidence: high

### Q7: What zoom returns — summary

- [W3.30] **OptMem zoom returns**: a list of two lines (the children), each either a raw memory or a tree summary. Not a sub-tree, not a structured object — just text printed to stdout. The agent parses the output to decide the next zoom. — source: `/tmp/OptMem/memo:762-782` — confidence: high

- [W3.31] **OptChat zoom returns**: the two children lines rendered as `id+n|text`, or the whole message text if `n == 1`. Not a sub-tree — just the immediate children. The agent calls zoom again to descend further. — source: OptChat gist §7.1 — confidence: high

- [W3.32] **Neither system returns a sub-tree**: both return exactly one level of descent. This is a deliberate design choice — the agent controls the descent, one level at a time, and can stop at any level. Returning a sub-tree would (a) blow the output budget, (b) remove the agent's ability to choose which branch to follow, and (c) potentially show irrelevant detail. — source: [INFERENCE] from both systems' design — confidence: medium

## Conflicting evidence

- None. OptMem and OptChat are internally consistent. The two systems use different addressing conventions ((lo,hi) vs (id,n)) but the semantics are equivalent: both open one node into its two children, both can return raw messages at the base case, both are pure reads that don't modify the view.

## Gaps

- OptMem's `RAW_MAX=16` means blocks ≤ 16 are compressed from raw log, not from two halves. This creates a hybrid tree that OptChat explicitly rejected. How this affects zoom descent (the agent may need to zoom through a 16-memory block that was compressed raw, not from children) is not fully explored. — source: `/tmp/OptMem/memo:65,463-477` — confidence: medium
- OptChat's `settle()` function (§6) blocks the turn loop until all view parts are built. The interaction between settle and zoom (can the agent zoom while settle is waiting? does zoom trigger settle?) is not explicitly specified. — source: OptChat gist §6, §7 — confidence: medium
- Neither system specifies what happens when zoom is called on a block that has been forgotten (OptMem) or invalidated. OptMem's `forget` drops the summary and everything built on it; a subsequent zoom on a forgotten block would print "not compressed yet". — source: `/tmp/OptMem/memo:718-728` — confidence: medium
- The omp PLAN does not include a zoom-like command. The two-region design (raw tail + cold tree) is proposed in the brief but the zoom tool semantics for omp-chatroom are not yet designed. This finding should inform that design. — source: `brief.md:186-224` — confidence: high
