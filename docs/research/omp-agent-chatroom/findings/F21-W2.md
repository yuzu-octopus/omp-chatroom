# F21-W2: Cursor mapping onto tree nodes

## Angle
How does a per-agent cursor map onto a tree node? What happens when a member's cursor is inside a compressed node? Does the agent zoom, or is it forced forward? How does read since=<seq> compose with zoom? What does a late joiner's first read return? Kafka consumer group offset → tree node mapping.

## Claims

### Q1: In a two-region design, the cursor is a log seq, not a tree node ID

- [W2.1] The PLAN §3.5 defines the cursor as a **log sequence number** (`seq`), not a tree node ID. "One monotonic cursor per agent" where `seq` is "a monotonic counter minted by the store; the file is the durable log and `seq` is the cursor unit." — source: `docs/research/omp-agent-chatroom/PLAN-build.md:311-321` — fetch date: 2026-10-06 — confidence: high
- [W2.2] The tree is a **rebuildable cache** over the log, not the primary store. "The tree must never be required for correctness: the raw log stays authoritative and the tree must be rebuildable from it (OptMem's own property)." — source: `docs/research/omp-agent-chatroom/brief.md:214-215` — fetch date: 2026-10-06 — confidence: high
- [W2.3] Therefore the cursor maps to a **position in the raw log**. A tree node `[lo,hi)` covers a range of log seqs. A cursor at seq `S` falls inside whichever tree node's range contains `S`. The mapping is: `cursor (seq) → tree node [lo,hi) where lo ≤ S < hi`. — source: [INFERENCE] from PLAN §3.2 (`seq` is the cursor unit) + OptMem tree structure (`block [lo,hi)` covers memories `[lo,hi)`) — confidence: high
- [W2.4] The cursor is **not** a tree node ID because: (a) the tree is derived and rebuildable, so node IDs are ephemeral; (b) the log is the durable authority; (c) a cursor must survive tree rebuilds. — source: [INFERENCE] — confidence: high

### Q2: When a cursor points inside a compressed node — zoom, not force-forward

- [W2.5] OptMem's `wake` **refuses with exit 1** when a block needed for the view is not yet compressed. It prints "Cannot wake: the memory context needs #lo-hi, which is not compressed yet" and the nap prompt, then `sys.exit(1)`. It does NOT auto-zoom or force the cursor forward. — source: `/tmp/OptMem/memo:609-622` — fetch date: 2026-10-06 — confidence: high
- [W2.6] The comment at lines 612-615: "The ONLY reason to refuse: this document cannot be written without that summary. Work that the document does not need is handed over after the read instead, costing no round trip." — source: `/tmp/OptMem/memo:612-615` — fetch date: 2026-10-06 — confidence: high
- [W2.7] OptMem's `zoom(lo-hi)` is the mechanism to descend into a compressed node. It opens a block into its two halves: if a half is a single memory (`b - a == 1`), it prints the raw memory; otherwise it prints the summary (or "not compressed yet"). — source: `/tmp/OptMem/memo:762-782` — fetch date: 2026-10-06 — confidence: high
- [W2.8] OptChat's `settle()` **blocks the turn loop** until all view parts are built. "An agent turn (and a subagent spawn) waits until every line of the view is a summary before starting." It does NOT force the cursor forward — it waits for the compactor. — source: `/tmp/optchat.md:494-506` — fetch date: 2026-10-06 — confidence: high
- [W2.9] Neither OptMem nor OptChat **auto-zooms** when a cursor lands inside a compressed node. OptMem delegates the decision to the agent (via the nap prompt); OptChat waits for the compactor. The agent must explicitly call `zoom` to descend. — source: `/tmp/OptMem/memo:762-782`, `/tmp/optchat.md:494-506` — fetch date: 2026-10-06 — confidence: high
- [W2.10] **Design implication for the chatroom**: when a member's cursor points to a message inside a compressed node, the system should return the compressed summary for that node and let the agent explicitly `zoom` to descend. Forcing the cursor forward would violate the cursor's meaning (it tracks what the agent has seen, not what the tree has compressed). — source: [INFERENCE] — confidence: medium

### Q3: How `read since=<seq>` composes with `zoom`

- [W2.11] In OptMem, `wake` and `zoom` are **separate commands**. `wake` produces the tiling via `cover(T, budget)`; `zoom` opens a specific block. They compose: wake gives you the overview, zoom descends into a specific node. — source: `/tmp/OptMem/memo:584-651,762-782` — fetch date: 2026-10-06 — confidence: high
- [W2.12] In the PLAN, `read since=<seq>` returns records after the cursor, bounded by `limit`. The `zoom` operation would be a separate tool call to descend into a compressed node. — source: `docs/research/omp-agent-chatroom/PLAN-build.md:380-382` — fetch date: 2026-10-06 — confidence: high
- [W2.13] A read that spans both raw and compressed regions: `read since=<seq>` where `seq` is in the raw region but `seq + limit` extends into the compressed region. The system should return raw records for the raw portion and compressed summaries for the compressed portion, with a boundary marker. — source: [INFERENCE] — confidence: medium
- [W2.14] OptMem's `cover(T, budget)` already handles this: it tiles `[0,T)` with blocks of varying size, where size-1 blocks are raw and larger blocks are summaries. A `read since=<seq>` is equivalent to `cover(T, budget)` restricted to `[seq, T)`. — source: `/tmp/OptMem/memo:82-131` — fetch date: 2026-10-06 — confidence: high
- [W2.15] The `zoom` operation is **orthogonal** to `read since`. `read since` controls the range; `zoom` controls the resolution within a compressed node. An agent can `read since=<cursor>` to get the overview, then `zoom` into a specific compressed node to get more detail. — source: [INFERENCE] — confidence: high

### Q4: Late joiner's first read

- [W2.16] PLAN §3.5: "A joining agent starts at `logEnd - 50` (one screen); a rejoining agent resumes its stored cursor." — source: `docs/research/omp-agent-chatroom/PLAN-build.md:316-317` — fetch date: 2026-10-06 — confidence: high
- [W2.17] The late joiner's first read returns the **last 50 records** of the log. If the log has been compressed, these 50 records may span both raw and compressed regions. The join digest (§5.4) provides identity, roster, topic/purpose, and bounded history. — source: `docs/research/omp-agent-chatroom/PLAN-build.md:316-317,387` — fetch date: 2026-10-06 — confidence: high
- [W2.18] OptChat's initial view at load: "the view is not saved: it is folded again from message 0, running the same `append + fit` for every message in order (2,300 messages: 20 ms)." — source: `/tmp/optchat.md:452-455` — fetch date: 2026-10-06 — confidence: high
- [W2.19] OptMem on an empty log: "No memories yet. Record the first with: `memo note`." — source: `/tmp/OptMem/memo:598-602` — fetch date: 2026-10-06 — confidence: high
- [W2.20] **Design implication**: a late joiner's first read should return a bounded digest (the join cursor at `logEnd-50`), not the full compressed view. The join digest is a separate code path from `read since`. — source: [INFERENCE] — confidence: medium

### Q5: Kafka consumer group offset → log segment + offset mapping

- [W2.21] A consumer group's committed offset is stored as a keyed record in `__consumer_offsets`. The key is `(group.id, source topic name, source partition number)`. The value is the committed offset (next position to read). — source: `https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java` — fetch date: 2026-10-06 — confidence: high
- [W2.22] The group-to-partition mapping: `partition = abs(groupId.hashCode) % __consumer_offsets_partition_count`. The default partition count is 50 in some versions. — source: `https://github.com/apache/kafka/blob/trunk/group-coordinator/src/main/java/org/apache/kafka/coordinator/group/GroupCoordinatorService.java` — fetch date: 2026-10-06 — confidence: high
- [W2.23] When a consumer fetches at offset N, the broker finds the relevant log segment and uses the segment's **offset index** to get a nearby file position, then scans forward to find the first record with offset ≥ N. — source: `https://github.com/a0x8o/kafka/blob/master/core/src/main/scala/kafka/log/LogSegment.scala` — fetch date: 2026-10-06 — confidence: high
- [W2.24] If the offset is in a **deleted segment** (retention advanced past it), the consumer gets an out-of-range condition. The `auto.offset.reset` policy determines behavior: `earliest` (start at earliest retained), `latest` (start at end), `none` (raise `OffsetOutOfRangeException`). — source: `https://kafka.apache.org/26/configuration/consumer-configs/` — fetch date: 2026-10-06 — confidence: high
- [W2.25] **Mapping to the chatroom**: Kafka's committed offset is analogous to the PLAN's per-agent cursor (a log seq). Kafka's `auto.offset.reset` is analogous to the PLAN's retention policy: "5000 records or 7 days, never below `min(cursor)`" with a gap record on overflow. — source: `docs/research/omp-agent-chatroom/PLAN-build.md:496` — fetch date: 2026-10-06 — confidence: high
- [W2.26] Kafka's offset → segment mapping is **two-level**: first the logical offset (seq), then the physical segment + byte position. The chatroom's cursor → tree node mapping is similarly two-level: first the log seq, then the tree node `[lo,hi)` containing that seq. — source: [INFERENCE] — confidence: medium

### Q6: OptMem's wake/cover algorithm and cursor

- [W2.27] OptMem has **no cursor concept**. `wake` always reads from the beginning of the log, tiling `[0, T)` via `cover(T, budget)`. There is no per-agent cursor, no "read since" parameter. — source: `/tmp/OptMem/memo:584-651` — fetch date: 2026-10-06 — confidence: high
- [W2.28] The `T` parameter in `wake [part [T]]` is a **snapshot parameter** (which point in time to render as of), not a cursor. It defaults to `log_len(d)` (the current end). — source: `/tmp/OptMem/memo:584-596` — fetch date: 2026-10-06 — confidence: high
- [W2.29] OptMem's `cover(T, budget)` produces a **complete tiling** of `[0,T)`, not a delta. Every call re-tiles from scratch. This is the property OptChat rejected for caching reasons (§5.3: "Recomputing the view from scratch to fit a budget each turn (cache dies)."). — source: `/tmp/OptMem/memo:82-131`, `/tmp/optchat.md:459-464` — fetch date: 2026-10-06 — confidence: high
- [W2.30] **Design implication**: the chatroom's `read since=<seq>` is a delta read (records after the cursor), which is different from OptMem's `wake` (a full tiling). The chatroom needs both: a full tiling for the join digest, and a delta read for subsequent reads. — source: [INFERENCE] — confidence: medium

### Q7: OptChat's view and late joiner

- [W2.31] OptChat is **single-agent, single-chat**. There is no "late joiner" concept. The view is built from message 0 at load and kept live as messages arrive. — source: `/tmp/optchat.md:452-455` — fetch date: 2026-10-06 — confidence: high
- [W2.32] A **subagent** in OptChat gets the view at spawn time: "A subagent's first message is the view at spawn time (after `settle`), then its task." — source: `/tmp/optchat.md:698-700` — fetch date: 2026-10-06 — confidence: high
- [W2.33] The subagent's view is **context only**, not a cursor: "Your first message holds the view below, then your task. The view shows you what OptChat knows: what the user wants, decided and taught. Use it as context only." — source: `/tmp/optchat.md:711-714` — fetch date: 2026-10-06 — confidence: high
- [W2.34] **Design implication**: the chatroom's late joiner is analogous to OptChat's subagent at spawn time — both get a bounded view of the current state. But the chatroom's joiner gets a **cursor** (at `logEnd-50`) that tracks position for subsequent reads, while OptChat's subagent gets only context. — source: [INFERENCE] — confidence: medium

## Conflicting evidence
- **OptMem's `RAW_MAX=16` vs OptChat's purely binary tree**: OptMem compresses blocks of ≤16 memories directly from raw log entries; OptChat rejected this ("That had no real justification and made the structure confusing; OptChat dropped it. Every parent comes from exactly its two children."). This is a design disagreement about whether small blocks should be compressed from raw or from summaries. For the chatroom, the two-region design (raw tail + compressed cold tail) is closer to OptMem's approach than OptChat's purely binary tree. — source: `/tmp/OptMem/memo:65,463-477` vs `/tmp/optchat.md:145-148,777` — confidence: high
- **OptMem's `wake` recomputes vs OptChat's incremental fold**: OptMem re-tiles from scratch on every `wake` call; OptChat folds incrementally and never splits. OptChat explicitly rejected OptMem's approach for caching reasons. For the chatroom, the incremental approach is necessary for performance, but the re-tile approach is simpler for correctness. — source: `/tmp/OptMem/memo:82-131` vs `/tmp/optchat.md:459-464` — confidence: high

## Gaps
- The PLAN does not specify what happens when a cursor points to a message that has been **evicted by retention** (the gap record). The gap record is appended on overflow, but the interaction between cursor advancement and gap records is not detailed. — source: `docs/research/omp-agent-chatroom/PLAN-build.md:496` — confidence: high
- The PLAN does not specify the **zoom operation** in the tool surface. `read since=<seq>` is defined, but there is no `zoom` op in the `room` tool's op enum (`join/read/post/claim/release/board/topics/mute`). — source: `docs/research/omp-agent-chatroom/PLAN-build.md:371-382` — confidence: high
- The PLAN does not specify how the **tree is built** in the chatroom context. OptMem uses a lazy nap model (the agent compresses); OptChat uses a background compactor. The chatroom's multi-writer setting may require a different approach. — source: [INFERENCE] — confidence: medium
- The PLAN does not specify the **initial view** for a late joiner in tree terms. `logEnd-50` is a log seq, but the tree tiling of the last 50 records depends on the tree's current state. — source: [INFERENCE] — confidence: medium
- Kafka's `auto.offset.reset` is a **consumer-side** policy. The chatroom's retention policy is **server-side** (the store evicts old records). The analogy is imperfect: Kafka's broker retains data and the consumer decides what to skip; the chatroom's store evicts data and the agent must handle the gap. — source: [INFERENCE] — confidence: medium
