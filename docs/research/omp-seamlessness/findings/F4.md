# Angle 4 — Agent-facing tool design: what makes a tool great for an LLM to call

## Angle
Compare the plugin's `room` tool (12 ops, one tool) vs native omp tools (read, todo, wait, ask, eval, bash). What makes a tool great for LLMs: schema clarity, error messages, idempotency, discoverability. What does plugin do well/poorly; what would make agent reach for it unprompted?

## Claims

- Claim: The plugin's `room` tool ships a single tool with 12 ops via an `op` enum discriminator, mirroring native `todo` (single tool, `op` enum of 9 ops). [primary — read plugin/src/tools/room.ts:624-642, host todo.ts schema `TodoOp`]
- Claim: Native `todo` description is loaded from a separate `.md` prompt file (`../prompts/tools/todo.md`) and passed as `description`, keeping schema lean. Plugin inlines a 17-line `ROOM_DESCRIPTION` string constant inside source. [primary — read todo.ts import line, room.ts:49-65]
- Claim: Plugin uses Zod schema (`z.object`) vs native tools use `type()` from `@oh-my-pi/omptype` (TypeBox-style). Both compile to JSON schema; not a quality difference per se. [primary — read both]
- Claim: Every `room` param has a `.describe()` string; native `todo` uses `.describe()` on optional fields only. Plugin is more verbose but also more ambiguous: `op` description just echoes enum list, no "when to use which op" guidance. [primary — read room.ts:640-642 vs todo.ts]
- Claim: Error messages in plugin are structured and actionable: `fail("zoom requires lo and hi")`, `fail("pattern too long (max 200 chars)")`, `fail("invalid regex pattern")`, `fail("recall timed out")`, catastrophic-backtracking refusal with reason. [primary — read room.ts:1210-1247]
- Claim: Failures return `{content, details:{ok:false,error}}` and never throw — matches host contract (host coerces throwing tools to `isError:true`). Comment cites §4.5. [primary — read room.ts:174-183, 1249-1254]
- Claim: `content` is ALWAYS present (K1 comment) — host coerces a result without content array to `isError:true`. Plugin defends against this. [primary — read room.ts:149-151]
- Claim: Idempotency: `join` is idempotent (second join no-op, no second member record); `claim` renews lease if already held. `idemKey` on post dedupes retries. [primary — read room.ts:773-777, ROOM_DESCRIPTION, params]
- Claim: `strict: true` set on registration — host enforces additionalProperties false. Good for LLMs (no hallucinated params). [primary — read room.ts:755]
- Claim: `loadMode: "essential"` — tool loaded in essential set; discoverable. [primary — read room.ts:753]
- Claim: `approval: "read"` — no approval friction; LLM can call freely. [primary — read room.ts:754]
- Claim: Render hooks provided: `renderCall`, `renderResult`, `describeCall`, `describeResult` — native-grade TUI cards. [primary — read room.ts:756-759]
- Claim: Native `todo` description teaches *workflow* (when to call, parallel emission, never generated IDs) — action-oriented, behavioral. Plugin description teaches *mechanics* (ops list, "use it whenever several agents could touch the same work"). [primary — compare todo.md vs ROOM_DESCRIPTION]
- Claim: Plugin's tool is monolithic (12 ops) vs native pattern of *one op per tool* for some (wait_for_claim, wait_for_message, wait_for_agent are separate tools). Monolith reduces tool count but increases per-call param surface; LLM must pick op + right params. [primary — read host tools dir listing + plugin wait-for-*.ts]
- Claim: `room` tool has NO top-level examples in description of correct call sequences (e.g., "first call join, then read"). Native todo.md gives sequencing rules. [primary]
- Claim: Error messages include holder + expiresAt on claim conflict (`holder`, `expiresAt` in fail type) — actionable for retry/backoff. [primary — read room.ts:147]
- Claim: `recall` has safety guards: 200-char max, nested-quantifier refusal, 1s deadline. Good defensive design for LLM-generated regex. [primary — read room.ts:1210-1232]
- Claim: `read` limit clamped 1..200 default 50 (K20) — prevents token blowup. Good. [primary — read room.ts:153-154, 726]
- Claim: No "what would change" / failure-mode guidance in description; no counter-angle ("when NOT to use room"). Native todo.md has "NEVER takes a turn of its own". [primary]
- Claim: Plugin exposes `viewerFor`/`viewerStateFor` distinction documented in comments but not in schema — LLM can't know read paths don't mint membership. Minor. [primary — read room.ts:193-212]
- Claim: Tool result `details` discriminated by `op` — good for programmatic parsing; text is human/LLM-facing. Dual-channel design matches host. [primary]
- Claim: `strict: true` + many optional params means LLM can omit most; but `op` required. Fine. [primary]

## Conflicting evidence
- Monolith vs many-small-tools: native host uses BOTH (todo is monolith with op enum; wait_* are separate). So monolith is not inherently wrong; the difference is description quality and op-discovery. [inference from code]

## Gaps
- Did not read host's `ask.ts`, `eval.ts`, `bash.ts` descriptions in full; only todo.md sampled. May miss additional native patterns (e.g., tool result streaming, speculation). [gap]
- Did not measure actual LLM call success rates; no empirical data. [gap]

## Ranked improvements (for REPORT)
1. Rewrite ROOM_DESCRIPTION as behavioral workflow guide (like todo.md): when to call, sequencing (join first), parallel emission, anti-patterns. Move to a `.md` prompt file.
2. Per-op descriptions should state preconditions ("claim requires topic+key"; "post requires topic+body") not just field meanings.
3. Add a "when NOT to use room" clause (private 1:1 → agent://; bulk data → artifact).
4. Keep monolith (matches native todo pattern) but consider splitting blocking waits into the existing separate wait-for-* tools (already done) — good.
5. Add example call snippets in description for join/read/post/claim (few-shot for LLM).
6. Surface `viewerFor` vs read-only semantics? Low value; skip.
7. Keep strict + approval=read + essential loadMode — already native-grade.
8. Keep dual-channel result (content + details) and never-throw contract — already native-grade.

## Do not change
- Never-throw contract, content-always-present, strict, approval=read, loadMode essential, render hooks, idempotent join/claim, idemKey, recall guards, clamped read limit.
