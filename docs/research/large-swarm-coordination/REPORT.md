# Large-swarm coordination: what actually makes it work, and what should `omp-agent-chatroom` do about it

**Answer:** Build the **mechanics** track first — and the first mechanics item is not a new primitive but a *fencing token enforced on the write path*, because the plugin's claim board is currently an **efficiency-only lock advertised as a correctness mechanism** (`room{op:"post"}` appends unconditionally, never checking that the poster still holds the claim) [1][2]. The claim itself is wrong: no framework surveyed ships an exclusive, expiring, reclaimable lease — the plugin is *ahead* there — but every framework that measurably wins does so with three things the plugin lacks: a **designated router**, a **schema-checked per-turn status object** (Magentic-One's two ledgers; removing them costs **−31%** in its own ablation) [3][4], and an **isolation substrate** (git worktrees; parallel agents sharing one workspace score **55.5 vs 57.2** for a *single* agent in the one controlled ablation) [5][6]. Ship **guidance** second, in a disciplined shape only (a curated, on-demand Skill — the plugin's `SKILL.md` already fits; its always-on `routing-rule.md` duplicate is the thing to demote) [7][8]. (The first mechanics item, R2 in the list below, is already landing in the concurrent build round as renew-on-re-claim.) Ship **no runtime retrieval-of-coordination-papers tool**: there is **zero** primary support for it in either direction, and the evidence that *is* there points the other way (retrieval amplifies distractor errors by up to 80%, "retrieval harm is non-negligible", and frontier agents score only **9.39%** on deep literature discovery) [9][10][11]. And before any of it can be claimed as an improvement, the plugin must **grow four log record kinds** — `contended`, `delivered`+tier, `wait`+outcome, `member{leave}` — because today a failed claim appends *nothing*, which makes contention, duplicate work, tier distribution, findings-read, wait productivity and the **coordination-active subset** all structurally unmeasurable [12][13].

**Confidence:** High on the *ranking* (mechanics > guidance >> retrieval), because four independent clusters converge on it from different directions and the strongest single measurement — Magentic-One's −31% ablation of the ledger [3] — is a primary source with a self-reported caveat. Medium on the *fencing-token* recommendation specifically: the Kleppmann/Chubby evidence is unambiguous [1][2], but no source measures a room-shaped substrate, and a fencing token requires a **resource-side** check that the plugin cannot perform on a file an agent edits outside the room — that part is synthesis, not a measured result. Low on every *quantitative transfer* to our swarm: nothing in the corpus measures a flat topic-keyed append-only log with TTL leases and tiered delivery, and the noise-floor protocol says a coordination effect below ~15–20 pp on a paired protocol is indistinguishable from noise [13].

## Why

### 1. The plugin's primitives are right; its *guarantees* are not

Read from source: `ClaimState` is `{resource, holder, ttlMs, acquiredAt, seq}` — no generation counter, no dependency field, no renewal path (`plugin/src/store/claims.ts:5-11`); the claim record carries `resource` + `ttlMs` only (`plugin/src/store/schema.ts:30-38`); `grant()` is first-writer-wins and **a loss appends nothing** (`claims.ts:38-44`); `case "post"` appends unconditionally, without checking claim ownership (`plugin/src/tools/room.ts:748-794`); and there is no `renew` op among the twelve (`room.ts:60-72`).

That combination lands on the wrong side of Kleppmann's own split. A lock is "for efficiency or for correctness": efficiency avoids duplicated work at "a minor increase in cost"; correctness prevents "a corrupted file, data loss, permanent inconsistency" — and "if you need locks only on a best-effort basis… the locks are only approximate and may occasionally fail" [1]. The plugin's own tool description advertises the claim for "before editing a shared file" [14] — i.e. as a correctness mechanism — while its implementation is best-effort. A stale holder whose lease expired at 300 s and was reclaimed by another agent keeps editing, and its write lands last. Kleppmann's own worked example is a GC pause landing "between the last check and the write operation" [1]; Chubby's shipped answer is the **sequencer** — a lock-generation number the *protected server* is expected to test and reject on [2]. A lease without a server-side check is, in that vocabulary, an approximate lock.

The classic literature says the same from the other side. Smith's 1980 contract net made the **expiration time on a task announcement** a bid deadline, so a manager never waits forever, and made contractor failure recoverable because the manager holds the contract record and can re-announce [15] — which our reclaim-is-logged rule already mirrors. But the 1980 protocol also made **dependency ordering a first-class field**: the subcontract record carries `predecessors` and `successors`, and "a subcontract will not be announced… until its predecessors have been completed" [15]. Our claims have no such field.

### 2. What the frameworks actually ship — and the one axis where we are ahead

Across AG2/AutoGen, LangGraph, CrewAI, the OpenAI Agents SDK and Swarm, smolagents, Letta, Claude Code, and the role-playing societies, **no framework ships a lease**: no exclusive, expiring, reclaimable ownership token over a named resource [16][17][18][19][20]. The nearest analogues are weak or different in kind — Claude Code agent teams use OS **file locking** with no TTL and no reclaim semantics, and Letta's `Task*` board is an in-memory, process-lifetime map whose `owner` is a free-form string and whose dependency edges nothing enforces [21][22]. The classic analogues are equally bounded in kind: contract nets' formal guarantee is "no *unexpected* deadlock" and only under restrictive assumptions (one auctioneer, at most five bidders, deadlines as *future work*) [138], and the auction literature separates efficiency from fairness and stability, so a pure first-claim-wins allocator inherits the documented fairness gap [137]. Our TTL lease, explicit reclaim, logged reclaim, and oldest-waiter promotion are genuinely ahead.

What every framework that *wins* ships instead is a **designated router**: Magentic-One's Orchestrator, AG2 network's authoritative hub, Anthropic's fixed lead, CrewAI's manager agent, LangGraph's supervisor/router, CAID's manager [23][24][3][4][5][16][127]. Every one of them also ships a *bounded* default: AutoGen's group chat is documented as "hard to control if the number of participating agents is large", and its own teams page says to "start with a single agent for simpler tasks, and transition to a multi-agent team when a single agent proves inadequate" [17][167]. GPTSwarm sharpens it into a negative result: optimising the communication *graph* alone produced **no improvement over the single-agent baseline**; the gain (**+2.1% ± 1.1%**, 5 seeds) appeared only after the seven agents were **role-differentiated** [25]. And the measured coding-agent result points the same way: CAID — a manager, a dependency graph, per-agent git worktrees, and "structured JSON instructions and git commits rather than free-form dialog" — beat a single agent by **+25.6% absolute on PaperBench** and **+14.7% on Commit0**, while parallel agents sharing a workspace scored **55.5 against the single agent's 57.2** [5][6].

So the honest comparison is not "our room is better" or "our room is worse". It is: **we have the one primitive nobody else has, and are missing the three mechanisms that every *measured* win is built on.** Three more data points sharpen the gap. OpenAI's vendor guide says to "**maximize a single agent's capabilities first**", splitting only on "complex logic" or "tool overload" [128] — the same default-as-single-agent posture LangGraph [87] and OpenHands [88] take. And the parallelism-that-works recipes all coordinate **outside** the agent conversation: OpenAI's Asana deployment ran "up to four coding agents… each in a separate copy of the codebase" with a human reviewing every proposed change [129]; OpenAI's Symphony makes the **DAG** the coordination substrate and puts the human ceiling at "three to five sessions at a time" [130]; OpenHands' software-factory recipe coordinates through GitHub labels, branches, PRs and exact-head review statuses, and its profiles instruct users to "disable model switching and **sub-agents**" [131]. Anthropic's own 16-agent compiler run is the purest version: git push-conflict as the arbiter, no orchestrator at all [132].

### 3. Where the swarms break — the counter-angle, from the people who hit it

The practitioner corpus is the part vendors do not publish, and it is uniformly bad for a flat shared room.

**Duplicate work on the same file is the most-reported failure.** 9 of 17 `anthropics/claude-code` issue bodies read describe duplicate or racing work on the same artifact — "the loser's work is silently overwritten" [26]. Bun's first-party post: 64 Claude agents on a Zig→Rust port, one ran `git stash`, another `git stash pop`, a third `git reset HEAD --hard` — "They were stepping on each other" [27]. Cursor's own staff reply on a parallel-subagent thread admits the mechanism: "parallel subagents sharing one working tree (no write-scope coordination), overlapping edits collided" [28]. The measured stakes: AI-agent PRs conflict at **27.67%** (142k+ agentic PRs) versus **0.2%** for humans under PRs, and **41.7%** for cross-agent co-active pairs versus **19.8%** for intra-agent [29][30][153].

**A shared-file lock protocol fails at scale, first-party.** Cursor: "Our initial approach gave agents equal status and let them self-coordinate through a shared file… we used a locking mechanism. This failed in interesting ways: 1. Agents would hold locks for too long, or forget to release them entirely. Even when locking worked correctly, it became a bottleneck. **Twenty agents would slow down to the effective throughput of two or three**" [31]. Cursor's fix was to abandon worker-to-worker coordination entirely: a planner lays out the plan, an executor owns it, a judge verifies, and "Workers… don't communicate with any other planners or workers. They work on their own copy of the repo" [32]. That is the strongest available signal that a *peer-to-peer room* is the wrong shape at 20+ agents, and it is the single most important thing in this report for the plugin's scaling ceiling.

**Deadlock across wait mechanisms is a documented, reproduced failure in this exact product family.** The oh-my-pi issue: "When two or more task agents `hub wait` on messages from each other, the group stalls for the entire wait timeout (default 120 s) with no indication anything is wrong. The status line shows every agent as 'running'; no error is raised; the only unlock is the timeout." Root cause given: "the graph is maintained on every `wait()` and consumed on every matching `send()`, but **never inspected for cycles**", and "a cycle can span more than one wait mechanism" [33]. The plugin has three independent wait mechanisms — `wait_for_claim`, `wait_for_agent`, `wait_for_message` — so a per-mechanism check would miss a cross-mechanism cycle. The distributed-systems answer is Holt's: for single-unit resources, "the conditions of deadlock, 'not complete reducibility,' and 'existence of a cycle in the graph' become equivalent" [34], with prevention by "refusing to grant requests when the resulting state 'may lead to deadlock'" [34]. Coffman's four conditions are the frame [35].

**Coordination chatter is itself a failure mode, and it is measured.** Cohere's first-party scaling report found that with a PIV prompt "84% of messages went from workers to the lead" while "messages between workers averaged fewer than one per task", and that the planners' reports grew from 17,000 to 75,000 characters as worker count went 2→16 "while reward barely moved" — their conclusion is that "messages mostly repeated what the lead would have received in reports anyway", and that "shared goals, shared progress logs, or messages that carry checkable evidence may give agents more reason to talk" [121]. This is the practitioner measurement behind the plugin's T1/T2 tier split, and behind the 0.39-messages-per-agent-turn target in §7.

**The primitives people ask for are the ones nobody ships.** The same shape recurs across the trackers: a lost result never delivered back to a parent (claude-code #90264, #90256), a completion notification enqueued but never delivered so the parent re-ran an expensive duplicate (#85534), a parent blocked forever on a hung child with no timeout firing (#44783), and a mutual-wait circular blocker needing manual intervention to break [149][150]. On the framework side: a long tool call re-dispatched from a checkpoint *while the original was still running* (LangGraph #7417), a race silently dropping concurrent checkpoint writes (#8115), and a parent deadlocked inside an exhausted concurrency pool (#9280) [151]. The same cluster includes a re-entrant send deadlocking a message handler (AutoGen #5915), a duplicated agent name silently misrouting messages (ag2 #2332), a termination signal **silently ignored** so the run continued to `max_rounds` (ag2 #2575), duplicate agent tool calls silently dropped because they were keyed by an untrusted possibly-empty id (smolagents #2683), a sub-agent's failure laundered into a confident answer because the manager could not tell completion from failure (smolagents #2747), and a crashed agent permanently bricked by orphaned tool messages (letta #3250) [152][163][164][165]. Idempotency keys were requested in **five** independent trackers and shipped in none: LangGraph #8464 proposes a `DurableClaimStore` that "pre-claims a stable request key in durable storage before tool execution… ensuring exactly-once semantics" [36]; crewAI #5802 "Tool re-execution on task retry has no idempotency guard" [37]; OpenAI's #4775 was closed by a maintainer with "**This closure does not mean the reported code path has been fixed**" [38]. Anthropic's own CHANGELOG shipped three duplicate-execution fixes in three consecutive releases, including "a scheduled routine run that failed partway being run again from the start… which could **repeat work such as posting the same report twice**" [39]. Per-participant deadlines: AutoGen #7828, "the entire group chat is deadlocked" if one agent hangs [40]; Microsoft's agent-framework #7454 shipped a 300 s default because the wait "waits with no bound" [41]. Deterministic loop breakers: crewAI #6414, closed NOT_PLANNED [42]. Harness-enforced budgets: ag2 #565, "a hard termination based on cumulative token spend isn't currently supported" [43]; OpenAI #3353, "This couldn't be done only by SDK side changes" [44].

**Anthropic's own release notes admit their fan-out cap is advisory:** the "Dynamic workflow size" setting is "**an advisory guideline, not an enforced cap**" [39]. That is the intra-corpus proof that guidance cannot substitute for mechanics — the same vendor that ships the best delegation playbook admits the cap does not bind.

### 4. Guidance: cheap, real, and mostly about process

The strongest published support for the guidance track is the **Collaboration Tax** paper: a four-stage cascade (L1 grounding, L2 querying, L3 integration, L4 re-derivation) where "one system-prompt clause per stage closes **38.3% ± 14.1%** of the tax at zero mechanical cost" [45]. But it is **dyadic (N=2)** and its own authors flag N≥3 as unstudied — our room is N=32.

The rest is more sober, and the structure of the artifact matters less than its discipline: across 1,650 Claude Code sessions and 16,050 function-level observations, **none** of four config-file structure variables (size, position, architecture, adjacent-conflict) produced a detectable contrast after multiple-testing correction [161]. Two studies found AGENTS.md-class context files **do not improve task success** while raising cost: "Evaluating AGENTS.md" reports LLM-generated files at **−3%** average success, developer-provided at **+4%**, and cost **+20%** (SWE-bench Lite) / **+23%** (AGENTBENCH), concluding files should describe "only minimal requirements" [46]; Khatri's 288-run controlled study found correctness **null** (TOST bounded ≤10–15 pp, omnibus p=1.000) but a real *process* gain — blind full-test-suite runs **3.67 → 2.44 → 1.67** across none/always_on/selective, ~24% wall-clock cut — because the file warned the suite was slow [47]. Lulla et al. found **−28.64%** median wall-clock and **−20.08%** mean output tokens with comparable completion behaviour (correctness not evaluated) [48]. The reconciliation is clean: **guidance moves process and cost; whether it moves outcome depends on the task's bottleneck** [49].

The guidance layer is now standardised rather than folkloric: AGENTS.md is a Linux-Foundation-stewarded convention [146], Agent Skills is a published cross-platform spec built on progressive disclosure [51][144], MCP carries a first-party natural-language `instructions` channel [147], and Anthropic's context-management work shows the mechanism paying for itself in the other direction — memory tool + context editing **+39%** on an internal agentic-search eval, context editing alone **+29%**, and **−84%** tokens in a 100-turn web-search eval [145]. The standard's own warning is that *always-on* context is the failure mode: Anthropic's first-party tool-writing post says "**More tools don't always lead to better outcomes**", and a bloated tool set creates "ambiguous decision points about which tool to use" [61]. The winning *shape* is a curated, on-demand Skill, not an always-on protocol dump: SkillsBench measures curated Skills at **+16.6 pp** (33.9% → 50.5%) across 18 model-harness configurations, with "focused Skills with at most three modules" beating larger bundles and — decisively — "**Self-generated Skills provide no benefit on average**" [50]. The counter-case is OpenHands' own skills evaluation, which requires a no-skill baseline ("If you only test the skill-enabled version, success tells you almost nothing") and reports that at least one model **regressed** on the skill-enabled version — "skills can be counterproductive" [166]. The standard's own authoring guidance says "**Overly comprehensive skills can hurt more than they help**… **Add what the agent lacks, omit what it knows**… **Provide defaults, not menus**" [51][169]. OpenAI ships the same idea as *code*: `prompt_with_handoff_instructions()` is a first-party helper whose recommended prefix tells a handoff agent "Transfers between agents are handled seamlessly in the background; do not mention or draw attention to these transfers in your conversation with the user" — a major vendor treating the coordination prompt as part of the mechanism, not an afterthought [162]. Anthropic's own context-engineering post prescribes the hybrid: "**CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time**… the guiding principle remains the same: **find the smallest possible set of high-signal tokens**" [52].

**The plugin already ships the recommended artifact, and duplicates it.** `plugin/skills/omp-agent-chatroom/SKILL.md` is 143 lines / 1,266 words with trigger-rich frontmatter — the L1-metadata / L2-body shape the standard describes [51]. But the same routing decision is *also* injected as a static system-prompt block every turn (`plugin/src/onboarding/routing-rule.md`, 45 lines, via `onboarding/hook.ts`) [53][54]. On the evidence, the always-on duplicate is the piece that costs and does not pay; the Skill is the piece that pays.

### 5. The retrieval question: **no**

The brief asks this explicitly, so it gets an explicit answer.

**There is no primary evidence that agents reading coordination literature at runtime improves swarm outcomes.** Not one source in the corpus — frameworks, practitioner reports, or papers — reports an agent consulting prior art mid-task [16][55]. The near-neighbours are negative: a shared catalogue that two agents consult was silently clobbered [55].

The mechanism evidence points the other way. Context itself is unreliable at scale: Chroma's evaluation of 18 models found "model performance grows increasingly unreliable as input length grows", that needle-question-style probes overestimate capability, and that "distractor impact amplifies as input length grows" [157] — corroborated by RULER ("almost all models exhibit large performance drops as the context length increases") and NoLiMa (11 of 13 models claiming ≥128K fall below half their short-context baseline at 32K) [158]. Retrieval amplifies distractor errors: across 11 datasets, contextual distractors cause "**performance drops of up to 80%**", "agentic workflows often amplify these errors by over-trusting noisy tool outputs", and there is an **inverse scaling** trend — more test-time compute, worse performance in noisy settings — while "prompting, context engineering, SFT, and outcome-reward only RL fail to ensure robustness" [56]. Interference in multi-turn search agents "primarily arises from the latest retrieved documents" [57]. "Retrieval harm is non-negligible" [58]. And a "search the literature" tool is a tool-retrieval problem where IR is bad: ToolRet's 7.6k tasks over **43k tools** show "even the models with strong performance in conventional IR benchmarks, exhibit **poor** performance… This low retrieval quality degrades the task pass rate of tool-use LLMs" [59]; a full library of candidates "becomes costly, slow, and less reliable" [60]. Anthropic's own first-party tool-writing post: "**More tools don't always lead to better outcomes**" — a tool-description rewrite alone cut future agents' task completion time by **40%** [61].

The counter-case is real but about a different task: retrieval over a **domain corpus** works — OpenScholar over 45M papers beats GPT-4o by 5% on correctness and "GPT4o hallucinates citations 78 to 90% of the time" [62]. That is content QA, not coordination. And agents are demonstrably bad at deep literature discovery: **9.39%** on AutoResearchBench Deep Research, **9.31% IoU** on Wide Research [63]; AI-Scientist's literature reviews "produced **poor novelty assessments**" and hallucinated numbers [64].

**The pattern that does work is accumulate-and-distill.** Agent Workflow Memory induces reusable workflows from past experience and provides them selectively: **+24.6%** (Mind2Web) and **+51.1%** (WebArena) [65]; ACE's evolving playbook (Generator→Reflector→Curator) gives **+10.6%** on agent benchmarks with no labelled supervision [66]. And the shipped template is a *distilled artifact*, not a search: GitHub's `gh-aw` ships `multi-agent-research.md`, "**Distilled from the OpenAI Cycle Double Cover (CDC) prompt**", which explicitly forbids retrieval for the solution — "Web search and external retrieval may be used only for background material and named standard results. **Do not search for a solution to this exact task.**" [67]. Its `patterns.md` is a *router* that matches a request to one named playbook, not a corpus to search blindly [68]; its `llms.txt` index says "the file itself stays small enough to fit in context. The detail lives behind the links, and is fetched only when needed" [69]; and the workflow docs make the two-layer split explicit — "**Markdown defines the task; frontmatter defines the workflow's capabilities and boundaries; safe outputs define which GitHub writes are allowed**" [148].

**So: distil, don't retrieve.** The strongest support for "a distilled protocol plus a runtime gate" is TraceFix: a synthesised protocol topology, verified with PlusCal and repaired against TLA+ counterexamples, compiled into per-agent system prompts and enforced by a **runtime monitor that rejects out-of-topology coordination operations** — deadlock/livelock **31.1% → 14.1%** in a paired ablation, and "under reduced model capability, verified protocols **degrade at roughly half the rate** of prompt-only and chat-only baselines" [159]. The mirror-image result is equally instructive: adding contracts and verification to a system that already coordinated *reduced* the means [159]. Visibility is the cheap part: two homogeneous agents in a shared Git tree, each observation prepended with a structured peer-activity block, cut cost per resolved task by **20%** and destructive concurrent edits by **47%** versus the silent two-agent baseline [159].

The vendor doctrine is explicit that complexity must earn its place: "the most successful implementations use simple, composable patterns rather than complex frameworks" and "**add complexity only when it demonstrably improves outcomes**" [143]. If the plugin wants a "consult prior art" capability, the correct form is a *curated playbook the plugin ships* — the plugin's `SKILL.md` is already that shape — plus (optionally) a read-only index over the plugin's **own durable record** (the room log + cold tree), which is the one retrieval target with a real corpus and a real payoff: "a finding posted by one agent is usable by a later one" is the plugin's own stated goal, and today `recall` is a regex over the raw log with the `SKILL.md` admitting "**There is no semantic search**" [70]. That is a different build (indexing the room's own log), not a literature-retrieval tool.

### 6. Measurement: the plugin cannot currently observe its own coordination

This is where the three tracks converge, and it is the most actionable finding in the report.

A 16-metric computability catalogue against the room's JSONL found what is computable now and what is not [12]. Computable: orphan/expired-claim rate (`#release{reason:"expired"} / #claim`); claims-per-post; rework rate (same-agent re-claim, the exact DORA "unplanned remediation" construction); resource idle-gap and handover-gap; duplicate-overlapping-claim rate — **with a load-bearing caveat**: a failed claim appends *nothing*, so contention attempts are invisible and the duplicate-work signal only appears after the damage [12][71].

**Not computable, and these are the important ones:** wait outcomes (the waiter queue is in-memory, `wait_for_claim` returns a tool result and never a record); delivery events and tier assignment (tier is computed *per viewer* at delivery time and never stored, so T0/T1/T2 distribution is unmeasurable); findings-read (no read receipts); true last-agent-standing (no `member{action:"leave"}` record is ever appended — the schema permits it, no call site emits it, which is why the digest had to be changed to "1 joined · 32 live" instead of a growing lifetime counter) [72][73].

This matters more than a normal observability gap, because the noise-floor protocol establishes the bar any claimed improvement must clear: configuration-equivalent, coordination-inert protocols differ by **[−3, +18] pp** across two n=100 seeds, the largest single-seed contrast (**+18 pp**) **did not reproduce** at the second seed, and **7 of 10** recent multi-agent coordination papers report headline gains *below* that envelope [13]. The same paper's remedy is exactly what the plugin is missing: restrict measurement to trials where the mechanism was **logically active** — for the room, an interval in which a claim was *contended*, a `wait_for_claim` was *enqueued*, or a record was actually *delivered* [13]. Today the room cannot produce a coordination-active subset at all.

The right instrument shapes exist: OpenTelemetry's GenAI conventions define `gen_ai.invoke_agent.duration`, `.inference_calls`, `.tool_calls` and the `create_agent` / `invoke_agent` / `invoke_workflow` / `plan` / `execute_tool` spans (now in a dedicated repo) [74]; A2A's proposed `a2a.server.task.message_count` is the direct analogue of a per-room message counter [75]; Arize Phoenix and Langfuse give trace→span trees with Agent/Tool/LLM span kinds [76][77]. The evaluation doctrine to copy is Anthropic's own transcript/outcome separation — task, grader, transcript, outcome, harness — with the tracked metrics named explicitly (`n_turns`, `n_toolcalls`, `n_total_tokens`, `time_to_first_token`, `output_tokens_per_sec`) and the warning that checking specific step sequences is "too rigid and results in overly brittle tests" [141]. First-party swarm tracing already exists to model against: the OpenAI Agents SDK traces handoffs automatically and ships a `handoff_span(from_agent=…, to_agent=…)` span type [142]. And the metric that best fits a room already exists in a benchmark: **MultiAgentBench's milestone-contribution KPI**, `KPI_j = n_j / M`, `KPI_overall = (1/(N·M))·Σ_j n_j` [78]. Its ablations are directly actionable: overall KPI **decreases** as agent count rises 1→3→5→7; iteration count rises 1→7 then drops sharply at 10; and token usage tracks task score across topologies (graph best, tree worst) [78]. The adjacent construct-level benchmarks are equally usable: CoCoBench scores exactly the four coordinates a room must get right — task allocation, sequential ordering, **mutual exclusion**, and handoff coordination — and reports that "coordination ability is highly construct-specific" [154]; τ-bench's `pass^k` is the metric that catches coordination flakiness under repetition, with gpt-4o's `pass^1` at 61.2% on τ-retail falling below 25% at `pass^8` [154]; and TeamBench's finding — LLM verifiers **false-accept 49.4%** of failing submissions, and the verification role adding overhead rather than quality — is the argument for a cheap deterministic check over a model-judged one [154].

Two more measurement facts worth carrying: **METR's primary is human-equivalent duration, and "agent time" is not a settled concept** — METR explicitly refuses to publish agent wall-clock ("time horizon… is a measure of the difficulty of a task, rather than the time an AI spends to complete the task"), so any wall-clock metric here must be labelled as our construction [79]. And **a coordination metric does not predict task success** — MultiAgentBench's own coordination score is 75.00 on an instance where task score is 0.21 [78]; a room that reports only coordination health will not predict outcomes. Pair coordination metrics with an outcome metric, or report nothing.

### 7. The cost side, stated honestly

Multi-agent costs 3–10× single-agent tokens for equivalent tasks, per Anthropic's 2026 first-party post, and the overhead stems from "duplicating context across agents, coordination messages between agents, and summarizing results for handoffs" [80]. The 2025 post's 15× is **vs chat**, not vs single-agent — never cite it without its baseline [81]. Head-to-head, one primary measures MAS consuming **4×–220×** the input (prefill) tokens of its single-agent counterpart across 9 datasets and 4 frameworks, and **2×–12×** more decode tokens even assuming perfect context reuse [82]; the same paper finds the MAS advantage *shrinks* as models improve (MetaGPT-HumanEval 10.7% → 3.0% on a stronger backbone) [82]. Communication overhead is separately measured: MetaGPT **72%**, CAMEL **86%**, AgentVerse **53%** duplicate tokens, with **72%** of MetaGPT's tokens spent in verification [83].

The load-bearing number for this plugin is the *direction*: the message density of a successful swarm **saturates at ≈0.39 coordination messages per agent-turn** [84] — and the only controlled first-party multi-agent-vs-single-agent measurement on a public benchmark says the same in latency terms: Anthropic's Opus 4.8 system card reports a five-agent team at 85.4% against a single agent's 84.3%, "using just **20% of the latency**", but "On the easiest problems with 100% pass rate, the five-agent team delivered **no speedup**, likely because coordination overhead roughly offset the gains from parallelism" [156], and total reasoning turns grow **super-linearly** in agent count — `T = 2.72 × (n+0.5)^1.724`, R² = 0.974 [84]. So per-agent room traffic must be **O(1) in n**, or the room becomes the cost. Our current caps (10 T1 records / 2,048 tokens per turn, 1 post/2 s with burst 10) are in the right shape; the plugin's own README already concedes "The room is not a token-cost win… Its value is correctness — preventing duplicated work on a shared resource — not efficiency" [85]. The research agrees with that framing, and sharpens it: the room must be **selectively** used. Anthropic's own gate is the one to copy: multi-agent pays where there is heavy parallelisation and information exceeding one context; it does not pay where "all agents [must] share the same context or involve many dependencies between agents" — "most coding tasks involve fewer truly parallelizable tasks than research" [81]. The controlled scaling study puts a number on the gate: once the single-agent baseline passes ~45% accuracy, additional agents have **negative** returns (β = −0.236, p = 0.004), and the resulting rule picks the optimal architecture for **87%** of held-out configurations [84]. Two more rules follow from the same corpus, and both bear directly on how a room should be used: **size a team by composition, not count** — "2 diverse agents can match or exceed 16 homogeneous agents", because homogeneous agents saturate early as their outputs become strongly correlated [154]; and **prefer divergent over convergent fan-out**, since "reversing the directions of specific topologies can lead to significant performance degradation" and convergent aggregation at one node is hard [155]. No primary source establishes a universal optimum agent count — the four answers in the literature (the ~45% capability threshold, 2-diverse-≈-16-homogeneous, Anthropic's 1/2-4/3-5-by-complexity, and logistic growth past 1000 agents) are all conditional [84][154][155][86].

### 8. What the literature says about the *shape* — and the honest conflict

Every framework that wins uses a **designated router**; our plugin is deliberately flat. This is the most consequential conflict in the corpus, and it does not resolve in our favour.

- **Router evidence:** Magentic-One's orchestrator + ledgers (−31% without the ledgers) [3]; CAID's manager (+25.6%) [5]; Anthropic's fixed lead (+90.2% on their internal research eval) [86]; AG2's authoritative hub [23]; LangGraph's supervisor [87]; CrewAI's manager agent [18]; GPTSwarm's gains only after role differentiation [25].
- **Flat evidence:** LangGraph's "not every complex task requires this approach" [87]; OpenHands' "Don't Sleep on Single-agent Systems" — structure-right, context-preservation and maintainability costs [88]; Letta's fan-out with "no shared scratchpad" [89]; OpenCollab's single-agent configuration using the fewest tokens across all suites [90]; and the "When Agents Coordinate" study's finding that "**naming one agent 'coordinator' creates no communication hub and gives no reliable improvement in success**" [91].

**Resolution: different conditions, and the boundary is the real answer.** The router wins on every *measured* result; the flat model wins on *cost* and on tasks where peer-ness is the point. The reconciling condition is what "coordinator" means: a *named role* without a *protocol* is cosmetic, whereas a named role *with* a task list, dependency-gated claims and a verification step is the thing that works. That is exactly the gap between "a named coordinator" and "the ledger".

And a *flat* room is not the same as "no router" — but a flat room is a room in which **the protocol is the shared record**. That is the argument for the ledger-shaped recommendation below: it is the cheapest way to give a flat room the thing every router-based system has, without importing a router.

## The ranked change list for THIS plugin

Ranked by (evidence strength × failure prevented) ÷ cost. "Cost" is engineering cost in this repo, not token cost.

> **Status as of 2026-10-20 (post-dating the research):** this report is now the input to `plans/020-effectiveness-round.md`, and part of the round has already landed in the working tree — **R2 (lease renewal)** is in flight as a *renew-on-re-claim* rule (`renew()` in `plugin/src/store/claims.ts`, wired through the `room` tool path and `/room claim`) rather than as a separate `renew` op. That is a sound choice: it removes an op and keeps the TTL guess honest, and it matches the report's requirement that a holder can extend a live lease. The remaining items (R1, R3–R10) are not yet in the tree. The rankings below are unchanged by that partial landing; the *evidence* for R2 is in §1 and §4 below.

### R1 — Make the claim honest, then make it enforceable: a **generation token on the claim, and a write-path check**
*Build:* add a monotonic `gen` counter to `ClaimState` and to the `claim` record; increment on every grant; expose it in `details` on `claim`/`release` and on the board row. Then enforce it where the write happens: a `room{op:"post"}` on a topic the poster claims must carry the poster's current generation, and a claim whose generation is stale is refused.
*Evidence:* the causal-ordering primitive that makes "were these two writes concurrent?" answerable is the vector clock — "a linearly ordered structure of time is not always adequate for distributed systems… we propose a generalized nonstandard model of time which consists of vectors of clocks", whose decision rule is that two events are causally related iff one vector dominates the other, and otherwise are "causally independent" [133]; a vector clock says *whether* two writes were concurrent, not whether they are semantically compatible, which is the merge decision's job [93][94]. Kleppmann: "you need to include a *fencing token* with every write request… the storage server remembers that it has already processed a write with a higher token number (34), and so it rejects the request with token 33" — and crucially "this requires the storage server to take an active role in checking tokens" [1]. Chubby's sequencer is the shipped precedent: lock name + mode + "lock generation number", which "the recipient server is expected to test… if not, it should reject the request" [2]. Birman & Joseph's **site incarnation number** is the direct ancestor: "incremented each time a site recovers… Messages from a failed incarnation are discarded by the input filter" [92]. The measured stakes: **27.67%** conflict rate on AI-agent PRs vs **0.2%** for humans under PRs, and **41.7%** cross-agent vs **19.8%** intra-agent [29][30]; CAID's soft-isolation ablation: single agent **57.2** / worktree isolation **63.3** / shared-workspace separation-by-instruction **55.5** [5][6].
*Failure prevented:* a stale holder's late write clobbering the new holder's work — the single most-reported failure in the practitioner corpus [26][27][28].
*Cost:* medium. The counter-token is easy; the write-path check is the hard part, because agents edit files *outside* the room. The optimistic-concurrency alternative is documented and is a real option: OCC's read → **validation** → write phases are the classical "hoping" scheme, and its authors' own warning is that pessimistic locking is the expensive option, because "**if the locking protocol is not deadlock-free, deadlock detection must be considered to be part of lock maintenance overhead**" [134]. Honest scoping: the room can fence **room operations** (post/claim/release on a claimed resource) and can **publish** the generation for an external tool to check, but it cannot fence a raw `edit` on a file. Treat this as the *enforcement point*, not a complete solution: the generation is what a future file-write wrapper would check.
*Honest caveat:* the "fence the file write" part is a synthesis across Kleppmann + Parker + Git [1][93][94], and no source measures it on a room-shaped substrate. Ship the generation + the room-level check, and treat the file-level check as a separate, unproven step.

### R2 — A **claim renewal** op, and self-fencing on loss
*Build:* add `room{op:"renew", topic, key}` that extends a lease the caller still holds; return the new expiry. An agent that misses a renewal must stop treating the resource as its own.
*Evidence:* Chubby's lease is renewable and renewal is what keeps a slow-but-alive client alive: "The master advances the lease timeout… when it responds to a **KeepAlive** RPC from the client" (12 s default), and a client whose local lease expires enters **jeopardy** — it "empties and disables its cache" and waits 45 s, i.e. it **stops writing** rather than writing optimistically [2]. The failure-detection literature is the reason a timeout is not enough: "it is impossible in an asynchronous distributed system to reliably distinguish a process that has crashed from one that is merely very slow" [95]; "failure detection by time-out cannot be more reliable than the underlying communication system" [92]; and the engineering form — "one would never be satisfied with making repeated phone calls… for half an hour and then declaring the disappearance a fact, no matter whether the phone was picked up, a busy tone was heard or the phone was disconnected" [96]. The heartbeat-vs-timeout distinction is explicit in the original: a heartbeat *counter* detector "does *not* use timeouts… it just counts the *total number of* heartbeats received" [97].
*Failure prevented:* a live-but-slow agent losing its lease at 300 s to a reclaiming peer — currently the plugin's `isStale` is `now >= acquiredAt + ttlMs` **or** holder parked/aborted (`plugin/src/store/claims.ts:24-31`), with no renewal path (`room.ts:60-72`).
*Cost:* low. One op, one projection change, one log kind.

### R3 — **Dependency ordering between claims**, enforced by the claim primitive
*Build:* extend the claim record with `dependsOn: string[]` (resource strings). A claim whose dependencies are not satisfied is refused — or, better, is **held** and promoted when they clear, exactly as `wait_for_claim` already promotes the oldest waiter.
*Evidence:* Smith's 1980 contract net makes it a first-class field: the subcontract record carries `predecessors` and `successors`, and "**A subcontract will not be announced… until its predecessors have been completed**" [15]. Claude Code's shipped agent teams do the same: "a pending task with unresolved dependencies **cannot be claimed** until those dependencies are completed" [21]. GitHub's `gh-aw` work-queue protocol ships the mechanics: "Predecessors consume no Claims; **successors wait for predecessor Results**", with immutable DAGs, fair scheduling and bounded dispatch [98]. The LLM-MAS literature names the gap explicitly: the role-assignment/dependency question is open, and "no primary paper measures 'dependency ordering between claims' or a queryable 'who is blocked on what' graph" [99]. The classic literature is blunter about why this matters: distributed problem solving historically "assumed… **Complete knowledge of timing and precedence relations between tasks**", and distributed coordination instead has to *discover* precedence by negotiation [135]. The shipped protocol-as-code template encodes it as mechanics rather than prose, and the same DAG discipline is what OpenAI's Symphony makes its primary substrate [98][130].
*Failure prevented:* agents working on a resource whose prerequisite is still in flight — which is also the regime the scaling study says multi-agent handles *worst*: all MAS architectures degrade **−39% to −70%** on sequential planning, with the mechanism named as "coordination-saturation"/"communication overload" [84].
*Cost:* medium. Schema change + a promotion path. This is the single most-cited classic precedent in the corpus.

### R4 — **Cycle detection over a wait-for graph spanning all three wait mechanisms**
*Build:* maintain a wait-for graph across `wait_for_claim`, `wait_for_agent` and `wait_for_message` (edges: agent → resource/agent/message it is blocked on). On each new wait edge, check for a cycle; if the new edge closes one, refuse the wait with a structured error naming the cycle, rather than letting every participant time out.
*Evidence:* the same-product-family bug: "the graph is maintained on every `wait()` and consumed on every matching `send()`, but **never inspected for cycles**"; the group "stalls for the entire wait timeout (default 120 s) with no indication anything is wrong. The status line shows every agent as 'running'; no error is raised; the only unlock is the timeout"; and "a cycle can span more than one wait mechanism", so a bus-only cycle check misses cross-mechanism cycles [33]. Holt: for single-unit resources, "the conditions of deadlock, 'not complete reducibility,' and 'existence of a cycle in the graph' become equivalent" [34]; prevention is "**refusing to grant requests when the resulting state 'may lead to deadlock**'" [34]. Coffman's four conditions are the frame [35]. The measured LLM-agent analogue: DPBench's deadlock rate ranges **25.0%–90.0%** at N=5, and is driven to ~0% by three protocol variables — three rounds of pre-commitment, an ordering/symmetry-breaking primitive, and a group-size change — with the paper's own conclusion that "whether the same model coordinates or deadlocks is determined by the **protocol**, not by the model's capability" [100]. Lindau's DPBench result is the direct precedent for a *deterministic* rather than model-decided fix, and matches crewAI's "Deterministic Trajectory Guardrail" ask [42].
*Failure prevented:* a self-deadlocking swarm that burns the full wait timeout (up to 300 s) with every agent reporting "running" — invisible to the human watching the panel.
*Cost:* medium. The graph is in-memory (like `store.waiters`), and the cycle check is a DFS at wait-entry.
*Note:* this is a **detection** fix, not a **prevention** fix; prevention (no hold-and-wait) is harder in an LLM swarm and the classic literature does not offer a clean version of it. The over-commitment analogue is documented too — the *Eager Bidder Problem*, where an agent that binds resources at bid time can win more awards than it can honour [139] — and the classical prevention is a *bounded, single-unit* resource with a safety check on the grant [34].

### R5 — **Four record kinds, so the room can be measured at all**
*Build:* append `contended` (a claim attempt that lost: resource, loser, holder), `delivered` (target, record seq, tier), `wait` (resource/target, waiter, enqueue ts, grant ts, outcome ∈ granted|timeout|aborted), and `member{leave}` (on park/abort). Add a `deliver` of the tier to the delivery path (tier is already computed per viewer — it just is not stored).
*Evidence:* the 16-metric computability catalogue: today "contention and duplicate work are structurally invisible" because a failed claim appends nothing; tier distribution, findings-read, wait productivity and true last-agent-standing are all N; and "the room cannot currently produce a coordination-active subset at all" — the one metric the noise-floor protocol requires before any coordination claim is credible [12][13]. `member{leave}` is already in the schema (`plugin/src/store/schema.ts:53-60`) and has **no call site** — the plugin's own code comments note the roster is a "monotonic lifetime counter" that only grows, which is why the digest reports "1 joined · 32 live" [72][73]. The instrument shapes exist: OTel `gen_ai.invoke_agent.*` metrics [74], `a2a.server.task.message_count` [75], Phoenix/Langfuse span trees [76][77].
*Failure prevented:* the plugin cannot currently prove that any change to it helps — which is the same failure the whole literature has: 7 of 10 published coordination gains sit below the [−3, +18] pp noise envelope [13].
*Cost:* low-to-medium. Four record kinds, one projection change each, and a `delivered` write on the delivery path (which must not break I8's per-root delivery serialisation).
*This is R5, not R1, because it is cheap and it gates everything else's evidence.* The incident literature says the same from the operations side: across 150 production incidents, quality gates catch **73%** of silent degradation before user impact, and circuit breakers cut cascade propagation by **89%** [126] — both of which need a record to act on.
> **Status as of 2026-10-26 (post-dating the research):** R5 landed with two deliberate deviations. `member{leave}` was decided OUT — a parked agent is live, and the metric is computable without it. `delivered` is in-memory tier counters plus a T0-only log record, not a write per delivery — a log record per fan-out delivery measured 3.3 ms/append (fsync), so the counters live in memory and only T0 (the interrupt tier) is logged. The rest (`contended`, `wait`+outcome) landed as specified. Rankings unchanged.

### R6 — A **status ledger** on the shared record: one schema-checked per-turn object plus a durable epistemic store
*Build:* the room gains a per-topic **status object** written by whoever holds the coordination role: a small fixed-shape JSON (is the request satisfied? is progress being made? is this a loop? who acts next? what is the instruction?), validated on write the way Magentic-One validates its ledger, plus a separate durable store of verified / to-look-up / to-derive / guessed facts. Promote it through the existing T0/T1 tiers.
*Evidence:* Magentic-One's progress ledger is exactly five keys — `is_request_satisfied`, `is_in_loop`, `is_progress_being_made`, `next_speaker`, `instruction_or_question`, each `{reason, answer}` — and it is **runtime-validated**: the orchestrator parses the JSON, checks a required-key list, feeds back the literal `KeyError`, retries up to `max_json_retries = 10`, then raises [3]. Its ablation is the strongest single number in the corpus: replacing the orchestrator with a plain group-chat speaker selector, "eliminating **both ledgers**, planning, progress tracking, loop detection, and explicit instructions", drops performance by **31%** [3]. Its stall counter (`is_in_loop OR !is_progress_being_made`, then replan + context reset, with `max_stalls_before_replan=3`, `max_replans=3`) is the ready-made loop-guard and escalation path the room lacks [3]. The task ledger's four fact sections (verified / to-look-up / to-derive / educated guesses) are the epistemic store [3]. Supporting: "system design, not model capability, is the first-order cause of MAS failure" — MAST's category-1 modes (step repetition 15.7%, unaware of termination 9.82%, disobey task spec 11.8%) sum **44.2%**, exceeding category-2's 32.35% [101]. The IDE-agent analogue: IBM's silent-failure detector names cycles, drift, missing details and **context propagation failures** as the failure classes, with the cycle rule "any agent/tool invoked >1x" [102]. The role-play societies encode the same discipline as protocol rather than prose (MetaGPT's own source: agents "communicate through documents and diagrams (structured outputs) rather than dialogue", and "an agent activates its action only after receiving all its prerequisite dependencies") [168]: MetaGPT's "`Code = SOP(Team)`" exists specifically to kill idle chatter, and ChatDev's dual-agent grammar ends a subtask "after two unchanged code modifications or after 10 rounds of communication" with a literal `<SOLUTION>` token [155]. And the platform-level consensus is that coordination belongs in *components*, not in behaviour: AgentScope's fault-tolerance ladder, CAMEL's Critic-in-the-Loop, and AutoGen's `SelectorGroupChat` with its retry-on-invalid-speaker loop all treat the coordination check as a thing you ship [155][167].
*Failure prevented:* a swarm that keeps talking without converging — MAST's largest single mode (step repetition, 15.7%) and its "unaware of termination" mode (9.82%) [101]; and the "conversation reset" and "premature termination" modes the room's T0/T1 tiers currently do not detect. (The per-mode decimals are version-specific: the v2 §4.1 read gives step repetition 17.14%, disobey task spec 10.98%, fail-to-ask 11.65%; the v3 set is lower. Cite the version you mean [101].)
*Cost:* high. It is a new record kind, a validation path, a schema, and — the hard part — **it requires deciding who writes it**, which is the router question. The scope of the shared state is also a decision the evidence settles for us: a *flat* shared store loses to **no memory at all** in the primary ablations (under DyLAN, G-Memory 59.53 vs a no-memory baseline of 67.78; MetaGPT 52.80; MemoryBank 50.92), with the two named mechanisms being "noise accumulation" and "behavioral homogenization" — role-specific trajectories averaged out until the policies converge — while a *gated* shared store with per-agent private memory beats both [160]. So the ledger must be gated and paired with private state, not a shared scratchpad; and the private layer is the stronger safeguard, which is exactly what a claim board with a designated writer is. In a flat room the natural answer is "whoever holds the claim on the topic", which makes the ledger a *by-product of ownership* rather than a new hierarchy. That is the whole point of R3+R6 together.
*Honest caveat:* the −31% ablation was measured **with** an orchestrator [3]; the report's own gap list says "no primary source measures ledger/SOP discipline inside a flat, orchestrator-free room" [16]. This is the least-validated item on the list, and it is the one most likely to be wrong. The reason it is ranked 6 and not 1 is exactly that.

### R7 — **Idempotency keys on `post`**
*Build:* an optional `idemKey` on `room{op:"post"}`; a repeat with the same key returns the original record instead of appending a second.
*Evidence:* Stripe's first-party contract, directly copyable: "use an idempotency key. Then, if a connection error occurs, you can safely repeat the request without risk of creating a second object"; "Stripe saves the status code and body of the first request… **Retries with the same key return the saved response, including 500 errors**"; the boundaries (results saved only after execution begins; mismatched parameters are an error; keys pruned at ≥24 h) [103]. Demand-side: requested in **five** independent trackers and shipped in none [36][37][38][44]; Anthropic's CHANGELOG shipped three duplicate-execution fixes in a row, including "**running an already answered message a second time**" and "**repeat work such as posting the same report twice**" [39].
*Failure prevented:* a retried post appending a second record — which, with a mention, double-wakes a peer (T0 is a wake+steer).
*Cost:* low. One field, one lookup, one log record.

### R8 — **Guidance: keep the Skill, demote the always-on duplicate, and add the four missing procedures**
*Build:* (a) trim `routing-rule.md` to a one-line pointer and let `SKILL.md` carry the procedure — or drop the always-on copy entirely; (b) add to the Skill the four procedures the evidence actually names, as *procedures* not declarations: when to claim vs. when to look for an unclaimed resource; when to wait vs. when to escalate; how to hand off (an artifact + a reference, not a summary); how to record a finding so a later agent can use it; (c) ship a "when NOT to use the room" gate.
*Evidence:* the shape is settled — "**Overly comprehensive skills can hurt more than they help**… **Add what the agent lacks, omit what it knows**… **Provide defaults, not menus**… The highest-value content in many skills is a list of **gotchas**" [51]; "focused Skills with at most three modules outperform larger or exhaustive bundles" and "**Self-generated Skills provide no benefit on average**" [50]; Anthropic's "**frameworks for collaboration that define the division of labor, problem-solving approaches, and effort budgets**", with the failure they had to fix by prompting being "spawning 50 subagents for simple queries… and distracting each other with excessive updates", and the fix being explicit scaling rules (1 agent for simple fact-finding, 3–5 for complex, "with clearly divided responsibilities") [86]. The handoff rule is measured: context-bearing handoffs cut median agent events **20–59%** and cumulative prompt tokens **42–63%** [104]. The "when not to" gate is measured: multi-agent has **negative** returns once the single-agent baseline passes ~45% [84], and Anthropic's own "most coding tasks… are not a good fit for multi-agent systems today" [81]. The *effect* of guidance is process, not outcome [46][47][48][49] — so this item should be sold on cost and process, never on correctness.
*Failure prevented:* wasted tokens and duplicated work from a protocol the agents improvise; and the always-on block's own cost (the "Evaluating AGENTS.md" study's +20% cost finding [46]).
*Cost:* low. Text edits.
*What to put in it, and what not:* MAST's intervention table is the sharpest available split — on ChatDev ProgramDev, **changing the topology** delivered **+15.6%** (25.0 → 40.6) while **improving the prompt/role specifications** delivered **+9.4%** (25.0 → 34.4) [101]. So the playbook must specify *structure and boundaries*, not *personas*: the measured evidence is that role **labels** are near-inert (societies differing only in trait/persona produced no detectable performance difference across MATH/MMLU/Chess), while the measured payoff comes from the *interaction pattern* — who proposes and who aggregates, who writes and who reviews [99]. Anthropic's own duplicated-work fix was the same shape: give each subagent "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" [86] — a structure, not a persona.
*Note:* the plugin's `SKILL.md` is already 143 lines and already says "**The more specific and concise your instructions, the more consistently Claude follows them**"-class guidance [105]; the work is to *cut* and *reorder*, and to add the four procedures.

### R9 — **A "who is blocked on what" view** (board pane + a queryable structure)
*Build:* a board view that renders the dependency/claim structure — who holds what, who waits on what, and which waits are cycle-adjacent. This is the panel half of R3+R4+R6.
*Evidence:* opencode's own feature request names the artefact: "overlap is often discovered only after two agents have already edited the same area. At that point, the parent agent must reconcile conflicting implementations, duplicate work, or incompatible assumptions. The goal is not to introduce rigid file locking. It is to make planned overlap visible early enough for the orchestrator or user to adjust task boundaries" — a published **intent record** naming semantic ownership, the files likely to change, and a read-only/additive/destructive flag [170]. The shipped precedents all have one: Anthropic's `claude agents --json` includes `waitingFor` showing "what a waiting session is blocked on" [39]; GitHub's `gh-aw` work-queue ships "blocked-route bookkeeping with reopen conditions" as protocol [98]; the blackboard's historical control component was "a blackboard monitor and a scheduler" that "kept an account of each change made to the blackboard, its primitive change type, and any new hypotheses" — the closest classic analogue to a digest + focus-of-attention [106]; Smith's 1980 protocol is explicit that the manager holds the contract record, so "the failure of any contractor… can be detected by its manager" [15]. And the classic efficiency criterion prices idle capacity as a loss [107].
*Failure prevented:* "an agent waiting because nobody claimed" being invisible, and a blocked swarm being invisible to the human watching `/room`.
*Cost:* low for the board pane, medium for the underlying structure (it depends on R3/R4).

### R10 — **Not now: runtime retrieval of coordination literature**
*Build:* nothing.
*Evidence:* §5 above. Zero supporting primary evidence; strong specific evidence against; the winning pattern is accumulate-and-distill, and the shipped template is a distilled artifact [67][68][69][65][66]. If a retrieval capability is wanted later, the correct target is the **room's own log** (the plugin's `recall` is a regex over the raw log and the `SKILL.md` admits "There is no semantic search" [70]), not the coordination literature.
*Failure prevented:* the token and distraction cost of a retrieval tool, and the "shared catalogue silently clobbered" failure mode [55].
*Cost:* zero. This item is a decision not to build.

## What would change this

The recommendation is falsifiable in five specific ways. Each is a measurement the plugin could actually run, and each would overturn a named part of the answer.

1. **If the plugin's contested claims turn out to be rare and always benign, R1 and R3 fall.** The whole mechanics case rests on contention being a live, damaging event. The first thing `contended` (R5) will show is the contended-claim rate. If it is near zero, the fencing token and the dependency edges are insurance against a failure that does not happen, and the ranking should collapse to R5 (measure) → R8 (guidance) → R7. If it is high *and* the contended claims are followed by a reclaim rather than a double-write, the case weakens further. Conversely: if the contended rate is high and any contended claim is followed by two agents editing the same file, R1 becomes urgent rather than first-among-equals.
2. **If a fenced write path cannot be built — because agents edit files through host tools the plugin cannot intercept — then the honest resolution is to demote the claim to advisory, explicitly, and R1 becomes a documentation change rather than a mechanism.** The plugin cannot enforce a token on a file write it never sees. A claim that cannot be enforced must not be advertised as a correctness mechanism. This is the branch where the "considered and rejected" entry on advisory-only claims becomes the *recommended* path, and the failure it prevents is the "rule is a suggestion" failure the 21-agent report names [108].
3. **If the room's contention turns out to be low but the *findings-never-read* rate is high, R6 and R9 move up and R1 moves down.** The plugin's own goal is that "a finding posted by one agent is usable by a later one". `delivered` records will show the read rate; if a posted finding is rarely read by anyone, the binding problem is discovery and structure, not ownership, and the ledger + a "who is blocked on what" view are the fix.
4. **If guidance turns out to change the plugin's swarm outcomes — not just its process — the R8/R6 ordering flips.** The literature's honest position is that guidance moves process and cost, not outcome [46][47][48][49], and the noise floor says a coordination effect below ~15–20 pp on a paired, coordination-active protocol is indistinguishable from noise [13]. If a *properly instrumented* A/B of the shipped `SKILL.md` + `routing-rule.md` shows a real outcome effect, then guidance deserves more of the budget than mechanics, and the claim in §4 that "mechanics > guidance" is wrong. The current evidence cannot support that claim either way — it can only support the *ranking*.
5. **If flat peer-to-peer coordination turns out to scale past ~20 agents in this plugin, the largest open question in the report dissolves.** Cursor's first-party finding is that a lock-based shared-file protocol throttled twenty agents to the throughput of two or three [31]; every remedy they and others shipped was hierarchical or git-mediated [32][129][132]. If the plugin's lease, with renewal and dependency ordering, carries a swarm of 20+ agents at full throughput, then the flat room is not merely a cheaper shape but a *viable* one, and the "add a router" evidence stops applying to this design. Conversely, if the plugin hits Cursor's ceiling at 8 or 10 agents, the flat design needs the router the report ranks as out of scope — and the whole ranking would need redoing around a different topology.

Two further results would change the *measurements* rather than the ranking. If the plugin's coordination density per agent-turn is far from the ≈0.39 the scaling study reports [84], the T1/T2 caps are miscalibrated and the cost analysis in §7 changes shape. And if a room-shaped benchmark appears — the corpus has none, since every coordination benchmark assumes a turn-taking, message-addressed, or container-isolated substrate [12][16] — it would supply the baseline the plugin currently has none of.

## Considered and rejected

**Add a designated router / coordinator agent to the room.** Rejected as *architecture*, retained as *content*: the router wins on every measured result [3][5][86], but a flat room's whole value is that it does not centralise, and the counter-evidence is real ("naming one agent 'coordinator' creates no communication hub and gives no reliable improvement in success" [91]). The synthesis that survives is R6: give the flat room the *protocol* a router provides (a validated status object + dependency-gated claims + a loop guard) without the hierarchy. Also: the plugin's own domain — one main session plus `task` subagents — already has a natural router in the main session; the question is whether the room *forces* the traffic through it, and the evidence says forcing it is what breaks [88].

**Make the claim board advisory and rely on guidance instead.** Rejected — but this is the closest call, and the honest framing is that the plugin must pick one. Kleppmann's rule is that a lease without a resource-side check cannot be relied on for correctness [1]; the alternative is to stop advertising the claim as a correctness mechanism and say plainly that it is a *signal*. The evidence for "signal not lock" is genuinely strong: a 21-agent practitioner's rule is "**The task claim isn't a lock. It's a signal.**" [108], and Cursor's first-party finding is that a mutex agents held badly *was* the bottleneck [31]. But "advisory only" is a retreat from the plugin's stated purpose, and the measured conflict rates (27.67% agent-PR; 41.7% cross-agent) say the default behaviour is bad enough to be worth a mechanic. **Recommendation: ship R1+R2+R3 (mechanics) and describe the claim's guarantees honestly in the tool description and `SKILL.md` — do not quietly leave the gap between advertised and actual.** If the file-write fence proves impossible, the fallback is to demote the claim to advisory *explicitly*, with the conflict rates cited as the reason.

**A per-agent token budget on room chatter.** Rejected for now, though the demand is documented: ag2 #565 "isn't currently supported" [43]; OpenAI #3353 "couldn't be done only by SDK side changes" [44]; Microsoft ships a family of open budget requests [109]; users "explicitly asked for **hard budget guardrails, not dashboard alerts**, as a pre-deployment gate" [110]. The plugin already has per-turn caps (K=10, B=2,048) and a rate limit (1 post/2 s, burst 10), and the measured target is ≈0.39 messages per agent-turn [84] — so the cheap, evidence-backed version is to *tune the existing caps against that number and instrument the result* (R5), not to build a budget system.

**A shared task list (a first-class task entity separate from claims).** Rejected *as a separate object*, adopted *as R3's dependency fields*. Claude Code's shipped task list and Letta's `Task*` board both separate "task" from "ownership" [21][22], and the classic contract net keeps them together (a subcontract has predecessors, successors, manager, report recipients) [15]. Splitting them doubles the state to maintain for a benefit the dependency fields already deliver. Revisit if R3 lands and the board still cannot answer "what is left".

**Work stealing / load balancing.** Rejected as inapplicable, with one retained piece. The plugin has a board of *exclusively held* resources, not a queue of unclaimed work, so the classic mechanism does not apply [111]. The shared-memory line of the classical literature agrees about the shape: blocking is the *intended* semantics of a bounded buffer, and backpressure is a derived property of the trace restriction rather than a separate mechanism [140] — which argues for tuning the plugin's existing per-turn caps rather than for a new scheduler. But the fairness framing is worth keeping: Tokio's guarantee is bounded-delay eventual fairness, explicitly **not** equal fairness — "the runtime may schedule A five times before it schedules B… **All that is guaranteed is that it will schedule B eventually**" [112]. The plugin's oldest-waiter promotion is already a starvation-freedom mechanism in this sense, and the room's per-turn caps are the analogue of Gray & Cheriton's own rule — a write waiting for approval blocks new leases, "to avoid starvation of writes" [113].

**A semantic index over the room log (embeddings).** Not rejected — deferred, consistent with the repo's existing decision and its stated revisit trigger (log past ~10⁵ records, or observed "we discussed this but I cannot find it" failures — counted as zero-match `room recall` results with `recallMiss:true` in details) [114]. The research adds a *specific* measurement prerequisite: an index is only worth it if the room can show the "cannot find it" failure rate, which R5's `delivered` record makes measurable. Note also the tool-retrieval evidence: a 43k-tool corpus degrades tool-use pass rates, and 100 tool descriptions ≈ 20,000 prompt tokens [59][60] — so any index must be *compressed and selected*, never dumped.

**A stigmergic design — agents coordinate only through the shared log, never through each other.** The classic case is strong: stigmergy needs "a persistent, shared, readable state", and it buys scale and fault-tolerance precisely because it needs "no planning or anticipation, no memory, no communication, no mutual awareness" [136]. The plugin already has the medium (an append-only JSONL log plus a cold summary tree). But the classic's own caveat is the one that bites: it "does not guarantee an optimal use of the 'workforce'" [136] — and the plugin's version of that gap is Cursor's, where a shared file plus a lock protocol throttled twenty agents to the throughput of two or three [31]. A stigmergic room is a *cheaper* room, not a *better-coordinated* one, and the plugin's stated goal is coordination.  **Multi-agent debate as a coordination primitive.** Out of scope by the brief, and the evidence is against it as a *coordination* mechanism: debate frequently fails to beat single-agent self-consistency, correct→incorrect flips dominate every configuration, and the harm is not fixed by a correctness-payoff prompt [115][116]. Noted only because a room is a natural place to *attempt* it — and that is exactly where the failure mode lives.

## Measurement: what to instrument, and what it buys

The plugin's one measured number today is the unprompted **discovery** rate — 75.0–85.7% over 16 trials — which measures whether a model finds the room, not whether the swarm coordinates [117]. Everything below is either computable from today's log (Y), computable with a caveat (Y*), or not computable until R5 lands (N).

| Metric | Definition | Verdict | Fields needed | Why it matters |
|---|---|---|---|---|
| Contended-claim rate | `#contended / #claim` | **N** → R5 | new `contended` kind | the duplicate-work early-warning signal; invisible today because a lost claim appends nothing [12] |
| Overlapping-claim rate | resources with ≥1 intersecting lease window / distinct resources claimed | Y* | `claim{resource,ts,ttlMs}`, `release{resource,ts,reason}` | the room's "tragedy of the commons" [12] |
| Orphan/expired-claim rate | `#release{reason:"expired"} / #claim` | **Y** | existing | fleet health; already computable [12] |
| Rework rate | resources claimed ≥2× by the *same* agent / distinct resources claimed | **Y** | existing | DORA's exact "unplanned remediation" construction [118] |
| Claims-per-post | `#claim / #msg`, per agent too | **Y** | existing | the room's own "coordination tax" proxy; MultiAgentBench showed token usage and task score move together [78] |
| Coordination tokens/turn | Σ over injected records of `ceil(len/4)` per turn | Y* (proxy) | needs a per-turn record | the only way to compute an Anthropic-equivalent overhead ratio for this room [12][80][81] |
| Coordination density | coordination records per agent-turn | Y* | needs a per-turn record | the measured optimum is ≈**0.39**/agent-turn [84] |
| Tier distribution (T0/T1/T2), T0 wake rate | share of deliveries by tier | **N** → R5 | `delivered{target,seq,tier}` | T0 *is* the interruption budget, and nobody publishes a "cost per interrupt" [12] |
| Findings posted vs read | posted / read-receipted | **N** → R5 | `delivered` | the plugin's own goal — "a finding posted by one agent is usable by a later one" [85] |
| Wait productivity | waits ending `granted` / total; time-to-grant | **N** → R5 | `wait{waiter,resource,outcome,grantTs}` | distinguishes a productive wait from a stall [12] |
| Idle-gap / handover-gap | `claim₂.ts − release₁.ts`; `release₁.ts − claim₁.ts` | **Y** | existing | the closest analogue of Google's review/merge wait pair [119] |
| Last-agent-standing / quiet collapse | per-agent `last_activity_ts` vs room head | Y* | existing; R5's `member{leave}` makes it exact | the "phantom agents" failure [120] |
| Coordination-active subset | restrict any effect measure to intervals where a claim was contended, a wait enqueued, or a record delivered | **N** → R5 | R5's kinds | the noise-floor protocol's required reporting protocol [13] |
| Duplicate-work rate | claims on the same resource by different agents without a release between | Y* | existing + `contended` | excludes deliberate replication, which the Collaboration Tax paper says is not waste [45] |
| Task outcome | — | **N** | external grader | no coordination metric predicts task success [78] |

**The reporting bar.** Because 7 of 10 published coordination gains sit inside a [−3, +18] pp paired noise envelope [13], any claim that a change to this plugin improves coordination must be reported as a **paired, coordination-active** measurement with a detectable effect of roughly **≥15–20 pp** — and, per MultiAgentBench's own finding that coordination score and task score can diverge wildly (CS 75.00 with TS 0.21) [78], it must pair a coordination metric with an outcome metric. Until R5 lands, the plugin cannot produce such a measurement at all. **That is the argument for R5 being cheap and first among the mechanics.**

**Instrument shapes to copy, not invent:** OTel GenAI's `gen_ai.invoke_agent.duration` / `.inference_calls` / `.tool_calls` and the `create_agent` / `invoke_agent` / `invoke_workflow` / `plan` / `execute_tool` spans, with `gen_ai.agent.id` as a *stable provider-assigned* id (transient in-memory instance ids are explicitly NOT RECOMMENDED) [74]; A2A's proposed `a2a.server.task.message_count` and `a2a.server.task.state` [75]; Phoenix's / Langfuse's trace→span trees with Agent/Tool/LLM span kinds [76][77]; and Aider's per-run cost dashboard (pass@1/pass@2, prompt/completion tokens, seconds per case, total cost) as the model for a per-run panel [122]. For cost baselines, note Anthropic's own "**Multi-agent systems use about 15× more tokens than chats**" (vs chat) [81] and the 2026 restatement "**3-10x more tokens than single-agent approaches**" (vs single-agent) [80] — always with the baseline attached.

## Open questions

1. **Does the plugin's claim board actually cause duplication today?** No primary source measures a room-shaped substrate, and the plugin has no contention record [12][16]. R5's `contended` kind is the only way to find out. Until then, "the room prevents duplicate work" is a design claim, not a measurement.
2. **Can the file-write fence be enforced at all?** Agents edit files through the host's edit tool, outside the room. Kleppmann requires the *resource* to check the token [1]; a room cannot check a file. The plausible shape is a generation published by the room and checked by a write wrapper — but no source measures that, and this is the largest single unknown in the report.
3. **Is the flat room's scale ceiling below Cursor's ~20 agents?** Cursor's first-party finding is that a lock-based shared-file protocol throttles 20 agents to the throughput of 2–3 [31]; our lease has no TTL-renewal, no dependency ordering and no cycle detection, so the plugin may hit that ceiling earlier. Untested.
4. **Does a ledger work without a router?** The −31% ablation was measured with an orchestrator [3]; the repo's own gap list says no primary source measures ledger discipline in a flat, orchestrator-free room [16]. R6 is the highest-value and least-validated item on the list.
5. **What is the cost of an interrupt?** No primary source measures "cost per interrupt" in an agent swarm [12]. The plugin's T0 wake+steer budget is an unmeasured design choice. Anthropic's qualitative "distracting each other with excessive updates" [86] and the noise-floor protocol's "per-match injection noise" [13] are the nearest signals.
6. **Is the 0.39 messages/agent-turn target applicable to a room?** It was measured on token-matched reasoning-heavy configurations, not on coordination chatter [84]. It is the best available number to calibrate the T1/T2 caps against, but it is a transfer, not a measurement.
7. **Would the "which mechanism prevented which failure" mapping hold for a room with a different failure surface?** The classic mapping is established (blackboard ⇒ duplicated work from too-coarse shared state; contract net ⇒ starvation and the Eager Bidder Problem; tuple space ⇒ semantic mismatch and no delivery guarantee; stigmergy ⇒ no optimal workforce use) [15][106][123][124], but the room's surface — a tiered interrupt channel with per-viewer classification — has no classical analogue.
8. **Does the plugin's guidance help at all?** The 75.0–85.7% discovery rate measures discovery, not coordination quality [117]. No source lets us claim the shipped `routing-rule.md` + `SKILL.md` improves swarm outcomes; that would need the same paired, coordination-active protocol as everything else [13].
9. **Is a shared room the right shape at all beyond ~20 agents?** The only first-party report of a lock-based shared-file protocol at scale says twenty agents degraded to the throughput of two or three [31], and the remedies everyone shipped were *hierarchical* (planner/executor/judge) or *git-mediated* [32][129][132]. Our lease has no renewal, no dependency ordering and no cycle detection, so the plugin may hit that ceiling earlier — but every one of those remedies costs the flat, peer-to-peer property the plugin exists to provide. This is the report's biggest open design question, and it is not answerable from the literature. 10. **Citation corrections to carry forward** (each verified against a primary or an authoritative index during this research): the "Holt 1970 *Deadlock Detection Using Wait-for Graphs*" citation does not exist — the real paper is Holt, *Some Deadlock Properties of Computer Systems*, ACM CSUR **4(3):179–196, 1972** [34]; "Richardson 1988 *Sagas*" does not exist — the original is Garcia-Molina & Salem, SIGMOD 1987 [125]; Anthropic's 15× is vs *chat* while 3–10× is vs *single-agent* [80][81]; MAST's category-1 modes (44.2%) exceed category-2's (32.35%), so the widely-repeated "36.94% inter-agent = largest category" is a misreading [101][13]; the SWAN original (IBM RC 19807) was unreachable and is therefore not cited [95][96]; and several arXiv IDs commonly attached to this literature are wrong (2509.09676 is a video dataset, not an agentic scaling law; 2501.12911 is a homomorphic-encryption paper, not an OpenHands fleet paper; 2504.09713 and 2502.04038 are unrelated) [84][5][99].
