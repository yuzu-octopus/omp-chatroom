## Claims

### F13 — primitives (source file: `findings/F13.md`)

- **Lease (Gray & Cheriton, SOSP 1989).** A lease is "a contract that gives its holder specified rights over property for a limited period of time"; the server must honour it for the whole term, including after its own crash. **Does NOT guarantee:** consistency under **clock failure** — "Leases ensure consistency provided that the hosts and network do not suffer certain Byzantine failures including **clock failure**. Leases depend on well-behaved clocks." Also no availability cost from the caches ("an unreachable client at most briefly delays write access"). https://www.cs.cmu.edu/afs/cs.cmu.edu/academic/class/15712-s12/www/papers/gray89.pdf — **primary**
- **Fencing token (Kleppmann, canonical write-up).** "you need to include a *fencing token* with every write request… a fencing token is simply a number that increases… every time a client acquires the lock"; the resource must enforce it ("the storage server remembers that it has already processed a write with a higher token number (34), and so it rejects the request with token 33") — "this requires the storage server to take an active role in checking tokens", so a client-side lease check is **not** sufficient. Prevents: a GC-paused or delayed client writing after its lease expired → "corrupted file, data loss, permanent inconsistency" (Kleppmann cites HBase having exactly this bug). https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html — **primary**
- **Efficiency vs correctness (same source).** Locks are "for efficiency or for correctness": efficiency = avoid duplicate work, "a minor increase in cost"; correctness = "If the lock fails and two nodes concurrently work on the same piece of data, the result is a corrupted file, data loss, permanent inconsistency"; "the locks are only approximate and may occasionally fail" if used best-effort. Same URL — **primary**
- **Chubby's shipped answer (Burrows, OSDI 2006).** The **sequencer** = lock name + mode + **lock generation number**, passed to the protected server, which "is expected to test whether the sequencer is still valid… if not, it should reject the request". Chubby also ships the weaker **lock-delay** and admits it: "While imperfect, the lock-delay protects" (against an inaccessible holder making a resource unavailable). https://www.usenix.org/legacy/events/osdi06/tech/full_papers/burrows/burrows.pdf — **primary**
- **Lease renewal (same Chubby paper).** "The master advances the lease timeout… when it responds to a **KeepAlive** RPC from the client" (default extension 12 s); a client whose local lease expires enters **jeopardy** — it "empties and disables its cache" and waits 45 s, i.e. it **stops writing** rather than writing optimistically. Same URL — **primary**
- **Failure detectors (Chandra & Toueg, JACM 43(2), 1996).** Strong completeness = "Eventually every process that crashes is permanently suspected by *every* correct process"; weak completeness = by *some*; strong accuracy = "No process is suspected before it crashes"; weak accuracy = "Some correct process is never suspected". Class **S** (strong completeness + weak accuracy) is what makes Consensus solvable "despite any number of crashes". **The key impossibility, in the authors' words (§1, §9.1):** "it is impossible in an asynchronous distributed system to reliably distinguish a process that has crashed from one that is merely very slow." Detector mistakes must cost **liveness, not safety**: "processes may be prevented from deciding, but they never decide different values." The timeout scheme must self-correct: on receiving a late alive-message, the suspecting process removes the suspect and "**increases the length of its timeout period**". And: "all reasoning about failure detectors… should be done in terms of their abstract properties and not in terms of any particular implementation". https://courses.csail.mit.edu/6.852/08/papers/CT96-JACM.pdf — **primary**
- **Timeout-based detection cannot beat the network (Birman & Joseph, ACM TOCS 5(1), 1987).** "failure detection by time-out cannot be more reliable than the underlying communication system: A series of message losses can always mimic a failure." Same paper supplies the **site incarnation number** — "incremented each time a site recovers" — the direct ancestor of the fencing token; "Messages from a failed incarnation are discarded by the input filter". https://www.cs.swarthmore.edu/~newhall/readings/isis2.pdf — **primary**
- **Heartbeat counters ≠ heartbeat timeouts (Aguilera, Chen & Toueg, WDAG 1997).** The counter-based detector "just counts the *total number of* heartbeats received from each process… it should not be confused with existing implementations of failure detectors… **Even though existing failure detectors are also based on the repeated sending of a heartbeat, *they use timeouts* on heartbeats… applications can only see these lists.**" https://www.microsoft.com/en-us/research/uploads/prod/1997/09/wdag97_hb.pdf — **primary**
- **Engineering form of the same point (Vogels, 1996).** "one would never be satisfied with making repeated phone calls to the same location for half an hour and then declaring the disappearance a fact, no matter whether the phone was picked up, a busy tone was heard or the phone was disconnected." https://www.cs.cornell.edu/Projects/spinglass/public_pdfs/World%20Wide.pdf — **primary**
- **Optimistic concurrency control (Kung & Robinson, ACM TODS 6(2), 1981).** Nonlocking control "rel[ies] mainly on transaction backup as a control mechanism, '**hoping**' that conflicts between transactions will not occur"; phases = read (local copies) → **validation** → write. Pessimistic locking's cost: "Even read-only transactions… must, in general, use locking"; "**if the locking protocol is not deadlock-free, deadlock detection must be considered to be part of lock maintenance overhead**"; "There are no general-purpose deadlock-free locking protocols for databases that always provide high concurrency." https://db.cs.cmu.edu/papers/1981/kung-tods1981.pdf — **primary**
- **Version vectors = conflict detection for a replicated file (Parker et al., IEEE TSE SE-9(3), 1983).** "A set of version vectors are compatible when one vector is at least as large as any other vector in every site component… **A set of vectors conflict when they are not compatible.**"; reconciliation is free: "Two file copies with version vectors u, v which are not in conflict may be reconciled without any further action; the version vector of the reconciled file is sup u v." https://pages.cs.wisc.edu/~remzi/Classes/739/Papers/parker83detection.pdf — **primary**
- **Three-way merge, first-party (Git docs).** `git merge-file` "incorporates all changes that lead from *base* to *other* into *current*"; "**A conflict occurs if both *current* and *other* have changes in a common segment of lines.**" https://git-scm.com/docs/git-merge-file and https://git-scm.com/docs/merge-strategies — **primary**
- **Vector clocks (Mattern, 1989).** "a linearly ordered structure of time is not always adequate for distributed systems… propose a generalized nonstandard model of time which consists of vectors of clocks. These clock vectors are partially ordered… the structure of causality is represented in an isomorphic way." Decision rule: two events are causally related iff one vector dominates the other, otherwise "causally independent". The use is **detection** ("a potential race condition exists if there is no causal relationship between two events") — a vector clock says *whether* two writes were concurrent, **not** whether they are semantically compatible (that needs a merge decision). https://pages.cs.wisc.edu/~remzi/Classes/739/Fall2015/Papers/mattern89.pdf — **primary**
- **Tuple space (Gelernter, ACM TOPLAS 7(1), 1985).** Linda: messages are added "in **tuple-structured form**… where they exist as named, independent entities until some process chooses to receive them"; ops `out` / `in` / `rd` / `eval`. Atomicity: "tuples be inserted into and withdrawn from TS atomically. If two in( ) statements contend for one tuple, one gets it and the other does not; **they cannot split it.**" **Does NOT guarantee:** FIFO order ("which is logically nondetermined"), nor delivery ("The system will not guarantee delivery, but should promise highly probable delivery"). https://cseweb.ucsd.edu/groups/csag/html/teaching/cse291s03/Readings/p80-gelernter.pdf — **primary**
- **Tuple-space properties and its two named gaps (Carriero, Gelernter et al., Yale TR-567, 1987).** "Its shared, associative memory semantics is the single most important property of tuple space"; because there is remove+insert rather than update-in-place, "it is easy to update atomically structures built in tuple space"; sender and receiver need not know each other, "merely that the two agree on the format of the data". **Gap 1 — Protection:** "Currently tuple space is 'flat'. It is the user's responsibility to choose the format and content of tuples such that unintentional 'aliasing' does not occur." **Gap 2 — Duplication:** the original asks for "some type of duplicate detection — that is, set semantics rather than multiset." **Free load balancing:** "Because of decoupling, there is no logical difference between running with 1 or n workers… **automatic load balancing**… all workers will tend to be kept busy." https://engineering.yale.edu/application/files/8517/3714/4920/tr567.pdf — **primary**
- **Sagas (Garcia-Molina & Salem, SIGMOD 1987 / Princeton CS-TR-070-87).** "The database management system guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution." **A compensation is not a rollback:** "The compensating transaction **undoes, from a semantic point of view**, any of the actions performed by T_i, but **does not necessarily return the database to the state that existed when the execution of T_i began.**" Ordering: compensations run "in **reverse order**", and child compensations before parent compensations; cascading rollback is the named hazard. Pure forward recovery is the alternative when compensations are hard to write. https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf and https://www.cs.princeton.edu/techreports/1987/070.pdf — **primary**
- **Idempotency keys (Stripe first-party).** "use an idempotency key. Then, if a connection error occurs, you can safely repeat the request without risk of creating a second object"; "Stripe saves the status code and body of the first request… **Retries with the same key return the saved response, including 500 errors.**" Boundaries: results are saved "only after the execution of an endpoint begins" (validation failures and concurrent conflicts save nothing); mismatched parameters are an error; keys are pruned at ≥24 h. https://docs.stripe.com/api/idempotent_requests — **primary**
- **Work stealing (Blumofe & Leiserson, FOCS 1994).** "the expected time T_P… is **T_P = O(T_1/P + T_∞)**… the space S_P required by the execution satisfies S_P ≤ S_1 P… the expected total communication… is at most O(T_∞ S_max P)… **All three of these bounds are existentially optimal to within a constant factor.**" Mechanism: "**underutilized processors take the initiative**"; the invariant behind the space bound is "**all leaves in the activation subtree have processors working on them**". https://www.cs.cornell.edu/courses/cs612/2006sp/papers/blumofe94.pdf — **primary**
- **Work stealing, runtime form (Vyukov, Go scheduler design doc, 2012 + `src/runtime/proc.go`).** "if the list is empty, P chooses a **random victim** (another P) and tries to steal a **half** of runnable goroutines from it"; "scheduler state is intentionally distributed (in particular, per-P work queues), so it is not possible to compute global predicates on fast paths". Source: `stealWork` tries `stealTries = 4` randomised victims and skips idle Ps. https://go.dev/s/go11sched and https://raw.githubusercontent.com/golang/go/master/src/runtime/proc.go — **primary**
- **Starvation freedom is a bounded-delay guarantee, and only from the runtime docs (Tokio).** "If the total number of tasks does not grow without bound, and no task is blocking the thread, then it is guaranteed that tasks are scheduled fairly… there is some number MAX_DELAY such that when a task is woken, it will be scheduled by the runtime within MAX_DELAY time units." **And explicitly NOT equal fairness:** "there is no guarantee that the runtime is equally fair to all tasks… the runtime may schedule A five times before it schedules B… **All that is guaranteed is that it will schedule B eventually.**" https://docs.rs/tokio/latest/tokio/runtime/ — **primary**
- **Deadlock conditions (Coffman, Elphick & Shoshani, ACM CSUR 3(2), 1971).** The four conditions, verbatim: "1) Tasks claim exclusive control of the resources they require ('**mutual exclusion**' condition). 2) Tasks hold resources already allocated to them while waiting for additional resources ('**wait for**' condition). 3) Resources cannot be forcibly removed… ('**no preemption**'). 4) A circular chain of tasks exists… ('**circular wait**')." Prevention = "prohibiting operations which may lead to deadlock". https://uobdv.github.io/Design-Verification/Supplementary/System_Deadlocks-Four_necessary_and_sufficient_conditions_for_deadlock.pdf — **primary**
- **Wait-for graph (Holt, ACM CSUR 4(3), 1972 — not 1970).** "**If each reusable resource has exactly one total unit, it can be shown that the conditions of deadlock, 'not complete reducibility,' and 'existence of a cycle in the graph' become equivalent.**" Prevention variant: "an acquisition operation is said to be **safe** if it results in a state whose claim limited graph is completely reducible" / "deadlock can be prevented… by **refusing to grant requests when the resulting state 'may lead to deadlock'.**" Same paper records the OS/360 timeout-as-backstop admission: "To prevent waiting forever, OS/360 allows an arbitrary absolute limit of **30 minutes** waiting time before canceling the job." https://courses.cs.umbc.edu/graduate/CMSC621/fall02/lectures/some-deadlock-properties-of-computer-systems.pdf — **primary**
- **F13's direct answer to "which primitive is the claim-board lease missing"** (source-reading of our plugin, primary for our own code): **(1) Fencing token is load-bearing.** Our claim record is `{resource, holder, ttlMs, acquiredAt, seq}` — no generation field — and `src/tools/room.ts` `case "post"` appends **unconditionally** without checking claim ownership. Per Kleppmann's efficiency-vs-correctness split, the board is therefore an **efficiency-only, approximate lock today**, while its own tool description advertises it for "before editing a shared file". Fencing must ride the **write path** (file / three-way merge / version vector), not only the board. **(2) Renewal/heartbeat is the second missing piece** — Chubby KeepAlive + the failure-detector literature ("timeout is only a guess"; a client that cannot renew must stop writing) mean a live-but-slow agent currently loses its lease at 300 s and is displaced. **(3) Dependency ordering between claims is the third** — Coffman conditions 2+4 + Holt's cycle equivalence: two agents each holding a claim and waiting on the other is a deadlock no TTL fixes (each waits out its lease and re-contends forever); our three blocking waits can form a cycle **across mechanisms**, so per-mechanism checking misses it. **(4) Vector/version clocks belong to file-conflict detection, not the lease**; the log's per-agent `seq`+cursor is already a Lamport-style scalar clock, and only the vector form is missing. **(5) Work stealing is unusable as-is** (no queue of unclaimed work to steal — the board holds exclusively-owned resources), but the **waiter-promotion** pattern and the **starvation-freedom framing** (bounded work + bounded service time ⇒ bounded delay, eventual not equal fairness) are the right models; our rate limit (1 post/2 s) and T1 budget are the same "no starvation of writes" rule Gray & Cheriton state for leases. **(6) Idempotency keys are the missing exactly-once semantics for `post`** — a retried post appends a second record and would double-deliver a mention. **(7) Tuple space is the model for the shared record** and we already implement most of it (`out`=post, `in`=read-with-cursor, `rd`=recall, claim board = typed entry set), missing exactly two of the original's named properties: **duplicate detection / set semantics** (our log is a multiset) and **per-space protection** (our resources are flat `"<topic>/<key>"` strings; no notion of a claim *on a topic*).

### F14 — measurement (source file: `findings/F14.md`)

- **MultiAgentBench's coordination KPI is the most transferable metric definition for a room**: per-agent `n_j` = milestones contributed; `KPI_j = n_j / M`; `KPI_overall = (1/(N·M))·Σ_j n_j`. Coordination Score `CS = mean(Communication Score, Planning Score)` (5-point LLM-judged, ×20). Ablations that map onto our caps: (i) protocol comparison reports **token usage alongside** task/coordination scores (graph best, tree worst = high tokens, lowest TS and CS); (ii) agent-count ablation 1→3→5→7: **overall KPI DECREASES with more agents** while CS improves 1→3 then degrades; (iii) iteration ablation: TS/CS rise 1→7 iterations then drop sharply at 10, attributed to "communication overhead or conflicting directives emerging over prolonged interactions"; (iv) group discussion scored worst. https://arxiv.org/html/2503.01935v1 — **primary**
- **τ-bench's pass^k** = probability all k i.i.d. trials succeed, unbiased estimator `pass^k = E[C(c,k)/C(n,k)]`; reported gpt-4o function-calling `pass^1` = 61.2% τ-retail / 35.2% τ-airline, **falling below 25% at pass^8 on retail** — i.e. reliability-under-repetition is the metric that catches coordination flakiness. https://arxiv.org/html/2406.12045v1 — **primary**
- **"The Collaboration Tax" (EMNLP 2026 Main) — the strongest published evidence for the GUIDANCE track.** `tax(M,T) = s_solo-full(M,T) − s_homo(M,T)`; the mechanism is a 4-stage cascade: **L1 Grounding** (ungrounded claims, strict necessary condition), **L2 Querying** (did not ask the partner), **L3 Integration** (no explicit combined-state message — strongest single predictor), **L4 Re-derivation**; one system-prompt clause per stage **closes 38.3% ± 14.1% of the tax at zero mechanical cost**. Weakest models lose ~half their solo success to coordination. https://arxiv.org/html/2608.22152v2 (per F14) — **primary** — **but dyadic (N=2); the authors state N≥3 is unstudied, and our room is N=32.**
- **The noise floor is the bar any change must clear (2606.20695, KDD 2026 workshop).** Configuration-equivalent (coordination-inert) protocols differ by **[−3, +18] pp** across two n=100 seeds, pooled CI **[−2, +12] pp**; the largest single-seed contrast **+18 pp (p_corr=0.012) did not reproduce** at the second seed (−3 pp, p_corr=1.0); **7 of 10** recent multi-agent coordination papers report headline gains *below* this envelope. Proposed minimum reporting protocol: **coordination-active pass^k** = pass^k restricted to trials where the coordination mechanism was logically active. https://arxiv.org/abs/2606.20695 — **primary**
- **MAST (14 failure modes, 1,642 traces, 7 frameworks) — the failure taxonomy to instrument against.** Category-1 (system design) modes sum **44.2%**; category-2 (inter-agent misalignment) modes sum **32.35%** (task derailment 7.4%, reasoning/action mismatch 13.2%, proceeded with wrong assumptions 6.8%, conversation reset 2.2%, ignoring another agent's input 1.9%, information withholding 0.85%). https://arxiv.org/html/2503.13657v3 (per F14) — **primary**
- **TeamBench** — role separation enforced by OS isolation; **Teamwork Necessity Index** `TNI = (S_team − S_restricted) / max(ε, S_oracle − S_restricted)`; LLM Verifiers **false-accept 49.4%** of failing submissions (Wilson CI [45.9, 52.9], n=1,083); and "No-Verify and Full Team tie on average (0.592)", i.e. the verification role was adding overhead rather than quality. https://arxiv.org/abs/2605.07073 + https://teambench.github.io/ — **primary**
- **CoCoBench** scores four constructs — **task allocation, sequential ordering, mutual exclusion, handoff coordination** — motivated by "duplicated work, violations of ordering constraints, resource contention, and desynchronized handoffs"; "coordination ability is highly construct-specific". https://arxiv.org/abs/2608.28266 — **primary** (our failure surface is exactly these four).

- **First-party swarm tracing exists** (OpenAI Agents SDK traces handoffs automatically, `handoff_span(from_agent, to_agent)`, `custom_span`; Arize Phoenix / Langfuse give trace→span trees with OpenInference kinds Agent/Tool/LLM/Chain/Retriever). https://openai.github.io/openai-agents-python/tracing/ ; https://arize.com/docs/phoenix/tracing ; https://langfuse.com/docs/observability/features/agent-graphs — **primary**
- **F14's computability verdict for our room (16 metrics, formulas + fields).** **Computable now (Y):** orphan/expired-claim rate (`#release{reason:"expired"} / #claim`), claims-per-post (`#claim/#msg`, per-agent too), rework rate (same-agent re-claim / distinct resources claimed — the exact DORA "unplanned remediation" construction), resource idle-gap / handover-gap (the closest analogue of Google's review/merge wait pair), duplicate-overlapping-claim rate (**Y-with-caveat**). **Not computable (N) — and these are the important ones:** *wait outcomes* (wait_for_claim results are tool results, never log records; the waiter queue is in-memory), *delivery events / tier assignment* (tier is computed per viewer at delivery time and never stored → **tier distribution, T0 wake rate, per-agent unread lag, findings-read are all unmeasurable**), *read receipts / cursors* (only the session's own cursor is persisted outside the log), *member leave* (the schema permits `member{action:"leave"}` and `release{reason:"aborted"}` but **no call site emits either**, so agent death mid-lease is invisible except as a later expiry/reclaim), *coordination tokens per turn* (no token counts, no turn boundaries), *task success / outcome* (no grader). **The load-bearing caveat:** a **failed claim appends nothing** (first-writer-wins returns the current holder and expiry), so contention attempts and duplicate-work attempts are **structurally invisible**; and there is **no way to build a coordination-active subset**, which is exactly the filter the noise-floor protocol requires. → **Four missing record kinds: `contended`, `delivered` (with tier), `wait` (with outcome + grant ts), `member{action:"leave"}`.**

### F15 — guidance vs retrieval (source file: `findings/F15.md`)

## Conflicting evidence

1. **Anthropic's token multiplier: 15× (2025) vs 3–10× (2026).** Not a contradiction — different baselines: 15× is **vs chat**, 3–10× is **vs single-agent** for equivalent tasks. Both first-party. **Resolution: never cite "15×" without "vs chat"; use the 2026 figure for per-task overhead and the 2025 figure for chat-vs-agent context cost.** (F14)
2. **"Anthropic says parallelization speeds research up (up to 90%)" vs "multi-agent systems often take longer overall than single-agent systems".** Both Anthropic. **Resolution: 90% = parallel tool calls / parallel subagents on research queries; "longer overall" = total end-to-end elapsed including coordination.** Per Anthropic, "the primary benefit of parallelization is thoroughness, not speed" — so a room should report throughput *and* elapsed separately. (F14)
3. **MAST's category share.** The noise-floor paper asserts MAST attributes **36.94%** of failures to inter-agent coordination and calls it "the single largest category". **MAST's own table contradicts that**: category 1 (system design) sums **44.2%** > category 2 (inter-agent) **32.35%**. **Winner: MAST (primary).** Prefer the six primary mode percentages and drop the "36.94% / largest category" claim. (F14; F15 reaches the same paper via the noise-floor route.)
4. **Noise floor vs published coordination gains.** The noise-floor protocol measures a [−3, +18] pp paired gap between *configuration-equivalent* (coordination-inert) protocols and finds 7 of 10 published coordination gains below the envelope — directly undercutting MultiAgentBench, TeamBench, CoCoBench, ProtocolBench and the Collaboration Tax paper, none of which ran a paired control. **Reconciliation offered by the authors: the comparison is heterogeneous and "any individual row may be entirely real in its original setting", but a same-model paired replication is untested.** **Not resolvable by us; the operative consequence is that OUR report must require a paired, coordination-active protocol before claiming any improvement.** (F14, F15 — both cite 2606.20695; the numbers agree: two seeds +10 pp and 0 pp, pooled CI [−2, +12], largest single-seed +18 pp did not reproduce at −3 pp.)
5. **Merge-conflict rates across populations.** 0.2% (humans, PR scenarios, VSS+19) vs 27.67% (AI-agent PRs, AgenticFlict) vs 41.7% cross-agent / 19.8% intra-agent (co-active PR replay). **Different denominators (merge scenario vs PR vs co-active pair) — do not blend or average.** For our plugin, the relevant comparator is the **cross-agent vs intra-agent gap**, since our agents are co-active on one tree. (F14)
6. **DORA 2024 (AI ↓ throughput 1.5%, ↓ stability 7.2% per 25% adoption) vs F15's guidance-gain papers (process positive, outcome null).** Not contradictory at the same level: DORA is org-level, self-reported, about AI adoption; F15's studies are per-task artifacts. But it does mean **no guidance effect may be claimed to improve delivery outcomes**. (F14, F15)
7. **Google FSE'22: measured review wait time is NOT causally linked to productivity (p50 p=0.875) while perceived slowness IS (p=0.004).** **Resolution: report a perception/interruption proxy (T0 interrupts to the holder, wait timeouts) alongside the wait-time number; a bare wait-time metric may be measuring noise.** (F14)
8. **MultiAgentBench's own coordination score does not track task score** (Llama-3.1-70B: CS 75.00 with TS 0.21 on Minecraft). **Consequence: a room that reports only coordination health will not predict task success — the report must pair coordination metrics with an outcome metric.** (F14)

## Gaps

- **No primary study ablates a shipped *coordination playbook* vs none inside a shared room**, with a noise-floor-corrected, coordination-active protocol. Closest analogues measure generic context files (2602.11988, 2607.27250), Skills in non-coordination domains (2602.12670), or system-level protocol+monitoring (2605.07935). **Nothing measures a coordination playbook.**
- **No primary evidence whatsoever on agents reading *coordination* literature at runtime.** The literature-search evidence is about content QA (OpenScholar, PaperQA2) or about agents failing at deep literature discovery (AutoResearchBench 9.39%; AI-Scientist's "poor novelty assessments", hallucinated numbers). **The "agents read papers at runtime" track has no supporting primary evidence in either direction — it is an unmeasured idea, not a rejected one.**
- **No primary source measures the cost of INTERRUPTIONS in an agent swarm** — nobody publishes a "cost per interrupt". Our T0 wake+steer budget is an unmeasured design choice. Nearest signals are qualitative (Anthropic's "distracting each other with excessive updates") and the noise-floor protocol's "per-match injection noise (mean 2.77 events/trial)".
- **No primary work measures "agent time" as distinct from wall-clock.** METR deliberately refuses to publish agent completion time; Google's active-vs-wall-clock coding-time split is the closest construct. Any "agent time" metric must be labelled as our construction.
- **Nobody publishes a benchmark for a bus-shaped coordination substrate** (append-only log + claim leases + tiered delivery). Every coordination benchmark assumes turn-taking, message-addressed, or container-isolated substrates. The nearest analogue is the ET-MCP negative-knowledge store inside the noise-floor protocol, itself unpublished.
- **Four room record kinds are missing** (`contended`, `delivered`+tier, `wait`+outcome, `member{leave}`) → contention, duplicate-work attempts, tier distribution, findings-read, wait productivity, true last-agent-standing, and the **coordination-active subset** are all unmeasurable today. Largest measurement gap; it is a **mechanics** gap.
- **Citation corrections carried out (do not repeat the originals):** "Holt 1970 *Deadlock Detection Using Wait-for Graphs*" **does not exist** — the real paper is Holt, *Some Deadlock Properties of Computer Systems*, ACM CSUR **4(3):179–196, 1972** (verified against DBLP's full 1970 CSUR vol-2 TOC); "Richardson 1988 *Sagas*" **does not exist** — the original is Garcia-Molina & Salem, SIGMOD 1987 / Princeton CS-TR-070-87.

## Cluster verdict

1. **MECHANICS is the best-evidenced track, and F13 names the exact gaps in priority order:** (a) **fencing token enforced at the write path** — our `post` is unconditional, so the claim board is an *efficiency-only* lock today (Kleppmann's efficiency-vs-correctness split); (b) **renewal/heartbeat** — a live-but-slow agent currently loses its lease at 300 s (Chubby KeepAlive; "timeout is only a guess"); (c) **dependency ordering** — a **wait-for graph across all three wait mechanisms** with cycle detection and grant-refusal (Coffman 2+4, Holt's cycle equivalence), because per-mechanism checks miss cross-mechanism cycles; (d) **idempotency keys** on `post`; (e) **version vectors / three-way merge** for shared-file conflict detection, not for the lease.
2. **MEASUREMENT says the same thing for a different reason: the plugin currently cannot observe its own coordination.** Four missing record kinds — `contended` (a failed claim appends nothing, so contention and duplicate work are structurally invisible), `delivered`+tier, `wait`+outcome, `member{leave}` — gate tier distribution, findings-read, wait productivity, last-agent-standing, and the **coordination-active subset** the noise-floor protocol requires; and any future gain claim must be reported against a **paired noise floor of roughly [−3,+18] pp** with a **≥15–20 pp** detectable effect, because 7 of 10 published coordination gains sit below that envelope.
3. **GUIDANCE is cheap and supported, but only in a disciplined shape.** The strongest published evidence for it is the Collaboration Tax paper (one system-prompt clause per cascade stage closes 38.3%±14.1% of the tax, zero mechanical cost) — but it is **dyadic (N=2)** and its authors say N≥3 is unstudied. Guidance reliably changes *process and cost* (24–29% wall-clock / token reductions; blind test-suite runs 3.67→1.67), **not** outcome (Khatri: correctness null; "Evaluating AGENTS.md": no success gain, **+20% cost**). SkillsBench's **+16.6 pp** is the disciplined version (on-demand, focused ≤3 modules, procedural, **curated** — self-generated skills give no benefit) and matches our own SKILL.md, which we currently *duplicate* into an always-on prompt block.
4. **RUNTIME RETRIEVAL OF COORDINATION LITERATURE: NO.** Zero primary sources support it, and the evidence against is strong and specific: retrieval amplifies distractor errors (up to 80% drops, inverse scaling with test-time compute), "retrieval harm is non-negligible", IR over 43k tools degrades task pass rate, agents score only **9.39%** on deep literature discovery, and Anthropic's own guidance says "runtime exploration is slower than retrieving pre-computed data" and "find the smallest possible set of high-signal tokens". The winning pattern is **accumulate-and-distill** (AWM +24.6/+51.1%, ACE +10.6%, Agent Skills progressive disclosure) plus **gh-aw's** shipped shape — a curated `multi-agent-research.md` "Distilled from the OpenAI CDC prompt" that *forbids* retrieval for the solution, with `patterns.md` as a router and `llms.txt` as a small index, and `work-queue.md` shipping the dependency-ordered DAG+Claim mechanics as protocol rather than guidance. **Answer: ship the protocol as a curated, Skill-shaped playbook (with the mechanics behind it enforced), and do not give agents a coordination-literature retrieval tool.**
