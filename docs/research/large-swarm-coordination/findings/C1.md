## Claims

### A. The coordination substrate in every framework is a *broadcast thread*, a *shared state object*, a *shared block*, or *artifacts* — never a lease/claim board

- **A1. No framework in this cluster ships a claim/lease/TTL/blocking-wait primitive.** AG2/AutoGen: the only ownership-like constructs are speaker-transition allow/deny lists, `Handoff`/`handoffs`, `TransitionGraph`+`AgentTarget`, and AG2-network `Resume(claimed_capabilities=[...])` (an advertisement, not a lock). / https://docs.ag2.ai/docs/user-guide/network/views_and_skills/ , https://classic.docs.ag2.ai/latest/docs/user-guide/advanced-concepts/groupchat/groupchat/ / 2026-10-20 / primary (absence, scoped to pages read) / [F1]
- **A2. CrewAI / OpenAI Agents SDK / Swarm**: every inter-agent step is mediated by an LLM turn (tool call, handoff, manager allocation) or host control flow (Flow `@listen`/`@router`, `asyncio.gather`, Swarm's single-threaded loop). No board, no lease, no TTL, no blocking wait. / https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md , https://docs.crewai.com/v1.15.28/en/concepts/collaboration / 2026-10-20 / primary (absence, scoped) / [F3]
- **A3. LangGraph**: no lease/claim, no shared cross-agent task list (`write_todos` is *per-agent* state), no "who is blocked on what", no chatter backpressure, no per-agent budgets. Verified against the complete `ErrorCode` enum (5 members, none conflict/budget-related) and the docs page inventory. / https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/errors.py , https://docs.langchain.com/oss/python/deepagents/subagents / 2026-10-20 / primary / [F2]
- **A4. smolagents ships no shared substrate at all** — the only cross-agent memory transfer in the docs is a *commented-out* manual assignment (`agent.memory.steps = previous_agent.memory.steps`). / https://huggingface.co/docs/smolagents/en/tutorials/memory / 2026-10-20 / primary / [F5]
- **A5. Nearest first-party analogues to our claim board (both are first-party, both weak):** Claude Code agent teams — shared task list, "a pending task with unresolved dependencies cannot be claimed until those dependencies are completed", "Task claiming uses **file locking** to prevent race conditions when multiple teammates try to claim the same task simultaneously", mailbox = per-agent JSON file at `~/.claude/teams/{team}/inboxes/{agent}.json`. / https://code.claude.com/docs/en/agent-teams / 2026-10-20 / primary / [F4]
- **A6.** Letta Code `Task*` board — `TaskRecord{taskId, subject, description, status(pending|in_progress|completed|deleted), owner, blocks[], blockedBy[], metadata}`, tools `TaskCreate/Get/List/Update`. Caveat verbatim from source: "**Scope: process-lifetime**" (in-memory `Map`; not durable, not cross-process, no lease/TTL, `owner` a free-form string). Dependency edges stored; no first-party doc states any agent or the harness *enforces* them. / https://github.com/letta-ai/letta-code/blob/main/src/tools/impl/tasks/store.ts , https://github.com/letta-ai/letta-code/blob/main/src/tools/schemas/TaskUpdate.json / 2026-10-20 / primary / [F5]
- **A7. Our plugin's claim board (TTL lease, explicit reclaim + log, oldest-waiter promotion) is *ahead* of every framework in this cluster.** No framework here has an exclusive, expiring, reclaimable ownership token over a resource. The nearest equivalent (Claude Code) uses OS file locks with no TTL and no reclaim semantics; Letta's is unenforced and process-lifetime. / cross-file synthesis of A1-A6 / 2026-10-20 / primary (each component traced) / [F1][F2][F3][F4][F5]
- **A8. Where frameworks *do* have shared state, it is either unbounded, blackboard-last-writer-wins, or git-versioned.** AutoGen v0.4 default context = `UnboundedChatCompletionContext` (opt-in `BufferedChatCompletionContext` / `TokenLimitedChatCompletionContext`). / https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html / 2026-10-20 / primary / [F1]
- **A9. Letta's shared memory block is the closest published blackboard, and Letta documents it as unsafe under concurrency.** Verbatim table: `memory_insert` = "**Yes (append-only)**"; `memory_replace` = "Mostly (fails if target string changed)"; `memory_rethink` = "**No (last-writer-wins)**". Anti-pattern: "Multiple agents doing `memory_rethink` on the same block simultaneously leads to lost updates." Mitigation: "Designate one agent (or sleep-time memory) as the 'owner' for heavy edits. Other agents append via `memory_insert`." Visibility is **turn-boundary**, not write-boundary. Read-only is per-block, not per-agent. / https://docs.letta.com/v1-sdk/memory/shared-memory/ / 2026-10-20 / primary / [F5]
- **A10. Letta's current answer replaces the real-time block with git:** shared memory repositories are git repos; "Every memory edit is committed to the MemFS git repository. This provides version history, conflict resolution…"; concurrent background editing uses **git worktrees**. Legacy blocks page is marked "We do not recommend building on memory blocks anymore." Net: durable + conflict-resolved but **eventually consistent, not immediately consistent**. / https://docs.letta.com/concepts/shared-memory/ , https://docs.letta.com/concepts/memfs/ / 2026-10-20 / primary / [F5]
- **A11. Anthropic's answer to "telephone game" is *artifacts*, not messages.** "Subagent output to a filesystem to minimize the 'game of telephone'… Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead from copying large outputs through conversation history." Subagent returns a "condensed, distilled summary of its work (often 1,000-2,000 tokens)" after "tens of thousands of tokens" of exploration. / https://www.anthropic.com/engineering/multi-agent-research-system , https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents / 2026-10-20 / primary / [F4]

### B. Strongest convergent finding: every system that *wins* attributes the win to a **designated router/orchestrator**, not to peers inferring structure

- **B1. Cross-framework synthesis (F6, primary-sourced):** MetaGPT = fixed SOP pipeline; ChatDev = strict 2-agent chain; AgentVerse = solver/reviewer or aggregation function; Magentic-One = Orchestrator + 5-field progress ledger. The only framework optimising *peer-to-peer* topology is GPTSwarm, and its optimisation target is a **graph edge set** ("who may talk to whom"). / https://arxiv.org/abs/2308.00352 , https://arxiv.org/abs/2307.07924 , https://arxiv.org/abs/2308.10848 , https://arxiv.org/abs/2411.04468 , https://arxiv.org/abs/2402.16823 / 2026-10-20 / primary / [F6]
- **B2. AutoGen's own successor architecture makes the hub authoritative:** "The hub is authoritative. Turn-taking, state, audit, and expectation enforcement all live in the hub." / https://docs.ag2.ai/docs/user-guide/network/adapters_overview/ / 2026-10-20 / primary / [F1]
- **B3. Anthropic's Claude Code agent teams: the lead is fixed and non-transferable** — "Lead is fixed: the main session is the lead for its lifetime. You can't promote a teammate to lead or transfer leadership." "No nested teams: teammates cannot spawn their own teammates." / https://code.claude.com/docs/en/agent-teams / 2026-10-20 / primary / [F4]
- **B4. LangGraph's supervisor pattern keeps all routing through one agent** ("centralized control (all routing passes through the main agent)"); the Router pattern uses "a dedicated routing step". / https://docs.langchain.com/oss/python/langchain/multi-agent/subagents , https://docs.langchain.com/oss/python/langchain/multi-agent/router / 2026-10-20 / primary / [F2]
- **B5. CrewAI's hierarchical manager is itself just an agent with two hard-wired tools** (source: `_create_manager_agent()` builds `Agent(role="Crew Manager", …, allow_delegation=True)`; for a user-supplied `manager_agent` the code forces `allow_delegation=True` and clears its tools). / https://github.com/crewAIInc/crewAI/blob/main/lib/crewai/src/crewai/crew.py / 2026-10-20 / primary / [F3]
- **B6. The measured coding-agent result points the same way:** CAID (manager + dependency graph + per-agent git worktrees) beats a single agent by **+25.6% absolute on PaperBench** and **+14.7% on Commit0**; PaperBench Table 3: single agent **57.2** / CAID worktree isolation **63.3** / multi-agent *soft isolation* (shared workspace, non-overlap by instruction only) **55.5** — i.e. flat parallel agents that must talk **score below one agent**. - **B8. - **B10. OpenHands' own 2024 first-party position (pre-empting the whole cluster):** "Don't Sleep on Single-agent Systems" — multi-agent costs (i) getting the structure right (a specialised agent lacks its peers' tools), (ii) preserving context (summarising handoffs loses information), (iii) maintainability. Prescription: one generalist + one concatenated tool/action space. / https://www.openhands.dev/blog/dont-sleep-on-single-agent-systems / 2026-10-20 / primary / [F7]

### C. The ledger / structured-status-object primitive is real, schema-checked, and load-bearing (candidate MECHANICS primitive)

- **C1. Magentic-One has TWO ledgers, not three.** Task ledger = four sections (GIVEN OR VERIFIED FACTS / FACTS TO LOOK UP / FACTS TO DERIVE / EDUCATED GUESSES) + the plan. Progress ledger = per-turn JSON with exactly five keys: `is_request_satisfied`, `is_in_loop`, `is_progress_being_made`, `next_speaker`, `instruction_or_question`, each as `{reason, answer}`. There is **no "fact ledger" class** — "facts" is a *section* of the task ledger, produced by a separate closed-book pre-survey call. / https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py / 2026-10-20 / primary (first-party code) / [F6] *(F1 independently corroborates the two-ledger structure from the paper; F6's source read wins on the exact schema.)*
- **C2. The ledger is validated at runtime, not just prompted.** `LedgerOrchestrator.update_ledger()` parses the model output as JSON, checks a required-key list, feeds the literal `KeyError: '<key>'` back to the model, retries up to `max_json_retries = 10`, then raises `ValueError("Failed to parse ledger information after multiple retries.")`. / https://raw.githubusercontent.com/microsoft/autogen/v0.4.4/python/packages/autogen-magentic-one/src/autogen_magentic_one/agents/orchestrator.py / 2026-10-20 / primary / [F6]
- **C3. Stall detection + escalation are the loop-guard:** stall = `is_in_loop == True` **or** `is_progress_being_made == False`; on exceeding the counter → rewrite facts + new plan → broadcast `ResetMessage` to all agents → rebroadcast plan → agents' contexts cleared. Shipped defaults: `LedgerOrchestrator(max_rounds=20, max_stalls_before_replan=3, max_replans=3)`. / same source / 2026-10-20 / primary / [F6]
- **C4. The ledger's marginal value (self-reported, the single most load-bearing number for this primitive):** on GAIA validation, replacing the Orchestrator with AutoGen's plain `GroupChat` speaker-selector — "eliminating **both ledgers**, planning, progress tracking, loop detection, and explicit instructions to other agents" — drops performance by **31%**. Removing any single worker drops 21% (Coder/ComputerTerminal) to 39% (FileSurfer). / https://arxiv.org/abs/2411.04468 §5.3 / 2026-10-20 / primary (self-reported; in-house baseline, same authors) / [F6]
- **C5. Caveat on C4's own honesty:** the plan is advisory, not binding — "neither the Orchestrator nor the other agents are required to follow it exactly"; and the authors disclose WebArena validation→test over-fitting (35.1% → 30.5%) and that the leaderboard "is based on self-reported results". / https://arxiv.org/abs/2411.04468 §4.1, §5.1-5.2 / 2026-10-20 / primary (self-reported) / [F6]
- **C6. The same idea appears as a *protocol over message types*, not prose.** MetaGPT: agents "communicate through documents and diagrams (structured outputs) rather than dialogue"; shared global message pool + publish/subscribe; each agent subscribes by role; "an agent activates its action only after receiving all its prerequisite dependencies". Code confirms: `Environment.publish_message` fans out by address, each role buffers into a private `MessageQueue`, `Role._watch` populates `rc.watch` (action tags) used by `memory.get_by_actions(self.watch)`. / https://arxiv.org/abs/2308.00352 §3.2 , https://raw.githubusercontent.com/FoundationAgents/MetaGPT/main/metagpt/environment/base_env.py , https://raw.githubusercontent.com/FoundationAgents/MetaGPT/main/metagpt/roles/role.py / 2026-10-20 / primary / [F6]
- **C7.** ChatDev's discipline is a *mechanical subtask grammar*: every subtask is exactly two agents; the assistant must ask for more detail before concluding (communicative dehallucination); a subtask ends "after two unchanged code modifications or after 10 rounds of communication"; consensus is marked with the literal `<SOLUTION>`. Rationale for the shape: "The dual-agent communication design **simplifies communications by avoiding complex multi-agent topologies**". / https://arxiv.org/abs/2307.07924 §3.1-3.2, §4 / 2026-10-20 / primary / [F6]
- **C8.** LangGraph's analogue is the *per-key reducer*: each shared-state key has an independent merge function; with no reducer a key is overwritten. `/ https://docs.langchain.com/oss/python/langgraph/graph-api / 2026-10-20 / primary / [F2]`
- **C9. The transferable form (synthesis, each component traced):** a **per-turn, schema-checked status object** (who acts now / is it satisfied / is it looping / is progress being made / what instruction) **plus** a **separate, longer-lived epistemic store** (verified / to-look-up / to-derive / guesses) **plus** structured artifacts written to a shared store rather than re-broadcast. / https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py , https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / primary + synthesis / [F6][F4]

### D. Cost: the only sourced multipliers, and what they do and don't cover

- **D1. Anthropic 2025 (VERBATIM):** "agents typically use about **4×** more tokens than chat interactions, and multi-agent systems use about **15×** more tokens than chats." Multi-agent = Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by **90.2%** on our **internal** research eval". / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / primary / [F4] *(F2 and F7 cite the same post — one source, not three corroborations.)*
- **D2. Anthropic 2026 (VERBATIM, different denominator):** "multi-agent implementations typically use **3-10x** more tokens than single-agent approaches for equivalent tasks. This overhead stems from duplicating context across agents, coordination messages between agents, and summarizing results for handoffs." Also: "multi-agent systems often take longer overall than single-agent systems… The primary benefit of parallelization is thoroughness, not speed." / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / primary / [F4]
- **D3. The only controlled first-party multi-agent-vs-single-agent measurement on a public benchmark is Anthropic's Opus 4.8 system card §8.11 (BrowseComp, 1266 problems):** "Orchestrator with Blocking Subagents reached our highest score of **88.5%**"; "the five-agent team (**85.4%**) also exceeded the single-agent baseline (**84.3%**)"; the five-agent team under a 5M-token total limit "scored higher than a single agent with a 10M-token limit (85.4% vs. 84.3%), using just **20% of the latency**"; and — the load-bearing caveat — "On the easiest problems with 100% pass rate, the five-agent team delivered **no speedup**, likely because coordination overhead roughly offset the gains from parallelism. On the hard tail where the pass rate is below 0.5, the median speedup is around **3×**." / https://www-cdn.anthropic.com/0b4915911bb0d19eca5b5ee635c80fef830a37ea.pdf §8.11 / 2026-10-20 / primary / [F4]
- **D4. Token usage, not agent count, drove Anthropic's win:** "token usage by itself explains **80%** of the variance" in BrowseComp performance; "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7". / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / primary / [F4]

### E. Documented failure modes — the ones a shared room will actually hit

- **E1. Duplicate work from missing boundaries** (Anthropic) → B9. **E2. Lost updates on a contended shared store** (Letta) → A9. **E3. Telephone-game distortion** (MetaGPT's stated motivation for structured documents) → C6. **E4. Runaway fan-out** ("spawning 50 subagents for simple queries", "scouring the web endlessly for nonexistent sources", "distracting each other with excessive updates") → Anthropic 2025 / 2026 / F4.
- **E5. Sub-agent failure laundered into a confident answer (smolagents):** "When a sub-agent used as a managed agent hits a tool error and loops, or exhausts `max_steps`, `MultiStepAgent.run()` never raises: it falls back to a best-effort, LLM-generated answer via `provide_final_answer()`… The manager has no way to tell task completion from task failure." / https://github.com/huggingface/smolagents/issues/2747 / 2026-10-20 / primary / [F5]
- **E6. Sub-agent memory silently wiped on every delegation (smolagents):** `run(..., reset: bool = True)` is the default and `reset` never reaches `run()` from `execute_tool_call`; upstream issue #1695 "the sub-agent's memory will be cleared"; fixes #2023/#2244 still open. / https://github.com/huggingface/smolagents/issues/1695 , https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py / 2026-10-20 / primary / [F5]
- **E7. Silent parallel-collision (smolagents):** calling the same managed agent twice in one step in parallel shares one instance's state and "all calls produce identical or very similar results" (issue #1781); mechanism confirmed in source (`ThreadPoolExecutor(self.max_tool_threads)` dispatch). / https://github.com/huggingface/smolagents/issues/1781 / 2026-10-20 / primary / [F5]
- **E8. Misrouting degrades into a model-visible string, not a failure (CrewAI):** delegation matches the `coworker` string to `agent.role`; a miss returns a **string** error ("coworker mentioned not found…") instead of raising. / https://github.com/crewAIInc/crewAI/blob/main/lib/crewai/src/crewai/tools/agent_tools/base_agent_tools.py / 2026-10-20 / primary / [F3]
- **E9. Ambiguous addressing (Swarm / OpenAI):** Swarm "If an `Agent` calls multiple functions to hand-off to an `Agent`, **only the last handoff function will be used**"; AutoGen `Swarm` docs warn parallel tool calling can produce multiple handoffs → "unexpected behavior" (mitigate: disable `parallel_tool_calls`); Letta's tag-broadcast tool appends a lowercased copy of the message "to make downstream matching deterministic across LLM capitalization choices" — a documented hack for non-deterministic routing. / https://github.com/openai/swarm/blob/main/README.md , https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/swarm.html , https://github.com/letta-ai/letta/blob/archive/letta/functions/function_sets/multi_agent.py / 2026-10-20 / primary / [F3][F1][F5]
- **E10. Multi-agent worse than solo, measured (AgentVerse):** GPT-4 MGSM solo **96.0** vs group **95.2**; GPT-3.5 MGSM solo 82.4 vs group 80.8; attributed to "incorrect agent feedback in math reasoning". / https://arxiv.org/abs/2308.10848 §3.1-3.2 / 2026-10-20 / primary (self-reported) / [F6]
- **E11. Verification subagents rubber-stamp:** "The most significant failure mode for verification subagents is marking outputs as passing without thorough testing"; Anthropic's mitigation is a literal instruction: "You MUST run the complete test suite before marking as passed". / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / primary / [F4]
- **E12. Destructive emergent behaviour in open societies (AgentVerse, Minecraft):** "an agent occasionally bypasses the procedure of gathering raw materials and resorts to harming other agents or destroying an entire village library to acquire the necessary materials"; authors call preventing this "a critical area for future research". / https://arxiv.org/abs/2308.10848 §4 / 2026-10-20 / primary (self-reported observation) / [F6]
- **E13. ## Conflicting evidence

1. **Multi-agent: big win vs. not worth it.** Sources: Anthropic 2025 (+90.2% internal eval, D1); Anthropic 2026 ("teams invest months… improved prompting on a single agent achieved equivalent results", I5); Anthropic system card (five-agent team 85.4% vs single 84.3%, no speedup on easy problems, D3); OpenAI's guide (I1); OpenHands 2024 (I9); OpenHands/CAID 2026 (+25.6%/+14.7%, I10); AgentVerse (group < solo on math, E10). **Resolution: not a contradiction — different conditions.** The system card's own decomposition is the reconciling document: the win is on the *hard tail* of parallelizable, context-isolatable tasks, and coordination overhead cancels the gain on easy/short/shared-context tasks. Anthropic 2026 supplies the vendor's own rule of thumb (three conditions where it wins; "outside these situations, the coordination costs typically exceed the benefits"). **For the report, the 90.2% figure must be cited as (a) relative improvement, (b) on Anthropic's internal eval, (c) not BrowseComp** — the system card numbers are the only reproducible ones.
2. **Token multiplier: 15× vs 3-10×.** Different denominators: 15× = multi-agent vs *chat*; 3-10x = multi-agent vs *single agent* (D1, D2). **Neither is wrong; quoting 15× as "vs single agent" is wrong.** Both are Anthropic primary, one source pair.
3. **"Faster" vs "slower overall."** Anthropic 2025: parallelisation "cut research time by up to 90%". Anthropic 2026: "multi-agent systems often take longer overall… The primary benefit of parallelization is thoroughness, not speed." CAID: "wall-clock runtime is not substantially reduced despite parallel execution." **Resolution: the system card wins** — latency gain lives on the hard tail (median ~3× where pass rate < 0.5), none on easy problems (D3). Report: parallelism buys *thoroughness*, not speed.
4. **Async vs blocking subagents.** Anthropic 2025 says sync is the bottleneck (E14); the 2026 system card measures async-subagents as *intermediate* (improves on single agent, smaller margin than the three-agent team). LangGraph keeps inline subagents blocking and ships async as out-of-band process machinery (`start_async_task` / `check_async_task` / `update_async_task` / `cancel_async_task` / `list_async_tasks`, built on the Agent Protocol; `task_id` = subagent's thread id); OpenHands' `TaskToolSet` is "synchronous — the parent blocks until the sub-agent finishes" and is "designed for sequential blocking tasks"; Letta ships background subagents with completion notification and *blocks* foreground polling. **Resolution: the system card is the only measured comparison, so it wins on ranking (async ≈ between); the framework docs win on mechanics.** Note this is the single clearest gap our room could occupy: Anthropic's named bottleneck ("the lead agent can't steer subagents, subagents can't coordinate") is precisely a T0-interrupt + wait primitive.
5. **Does a flat room beat a designated router?** Router-evidence: B1-B8 (F6 synthesis, Anthropic's fixed lead, AG2 network hub, LangGraph supervisor/router, CrewAI manager agent, CAID manager, GPTSwarm's role-precondition). Flat-evidence: LangGraph's "not every complex task requires this approach" (I3), OpenHands 2024 (I9), OpenCollab's cheapest-is-single-agent (E13), Letta's fan-out with "no shared scratchpad" (H4), and our own plugin's flat design. **Resolution: the router wins on every *measured* result (Magentic-One -31% without ledgers, CAID +25.6%, Anthropic +90.2%, GPTSwarm +2.1% only after role differentiation); the flat model only wins on *cost* and on tasks where the whole point is that agents are peers.** This is the most consequential conflict in the cluster: our plugin's flat room + claims is a router-less topology, which the literature says must be compensated for with (i) role specialisation, (ii) a structured per-turn status object, and (iii) an isolation substrate — or it underperforms a single agent.
6. **"Parallel instances are simpler and often better" (the assignment's headline) vs "coordinated multi-agent wins."** OpenAI/Asana (FI5) and OpenHands' parallel-refactor recipe (FI6) succeed with *no* coordinating agent, but both rely on **separate copies / branches / human review**. CAID shows parallel agents that *share* a workspace score **below a single agent** (55.5 vs 57.2) and that coordination costs more API tokens without cutting wall-clock. **Resolution: both are right under different conditions** — the claim holds when work is *isolatable* and the integrator is git/tests/human; it fails when agents co-edit one tree and must talk. There is **no** first-party controlled "parallel instances vs one coordinating instance" ablation (F7 gap); the headline claim rests on practitioner write-ups, not measurement.
7. **LangGraph: deterministic ordering vs. no ordering guarantee.** Design blog: update application order "doesn't depend on which one started or finished first… ensures that the execution order and latency of each node never influences the final output". Current docs: "updates from a parallel superstep may not be ordered consistently. If you need a consistent, predetermined ordering… you should write the outputs to a separate field in the state together with a value with which to order them." **Resolution: docs win** — runtime determinism ≠ user-visible ordering guarantee; users must sort explicitly. (F2)
8. **LangGraph conflict handling: fail loudly vs. arbitrate.** RFC #7907 (cross-node write-intent registry, admission policies) was closed with "langgraph already handles the case this targets: parallel writes to a plain (LastValue) key in one step raise InvalidUpdateError instead of silently keeping one." **Resolution: the maintainer wins** — LangGraph deliberately *fails* on conflicting parallel writes and has no arbitration, admission control, or lease. The teaching point for us: a shared room should pick fail-loud vs. arbitrate deliberately; our claim board silently *prevents* conflict rather than detecting it, and there is no shared-resource conflict detector at all.
9. **Magentic-One stall threshold: "≤ 2" (paper) vs `max_stalls_before_replan=3` (code).** **Not a contradiction** — the paper describes their experimental setting, the code ships a default. Cite the code for the shipped default, the paper for the experiment. (F6)
10. **Magentic-One ledgers: two vs three.** The assignment brief said "task ledger/fact ledger/progress ledger". **Source wins: there are two** — task ledger (4 fact sections + plan) and progress ledger (5-field per-turn JSON); "fact ledger" is not a class. (F6)
11. **OpenAI guardrails: "enforce shared SDK guardrails in one place" vs. per-boundary coverage.** `multi_agent.md` sells the manager pattern partly on shared guardrails; `guardrails.md` says input guardrails run only for the *first* agent, output guardrails only for the *last*, tool guardrails "do not apply to the handoff call itself", and hosted tools bypass the pipeline. **Resolution: mechanics win** — a multi-agent chain is *less* covered by one guardrail than the pattern table implies. 12. **OpenHands 2024 (one agent) vs OpenHands-hosted CAID 2026 (manager + worktrees).** **Resolution: the 2026 measured result wins on evidence** (the 2024 piece is an argument without a measurement), but note the 2026 result *requires* isolation + a manager, so it does not vindicate flat multi-agent.

## Gaps

- **No first-party controlled "parallel independent instances vs. one coordinating instance" ablation** (F7). CAID's baseline is *single* agent, not parallel-isolated; the Asana write-up has no counterfactual. The assignment's headline claim is practitioner testimony, not measurement.
- **No primary source measures a *shared-message-room* coordination substrate** (a blackboard + claims + tiers) against a router-based baseline. Nothing in F1-F7 evaluates the plugin's own shape. Any room-level ledger/claim primitive derived from this cluster needs its own measurement.
- **No primary source measures ledger/SOP discipline inside a flat, orchestrator-free room** (F6). The ledger evidence (Magentic-One -31%) is measured *with* an orchestrator. Our topology is the untested one.
- **No per-primitive overhead accounting anywhere.** Every system reports end-to-end token/time cost; nothing isolates the cost of the ledger, the claims board, the summaries, or the tiering from the cost of the work. (This is the measurement gap the report should name.)
- **No source measures whether a shipped *playbook* improves swarm coordination** (as opposed to single-agent quality). Anthropic's playbook evidence is about *one* lead agent's delegation quality; OpenHands' skills evidence is single-agent, 3 tasks, 5 models, and includes a regression. Guidance-track evidence is currently the weakest link in the whole cluster.
- **No first-party study of a shared, agent-writable ledger as a prompt-injection / tampering surface** (F6). Magentic-One warns about webpage injection generally; nothing analyses whether one agent can poison a shared room's status object.
- **Absence claims are scoped.** "No claim/lease/TTL/blocking-wait primitive" (A1-A4) was verified against the pages/files each worker read, not exhaustively across every framework repo; GitHub raw/API was unreachable from F1's host and F7 found no SWE-agent multi-agent variant. F2 could not crawl the JS/TS docs mirror or the Agent Protocol spec.
- **Anthropic's 90.2% is not reproducible** (no task set, no rubric, no n) and the 15× has no stated chat baseline or distribution. The system card's BrowseComp figures live in PDF figures, not text tables, and the exact five-agent token multiplier is "unverified" from text.
- **Open-source "fleet of agents" paper absent** (F7) and **Letta's v1 group/manager layer is retired/archived** (F5: `ManagerType.swarm` is a declared-but-unimplemented enum member; the `supervisor` manager body is commented-out scaffolding) — so Letta's "groups" cannot be cited as a shipped swarm coordinator.
- **Not reviewed:** Anthropic's "How we built Claude Managed Agents" post and `advanced-tool-use` (the 85% token-reduction figure is only cited second-hand in F4); LangGraph's `stores` semantics as a cross-agent substrate; CrewAI AMP/platform internals; OpenAI Agents SDK JS/TS and realtime/voice multi-agent; the Agent Protocol spec.
- **The plugin has no coordination-quality baseline** (only a discovery rate of 75.0-85.7% over 16 trials). Nothing in the cluster gives a target number for duplicate-work rate, wait-time, or coordination-token share — the report must derive its own metrics and label them as the report's model, not a framework claim.

## Cluster verdict

1. **Our plugin is differentiated on exactly one axis and behind on three.** Nobody in F1-F7 ships an exclusive, expiring, reclaimable claim/lease token (A1-A7); nobody ships a tiered-attention interrupt channel (F4's `SendMessage`/`Wait for Message` are the nearest, and Anthropic names "the lead agent can't steer subagents" as its production bottleneck — E14). But every framework that *wins* does it with a **designated router**, a **schema-checked per-turn status object + durable epistemic store** (Magentic-One's two ledgers, C1-C4), and an **isolation substrate** (worktrees / separate copies, FI1-FI8) — all three of which a flat room does not have by default.
2. **The single strongest, cheapest candidate is the ledger**: a per-turn, schema-validated "who acts / satisfied / looping / progress / instruction" record plus a separate "verified / to-look-up / to-derive / guessed" store. It is the only coordination mechanism in this cluster with a measured ablation (Magentic-One: **-31%** when removed, self-reported) and it is implementable inside a flat room (C1-C9). The Magentic-One stall counter (`is_in_loop OR !is_progress_being_made`, with replan + context reset) is the ready-made loop-guard and escalation path our room lacks.
3. **The GUIDANCE track is weaker than the MECHANICS track on evidence, but it is the cheapest**: Anthropic ships an explicit delegation protocol (subagent-count by complexity, anti-overlap boundaries, dependency-first ordering, per-subagent tool-call budgets) and credits it with up to 90% research-time reduction — but OpenHands' own skills evaluation shows guidance is task- and model-dependent and can **regress** a model, so any playbook must ship with a no-guidance baseline (G1-G7).
4. **The costs are known and one-sided**: multi-agent ≈ **15×** chat tokens (or **3-10×** single-agent) from Anthropic, plus measured coordination overhead that *erases* the parallel gain on easy problems and can exceed the work itself (D1-D4, B8, D6). Any recommendation must state the coordination-token share explicitly, and must respect the consistent fan-out ceiling of **3-8** (FI1-H3).
5. **The AGENT-RESEARCH-RETRIEVAL track has no supporting evidence in this cluster** — no framework ships a retrieval-over-coordination-literature tool, and nothing measures whether consulting prior art improves swarm outcomes (G8). On current evidence it ranks last; a distilled in-plugin playbook plus the ledger primitive outranks it.
