# F3 — CrewAI + OpenAI Agents SDK + original Swarm

## Angle

What coordination models do CrewAI, the OpenAI Agents SDK, and original Swarm (openai/swarm) actually ship; what each says about **when** to use multi-agent vs a single agent; and what each states about **cost**. Primary sources only: vendor docs + vendor source code + OpenAI's own published engineering guide (PDF). Docs snapshot: docs.crewai.com v1.15.28, openai-agents-python `main` (2026-10-20), openai/swarm `main` (sha 6af0b4c).

## Claims

### Swarm (openai/swarm) — minimal primitives

- Swarm is explicitly experimental/educational and **superseded**: README banner says "Swarm is now replaced by the OpenAI Agents SDK, which is a production-ready evolution of Swarm… We recommend migrating to the Agents SDK for all production use cases." / https://github.com/openai/swarm/blob/main/README.md / 2026-10-20 / primary
- Swarm's entire coordination surface is two primitives: "Swarm focuses on making agent **coordination** and execution lightweight, highly controllable, and easily testable… through two primitive abstractions: `Agent`s and **handoffs**." No shared board, no claims, no leases, no blocking wait. / https://github.com/openai/swarm/blob/main/README.md / 2026-10-20 / primary
- Swarm's stated criterion for reaching for multi-agent: approaches "similar to Swarm are best suited for situations dealing with **a large number of independent capabilities and instructions that are difficult to encode into a single prompt**." (i.e. the *split* argument, never a throughput/parallelism argument). / https://github.com/openai/swarm/blob/main/README.md / 2026-10-20 / primary
- Swarm is stateless between calls: "Swarm is entirely powered by the Chat Completions API and is hence **stateless between calls**"; `client.run()` "saves no state between calls". Shared state within a call = `context_variables` (a dict mutated by tool functions, returned in `Response`). / https://github.com/openai/swarm/blob/main/README.md / 2026-10-20 / primary
- Swarm handoff mechanics: a handoff is a Python function that *returns an Agent* ("If a function returns an `Agent`, execution will be transferred to that `Agent`"); the tool call itself is the handoff signal. Multiple handoffs in one turn are lossy: "If an `Agent` calls multiple functions to hand-off to an `Agent`, **only the last handoff function will be used**." A richer `Result(value, agent, context_variables)` can update value + agent + context vars in one function. / https://github.com/openai/swarm/blob/main/README.md / 2026-10-20 / primary
- Swarm agent instructions are swapped on handoff, history is not: "Only the `instructions` of the active `Agent` will be present at any given time (e.g. if there is an `Agent` handoff, the `system` prompt will change, but the chat history will not.)" / https://github.com/openai/swarm/blob/main/README.md / 2026-10-20 / primary
- Swarm run loop (source): `while len(history) - init_len < max_turns and active_agent:` — completion → tool calls → `active_agent = partial_response.agent` → return; `max_turns` default `float("inf")`, i.e. **no default loop bound** (contrast: Agents SDK raises `MaxTurnsExceeded`; CrewAI caps `max_iter=20`). / https://github.com/openai/swarm/blob/main/swarm/core.py / 2026-10-20 / primary
- Swarm treats evaluation as the substitute for coordination guarantees: "Evaluations are crucial to any project, and we encourage developers to bring their own eval suites to test the performance of their swarms"; shipped examples carry `evals/eval_cases/*.json` and `evals/eval_results/*.json`. / https://github.com/openai/swarm/blob/main/README.md + https://github.com/openai/swarm/tree/main/examples/airline/evals / 2026-10-20 / primary
- **Correction to the assignment premise**: openai/swarm contains **no `handoffs.md` and no `routines.md`** (repo tree, 332 entries, untruncated). "Routines" exist only as example data (`examples/airline/data/routines/{baggage,flight_modification}`) and "routine" appears as a *procedure* term in OpenAI's practical guide ("When creating routines, use existing operating procedures…"). / https://api.github.com/repos/openai/swarm/git/trees/main?recursive=1 / 2026-10-20 / primary

### OpenAI Agents SDK — orchestration, handoffs, sessions, tracing, guardrails

- Two orchestration families, both endorsed: (1) LLM-decided ("uses the intelligence of an LLM to plan, reason, and decide on what steps to take") and (2) code-driven; the SDK states code orchestration "makes tasks more deterministic and predictable, in terms of **speed, cost and performance**." / https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md / 2026-10-20 / primary
- Two core patterns and an explicit "best when" rule: **Agents as tools** — "A manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`… You want one agent to own the final answer, combine outputs from multiple specialists, or enforce shared SDK guardrails in one place"; **Handoffs** — "A triage agent routes the conversation to a specialist, and that specialist becomes the active agent for the rest of the turn… You want the specialist to respond directly, keep prompts focused, or have the handoff switch the active instructions without requiring the manager to narrate the result." They can be combined (triage → handoff → specialist calls other agents as tools). / https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md / 2026-10-20 / primary
- Agents.md restates the same two patterns and adds the graph framing: manager = "A central manager/orchestrator invokes specialized sub-agents as tools and retains control of the conversation"; handoffs = "Peer agents hand off control to a specialized agent that takes over the conversation. **This is decentralized.**" / https://github.com/openai/openai-agents-python/blob/main/docs/agents.md / 2026-10-20 / primary
- Handoffs are tools to the model, and are **one-way**: "Handoffs are represented as tools to the LLM… the tool would be named `transfer_to_refund_agent`"; in the practical guide "Handoffs are a one way transfer"; receiving agent gets the conversation history and takes the next turn. / https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md + https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf / 2026-10-20 / primary
- **Guardrail scope is per-run-boundary, not per-agent**: "Input guardrails run only for the first agent in the chain. Output guardrails run only for the agent that produces the final output. Tool guardrails run on every guarded function-tool invocation"; docs explicitly tell you to use tool guardrails "when you need checks around each custom function-tool call inside the workflow" that includes managers/handoffs/delegated specialists. Tool guardrails do **not** apply to the handoff call itself. / https://github.com/openai/openai-agents-python/blob/main/docs/guardrails.md / 2026-10-20 / primary
- Guardrails are explicitly a **cost** lever, and their default is cost-negative: parallel execution "the best latency… However, if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled"; blocking execution "is ideal for **cost optimization** and when you want to avoid potential side effects from tool calls." / https://github.com/openai/openai-agents-python/blob/main/docs/guardrails.md / 2026-10-20 / primary
- Handoff payload control is first-class: `input_filter` (what the next agent sees), `input_type` (small model-generated metadata: "reason, language, priority, or summary", delivered to `on_handoff`), `on_handoff` callback, `is_enabled` (dynamic enable/disable, evaluated before the model returns handoff arguments), and beta `RunConfig.nest_handoff_history` (compacts prior history into `<CONVERSATION HISTORY>` summary segments). The docs also state the security caveat: nesting "does not redact sensitive data". / https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md / 2026-10-20 / primary
- `is_enabled`/input-type is **not** an authorization mechanism: "The callbacks control which capabilities the SDK exposes for the current run; they cannot authorize a model-generated argument or resource selection"; for handoffs with `input_type`, "perform the check at the start of `on_handoff`, before any application side effects." / https://github.com/openai/openai-agents-python/blob/main/docs/context.md + handoffs.md / 2026-10-20 / primary
- Sessions = client-managed conversation memory: "Sessions store conversation history for a specific session… eliminating the need to manually handle `.to_input_list()` between turns"; per run the SDK "retrieves the conversation history… prepends it" then persists all new items. Four documented state strategies with an explicit trade-off table (`to_input_list()` / `session` / `conversation_id` / `previous_response_id`), and "In most applications, pick one persistence strategy per conversation." Session cannot be combined with server-managed continuation in the same run. / https://github.com/openai/openai-agents-python/blob/main/docs/sessions/index.md + running_agents.md / 2026-10-20 / primary
- Tracing ships a per-workflow event record with a **grouping key for multiple traces of one conversation**: "Traces represent a single end-to-end operation of a 'workflow'… `group_id`: Optional group ID, to link multiple traces from the same conversation"; default spans cover agent/generation/function/guardrail/**handoff** spans; default trace name is the literal `"Agent workflow"`. / https://github.com/openai/openai-agents-python/blob/main/docs/tracing.md / 2026-10-20 / primary
- Loop bound is explicit and recoverable: exceeding `max_turns` raises `MaxTurnsExceeded` (`max_turns=None` disables), and `Runner` accepts `error_handlers` keyed `"max_turns"`, `"model_refusal"`, `"invalid_final_output"` to return a controlled final output. / https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md / 2026-10-20 / primary
- Human-in-the-loop is run-wide, including nested specialists: "That approval surface is run-wide, not limited to the current top-level agent. The same pattern applies when the tool belongs to… an agent reached through a handoff, or a nested `Agent.as_tool()` execution"; paused runs serialize via `RunState` and resume. / https://github.com/openai/openai-agents-python/blob/main/docs/human_in_the_loop.md / 2026-10-20 / primary
- OpenAI's explicit "when to go multi-agent" rule (vendor engineering guide, primary): "**Our general recommendation is to maximize a single agent's capabilities first.** More agents can provide intuitive separation of concepts, but can **introduce additional complexity and overhead**, so often a single agent with tools is sufficient." Split triggers named: "Complex logic" (prompts with many branches) and "Tool overload" ("Some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools"). Conclusion: "Use orchestration patterns that match your complexity level, **starting with a single agent and evolving to multi-agent systems only when needed**." / https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf / 2026-10-20 / primary
- Same guide: manager pattern "is ideal for workflows where you only want one agent to control workflow execution and have access to the user"; decentralized/handoff pattern "is optimal when you don't need a single agent maintaining central control or synthesis"; and a first-party jab at graph DSLs — declarative frameworks "can quickly become cumbersome and challenging as workflows grow more dynamic and complex, often necessitating the learning of specialized domain-specific languages", versus the SDK's "code-first approach". / https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf / 2026-10-20 / primary
- Same guide, cost/latency guidance: model choice is the main cost lever — "a simple retrieval or intent classification task may be handled by a smaller, faster model… Optimize for cost and latency by replacing larger models with smaller ones where possible"; and human intervention triggers: "Exceeding failure thresholds" and "High-risk actions". / same PDF / 2026-10-20 / primary

### CrewAI — processes, delegation, memory, planning, flows, guardrails, A2A

- Only two processes exist: "**Sequential**: Executes tasks in sequentially… **Hierarchical**: Organizes tasks in a managerial hierarchy, where tasks are delegated and executed based on a structured chain of command. A manager language model (`manager_llm`) or a custom manager agent (`manager_agent`) must be specified…". The `Process` class is an Enum restricted to those two values. / https://docs.crewai.com/v1.15.28/en/concepts/processes / 2026-10-20 / primary
- Hierarchical semantics: "Tasks are **not pre-assigned**; the manager allocates tasks to agents based on their capabilities, reviews outputs, and assesses task completion." Sequential semantics: "the output of one task serving as context for the next", customized via `Task.context`. / same page / 2026-10-20 / primary
- Peer-to-peer coordination is opt-in and tool-mediated: "When `allow_delegation=True`, CrewAI automatically provides agents with two powerful tools: **Delegate work to coworker** (`task`, `context`, `coworker`) and **Ask question to coworker** (`question`, `context`, `coworker`)." / https://docs.crewai.com/v1.15.28/en/concepts/collaboration / 2026-10-20 / primary
- Delegation is **role-name keyed and soft-failing** (source): `BaseAgentTool._execute` matches the `coworker` string to `agent.role` case-insensitively/whitespace-normalized; a list-form value `"[a, b]"` is truncated to the first element; a miss returns a **string** error ("coworker mentioned not found, it must be one of the following options: …") instead of raising — i.e. misrouting degrades into a model-visible message, not a failure. Execution creates a fresh `Task` with `expected_output=I18N_DEFAULT.slice("manager_request")` and calls `agent.execute_task(task, context)`. / https://github.com/crewAIInc/crewAI/blob/main/lib/crewai/src/crewai/tools/agent_tools/base_agent_tools.py / 2026-10-20 / primary
- The hierarchical manager is itself just an agent with two hard-wired tools (source): `_create_manager_agent()` builds `Agent(role="Crew Manager", goal="Manage the team to complete the task in the best way possible.", backstory="You are a seasoned manager with a knack for getting the best out of your team… ability to delegate work to the right people, and to ask the right questions…", allow_delegation=True)`; for a user-supplied `manager_agent` the code **forces `allow_delegation = True`** and **clears its tools** (`manager.tools = []`). / https://github.com/crewAIInc/crewAI/blob/main/lib/crewai/src/crewai/crew.py + lib/crewai/src/crewai/translations/en.json / 2026-10-20 / primary
- Delegation is off by default and bounded: `allow_delegation` "Default is False"; `max_iter` "Maximum iterations before the agent must provide its best answer. Default is 20"; hierarchical doc lists "**Delegation Control**: Delegation is now disabled by default to give users explicit control." / https://docs.crewai.com/v1.15.28/en/concepts/agents + /en/learn/hierarchical-process / 2026-10-20 / primary
- CrewAI's stated cost position on hierarchy is a single unsupported Tip: hierarchical process "is designed to leverage advanced models like GPT-4, **optimizing token usage** while handling complex tasks with greater efficiency." No token or dollar figure is given anywhere in the reviewed pages. / https://docs.crewai.com/v1.15.28/en/learn/hierarchical-process / 2026-10-20 / primary
- Planning = a pre-iteration planner whose output is injected into every task description: "before each Crew iteration, all Crew information is sent to an `AgentPlanner` that will plan the tasks step by step, and this plan will be added to each task description"; `planning=True` on the Crew, planner LLM defaults to **`gpt-4o-mini`** and "requires a valid OpenAI API key" even if the agents use other LLMs. / https://docs.crewai.com/v1.15.28/en/concepts/planning / 2026-10-20 / primary
- CrewAI's shared-record primitive is a **hierarchical memory scope tree**, not a message board: one unified `Memory` class (replacing separate short/long-term/entity/external stores) where an LLM infers "scope, categories, and importance" at save time; scopes are paths (`/project/alpha`, `/agent/researcher`, `/agent/researcher/project-alpha`); recall = composite score of semantic similarity + recency + importance; `memory.forget(scope=…)`, `memory.tree()`, `memory.info(…)`. Agent-level memory gives a private scope ("Researcher gets a private scope — only sees /agent/researcher"); otherwise agents share the crew scope. / https://docs.crewai.com/v1.15.28/en/concepts/memory / 2026-10-20 / primary
- Flows = the deterministic/event-driven half: "structured, event-driven workflows… connect multiple tasks, manage state, and control the flow of execution"; `@start()` / `@listen()` / `@router()`; each flow state auto-gets a UUID; structured (Pydantic) or unstructured state; crews can be embedded inside flows as steps. / https://docs.crewai.com/v1.15.28/en/concepts/flows / 2026-10-20 / primary
- Task-level guardrails with feedback loops: function-based (`guardrail`) and LLM-based (string → auto `LLMGuardrail` using the task agent's LLM); `guardrail_max_retries` "Maximum number of retries when guardrail validation fails. Defaults to 3"; on failure the agent is re-prompted with the validation error and its previous output (i18n `errors.validation_error`: "Previous attempt failed validation… Try again, making sure to address the validation error"). / https://docs.crewai.com/v1.15.28/en/concepts/tasks + lib/crewai/src/crewai/translations/en.json / 2026-10-20 / primary
- Crews-vs-Flows decision procedure (their "when multi-agent" answer): a complexity × precision matrix; Crews for "collaborative intelligence", "emergent thinking", adaptability over structure, flexible output; Flows for "precise control over execution", complex state, structured outputs, conditional logic, mixing AI with procedural code; "Flows orchestrating multiple Crews" for high-complexity/high-precision. Step-4 trade-offs: "Crews are often faster to prototype", "Flows provide better long-term maintainability", "Flows typically scale better for complex applications". Closing advice: "Start with the simplest solution that meets your needs". / https://docs.crewai.com/v1.15.28/en/guides/concepts/evaluating-use-cases / 2026-10-20 / primary
- Cross-process/cross-service delegation is delegated to the **A2A protocol**, not built in: "CrewAI treats A2A protocol as a first-class delegation primitive"; client mode "agents autonomously choose between local execution and remote delegation based on task requirements"; `A2AClientConfig` defaults: `timeout=120` s, `max_turns=10`, `fail_fast=True`, `trust_remote_completion_status=False` (default: the server agent gets to review the remote result), updates via `StreamingConfig` / `PollingConfig` / `PushNotificationConfig`; `crewai.a2a.config.A2AConfig` deprecated for v2.0 in favour of `A2AClientConfig`/`A2AServerConfig`. / https://docs.crewai.com/v1.15.28/en/learn/a2a-agent-delegation / 2026-10-20 / primary
- **Negative finding on "cowork"**: no CrewAI "Cowork" feature found. Zero occurrences of "cowork" in the CrewAI docs index (`https://docs.crewai.com/llms.txt`, 235 lines) or the CrewAI platform index (`https://docs-platform.crewai.com/llms.txt`, 30523 bytes); `site:crewai.com cowork` returns only the docs homepage. The word "coworker" appears only as the *parameter name* for CrewAI's delegation tools. / those three URLs / 2026-10-20 / primary
- No reviewed framework ships a **claim / lease / TTL / blocking-wait** primitive. In all three, every inter-agent step is mediated by an LLM turn (tool call, handoff, manager allocation) or by host-language control flow (CrewAI Flow `@listen`/`@router`, Agents SDK `asyncio.gather`, Swarm's single-threaded `client.run` loop). Scope: the reviewed pages listed above. / aggregated from the URLs above / 2026-10-20 / primary (absence in reviewed docs; see Gaps)

## Conflicting evidence

- **OpenAI's own two documents pull in different directions on default complexity.** `multi_agent.md` presents LLM-decided orchestration as "great when the task is open-ended and you want to rely on the intelligence of an LLM", while the practical guide says "maximize a single agent's capabilities first… starting with a single agent and evolving to multi-agent systems only when needed" and calls code orchestration better on "speed, cost and performance". Same vendor, same date — resolve by reading the guide as the vendor's *portfolio-level* recommendation and `multi_agent.md` as the SDK's *feature* description. (both URLs above)
- **Guardrail coverage claim vs guardrail mechanics.** `multi_agent.md`'s pattern table sells agents-as-tools partly for the ability to "enforce shared SDK guardrails in one place", but `guardrails.md` states agent-level input guardrails run only for the *first* agent and output guardrails only for the *last*, tool guardrails "do not apply to the handoff call itself", and hosted/built-in tools bypass the guardrail pipeline entirely. A multi-agent chain is therefore **less** covered by one guardrail than the table implies. (both URLs above)
- **Swarm "stateless" vs Swarm shared state.** README says Swarm "saves no state between calls" and is "stateless between calls", yet `context_variables` is exactly a shared mutable channel threaded through all agents and tools *within* a call, and `Result` lets a tool write it. "Stateless" here means "no server-side persistence", not "no shared state".
- **CrewAI's hierarchy-vs-practical-guide tension.** CrewAI ships hierarchical + delegation as a first-class headline feature with a dedicated doc page, yet its own decision matrix and OpenAI's guide both advise starting from the simpler single-agent/sequential form. CrewAI's only stated cost argument for hierarchy is an unsourced Tip ("optimizing token usage"); no measured token or dollar delta is published for sequential vs hierarchical crews, nor for delegation-enabled vs plain crews.
- **Failure-mode asymmetry across frameworks.** CrewAI's delegation miss returns an error *string* into the model's context (recoverable, silent-ish); the Agents SDK's handoff authorization miss requires the app to raise inside `on_handoff`; Swarm's handoff to an unknown agent is not expressible (the function returns the Agent object directly). Not a contradiction, but three different defaults for "agent addressed a peer that isn't there".
