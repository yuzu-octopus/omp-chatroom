# F12 — Coordination bugs in frameworks' own trackers + first-party postmortems

## Angle

Question: **what coordination failures do the framework maintainers THEMSELVES acknowledge?**

Method: read the maintainers' own GitHub issue trackers, their own release notes / changelogs, and their own
engineering write-ups. For each acknowledged failure I record (a) the maintainer's stated ROOT CAUSE, (b) the FIX,
(c) whether the fix is a **generalizable primitive** (lease / heartbeat / deadline / shared task list / idempotency
key / explicit handoff confirmation / single-writer / atomic write / stable identity / budget cap / circuit breaker /
durable completion marker / artifact passing / bounded context). This flag is the primary output.

Evidence strength tiers used in the confidence field:
- `primary` = maintainer's own tracker issue, maintainer's own release note, or maintainer's own doc/blog.
- `primary (unacknowledged)` = a report living in the maintainer's tracker that has **no** maintainer response and
  **no** linked fix PR — a report, NOT a maintainer admission.
- `secondary` = a first-party system described by someone other than its maintainer.

## Claims

### A. Anthropic first-party engineering write-up (multi-agent research system)

- Anthropic states multi-agent systems "burn through tokens fast": agents use ~4× the tokens of chat interactions and
  **multi-agent systems use about 15× more tokens than chats**. https://www.anthropic.com/engineering/multi-agent-research-system
  / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: cost budget is a first-class design constraint of a swarm, not an afterthought.
- Anthropic states "**LLM agents are not yet great at coordinating and delegating to other agents in real time**", and
  that domains "which require all agents to share the same context or involve many dependencies between agents are
  not a good fit for multi-agent systems today". Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: multi-agent only pays off for *wide fan-out over independent* work; dense dependencies ⇒ stay single-agent.
- DUPLICATE WORK, acknowledged with a concrete example: "Without detailed task descriptions, agents duplicate work,
  leave gaps, or fail to find necessary information… one subagent explored the 2021 automotive chip crisis while 2
  others duplicated work investigating current 2025 supply chains, without an effective division of labor."
  Fix = a task-description contract per subagent (objective + output format + tool/source guidance + clear task
  boundaries). Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: **structured task brief as the delegation unit**; a one-line brief is a duplicate-work bug generator.
- OVER-SPAWN / OVER-USE acknowledged: "Early agents made errors like spawning 50 subagents for simple queries,
  scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates." Fix =
  scaling rules embedded in the lead agent's prompt (simple fact-finding = 1 agent / 3–10 tool calls; direct
  comparison = 2–4 subagents / 10–15 calls each; complex = >10 subagents "with clearly divided responsibilities").
  Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: **effort/fan-out budget encoded in guidance** (agents, tool calls, per-agent).
- CONTEXT OVERFLOW acknowledged: the lead agent saves its plan to Memory "since if the context window exceeds
  200,000 tokens it will be truncated and it is important to retain the plan." Same URL / fetch 2026-10-20 /
  confidence: primary.
  - PRIMITIVE: **externalize durable state before the context window truncates it**; the plan must live outside the model.
- CONTEXT DEGRADATION + recovery: "When context limits approach, agents can spawn fresh subagents with clean contexts
  while maintaining continuity through careful handoffs. Further, they can retrieve stored context like the research
  plan from their memory rather than losing previous work when reaching the context limit." Same URL / fetch 2026-10-20 /
  confidence: primary.
  - PRIMITIVE: **handoff + retrieval of externalized state**; clean-context child + durable lookup.
- RESUMABILITY acknowledged: "we built systems that can resume from where the agent was when the errors occurred…
  We combine the adaptability of AI agents built on Claude with deterministic safeguards like **retry logic and regular
  checkpoints**." Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: **durable resume + checkpoints + bounded retry**; errors are not restartable from zero.
- HEAD-OF-LINE BLOCKING acknowledged: with synchronous execution "the lead agent can't steer subagents, subagents
  can't coordinate, and **the entire system can be blocked while waiting for a single subagent to finish searching**."
  Async is the proposed fix, with the caveat that it "adds challenges in result coordination, state consistency, and
  error propagation across the subagents." Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: **per-child deadline + a steering channel** (our T0 interrupt) + explicit error propagation.
- INFORMATION LOSS / "game of telephone" acknowledged, with a fix: "Subagent output to a filesystem to minimize the
  'game of telephone'… implement artifact systems where specialized agents can create outputs that persist
  independently. Subagents call tools to store their work in external systems, then pass **lightweight references**
  back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead."
  Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: **artifact/handle passing instead of copying payloads through the transcript**; a pass-by-reference
    result channel, with a durable log behind it.
- EMERGENT-BEHAVIOUR admission: "small changes to the lead agent can unpredictably change how subagents behave" and
  "minor changes cascade into large behavioral changes, which makes it remarkably difficult to write code for complex
  agents that must maintain state in a long-running process." Same URL / fetch 2026-10-20 / confidence: primary.
  - PRIMITIVE: system-level (not per-agent) observability; interaction-structure monitoring, not just content.
- GUIDANCE framing (directly relevant to our "guidance" build track): "the best prompts for these agents are not just
  strict instructions, but **frameworks for collaboration that define the division of labor, problem-solving
  approaches, and effort budgets**." Same URL / fetch 2026-10-20 / confidence: primary.
- Deployment admission: agents run long and stateful, so updates must use "rainbow deployments" to avoid breaking
  running agents. Same URL / fetch 2026-10-20 / confidence: primary.

## Conflicting evidence

- **Termination is owned by different layers in different frameworks.** AutoGen docs: `termination_condition` defaults
  to None ⇒ "the group chat will run indefinitely"; `max_turns` default None ⇒ no limit
  (https://microsoft.github.io/autogen/stable//reference/python/autogen_agentchat.teams.html). But ag2 #2575 shows a
  *provided* termination signal being silently ignored (fixed), and OpenAI's Agents SDK ships `max_turns` plus
  `RunConfig` limits. So "the framework bounds the loop" is not a property of any framework — it must be added
  deliberately.
- **Anthropic's fan-out cap is advisory; LangGraph's is enforced by middleware.** Claude Code 2.1.202 explicitly says
  the "Dynamic workflow size" setting is "an advisory guideline, **not an enforced cap**", while LangGraph's
  maintainer points to a real "tool call limit" middleware as the closure of an infinite-loop bug (#6731). Both are
  first-party; they disagree on whether guidance can substitute for a runtime-enforced bound.
- **OpenAI refuses to ship the budget guardrail in the SDK** (#3353: "This couldn't be done only by SDK side
  changes"), yet AutoGen (Microsoft) and crewAI receive open feature requests for exactly that primitive
  (agent-framework #6397/#8862/#8961/#4142; crewAI #6414). The capability is wanted everywhere and implemented
  nowhere.
- **Idempotency is universally described as a need and universally left unimplemented.** LangGraph #8464 (proposes a
  `DurableClaimStore`), crewAI #5802, agent-framework #9204/#9031, OpenAI #4775 (explicitly closed *unfixed*), Claude
  Code shipping three separate duplicate-execution fixes (2.1.300/2.1.301) — five independent frameworks, zero
  shipped idempotency keys. This is the strongest cross-framework signal in the set.
- **Claude Code's own issue tracker is full of coordination bugs with no maintainer reply** (#68619 "infinite recursion,
  infinite token usage … and lost accumulated subagent work"; #89543 "SendMessage to a running background subagent
  never delivers"; #103096 "finished (resumed) subagent stays under Running with a stuck 'N running' counter"; #91503
  "a subagent's background-task completion notification is queued but has no idle-wake consumer — the subagent hangs
  until something else gives it a turn"). These contradict the polished CHANGELOG narrative and are the clearest
  evidence that a *room*-style API (SendMessage = our `room post`) has delivery/liveness bugs that only surface in
  production. No maintainer comments were present on any of them ⇒ confidence: primary (unacknowledged).
- **The gossip script's `issues` subcommand cannot do repo-scoped queries** — it runs a global `gh search issues` and
  the `repo:` qualifier is rejected. Any agent relying on it for per-repo mining will silently get zero results.
- **AutoGen #7828 (the single most on-point finding for our plugin — a group manager deadlocking on one unresponsive
  speaker) has no maintainer response.** The proposed fix (per-speaker timeout, remove from `_active_speakers` with a
  timeout error) is a *user proposal*, not a vendor commitment. Treat as "reported, not acknowledged".

## Gaps

- **All-Hands-AI/OpenHands was effectively not mined.** `gh issue list --repo All-Hands-AI/OpenHands --search <term>`
  returns **zero results for every term tried** (agent, conversation, loop, timeout, retry, infinite, delegate,
  microagent, stall, stuck, message loss) even though the repo has >18,700 issues (e.g. #18717) and the issue list
  API itself works. The tracker appears to be unindexed for search; Discussions are disabled (HTTP 410). Only two
  issues were read via direct number lookup (#18715, #18717). OpenHands is therefore **under-represented** in this
  findings file, not clean.
- **Many tracker issues in these repos are AI-authored triage reports** (several carry an "agent-authored — trust but
  verify" triage block, and many carry repetitive templated "Reliability note" comments). They are *reports*, not
  vendor admissions, and I have flagged them `primary (unacknowledged)`. I did not audit authorship.
- **No release-note or postmortem mining was done for crewAI, ag2, smolagents, Letta or AutoGen** beyond the GitHub
  trackers and the two Letta/AutoGen doc pages. Their CHANGELOGs (e.g. `crewAIInc/crewAI` release notes, Letta's
  `docs.letta.com/reference/changelog`) likely contain maintainer-admitted coordination fixes; not read.
- **Microsoft AutoGen's .NET and Python sides differ** (e.g. #5314 "Inconsistent Behavior in Agent Registration
  Between .NET and Python Libraries"); I read mostly Python-side issues. .NET-specific coordination bugs
  (agent-framework #3060, #7946, #8627) were listed from titles only.
- **The "silent agent failure" class is under-sampled.** The clearest maintainer-admitted instance is Claude Code
  2.1.301 ("workflow agents sometimes skipping their step, and the run still reporting success") and OpenHands #18715
  (status says Running on a dead runtime). A systematic sweep of "reported success but did nothing" across all nine
  trackers was not performed.
- **The "retry storm" class produced almost nothing** (no hits for `retry storm` in any tracker). The nearest
  neighbours are Letta #3288 (context-overflow death spiral) and AutoGen #7321 (retry amplification on a saturated
  peer) — both found via other terms. Absence of hits is not absence of the failure.

  fewer tokens, 4/3/8/5 model calls, ~14K+/~9K tokens) comes from the cited first-party source and is attributed to
