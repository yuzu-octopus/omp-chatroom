# F4 — Claude Agent SDK + Anthropic's multi-agent research system

## Angle
First-party Anthropic evidence on how a **lead agent + parallel subagents** should be coordinated: the multi-agent research system post (token multiplier, eval win, explicit "when it does not pay off" conditions, lead-agent prompting/delegation rules), the later "when to use multi-agent systems" guidance post (a *different, lower* token multiplier — 3–10x vs 15x — and context-centric decomposition), the open-sourced lead-agent and subagent prompts in the Anthropic cookbook, the Claude Agent SDK / Claude Code subagent + agent-team docs (message-passing mechanics, task lists, limits), and the Opus 4.8 system card's multi-agent section (the only first-party *measurement* of multi-agent harnesses vs single agent on a shared benchmark).

## Claims

### A. Multi-agent research system post — the canonical numbers (VERBATIM)

- **"We found that a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval."** / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  - Note the page writes `90.2%` (no space, percent sign). It is "outperformed by 90.2%", i.e. a *relative* improvement over single-agent Opus 4 on Anthropic's **internal** research eval — not a public benchmark, not 90.2 percentage points, and not from BrowseComp.
  - The same paragraph's worked example: identifying board members of IT S&P 500 companies — "the multi-agent system found the correct answers by decomposing this into tasks for subagents, while the single agent system failed to find the answer with slow, sequential searches."

- **"There is a downside: in practice, these architectures burn through tokens fast. In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats."** / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  - Verbatim forms: `4×` and `15×` (multiplication sign, U+00D7), not "4x"/"15x". Two distinct ratios: **single agent vs chat = ~4×**; **multi-agent vs chat = ~15×**. (Implied multi-agent vs single-agent ≈ 15/4 ≈ 3.75×, but that ratio is *not stated* — do not report it as Anthropic's number.)

- **Token-usage is the dominant driver of the win, not agent count:** "three factors explained 95% of the performance variance in the BrowseComp evaluation (which tests the ability of browsing agents to locate hard-to-find information). We found that token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  - Same post: "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7."
  - Caveat carried by the page itself: BrowseComp is OpenAI's benchmark (https://openai.com/index/browsecomp/), cited as an eval Anthropic ran themselves; the variance analysis is Anthropic's own analysis of their runs.

- **Documented conditions under which multi-agent does NOT pay off (VERBATIM, three explicit statements):** / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  1. Economic: "For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance."
  2. Domain fit: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time."
  3. Positive-scoped: "We've found that multi-agent systems excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools."

- **The lead agent is instructed to scale effort explicitly ("Scale effort to query complexity"):** "Agents struggle to judge appropriate effort for different tasks, so we embedded scaling rules in the prompts. Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities. These explicit guidelines help the lead agent allocate resources efficiently and prevent overinvestment in simple queries, which was a common failure mode in our early versions." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  - Adjacent verbatim: "**Teach the orchestrator how to delegate.** In our system, the lead agent decomposes queries into subtasks and describes them to subagents. Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information."
  - Failure mode named: "one subagent explored the 2021 automotive chip crisis while 2 others duplicated work investigating current 2025 supply chains, without an effective division of labor."

- **Parallelism prescription and its measured effect:** "For speed, we introduced two kinds of parallelization: (1) the lead agent spins up 3-5 subagents in parallel rather than serially; (2) the subagents use 3+ tools in parallel. These changes cut research time by up to 90% for complex queries." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**

- **Known coordination failure modes Anthropic hit and fixed via prompting:** "Early agents made errors like spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  - Also: "small changes to the lead agent can unpredictably change how subagents behave" (emergent behavior) and the "best prompts for these agents are not just strict instructions, but frameworks for collaboration that define the division of labor, problem-solving approaches, and effort budgets."

- **Synchronous execution is a documented bottleneck (the reason the current Research system is *not* fully async):** "Currently, our lead agents execute subagents synchronously, waiting for each set of subagents to complete before proceeding. This simplifies coordination, but creates bottlenecks in the information flow between agents. For instance, the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent to finish searching. Asynchronous execution would enable additional parallelism... But this asynchronicity adds challenges in result coordination, state consistency, and error propagation across the subagents." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**

- **Artifact/ filesystem pattern for subagent output (bypassing the lead agent):** "**Subagent output to a filesystem to minimize the 'game of telephone.'** Direct subagent outputs can bypass the main coordinator for certain types of results, improving both fidelity and performance... Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead from copying large outputs through conversation history." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**
  - Also from the appendix: "When context limits approach, agents can spawn fresh subagents with clean contexts while maintaining continuity through careful handoffs. Further, they can retrieve stored context like the research plan from their memory rather than losing previous work."
  - Lead agent writes its plan to Memory *before* spawning, because "if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan."

- **Eval methodology Anthropic recommends (relevant to any swarm: LLM-as-judge, one call, 0.0–1.0 + pass/fail):** "a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements"; "We started with a set of about 20 queries representing real usage patterns"; "A prompt tweak might boost success rates from 30% to 80%." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**

- **Tool-design loop with a measured payoff:** the tool-testing agent "found key nuances and bugs. This process for improving tool ergonomics resulted in a 40% decrease in task completion time for future agents using the new description." / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**

### B. "When to use multi-agent systems (and when not to)" — 2026 guidance, different multiplier

- **"In our testing, multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks. This overhead stems from duplicating context across agents, coordination messages between agents, and summarizing results for handoffs."** / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them (canonical: https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them; published 2026-01-23) / 2026-10-20 / **primary**
  - Verbatim form: `3-10x` (hyphen, lowercase x) — **not** the same metric as the 15× vs chat figure in the 2025 research post. This is multi-agent vs *single-agent*; the 15× is multi-agent vs *chat*. The page restates it once more as "Multi-agent systems typically consume 3 to 10 times more tokens than single-agent approaches for equivalent tasks."
  - Also: "multi-agent systems often take longer overall than single-agent systems because of the sheer increase in total computation. The primary benefit of parallelization is thoroughness, not speed."

- **Three situations where multi-agent "consistently outperform a single agent":** "when context pollution degrades performance, when tasks can run in parallel, and when specialization improves tool selection or task focus. Outside these situations, the coordination costs typically exceed the benefits." / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / **primary**

- **Strongest published caution (matters most for a swarm):** "we've seen teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results" and "We've observed teams build elaborate multi-agent systems with separate agents for planning, execution, review, and iteration, only to discover that they suffered from lost context at each handoff and spent more tokens coordinating than executing." / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / **primary**

- **Decomposition rule (context-centric, not problem-centric):** "**Context-centric decomposition (usually effective).** Dividing by context boundaries means an agent handling a feature should also handle its tests, because it already possesses the necessary context. Work should only be split when context can be truly isolated." Problem-centric splitting (planner/implementer/tester/reviewer) is called "often counterproductive"; in "one experiment with agents specialized by software development role (planner, implementer, tester, reviewer), the subagents spent more tokens on coordination than on actual work." / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / **primary**
  - Effective boundaries: independent research paths; separate components with clean interfaces; blackbox verification. Problematic: sequential phases of the same work; tightly coupled components; work requiring shared state.

- **The "early victory problem" in delegated verification** (a swarm failure mode worth copying): "The most significant failure mode for verification subagents is marking outputs as passing without thorough testing." Mitigations: concrete criteria, comprehensive checks, negative tests, and the explicit instruction "You MUST run the complete test suite before marking as passed". / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / **primary**

- **Single-agent escape hatches Anthropic now recommends before going multi-agent:** "Before adopting a multi-agent architecture, consider using the Tool Search Tool, which lets Claude dynamically discover tools on-demand rather than loading all definitions upfront. This can reduce token usage by up to 85% while improving tool selection accuracy." (links to https://www.anthropic.com/engineering/advanced-tool-use) / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / **primary** (the 85% figure is Anthropic's own engineering post, referenced here)

- **Quantitative trigger thresholds for going multi-agent:** "Managing many tools. When an agent has 15-20+ tools, the model spends significant context and attention understanding its options"; "Context isolation is most effective when subtasks generate high context volume (more than 1000 tokens) but most of that information is irrelevant to the main task". / https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them / 2026-10-20 / **primary**

### C. The open-sourced lead-agent and subagent prompts (Anthropic cookbook) — verbatim delegation granularity

- **Lead agent's subagent-count guidelines (the "scale effort" rule, as shipped):** "**Simple/Straightforward queries**: create 1 subagent"; "**Standard complexity queries**: 2-3 subagents"; "**Medium complexity queries**: 3-5 subagents"; "**High complexity queries**: 5-10 subagents (maximum 20)... **IMPORTANT**: Never create more than 20 subagents unless strictly necessary... Prefer fewer, more capable subagents over many overly narrow ones. More subagents = more overhead. Only add subagents when they provide distinct value." Also: "default to using 3 subagents for most queries" and "**Even for simple queries, always create at least 1 subagent to ensure proper source gathering**". / https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md (raw: https://raw.githubusercontent.com/anthropics/claude-cookbooks/main/patterns/agents/prompts/research_lead_agent.md) / 2026-10-20 / **primary**
  - **Query-type taxonomy the lead agent must classify first:** "**Depth-first query**" (one topic, many angles), "**Breadth-first query**" (distinct independent sub-questions), "**Straightforward query**" (single focused investigation).
  - **Explicit anti-duplication instruction:** "**Define extremely clear, crisp, and understandable boundaries between sub-topics to prevent overlap.**" and "Avoid overlap between subagents - every subagent should have distinct, clearly separate tasks, to avoid replicating work and wasting resources."
  - **Subagent task-description contract (VERBATIM):** "Specific research objectives, ideally just 1 core objective per subagent... Expected output format... Relevant background context... Key questions to answer... Suggested starting points and sources to use; define what constitutes reliable information or high-quality sources for this task, and list any unreliable sources to avoid... Specific tools that the subagent should use... If needed, precise scope boundaries to prevent research drift."
  - **Dependency ordering:** "Consider priority and dependency when ordering subagent tasks - deploy the most important subagents first. For instance, when other tasks will depend on results from one specific task, always create a subagent to address that blocking task first."
  - **Role separation:** "As the lead research agent, your primary role is to coordinate, guide, and synthesize - NOT to conduct primary research yourself."
  - **Time-pressure bail-out:** "if you are running out of time or a research process has already taken a very long time, avoid deploying further subagents and instead just start composing the output report immediately."

- **Subagent prompt (research_subagent.md) — per-agent budget and stopping rules:** "simpler tasks like 'when is the tax deadline this year' should result in under 5 tool calls, medium tasks should result in 5 tool calls, hard tasks result in about 10 tool calls, and very difficult or multi-part tasks should result in up to 15 tool calls"; "Execute a MINIMUM of five distinct tool calls, up to ten for complex queries"; hard cap "under a limit of 20 tool calls and under about 100 sources"; also a "**research budget**" the subagent plans for itself. / https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md / 2026-10-20 / **primary**
  - Subagent is explicitly told it "should be concise but more information-dense in reporting the results" and to flag uncertain/speculative claims, and to include conflicting information rather than silently resolving it.

- **Second-party lead-agent variant (SDK demo) showing an even stricter "lead never does the work" contract:** "You MUST delegate ALL research and report writing to specialized subagents. You NEVER research or write reports yourself... Break user research requests into 2-4 distinct research subtopics... Spawn multiple researcher subagents in parallel... Your ONLY tool is Task - you delegate everything to subagents"; "ALWAYS spawn 2-4 researcher subagents in parallel (not sequential)"; "ALWAYS wait for ALL researchers to finish before spawning the data-analyst"; "Give each researcher a SPECIFIC subtopic - don't give them the same task"; GOOD = parallel, BAD = sequential. / https://github.com/anthropics/claude-agent-sdk-demos/blob/main/research-agent/research_agent/prompts/lead_agent.txt / 2026-10-20 / **primary**
  - Also demonstrates the file-handoff pattern: researchers save notes to `files/research_notes/`, data-analyst reads them, report-writer reads notes + charts.

### D. Claude Agent SDK / Claude Code docs — coordination mechanics

- **Subagent context isolation contract (SDK):** "each subagent runs in its own conversation, which starts fresh unless the subagent is a fork. Either way, intermediate tool calls and results stay inside the subagent; only its final message returns to the parent." Benefits listed: context isolation, parallelization ("independent subtasks finish in the time of the slowest one rather than the sum of all of them"), specialized instructions, tool restrictions. / https://code.claude.com/docs/en/agent-sdk/subagents / 2026-10-20 / **primary**
  - Subagent inheritance: receives its own system prompt + the Agent tool's prompt string + CLAUDE.md (unless `omitClaudeMd`) + tool definitions; does **not** receive the parent's conversation history, tool results, or the parent's system prompt. "The only content you pass from parent to subagent is the Agent tool's prompt string, so include any file paths, error messages, or decisions the subagent needs directly in that prompt."

- **Foreground vs background semantics:** "By default, a subagent your main agent spawns runs in the background. The Agent tool result has `status: "async_launched"`, and the report arrives in a later turn. Claude waits when its next action needs the report: the call blocks and returns `status: "completed"`." / https://code.claude.com/docs/en/agent-sdk/subagents / 2026-10-20 / **primary**
  - Claude Code side: "**Foreground subagents** block the main conversation until complete... **Background subagents** run concurrently while you continue working." / https://code.claude.com/docs/en/sub-agents / 2026-10-20 / **primary**

- **Peer-to-peer messaging between agents exists and is explicitly the mechanism for coordination:** "A subagent that has the `SendMessage` tool starts with a list of the other named agents running in the session, so it knows which names it can send messages to. Claude Code adds the list to the subagent's first turn automatically." / https://code.claude.com/docs/en/agent-sdk/subagents / 2026-10-20 / **primary**
  - Claude Code side: a "**Sibling roster**: a system reminder listing `main` and every other named agent in the session, each a valid `to` value for `SendMessage`." / https://code.claude.com/docs/en/sub-agents / 2026-10-20 / **primary**
  - Claude Code agent-teams: mailbox is a JSON file per agent at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; "Claude Code reports a message as sent only when the write to the recipient's mailbox file succeeds." / https://code.claude.com/docs/en/agent-teams / 2026-10-20 / **primary**

- **Agent teams = shared task list with dependencies + file-locked claiming (the closest first-party analogue to a claim board):** "Tasks have three states: pending, in progress, and completed. Tasks can also depend on other tasks: a pending task with unresolved dependencies cannot be claimed until those dependencies are completed." "**Task claiming uses file locking to prevent race conditions when multiple teammates try to claim the same task simultaneously.**" "Claude Code manages task dependencies automatically: when a teammate completes a task that other tasks depend on, it unblocks the dependent tasks without any action from you." / https://code.claude.com/docs/en/agent-teams / 2026-10-20 / **primary**
  - Lead assigns vs self-claim: "**Lead assigns**: tell the lead which task to give to which teammate. **Self-claim**: after finishing a task, a teammate picks up the next unassigned, unblocked task on its own."
  - **Anti-anchoring pattern (worth copying for a swarm):** "The debate structure is the key mechanism here. Sequential investigation suffers from anchoring: once one theory is explored, subsequent investigation is biased toward it."

- **When NOT to use agent teams (VERBATIM):** "Agent teams add coordination overhead and use significantly more tokens than a single session. They work best when teammates can operate independently. For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." / https://code.claude.com/docs/en/agent-teams / 2026-10-20 / **primary**
  - Also: "Before you set up a team, check whether a lighter option does the job. Subagents work within a single session, and with cross-session messaging Claude can pass findings between the sessions you run yourself."
  - Team-size guidance: "Start with 3-5 teammates for most workflows... If you have 15 independent tasks, 3 teammates is a good starting point." and "Having 5-6 tasks per teammate keeps everyone productive and lets the lead reassign work if someone gets stuck."
  - Task sizing: "**Too small**: coordination overhead exceeds the benefit. **Too large**: teammates work too long without check-ins, increasing risk of wasted effort. **Just right**: self-contained units that produce a clear deliverable."
  - File conflicts: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files."

- **Agent-team limitations (first-party list of what a shared-room swarm will hit):** no session resumption with in-process teammates; "**Task status can lag**: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; shutdown can be slow; one team per session; "**No nested teams**: teammates cannot spawn their own teammates. Only the lead can manage the team."; "**Lead is fixed**: the main session is the lead for its lifetime. You can't promote a teammate to lead or transfer leadership."; permissions set at spawn. / https://code.claude.com/docs/en/agent-teams / 2026-10-20 / **primary**

- **Cost guidance for teams:** "Agent teams use significantly more tokens than a single session. Each teammate has its own context window, and token usage scales with the number of active teammates. For research, review, and new feature work, the extra tokens are usually worthwhile. For routine tasks, a single session is more cost-effective." Team cost controls: use Sonnet for teammates, keep teams small ("token usage is roughly proportional to team size"), keep spawn prompts focused, shut down teammates when done. / https://code.claude.com/docs/en/agent-teams and https://code.claude.com/docs/en/costs#agent-team-token-costs / 2026-10-20 / **primary**

- **Concurrency and depth limits (mechanisms a room would need to bound):** "By default, when 20 subagents are running in a session, spawning another with the Agent tool fails with `Concurrent subagent limit reached`"; nesting default 3 layers (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`); 15,000-token cap on combined subagent descriptions. / https://code.claude.com/docs/en/sub-agents / 2026-10-20 / **primary**

- **Context engineering post: the size of a subagent's return payload.** "Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Multi-agent chosen "when complex research and analysis where parallel exploration pays dividends" vs compaction (conversational flow) and note-taking (iterative development with clear milestones). / https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents / 2026-10-20 / **primary**
  - Also: "The sub-agent architectures ... showed a substantial improvement over single-agent systems on complex research tasks."

- **Managed Agents multiagent orchestration (first-party API surface, 2026):** three modes — **subagents** ("Delegation is one level deep, and a session can have at most 25 child threads at a time"), **dynamic workflows** (the agent writes a program running many agents in phases; "set a session budget to cap the session's spend, runs included"), and **advisor** (primary thread consults a second model mid-turn). Documented working patterns: "**Parallelization:** Fan out independent subtasks simultaneously... **Specialization:** Route to agents with domain-focused system prompts and tools... **Escalation:** Consult a more capable agent or model for a subset of complex subtasks." / https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration / 2026-10-20 / **primary**
  - **Guidance-steering via system prompt (a guidance-track mechanism Anthropic ships as first-class):** "To guide that choice, add an instruction like the following to the agent's system prompt... `You review contracts. When you're asked to review more than a few contracts, start a workflow run that reads them in parallel and combines the findings. Review one or two contracts yourself, without a run.`" Plus example steerers for "How to split the work", "What to do when an agent fails", "A time limit", "Plan first". "Keep runs to the tasks that need them, because every agent in a run uses tokens." / 2026-10-20 / **primary**
  - Failure isolation instruction Anthropic recommends: "One agent failing must not fail the run. If an agent fails to read a contract, list that contract as not covered."

- **Async multi-agent cookbook (message-hub pattern Anthropic publishes as the reference implementation):** a `Hub` with per-agent inbox lists + `asyncio.Event` blocking waits; two client-side tools — `send_message` ("This is the ONLY way to reach other agents — plain text in your turn goes nowhere") and `wait_for_message` ("messages also arrive automatically appended to the result of ANY other tool call, so only use this when you have nothing else to do"). Two patterns: **fixed N-agent team** (peer messaging through a shared hub) and **dynamically spawned async subagents**. / https://platform.claude.com/cookbook/patterns-agents-async-multi-agent-orchestration (published 2026-06-08; GitHub: https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/async_multi_agent_orchestration.ipynb) / 2026-10-20 / **primary**
  - The cookbook states these are "the shape of the two multi-agent orchestration patterns behind the multi-agent results in the Claude Opus 4.8 system card".
  - **Shared team clock** pattern (latency budget, first-party): one clock object per task, every agent sees `[elapsed 252s]` (or `[elapsed 252s / 600s]` with a budget) appended to its newest user message before every turn; "A helper spawned three minutes into the task sees `[elapsed 182s]` on its very first turn, not `0s`, because the clock belongs to the team, not the agent." / https://platform.claude.com/cookbook/patterns-agents-latency-multi-agent (published 2026-09-18) / 2026-10-20 / **primary**

### E. Opus 4.8 system card §8.11 — the only first-party controlled multi-agent vs single-agent measurement

Source PDF: https://www-cdn.anthropic.com/0b4915911bb0d19eca5b5ee635c80fef830a37ea.pdf (System Card: Claude Opus 4.8, May 28 2026), §8.11 Multi-Agent, pp. 209–215. / 2026-10-20 / **primary**

- **"Multi-agent harnesses achieved the highest scores. The *Orchestrator with Blocking* *Subagents* reached our highest score of 88.5%. Notably, the five-agent team (85.4%) also exceeded the single-agent baseline (84.3%), demonstrating that multi-agent configurations can productively absorb additional token budget by distributing work across agents."** (Multi-Agent BrowseComp)

- **Pareto result on latency vs tokens:** "The five-agent team, operating under a 5M-token total limit (1M token limit per agent), scored higher than a single agent with a 10M-token limit (85.4% vs. 84.3%), using just 20% of the latency."

- **Explicit token/latency trade-off:** "the latency improvement is at the cost of higher token usage than single-agent counterparts... when latency matters, a fixed-agents team can reach the same score faster, but will be at the cost of higher token consumption."

- **Coordination overhead is real and measurable — and cancels the parallelism gain on easy problems:** "On the easiest problems with 100% pass rate, the *five-agent team* delivered no speedup, likely because coordination overhead roughly offset the gains from parallelism. On the hard tail where the pass rate is below 0.5, the median speedup is around 3×. The aggregate latency improvement is therefore driven by the hard tail." (Figure 8.11.1.C is over "the full set of 1266 BrowseComp problems")

- **Coding (ProgramBench, 166 "golden" tasks):** "the three-agent team shows lower latency at equal score (equivalently, higher score at equal latency) throughout the run... the three-agent team reaches the same score of 0.6 with ~1.8× latency improvement than single agent. The async-subagent curve sits between the two: it improves on the single agent but by a smaller margin than the three-agent team."

- **The three harnesses Anthropic actually ran (this is the cleanest first-party taxonomy of coordination topologies):** §8.11.3
  1. **Orchestrator with blocking subagents** — "A single orchestrator coordinates the task by spawning subagents and blocking until all return. The orchestrator has no task tools of its own; its only capability is spawning subagents. Each subagent receives the full set of task tools... Subagents have a 200k-token context window without compaction, whereas the orchestrator uses context compaction triggered at 100k tokens, with an unlimited token budget."
  2. **Fixed-agent team** — "A team of three or five peer agents work on the task concurrently. One agent is designated the lead and is responsible for coordination and submitting the final answer, but all agents have identical tools and all see the full task description. In addition to the task tools, every agent has two messaging tools: Send Message, which delivers a message to one or more teammates (inserted following the recipient's next tool result), and Wait for Message, which blocks sampling until an incoming message arrives." On ProgramBench "each agent works in its own checkout of the task repository and can share code with other agents via Git."
  3. **Async subagents** — "the lead agent can spawn asynchronous, long-lived subagents while retaining direct access to the task tools. Unlike the blocking design, spawning returns immediately with a confirmation rather than waiting on subagent execution. Each subagent sees only the instructions provided by the lead, not the original task description, and subagents can message any other agent and the lead. A subagent's final response is delivered to the lead as a message, after which the subagent idles until the lead wakes it with new instructions." "Resource limits cap this harness at four concurrent subagents and 20 subagents in total... the lead additionally has tools to create subagents, to delete subagents (freeing concurrency slots), and to check subagent status (working, idle, or terminated)."

- **Methodology caveat Anthropic states:** "Latency is reported as a derived per-task latency rather than raw wall-clock time: we divide each agent's input and output token counts by fixed reference prefill and decode rates, and add measured tool-execution time. This isolates the structural latency of the harness... from serving-side variance." Also "token usage is calculated as the total number of tokens consumed across all agents on a task."

### F. "Building effective agents" (Dec 2024) — the orchestrator-workers pattern and the baseline stance

- **Orchestrator-workers pattern definition:** "In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results." "**When to use this workflow:** This workflow is well-suited to complex tasks where you can't predict the subtasks needed... Whereas it's topographically similar [to parallelization], the key difference from parallelization is its flexibility—subtasks aren't pre-defined, but determined by the orchestrator based on the specific input." Examples: "Coding products that make complex changes to multiple files each time"; "Search tasks that involve gathering and analyzing information from multiple sources". / https://www.anthropic.com/engineering/building-effective-agents / 2026-10-20 / **primary**
  - **Parallelization is split into sectioning vs voting:** sectioning = breaking a task into independent subtasks run in parallel; voting = running the same task multiple times for diverse outputs.
  - **Baseline stance:** "We suggest that developers start by using LLM APIs directly... If you do use a framework, ensure you understand the underlying code. Incorrect assumptions about what's under the hood are a common source of customer error." And: "you should consider adding complexity *only* when it demonstrably improves outcomes."
  - Note (post-publication banner): "Much of the tooling landscape described in this post has changed since December 2024. For our current approach, see how we built Claude Managed Agents."

## Conflicting evidence
- **Token multiplier: 15× vs 3–10x — different denominators, not a contradiction, but easy to conflate.** 2025 research post: multi-agent ≈ **15×** *chat* (and single agent ≈ 4× chat). 2026 guidance post: multi-agent ≈ **3-10x** *single-agent*. If a secondary source quotes "15x" as multi-agent-vs-single-agent, it is wrong; the primary says 15× vs chat. Sources: https://www.anthropic.com/engineering/multi-agent-research-system vs https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them.
- **90.2% vs 88.5% / 85.4% vs 84.3%** are different measurements on different evals: 90.2% is Opus-4-lead + Sonnet-4-subagents vs single Opus 4 on Anthropic's **internal** research eval (2025); 88.5%/85.4%/84.3% are Opus 4.8 multi-agent harnesses vs single agent on **BrowseComp** (2026 system card, §8.11.1). The 90.2% figure is *not* a BrowseComp number and must not be reported as one.
- **"Multi-agent is faster" vs "multi-agent is slower overall."** The research post claims parallelization "cut research time by up to 90% for complex queries"; the 2026 guidance post says "multi-agent systems often take longer overall than single-agent systems because of the sheer increase in total computation. The primary benefit of parallelization is thoroughness, not speed." The system card reconciles them: latency win is on the *hard tail* (median ~3× speedup where pass rate < 0.5) and *no* speedup on easy problems; "The aggregate latency improvement is therefore driven by the hard tail." All three are primary; the reconciliation is the system card's.
- **"Coordination overhead" magnitude differs by source**: 2025 post frames overhead as a prompting problem (duplicated work, 50-subagent runaway); 2026 post quantifies it as 3-10x tokens and reports a role-split experiment where "the subagents spent more tokens on coordination than on actual work"; system card measures it as "no speedup" on easy BrowseComp problems. Complementary, not contradictory.
- **Async vs blocking.** The 2025 post says Anthropic's production Research runs subagents **synchronously** and names that as a bottleneck ("the lead agent can't steer subagents, subagents can't coordinate"). The 2026 system card evaluates async subagents and finds them intermediate ("it improves on the single agent but by a smaller margin than the three-agent team"). So async is not simply better.

## Gaps
- The **90.2% internal research eval is not public** — no task set, no scoring rubric, no n, no per-query data. Unverifiable beyond Anthropic's assertion. The BrowseComp number (1266 problems) is the only reproducible multi-agent measurement, and its figures live in PDF figures, not text tables.
- **No first-party number for multi-agent vs single-agent token cost in Claude Code subagents** (only the qualitative "token usage is roughly proportional to team size" and the guidance post's 3-10x). The docs `/usage` page reports subagent attribution percentages but no baseline ratio.
- **The 15× figure is "in our data" from the 2025 Research product**, with no stated baseline chat task, no per-query distribution, and no sample size. It should be cited as "Anthropic reports ~15× chat tokens for multi-agent" and never as a controlled A/B.
- The **system card's multi-agent token-vs-score curves (Figures 8.11.1.B, 8.11.2.B) are images**; only the qualitative statement that multi-agent spends more tokens is available in text. The exact token multiplier for the five-agent team is **unverified** from text.
- **Claude Code agent teams are experimental and disabled by default** (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`); the shared task list / file-lock claiming / mailbox implementation is documented but there is **no first-party evaluation** of agent-team quality vs subagents.
