# F13 — Distributed-systems primitives we could borrow

## Angle

For each primitive, what does the ORIGINAL source say it guarantees and what does it explicitly NOT
guarantee, and which coordination failure does it prevent? Then: map each primitive onto the plugin's
concrete gap. The plugin's claim today is a TTL lease with (1) NO fencing token — a stale holder can
still write after its lease expired and another agent reclaimed, (2) NO renewal/heartbeat — a live but
slow agent loses its lease, (3) NO dependency ordering between claims — A can claim a resource that
B's claim depends on. Plugin facts read from source (read-only) at `/home/yuzu/projects/omp-chatroom/plugin`:
`src/store/claims.ts` (ClaimState = `{resource, holder, ttlMs, acquiredAt, seq}` — no token field, no
renewal op, no dependency field), `src/store/schema.ts` (claim record carries `resource` + `ttlMs`
only), `src/store/config.ts` (`claimTtlMs: 300_000`, `claimSweepMs: 5_000`), `src/tools/room.ts`
(`post` appends unconditionally — it does NOT check that the poster still holds the relevant claim;
`claim`/`release` are the only ops that consult `store.claims`).

## Claims

### A. LEASES + FENCING TOKENS

- **Claim (A1):** A lease is "a contract that gives its holder specified rights over property for a
  limited period of time"; the server must honour it for the whole term, and "when a server is
  recovering after crashing, it must honor the leases it granted before it crashed" (by delaying writes
  to all tiles for that period). / source: Gray & Cheriton, *Leases: An Efficient Fault-Tolerant
  Mechanism for Distributed File Cache Consistency*, SOSP 1989,
  https://www.cs.cmu.edu/afs/cs.cmu.edu/academic/class/15712-s12/www/papers/gray89.pdf
  (also https://courses.cs.duke.edu/compsci510/spring15/readings/leases-sosp89.pdf) / fetch
  2026-10-20 / confidence **primary**.
- **Claim (A2):** What the lease does NOT guarantee, in the authors' own words: "Leases ensure
  consistency provided that the hosts and network do not suffer certain Byzantine failures including
  **clock failure**. Leases depend on well-behaved clocks." Consistency survives message loss,
  partition, and client/server failure (writes persistent at the server) — but NOT clock failure.
  Availability is not reduced by the caches because "an unreachable client at most briefly delays
  write access by other clients." / source: same PDF, §5 "Fault-Tolerance" / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (A3):** A lease is a TIME-BOUNDED grant, and the original paper's own cost model is a
  trade-off, not a safety property: "The choice of lease term is based on the trade-off between
  minimizing lease extension overhead versus minimizing false sharing"; short terms reduce
  false-sharing overhead but increase extension traffic; the paper notes "To avoid starvation of
  writes, the server does not grant new leases on a file when a write is waiting for approval or for
  leases to expire." / source: same PDF, §3 "Choosing the Lease Term" / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (A4):** The fencing-token fix, in Kleppmann's canonical write-up: "you need to include a
  *fencing token* with every write request to the storage service. In this context, a fencing token is
  simply a number that increases (e.g. incremented by the lock service) every time a client acquires
  the lock." The protected resource must enforce it: "the storage server remembers that it has already
  processed a write with a higher token number (34), and so it rejects the request with token 33."
  Critically: "this requires the storage server to take an active role in checking tokens" — the client
  checking its own lease is NOT enough. / source: Kleppmann, *How to do distributed locking*,
  2016-02-08, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html / fetch
  2026-10-20 / confidence **primary** (author's own canonical write-up; the book chapters 8/9 are
  paywalled, this post is the same material).
- **Claim (A5):** The failure the fencing token prevents, stated by Kleppmann: a client paused by GC
  (or a delayed network packet) "may go ahead and make some unsafe change"; "You cannot fix this
  problem by inserting a check on the lock expiry just before writing back to storage. Remember that GC
  can pause a running thread at *any point*, including the point that is maximally inconvenient for
  you (between the last check and the write operation)." The bug it prevents: "the result is a
  corrupted file, data loss, permanent inconsistency". Kleppmann cites HBase as a real instance
  ("HBase used to have this problem"). / source: same post / fetch 2026-10-20 / confidence **primary**.
- **Claim (A6):** A real system already ships this: Chubby's **sequencer** — "At any time, a lock
  holder may request a sequencer, an opaque byte-string that describes the state of the lock
  immediately after acquisition. It contains the name of the lock, the mode in which it was acquired
  (exclusive or shared), and the lock generation number. The client passes the sequencer to servers
  (such as file servers) if it expects the operation to be protected by the lock. The recipient server
  is expected to test whether the sequencer is still valid and has the appropriate mode; if not, it
  should reject the request." / source: Burrows, *The Chubby lock service for loosely-coupled
  distributed systems*, OSDI 2006, https://www.usenix.org/legacy/events/osdi06/tech/full_papers/burrows/burrows.pdf
  / fetch 2026-10-20 / confidence **primary**.
- **Claim (A7):** Chubby also ships the *weaker* fallback and says so plainly: the **lock-delay** —
  "if a lock becomes free because the holder has failed or become inaccessible, the lock server will
  prevent other clients from claiming the lock for a period called the lock-delay. Clients may specify
  any lock-delay up to some bound, currently one minute; this limit prevents a faulty client from
  making a lock (and thus some resource) unavailable for an arbitrarily long time. **While imperfect,
  the lock-delay protects**" — Chubby's own admission that lock-delay is *not* a substitute for a
  sequencer, only a risk reducer for servers that cannot validate sequencers. / source: same PDF, §2.4
  / fetch 2026-10-20 / confidence **primary**.
- **Claim (A8):** Chubby's lease is *renewable* and its renewal is the thing that keeps a slow-but-alive
  client alive: "Each session has an associated lease—an interval of time extending into the future
  during which the master guarantees not to terminate the session unilaterally… The master advances
  the lease timeout in three circumstances: on creation of the session, when a master fail-over occurs
  …, and when it responds to a KeepAlive RPC from the client." Default extension 12s. A client whose
  local lease expires enters "jeopardy": it "empties and disables its cache" and waits a 45s grace
  period — i.e. it stops writing, it does not keep writing optimistically. / source: same PDF, §3
  "Sessions and KeepAlives" / fetch 2026-10-20 / confidence **primary**.

### B. HEARTBEATS / FAILURE DETECTION — "alive" vs "slow"

- **Claim (B1):** The failure-detector abstraction's core epistemic point, in the original: an
  unreliable failure detector "can make mistakes by erroneously adding processes to its list of
  suspects: i.e, it can suspect that a process *p* has crashed even though *p* is still running", and
  "the mistakes made by an unreliable failure detector should not prevent any correct process from
  behaving according to specification even if that process is (erroneously) suspected to have crashed
  by all the other processes." / source: Chandra & Toueg, *Unreliable Failure Detectors for Reliable
  Distributed Systems*, JACM 43(2):225–267, March 1996,
  https://courses.csail.mit.edu/6.852/08/papers/CT96-JACM.pdf / fetch 2026-10-20 / confidence
  **primary**.
- **Claim (B2):** The SBR (strong) vs S distinction, in the original's own definitions. **Strong
  completeness:** "Eventually every process that crashes is permanently suspected by *every* correct
  process." **Weak completeness:** "Eventually every process that crashes is permanently suspected by
  *some* correct process." Accuracy: **strong accuracy** = "No process is suspected before it crashes";
  **weak accuracy** = "Some correct process is never suspected." The class S (strong completeness +
  weak accuracy) is what lets Consensus be solved "despite any number of crashes" (f < n); the
  eventual-accuracy variants (◇S) require "a majority of correct processes". / source: same PDF,
  §2.3–2.4 and §6 / fetch 2026-10-20 / confidence **primary**.
- **Claim (B3):** The distinction the angle asks for — "is my peer still alive" vs "is my peer slow" —
  is IMPOSSIBLE to answer in the general case, and the original says so: the impossibility of
  Consensus/Atomic Broadcast "stem[s] from the inherent difficulty of determining whether a process
  has actually crashed or is only 'very slow'"; and in §9.1, "it is impossible in an asynchronous
  distributed system to reliably distinguish a process that has crashed from one that is merely very
  slow." Failure detectors are the *explicit relaxation* of that. / source: same PDF, §1 and §9.1 /
  fetch 2026-10-20 / confidence **primary**.
- **Claim (B4):** The safety/liveness split, which is the design rule any "is my peer dead?" check must
  obey: if the failure detector "misbehaves continuously … the application may lose *liveness* but not
  *safety*. For example, if a Consensus algorithm assumes the properties of W, but the failure detector
  that it actually uses misbehaves continuously, processes may be prevented from deciding, but they
  never decide different values." And the SBR class's formal definition (from the class list):
  "**Completeness.** There is a time after which every process that crashes is permanently suspected by
  some correct process. **Accuracy.** There is a time after which some correct process is never
  suspected by any correct process." A detector "can make an infinite number of mistakes". / source:
  same PDF, §1 and §2.3–2.4 / fetch 2026-10-20 / confidence **primary**.
- **Claim (B5):** The original's own implementation sketch of the timeout/heartbeat detector, including
  the crucial self-correction: "Every process *q* periodically sends a '*q*-is-alive' message to all. If
  a process *p* times-out on some process *q*, it adds *q* to its list of suspects. If *p* later receives
  a '*q*-is-alive' message, *p* recognises that it made a mistake by prematurely timing out on *q*: *p*
  removes *q* from its list of suspects, and **increases the length of its timeout period for *q* in an
  attempt to prevent a similar mistake in the future**." But it also says the naive scheme is not
  implementable in the asynchronous model: "an unbounded sequence of premature time-outs may cause every
  correct process to be repeatedly added and then removed from the list of suspects of every correct
  process, thereby violating the accuracy property of W." / source: same PDF, §1 / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (B6):** The original's own instruction to implementers: "we reiterate that all reasoning about
  failure detectors (and algorithms that use them) should be done in terms of their abstract properties
  and not in terms of any particular implementation… the reader should refrain from thinking of failure
  detectors in terms of specific time-out mechanisms." / source: same PDF, §1 / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (B7):** The SWAN-era original statement of the same point, in a systems paper: "Clearly,
  failure detection by time-out cannot be more reliable than the underlying communication system: A
  series of message losses can always mimic a failure. Moreover, the order in which failures are
  perceived to have occurred may vary from process to process. These observations lead us to adopt a
  logical approach to failure handling, rather than a physical one. That is, instead of a process acting
  directly after it detects a failure, which could lead to inconsistent actions, a protocol is run to
  reach agreement with other processes that a failure event has occurred." / source: Birman & Joseph,
  *Reliable communication in the presence of failures*, ACM TOCS 5(1):47–76, Feb 1987,
  https://www.cs.swarthmore.edu/~newhall/readings/isis2.pdf / fetch 2026-10-20 / confidence
  **primary**. (Same paper supplies the **incarnation number** mechanism — the direct ancestor of the
  fencing token: "A site incarnation number is incremented each time a site recovers; henceforth, the
  term 'site' always means 'incarnation of a site.' Messages from a failed incarnation are discarded by
  the input filter, and a 'you are dead' message is returned to the sender." — same URL, §4.1.)
- **Claim (B8):** The heartbeat primitive's own primary statement, and the sharp distinction between
  "heartbeat counter" and "heartbeat timeout": a process "periodically sends an '*I-am-alive*' message
  (a 'heartbeat') and every process receiving a heartbeat increases the corresponding counter" — and
  the detector "does *not* use timeouts on the heartbeats of a process in order to determine whether
  this process has failed or not. [It] just counts the *total number of* heartbeats received from each
  process, and outputs these 'raw' counters without any further processing or interpretation. Thus,
  [it] should not be confused with existing implementations of failure detectors … **Even though
  existing failure detectors are also based on the repeated sending of a heartbeat, *they use timeouts*
  on heartbeats in order to derive lists of processes considered to be up or down; applications can only
  see these lists.**" / source: Aguilera, Chen & Toueg, *Heartbeat: A Timeout-Free Failure Detector for
  Quiescent Reliable Communication*, WDAG 1997 / Cornell TR 97-1632,
  https://www.microsoft.com/en-us/research/uploads/prod/1997/09/wdag97_hb.pdf / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (B9):** A working engineer's operational statement of the same distinction, with the
  one-sentence formulation a plugin designer wants: "When trying to contact a person who has allegedly
  disappeared one would never be satisfied with making repeated phone calls to the same location for
  half an hour and then declaring the disappearance a fact, no matter whether the phone was picked up, a
  busy tone was heard or the phone was disconnected." And: "The failure management described in this
  paper is capable of following a similar strategy: if a process under investigation is not responding
  it will contact the operating system under which the process is running, or other nodes on the same
  sub-net to help reach a decision which has more confidence." / source: Vogels, *World Wide Failures*,
  Cornell / SIGCOMM 1996, https://www.cs.cornell.edu/Projects/spinglass/public_pdfs/World%20Wide.pdf /
  fetch 2026-10-20 / confidence **primary** (author's own system write-up).

### C. OPTIMISTIC CONCURRENCY vs PESSIMISTIC LOCKING, and conflict detection on a shared FILE

- **Claim (C1):** The OCC contract, in the original: "two families of nonlocking concurrency controls are
  presented. The methods used are 'optimistic' in the sense that they rely mainly on transaction backup
  as a control mechanism, '**hoping**' that conflicts between transactions will not occur." The phases:
  "During the read phase, all writes take place on local copies … In the validation phase [the system
  checks] that the changes the transaction made will not cause a loss of integrity, the local copies are
  made global in the write phase." / source: Kung & Robinson, *On Optimistic Methods for Concurrency
  Control*, ACM TODS 6(2):213–226, June 1981, https://db.cs.cmu.edu/papers/1981/kung-tods1981.pdf /
  fetch 2026-10-20 / confidence **primary**.
- **Claim (C2):** What pessimistic locking costs, in the original — and why the plugin's always-on claim
  board is the expensive option: "Lock maintenance represents an overhead that is not present in the
  sequential case. **Even read-only transactions (queries), which cannot possibly affect the integrity
  of the data, must, in general, use locking** in order to guarantee that the data being read are not
  modified by other transactions at the same time. Also, **if the locking protocol is not deadlock-free,
  deadlock detection must be considered to be part of lock maintenance overhead.**" And: "There are no
  general-purpose deadlock-free locking protocols for databases that always provide high concurrency." /
  source: same PDF, §1 / fetch 2026-10-20 / confidence **primary**.
- **Claim (C3):** The original's own framing of the choice, which is exactly the plugin's design
  question: the two options are "for efficiency or for correctness" and the question is "what would
  happen if the lock failed?" — "**Efficiency:** Taking a lock saves you from unnecessarily doing the
  same work twice… the result is a minor increase in cost… **Correctness:** Taking a lock prevents
  concurrent processes from stepping on each others' toes and messing up the state of your system. If
  the lock fails and two nodes concurrently work on the same piece of data, the result is a corrupted
  file, data loss, permanent inconsistency… If you need locks only on a best-effort basis (as an
  efficiency optimization, not for correctness) … the locks are only approximate and may occasionally
  fail." / source: Kleppmann, *How to do distributed locking*, 2016, §"What are you using that lock
  for?" and §Conclusion, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html /
  fetch 2026-10-20 / confidence **primary**.
- **Claim (C4):** The conflict-detection primitive for a replicated file, in the original: version
  vectors. "A version vector for a file *f* is a sequence of *n* pairs, where *n* is the number of
  sites at which *f* is stored. The *i*-th pair (S_i: v_i) gives the index of the latest version of *f*
  made at site S_i… **A set of version vectors are compatible when one vector is at least as large as
  any other vector in every site component** for which they each have entries. **A set of vectors
  conflict when they are not compatible.**" Reconciling is cheap: "Two file copies with version vectors
  u, v which are not in conflict may be reconciled without any further action; the version vector of the
  reconciled file is sup u v." The paper's framing of the problem: "even the detection of inconsistent
  copies is a nontrivial problem. Naive methods either 1) compare the multiple copies entirely or 2)
  perform simple tests which will diagnose some consistent copies as inconsistent." / source: Parker,
  Popek, Rudisin, Stoughton, Walker, Walton, Chow, Edwards, Kiser & Kline, *Detection of Mutual
  Inconsistency in Distributed Systems*, IEEE TSE SE-9(3):240–247, May 1983,
  https://pages.cs.wisc.edu/~remzi/Classes/739/Papers/parker83detection.pdf / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (C5):** The concrete three-way merge, in the first-party tool documentation: `git merge-file`
  "incorporates all changes that lead from *<base>* to *<other>* into *<current>*… **A conflict occurs if
  both *<current>* and *<other>* have changes in a common segment of lines.** If a conflict is found,
  `git merge-file` normally outputs a warning and brackets the conflict with lines containing `<<<<<<<`
  and `>>>>>>>` markers." And the branch-level default: `ort` "can only resolve two heads using a
  3-way merge algorithm". The general guarantee: unrelated edits combine automatically; overlapping
  edits conflict. / source: Git official docs, https://git-scm.com/docs/git-merge-file and
  https://git-scm.com/docs/merge-strategies / fetch 2026-10-20 / confidence **primary** (first-party
  tool documentation).
- **Claim (C6):** The operational-transformation original for real-time shared editing: Ellis & Gibbs,
  *Concurrency Control in Groupware Systems*, SIGMOD 1989,
  https://sigmodrecord.org/publications/sigmodRecord/8906/pdfs/66926.66963.pdf — title/venue verified

### D. VECTOR CLOCKS

- **Claim (D1):** The original's statement of what vector time buys over Lamport's scalar clock: "we
  argue that a linearly ordered structure of time is not always adequate for distributed systems and
  propose a generalized nonstandard model of time which consists of vectors of clocks. These clock
  vectors are partially ordered and form a lattice. By using timestamps and a simple clock update
  mechanism the structure of causality is represented in an isomorphic way." The defect it fixes:
  "by mapping the partially ordered events of a distributed computation onto a linearly ordered set of
  integers it is losing information. Events which may happen simultaneously may get different
  timestamps as if they happen in some definite order." / source: Mattern, *Virtual Time and Global
  States of Distributed Systems*, Proc. Workshop on Parallel and Distributed Algorithms, Chateau de
  Bonas, France, 1989, pp. 215–226, https://pages.cs.wisc.edu/~remzi/Classes/739/Fall2015/Papers/mattern89.pdf
  / fetch 2026-10-20 / confidence **primary**.
- **Claim (D2):** The decision procedure, in the original: "If *e* occurs at process P_i then for any
  event e' [e → e' iff C_e ≤ C_e']" — i.e. two events are causally related iff one vector dominates the
  other; "Otherwise they are causally independent." The test "can be simplified if the processes where
  the events occur are known." The same paper's application to files: "In Parker et al show how vectors
  can be used to detect situations in which copies of a file were modified independently in separate
  partitions. Each copy of a file has a so called version vector whose ith component counts the number
  of updates made to the file at site i. If u ‖ v and u ≯ v for two version vectors u, v then a version
  conflict is signalled." / source: same PDF, §"Application of vector time" and §"The structure of
  vector time" / fetch 2026-10-20 / confidence **primary**.
- **Claim (D3):** The important non-guarantee, in the original's own framing: causality is not
  agreement. A vector clock tells you *whether* two events are causally ordered (or concurrent); it
  does not tell you whether concurrent writes to the same file are semantically compatible — that
  requires a merge/conflict decision (D4/C4/C5). Mattern's own use is *detection* ("a potential race
  condition exists if there is no causal relationship between two events… This can be detected by
  comparing the timestamps of the vectors"). / source: same PDF / fetch 2026-10-20 / confidence
  **primary** (the "does not decide compatibility" reading is a direct consequence of the paper's
  definitions; flagged as inference).
- **Claim (D4):** Snapshot/consistency, for completeness: "the lattice of consistent cuts and the
  lattice of possible time vectors are isomorphic"; a cut is consistent iff "every message received was
  sent". / source: same PDF, §"Consistent cuts" / fetch 2026-10-20 / confidence **primary**.

### E. BLACKBOARDS / TUPLE SPACES (LINDA)

- **Claim (E1):** The tuple-space model, in the original: "Generative communication is the basis of a new
  distributed programming language … it differs from previous interprocess communication models in
  specifying that messages be added in **tuple-structured form** to the computation environment, where
  they exist as named, independent entities until some process chooses to receive them." Operations:
  `out` (insert), `in` (remove-and-receive), `rd` (read-without-removing), `eval` (evaluate a process
  and insert the result). / source: Gelernter, *Generative Communication in Linda*, ACM TOPLAS 7(1):80–112,
  Jan 1985, https://cseweb.ucsd.edu/groups/csag/html/teaching/cse291s03/Readings/p80-gelernter.pdf /
  fetch 2026-10-20 / confidence **primary**.
- **Claim (E2):** The atomicity guarantee, in the original: "The definitions require that tuples be
  inserted into and withdrawn from TS atomically. If two in( ) statements contend for one tuple, one
  gets it and the other does not; **they cannot split it.**" And the matching/ordering semantics: "Some
  suspended in( ) statement will receive it, but **which is logically nondetermined**" — tuple space
  gives you atomic take, not FIFO order. / source: same PDF, §1.1 / fetch 2026-10-20 / confidence
  **primary**.
- **Claim (E3):** What tuple space does NOT guarantee — the delivery statement, in the original's own
  words: "Linda does not undertake to deliver messages. out(+t) works correctly if and only if
  subsequent to execution +t has been inserted in TS… **The system will not guarantee delivery, but
  should promise highly probable delivery.**" And on failure: "if an instance of +t used to exist but
  has been lost, it is once again TS and not in( ) that has failed." / source: same PDF, §"Part II"
  (faults) / fetch 2026-10-20 / confidence **primary**.
- **Claim (E4):** The property that makes tuple space a *shared record* rather than a message queue:
  "Its shared, associative memory semantics is the single most important property of tuple space";
  "Because tuple space has remove and insert rather than update in-place, it is easy to update
  atomically structures built in tuple space"; "tuple space does not require the sender to know the
  receiver, or vice versa, merely that the two agree on the format of the data." Its unit of
  granularity is the tuple: "tuple space has the tuple as its unit of granularity, which means the
  granularity is determined by the user." / source: Carriero, Gelernter et al., *Implementation of Tuple
  Space Machines*, Yale TR YALEU/DCS/RR-567, Dec 1987, §2.4 "Properties of Tuple Space",
  https://engineering.yale.edu/application/files/8517/3714/4920/tr567.pdf / fetch 2026-10-20 /
  confidence **primary**.
- **Claim (E5):** The two gaps the original itself names, both directly relevant to the plugin: "**Protection:**
  Currently tuple space is 'flat'. It is the user's responsibility to choose the format and content of
  tuples such that unintentional 'aliasing' does not occur" — and the proposed fix is per-space
  attributes (one space per topic); and "**Duplication:** Many algorithms would be made considerably
  simpler if tuple space supported some type of duplicate detection — that is, set semantics rather
  than multiset." / source: same PDF, §2.6 "Problems" / fetch 2026-10-20 / confidence **primary**.
- **Claim (E6):** The load-balancing property, in the original's own words — free load balancing is a
  *consequence* of anonymous, decoupled execution: "Because of decoupling, there is no logical
  difference between running with 1 or n workers… **An additional advantage of this decoupling is
  automatic load balancing.** Workers that execute faster or receive simpler tasks will inp tasks more
  often, while those that run slower or are given more difficult tasks will request fewer total tasks.
  As a result all workers will tend to be kept busy." / source: same PDF, §2.5 "Some Idiomatic Uses of
  Tuple Space" (master/worker skeleton) / fetch 2026-10-20 / confidence **primary**.
- **Claim (E7):** The "no more than 6 ops" scoping: the six basic operations are `in, inp, rd, rdp, out,
  eval`; the async `p`-variants make "the determination of the non-existence of a tuple" possible
  (needed to detect completion, e.g. the "task generator finished" tuple) — the original notes the
  alternative of "maintaining a count of tuples in tuple space … requires at least two extra operations
  on tuple space per task". / source: same PDF, §2.3 and §2.5 / fetch 2026-10-20 / confidence
  **primary**.

### F. SAGAS (multi-step work with compensations)

- **Claim (F1):** The original definition and guarantee: "A LLT is a saga if it can be written as a
  sequence of transactions that can be interleaved with other transactions. **The database management
  system guarantees that either all the transactions in a saga are successfully completed or
  compensating transactions are run to amend a partial execution.**" / source: Garcia-Molina & Salem,
  *Sagas*, SIGMOD 1987 / Princeton CS-TR-070-87, https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf
  (author's own copy) and https://www.cs.princeton.edu/techreports/1987/070.pdf / fetch 2026-10-20 /
  confidence **primary**. (Note: the commonly cited "Richardson 1988 Sagas" is a *later* microservices
  popularisation by Chris Richardson; the ORIGINAL is Garcia-Molina & Salem 1987 — dblp/ACM records
  confirm no Richardson 1988 primary exists. Richardson's own "Microservices Patterns" credits
  Garcia-Molina & Salem. **The angle's attribution is a mis-citation.**)
- **Claim (F2):** What a compensation does NOT do, in the original's own words: "The compensating
  transaction **undoes, from a semantic point of view**, any of the actions performed by T_i, but
  **does not necessarily return the database to the state that existed when the execution of T_i began.**
  In our airline example, if T_i reserves a seat on a flight, then C_i can cancel the reservation (say
  by subtracting one from the number of reservations and performing some other checks) But C_i cannot
  simply store in the database the number of seats that existed when T_i ran because other transactions
  could have run between the time T_i reserved the seat and C_i canceled the reservation." Compensation
  is a *semantic undo*, not a rollback. / source: same PDF, §2 / fetch 2026-10-20 / confidence **primary**.
- **Claim (F3):** Sagas trade isolation for liveness, and the original says so: "the transactions in a
  saga are related to each other and should be executed as a (non-atomic) unit; any partial executions

### H. WORK STEALING (load balance + starvation freedom)

  **primary**.
- **Claim (H2):** The mechanism and the load-balance claim, in the original: "In work sharing, whenever
  a processor generates new threads, the scheduler attempts to migrate some of them to other processors

### I. DEADLOCK DETECTION / WAIT-FOR GRAPH, and "no hold-and-wait"

- **Claim (I1):** The four necessary conditions, in the original, verbatim: "1) Tasks claim exclusive
  control of the resources they require ('**mutual exclusion**' condition). 2) Tasks hold resources
  already allocated to them while waiting for additional resources ('**wait for**' condition). 3)
  Resources cannot be forcibly removed from the tasks holding them until the resources are used to
  completion ('**no preemption**' condition). 4) A circular chain of tasks exists, such that each task
  holds one or more resources that are being requested by the next task in the chain ('**circular
  wait**' condition). **The existence of these conditions effectively defines a state of deadlock.**" /
  source: Coffman, Elphick & Shoshani, *System Deadlocks*, ACM Computing Surveys 3(2):67–78, June 1971,
  https://uobdv.github.io/Design-Verification/Supplementary/System_Deadlocks-Four_necessary_and_sufficient_conditions_for_deadlock.pdf
  / fetch 2026-10-20 / confidence **primary**.
- **Claim (I2):** Prevention by breaking ONE condition, in the original: "The system is designed so that
  deadlock is not possible… A system which is not secure from deadlock can sometimes be made secure by
  **prohibiting operations which may lead to deadlock**." The "no hold-and-wait" reading is condition 2
  above: a task must release what it holds before it waits for more. / source: same PDF, §3 "Prevention
  of Deadlock" / fetch 2026-10-20 / confidence **primary**.
- **Claim (I3):** The wait-for-graph model in the original, and the equivalence that makes cycle
  detection sound: "A knot is a nonempty set K of nodes such that the reachable set of each node in K
  is exactly set K. (We shall show that in certain cases, **the existence of a knot in a system state
  graph is a necessary and sufficient condition for deadlock**.)" And for the single-unit case:
  "**If each reusable resource has exactly one total unit, it can be shown that the conditions of
  deadlock, 'not complete reducibility,' and 'existence of a cycle in the graph' become equivalent.**"
  The detection algorithm uses "wait counts" and "ordered requests": "1) for each process there is a wait
  count which gives the number of resources whose available units are less than those requested by the
  process; and 2) for each resource there is a list of processes requesting the resource, the list being
  in order by the number of units requested" — giving a detection algorithm whose "maximum execution time
  is proportional to mn". / source: Holt, *Some Deadlock Properties of Computer Systems*, ACM Computing
  Surveys 4(3):179–196, Sept 1972, https://courses.cs.umbc.edu/graduate/CMSC621/fall02/lectures/some-deadlock-properties-of-computer-systems.pdf
  / fetch 2026-10-20 / confidence **primary**.
- **Claim (I4):** The prevention variant, in the original: "The optimum acquisition policy for a claim
  limited reusable resource system is the one that eliminates acquisitions which are not safe"; "an
  acquisition operation is said to be **safe** if it results in a state whose claim limited graph is
  completely reducible"; and the practical form: "deadlock can be prevented (while granting as many
  requests as possible) by **refusing to grant requests when the resulting state 'may lead to
  deadlock'.**" / source: same PDF, §13, Theorem 6 / fetch 2026-10-20 / confidence **primary**.
- **Claim (I5):** The original's own warning that the "wait-for" condition is what makes a claim board
  deadlock-prone, in the OS/360 case: "If a job in OS/360 begins waiting (via a Wait macro) for an
  event, the system has no way of knowing if the event will ever occur. While the job is waiting for the
  event to occur, all resources allocated to the job, including core memory, will remain idle. **To
  prevent waiting forever, OS/360 allows an arbitrary absolute limit of 30 minutes waiting time before
  canceling the job.** Why 30 minutes and not 5 minutes or 50 minutes?" — i.e. the timeout-as-backstop
  is a known, ugly, first-party admission that a wait-for graph is not being checked. / source: same
  PDF, §2 / fetch 2026-10-20 / confidence **primary**.

### The direct answer: which primitive is the claim-board-style lease missing today?

- **The fencing token (A4–A7, B7, G3) is the load-bearing missing piece.** The plugin's claim is a
  TTL lease with no monotonic generation number, and — decisively — `src/tools/room.ts` `case "post"`
  appends unconditionally, without checking that the poster still holds the claim. So the plugin is
  *already* in the "efficiency-only" regime Kleppmann describes (C3) while its own tool description
  says "before editing a shared file … claim the resource" (i.e. it is advertised as a correctness
  mechanism). Kleppmann's own analysis of the HBase bug is exactly the plugin's failure mode: a live
  holder whose lease expired keeps writing, and the second holder's write is lost. A fencing token
  requires the *protected resource* to check it (A4) — for a shared FILE, the "resource" is the file
  itself, so the token must be attached to the write path (Git-style: base+ours+theirs three-way merge
  / version vectors), not just to the claim board. Chubby's sequencer is the shipped precedent (A6).
- **Renewal/heartbeat (A8, B5, B8, B9) is the second missing piece, and it is the one that makes the
  lease correct for the "live but slow agent" case.** The plugin's `isStale` is `now >= acquiredAt +
  ttlMs` OR holder parked/aborted — there is no renewal op, so an agent that is alive and working
  slowly loses its lease at 300 s and another agent reclaims it. Chubby's KeepAlive/lease-extension
  (A8) and the failure-detector literature's "timeout is only a guess" (B5, B6, B9) say the *client*
  must renew, and a client that cannot renew must stop writing (Chubby's "jeopardy" → disable cache).
  A "claim heartbeat / renew" op is the minimal mechanics change; an agent that misses renewals
  should self-fence.
- **Dependency ordering between claims (I1–I5, F1–F4) is the third missing piece, and it is the one
  the plugin's own blocking waits are already exposed to.** Coffman condition 2 ("wait for" /
  hold-and-wait) + condition 4 (circular wait) + Holt's cycle equivalence (I3) say: if A holds a claim
  and waits for B while B holds a claim and waits for A, that is a deadlock that no TTL will fix —
  each waits out its own lease and then re-contends, forever. The plugin has three independent blocking
  waits (wait_for_claim, wait_for_agent, wait_for_message), so a cycle can span more than one wait
  mechanism and a per-mechanism check would miss it. The fix is exactly Holt's: maintain a **wait-for
  graph across all wait edges** and detect a cycle (I3), and/or make claims declare dependencies so
  that a grant is refused when it would create a cycle (I4, Coffman's prevention). Note the Sagas
  complement (F1–F4): a multi-step piece of work that partially completes needs a *compensation*
  (semantic undo, reverse order) — the plugin's `release` reasons ("released" / "expired" /
  "reclaimed" / "aborted") are a partial compensation vocabulary with no ordering rule; F4 says
  compensations must run in reverse order and child-before-parent.
- **Vector clocks (D1–D4) and version vectors (C4) are the right primitive for "who is blocked on what"
  and for conflict detection on a shared file, but they are a *reporting* primitive, not a lease
  primitive.** The plugin already has a monotonic per-record `seq` in its log and a per-agent cursor
  (`src/store/cursors.ts`), which is a Lamport-style scalar clock per agent; the plugin lacks only the
  *vector* form needed to distinguish "concurrent" from "ordered" (D1, D2) — which is exactly what
  "A and B edited the same file independently" needs, and exactly what the file-conflict literature
  calls a version vector (C4). Recommendation: use version vectors for FILE conflict detection
  (C4/C5), not for the lease.
- **Work stealing (H1–H6) is the load-balancing primitive, and it is the one the plugin cannot use
  as-is** because it has no queue of unclaimed work to steal — it has a board of *exclusively held*
  resources. Two of the plugin's primitives map onto it anyway: the **idle-waiter steal** (Go's
  `stealWork` / Tokio's steal-half) is the model for promoting the oldest waiter when a lease is
  released (the plugin already does this: `resolveWaiters` grants the oldest waiter), and the
  **starvation-freedom framing** (H3) is the right way to state a fairness guarantee: bounded work +
  bounded service time ⇒ bounded delay, and *only* eventual fairness, never equal fairness. Note
  the plugin's own first-class rate limit and T1 budget (1 post/2 s, 10 records/2048 tokens per turn)
  are exactly the "no starvation of writes" rule Gray & Cheriton state for leases (A3) — a write
  waiting for approval blocks new leases, so a claim holder that is blocked on a peer must not be
  starved by a flood of new claims.
- **Idempotency keys (G1, G2) are the missing exactly-once semantics for `room{op:"post"}`.** The
  plugin's `post` is not idempotent: a retried post after a delivery error appends a second record
  (the log is append-only and the record has a fresh `id`/`seq`). Stripe's contract (G1, G2) is
  directly copyable: client-supplied key, result saved *after* execution begins, retries replay the
  saved result, parameter mismatch is an error, key retained ≥24 h. Note the interaction with the
  T0/T1 attention tiers: a duplicate post would be delivered twice, and a mention would double-wake a
  peer.
- **Tuple space (E1–E7) is the model for the shared record, and the plugin is already most of the
  way there but is missing two of the original's named properties.** The plugin's log IS an
  associative, typed, anonymous store: `out`=post, `in`=read-with-cursor (removal), `rd`=recall
  (non-removing read), and the claim board is a typed entry set. What the original flags as missing
  and the plugin also lacks: **duplication detection / set semantics** (E5 — the plugin's log is a
  multiset; a re-posted finding is a new record) and **per-space protection** (E5 — the plugin's
  resources are flat strings `"<topic>/<key>"`; a claim on `build/agentA` and a claim on
  `build/agentB` are unrelated, and the plugin has no notion of a claim *on a topic*). Tuple space's
  **automatic load balancing** property (E6) is also the honest answer to the plugin's "who should
  pick up this work" question: a task bag + `inp` pattern-match gives work-stealing-like balance for
  free, without a coordinator.

  nothing about starvation freedom or equal fairness. The starvation-freedom statement used here is
  Tokio's own first-party bounded-delay guarantee (H3), explicitly conditioned on bounded task count
  and bounded poll time, and explicitly *not* equal fairness. **Confidence: primary** (both docs read).
- **"O'Hare & Riley, *The Linda Coordination Language* (Ellis Horwood 1988)" could not be verified**
  as a bibliographic record from any searched catalogue. It is therefore NOT used as a source. The
  tuple-space claims are all from two verified primaries: Gelernter TOPLAS 1985 (the language
  semantics) and Carriero et al., Yale TR-567 (the tuple-space *properties*, protection/duplication
  gaps, and automatic load balancing). **Confidence: primary** for what is cited; the O'Hare–Riley
  attribution is flagged **unverified**.
- **Ellis & Gibbs (operational transformation, SIGMOD 1989) title/venue verified, content not read** —
  the sigmodrecord.org PDF is a scanned image and did not text-extract. No OT claim is asserted here.
- **Conflicting normative guidance, unresolved:** Kleppmann's rule is that a lease WITHOUT a
  server-side fencing check cannot be relied on for correctness (A4, A5, C3) — yet the plugin's
  `post` path is unconditional, so its current claim board is, in Kleppmann's terms, an
  *approximate / efficiency-only* lock even though its own tool description advertises it for
  "before editing a shared file". Gray & Cheriton (A2) additionally require well-behaved clocks, which
  the plugin cannot assume either (its TTL is wall-clock `Date.now()`-based). These two facts point
  the same way — the claim board as implemented cannot deliver the correctness it advertises — but
  they do not by themselves say whether the fix is mechanics (fence the write path) or guidance (tell
  agents the claim is advisory). That is a decision for the report, not for this angle.
- **Conflicting scope note on the "no hold-and-wait" framing:** Coffman's condition 2 is literally
  "wait for" (hold-and-wait) and condition 4 is "circular wait"; the *only* condition whose removal
  alone guarantees no deadlock in the reusable-resource case is the circular-wait one, since Coffman
  et al. show "the conditions of deadlock, 'not complete reducibility,' and 'existence of a cycle in
  the graph' become equivalent" for single-unit resources (I3). So "no hold-and-wait" as a slogan is
  imprecise: removing hold-and-wait does not remove circular wait unless the order is also imposed.
  The plugin's actionable item is therefore *cycle detection over the wait-for graph*, not merely
  "don't hold while waiting". **Confidence: primary.**
