# F7 — Coding agents: OpenHands + SWE-agent (multi-agent strategies)

## Angle
What open-source coding agents (OpenHands, SWE-agent) teach about **coordination vs. parallel single agents**: intra-instance multi-agent (delegation, orchestrator-worker) vs. many independent instances coordinated by git/GitHub/human primitives. Capture (a) OpenHands microagents/skills as context files, (b) OpenHands delegation + published multi-agent findings, (c) SWE-agent single-agent loop and any multi-agent variants, (d) the origin of the "parallel instances are simpler and often better than a single coordinating instance" claim.

- **OpenHands platform paper: multi-agent delegation is a platform feature, not a measured result.** OpenHands (arXiv 2407.16741v2) lists as feature (4) "Multi-agent delegation, allowing multiple specialized agents to work together" (§2.4 "Agent Delegation: Cooperative Multi-agent Interaction"): a special action type `AgentDelegateAction` lets a generalist CodeActAgent delegate web-browsing to a specialized BrowsingAgent. The paper's evaluation section compares agents across 15 benchmarks; it contains **no controlled multi-agent vs single-agent comparison** and no coordination-cost measurement. Table 1 lists OpenHands as the only framework with all of {standardized tools, sandbox, browser, multi-agent collaboration, human-AI collaboration, AgentHub, evaluation}. / https://arxiv.org/abs/2407.16741 , https://arxiv.org/html/2407.16741v2 / 2026-10-20 / **primary**

- **OpenHands' own first-party position (2024): prefer one strong agent over a multi-agent structure.** "Don't Sleep on Single-agent Systems" (Graham Neubig, 2024-09-26) argues multi-agent systems suffer three structural costs: (i) **getting the structure right** — a specialized agent lacks the tools of its peers (their example: a Verifier that needs file-localization tools cannot do its job); (ii) **preserving context** — summarizing handoffs loses information downstream agents need; (iii) **maintainability** — each agent is a separate prompt/codebase. Prescription: one generalist LLM + one concatenated tool/action space + one prompting technique (concatenate all prompts, or retrieval-augmented prompting); multi-agent is warranted only for privileged information or per-principal agents. Argument is reasoned, not measured. / https://www.openhands.dev/blog/dont-sleep-on-single-agent-systems / 2026-10-20 / **primary**

- **OpenHands SDK delegation primitive is synchronous/blocking by design.** `TaskToolSet` guide: "Each sub-agent runs **synchronously** — the parent blocks until the sub-agent finishes and returns its result"; Tip: "TaskToolSet is designed for **sequential** blocking tasks." Sub-agent types are registered via `register_agent(name, factory_func, description)`; each task returns `TaskObservation{task_id, subagent, status, text}`; conversations are persisted so a later call with `resume=<task_id>` continues the same sub-agent with full context. Stated use cases: specialized work, sequential steps by different experts, cross-interaction context, isolating sub-task complexity from the parent's context. / https://docs.openhands.dev/sdk/guides/task-tool-set.md / 2026-10-20 / **primary**

- **OpenHands SDK parallelism is intra-agent tool fan-out, and is off by default / experimental.** "Parallel Tool Execution": `tool_concurrency_limit` default = 1 (sequential); raising it "may improve runtime performance, but use at your own risk. Concurrent execution can lead to race conditions or unexpected behavior for tools that share state." Explicitly enables "Parallel Sub-Agent Delegation" (orchestrator + `TaskToolSet` with concurrency limit 8; each sub-agent may have its own limit). Docs list "operations that modify the same files" and "workflows where one tool's output feeds into another" as *when NOT to* parallelize. / https://docs.openhands.dev/sdk/guides/parallel-tool-execution.md / 2026-10-20 / **primary**

- **OpenHands' flagship "many agents" recipe coordinates through GitHub, not through an in-conversation coordinating agent.** "Software Factory" (Agent Canvas docs): four **independent** automations — triage, developer, reviewer, watchdog — each with its own agent profile and least-privilege token (reviewer cannot push code); profiles instruct users to "disable model switching and **sub-agents**". Coordination substrate = GitHub artifacts: `ready-for-dev` label, per-agent branch prefix `factory/issue`, PRs, exact-head review/test statuses, deterministic watchdog merging only when acceptance statuses + Actions pass. Recorded deployment: six issues triaged, six developers ran **concurrently** in Docker, six PRs (#87–#92) reviewed/accepted and all merged by the watchdog. / https://docs.openhands.dev/openhands/usage/use-cases/software-factory.md / 2026-10-20 / **primary**

- **OpenHands Agent Canvas README: parallelism = separate containers/worktrees; shared workspaces cause conflicting edits.** "Option 3: With Multiple Docker Sandboxes — useful for running several agents concurrently"; each container mounts its own workspace; "Conversations using the same host workspace still share those files; **choose separate directories or worktrees to avoid conflicting edits**." / https://raw.githubusercontent.com/OpenHands/OpenHands/main/README.md / 2026-10-20 / **primary**

- **OpenHands first-party "fleets of agents" recipe = decomposition done by a human, one commit per agent, branch-and-merge.** "Automating Massive Refactors with Parallel Agents" (Robert Brennan, 2025-10-09): "If you just tell an agent, 'port this codebase to Java 25', it'll probably spin its wheels for several hours"; the workflow is human decomposition into one-shot chunks, per-agent branch off a rolling `v1-refactor` branch, each agent opens a PR into `v1-refactor` (not `main`), human review + CI, "Don't worry about merge conflicts — agents can usually work through those easily"; Refactor SDK (private beta) adds task decomposition with dependency analysis, per-task fixers/verifiers, and progress tracking; author runs "around 5 agents" max; tasks are "often only 80–90% automatable" with a human still required. / https://www.openhands.dev/blog/automating-massive-refactors-with-parallel-agents / 2026-10-20 / **primary**

- **CAID (Geng & Neubig, arXiv 2603.21489) — the strongest measured comparison of coordinated multi-agent vs single agent in coding.** Built **on top of OpenHands**; central manager builds a dependency graph, delegates to concurrent engineer agents each in its **own git worktree**, integrates via git commit/merge with test-based verification. Measured vs a single-agent baseline on the same OpenHands agent: **+25.6% absolute on PaperBench and +14.7% on Commit0** (abstract of v2). "Communication between the manager and engineers uses structured JSON instructions and git commits rather than free-form dialog." / https://arxiv.org/abs/2603.21489 , https://arxiv.org/html/2603.21489v2 / 2026-10-20 / **primary**

- **CAID: naive parallel agents that share a workspace are WORSE than a single agent.** Table 3 (PaperBench): single agent **57.2** (66.8 iters) / CAID worktree isolation **63.3** (168.3 iters) / multi-agent **soft isolation** (shared workspace, manager enforces non-overlapping files by instruction only) **55.5** (190.0 iters) — soft isolation falls *below* the single agent. Commit0-Lite: single **53.1** (84.5) / CAID **59.1** (313.3) / soft isolation **56.1** (335.9). Paper text: "instruction-level separation is not sufficient to fully eliminate interference over longer trajectories"; the OpenHands-hosted blog states the same ablation as "Removing git worktree isolation ... causes a significant performance drop ... Isolation is not an engineering convenience. It is the prerequisite for multi-agent collaboration to work at all." / https://arxiv.org/html/2603.21489v2 (Table 3, §4.1) , https://www.openhands.dev/blog/asynchronous-software-engineering-agents / 2026-10-20 / **primary**

- **CAID: single agents plateau; more budget does not substitute for coordination.** Doubling the single agent's iteration budget (100→200) yields only a small gain, while the multi-agent gain "exceeds 25 percentage points" on PaperBench (MiniMax 2.5). Paper's strategic conclusion: "Treating multi-agent coordination as a fallback after a single-agent attempt is inefficient. A more cost-effective strategy is to adopt coordinated multi-agent execution from the outset rather than switching only after failure." / https://arxiv.org/html/2603.21489v2 (§3.4–3.5) / 2026-10-20 / **primary**

- **CAID: coordination overhead is real and measured.** "multi-agent execution consistently incurs **higher API cost** than single-agent baselines, and **wall-clock runtime is not substantially reduced** despite parallel execution" — extra communication rounds, merge operations, test executions. Parallelism sweet spot is bounded: Commit0 improves 2→4 engineers but **degrades at 8** ("overly fine-grained task delegation introduces integration overhead and conflict resolution cost"); optimal parallelism depends on the task's parallelizable structure *and* the central manager's delegation capacity. / https://arxiv.org/html/2603.21489v2 (§4.2, §4.4) / 2026-10-20 / **primary**

- **Anthropic (vendor's own system, first-party write-up): orchestrator-worker beats a single agent on breadth-first research, at ~15× token cost.** Multi-agent (Opus 4 lead + Sonnet 4 subagents) "outperformed single-agent Claude Opus 4 by **90.2%** on our internal research eval"; token usage alone explains **80%** of BrowseComp variance; multi-agent systems use "about **15×** more tokens than chats"; domains "that require all agents to share the same context or involve many dependencies between agents are **not a good fit** for multi-agent"; parallelization (lead spins up **3–5** subagents + subagents use **3+** tools in parallel) "cut research time by up to 90%"; known coordination failures: spawning 50 subagents for simple queries, agents "distracting each other with excessive updates". Delegation guidance: each subagent needs an objective, an output format, guidance on tools/sources, and clear task boundaries — without them "agents duplicate work, leave gaps, or fail to find necessary information". / https://www.anthropic.com/engineering/multi-agent-research-system / 2026-10-20 / **primary**

- **The "parallel instances are simpler and often better" claim — source located: OpenAI's Asana case study (first-party customer write-up).** "From a five-sentence prompt, **up to four coding agents worked in parallel, each in a separate copy of the codebase**. An engineer checked progress twice a day and reviewed every proposed change. **Simpler instructions worked better than a more elaborate setup.**" Migration completed in ~2 weeks (1.5 weeks of engineering effort), ~$12K model+infra cost vs Asana's estimate of ~$6M fully-loaded manual effort. No coordinating agent is mentioned; the coordinating substrate is git copies + human review. / https://openai.com/index/asana/ / 2026-10-20 / **primary**

- **OpenAI Symphony spec: board-as-control-plane parallel agents; the human ceiling is 3–5 concurrent sessions.** Symphony (open-sourced spec, github.com/openai/symphony) maps every open task to a dedicated agent workspace; agents pull work; the agent decomposes into a task tree with dependencies, and "Agents only start working on tasks that aren't blocked, so execution unfolds naturally and optimally in parallel for this DAG". Constraint: "most people could comfortably manage **three to five sessions** at a time before context switching became painful"; lessons: rigid state-machine transitions don't work ("treat agents as **objectives** instead of strict transitions"); "landed PRs increase by **500%** in the first three weeks" on some teams; agents file follow-up issues themselves. / https://openai.com/index/open-source-codex-orchestration-symphony/ / 2026-10-20 / **primary**

## Conflicting evidence
- **"Multi-agent coordination" — direction of effect differs by source.** OpenHands 2024 (Neubig) argues one strong agent beats structured multi-agent (no measurement); CAID 2026 (on OpenHands) measures +25.6%/+14.7% for manager+worktree coordination vs single agent; Anthropic measures +90.2% for orchestrator-worker vs single agent (research domain, not coding). Not a contradiction in domain-free terms — but the 2024 OpenHands position and the 2026 OpenHands-hosted CAID post pull in opposite directions.
- **CAID numbers differ across versions**: arXiv v2 abstract says +25.6% (PaperBench) / +14.7% (Commit0); the OpenHands blog (2026-04-27) says +26.7% (PaperBench) / +14.3% (Commit0). Same paper, different reported figures — cite the arXiv version, treat the blog deltas as stale/approximate.
- **"Parallel is simpler" vs "coordinated multi-agent wins"**: OpenAI/Asana (parallel copies of the codebase, simple prompt, human review) and OpenHands' parallel-refactor recipe succeed with *no* coordinating agent; CAID shows parallel agents that share a workspace (soft isolation) score *below* a single agent (55.5 vs 57.2 on PaperBench) and that coordination costs more API tokens without cutting wall-clock. The reconciliation both sources support: parallelism is safe only when each agent is isolated (separate copy/worktree) and the integrator is git/tests/human — not when agents co-edit one tree and must talk to each other.
- **Task count ceiling**: OpenHands' Brennan reports maxing out at ~5 concurrent agents; OpenAI's Symphony reports humans comfortably managing 3–5 sessions; Anthropic scaled to 3–5 subagents + 3+ tools per subagent. CAID's data point says performance *decreases* at 8 engineers on Commit0. Consistent across independent sources: the useful fan-out is small (<~8) and bounded by real parallelism in the task.
- **A coordinating manager is not free**: CAID measures higher API cost and no substantial wall-clock win vs single agent, while OpenCollab measures single-agent configurations as the cheapest in tokens across suites. Whether the manager earns its cost is task-dependent (long-horizon interdependent vs isolated atomic tasks).

## Gaps
- **No first-party controlled comparison of "parallel independent instances" vs "one coordinating instance" on identical tasks.** CAID compares manager+worktree coordination against a *single* agent, not against *parallel independent instances with isolation*. The Asana write-up is an uncontrolled customer case study (no baseline, no counterfactual). So the assignment's headline claim is supported by practitioner write-ups, not by an ablation.
- **No measured numbers for the plugin's own room-based coordination** from any of these sources (no OpenHands/SWE-agent measurement of a shared-message-room coordination substrate vs. git/worktree coordination).
- **Microagents/skills guidance has never been measured *inside a multi-agent swarm*** in these sources — OpenHands' skill evaluations are single-agent, 3 tasks, 5 models; no data on whether context files improve *swarm* coordination.
- **SWE-agent multi-agent variants**: none found in the repo, docs, FAQ, or paper. The only "multi-agent SWE-agent" artifacts are third-party (MarsCode Agent, arXiv 2409.00899 — a multi-agent *system*, not a SWE-agent variant; MSWE-agent = multilingual SWE-bench adaptation). If a SWE-agent multi-agent variant is needed, it must be sourced outside the SWE-agent project.
- **OpenHands' refactor-sdk is private beta** — its decomposition/progress-tracking internals are not publicly verifiable; only the blog description exists.
- The arXiv paper named in the assignment ("Scaling long-horizon tasks with a fleet of agents", 2501.12911) **does not exist**; any downstream report citing it must be corrected to CAID (2603.21489) / 2407.16741.
