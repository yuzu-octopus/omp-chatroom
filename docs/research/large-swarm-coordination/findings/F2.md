# F2 — LangGraph

## Angle
How LangGraph makes multi-agent coordination work, and what it explicitly does NOT guarantee. Focus: shared-state graph (nodes/edges), state reducers vs. overwrite, checkpointing, interrupts + human-in-the-loop, subgraphs as reusable teams, `Send`/parallel fan-out, durable execution. Special capture: the documented `INVALID_CONCURRENT_GRAPH_UPDATE` error (exact source string, exact raise site), how teams are actually modeled in current docs, and any official cost/coordination guidance.

Note on source drift: `langchain-ai.github.io/langgraph/concepts/multi_agent/` now serves a meta-redirect to `https://docs.langchain.com/oss/python/langgraph/graph-api` (`<link rel=canonical>` observed in page head). The live docs home is `docs.langchain.com`. Docs are versioned "OSS Python"; the repo also ships JS. Everything below is Python-OSS unless stated.

## Claims

### The concurrent-update error (the centerpiece)

- **LangGraph defines `INVALID_CONCURRENT_GRAPH_UPDATE` as a first-class `ErrorCode` enum member alongside `GRAPH_RECURSION_LIMIT`, `INVALID_GRAPH_NODE_RETURN_VALUE`, `MULTIPLE_SUBGRAPHS`, `INVALID_CHAT_HISTORY`; `create_error_message()` appends the canonical troubleshooting URL `https://docs.langchain.com/oss/python/langgraph/errors/{code}` to every message.** https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/errors.py — fetch 2026-10-20 — primary
- **The error is raised in `langgraph/channels/last_value.py`, `LastValue.update()`: `if len(values) != 1: raise InvalidUpdateError(f"At key '{self.key}': Can receive only one value per step. Use an Annotated key to handle multiple values.")` with `error_code=ErrorCode.INVALID_CONCURRENT_GRAPH_UPDATE`. `LastValue` is documented as "Stores the last value received, can receive at most one value per step."** https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/channels/last_value.py — fetch 2026-10-20 — primary
- **The raise path is data-driven, not special-cased: `apply_writes()` in `pregel/_algo.py` groups writes per channel (`pending_writes_by_channel[chan].append(val)`) then calls `channels[chan].update(vals)` — the channel itself decides whether the batch is valid. `apply_writes` sorts tasks by `writes_sort_key` for deterministic application order, so the *order* is deterministic, but multiple writes to a `LastValue` channel are rejected rather than last-writer-wins.** https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/pregel/_algo.py — fetch 2026-10-20 — primary
- **Official error page: "A LangGraph `StateGraph` received concurrent updates to its state from multiple nodes to a state property that doesn't support it."** Triggers on fanout/parallel execution where a key has no reducer. Fix: define a reducer (e.g. `Annotated[list, operator.add]`) so parallel nodes can both return that key. Troubleshooting bullet: "If your graph executes nodes in parallel, make sure you have defined relevant state keys with a reducer." https://docs.langchain.com/oss/python/langgraph/errors/INVALID_CONCURRENT_GRAPH_UPDATE — fetch 2026-10-20 — primary
- **Maintainer position, 2026-10-19, on RFC issue #7907 ("Cross-node write-intent registry for parallel graph execution"): "langgraph already handles the case this targets: parallel writes to a plain (LastValue) key in one step raise InvalidUpdateError instead of silently keeping one."** The RFC proposed node-level `writes=["status",...]` intent declarations plus admission policies (refuse/queue/warn) and was closed with that answer. The RFC itself states it is **not** a distributed lock, **not** transactional, and that multi-worker deployments would need a shared backend. https://github.com/langchain-ai/langgraph/issues/7907 — fetch 2026-10-20 — primary
  - Teaching: LangGraph's answer to conflicting parallel writes is *fail loudly at the channel*, not detect-then-arbitrate. There is no built-in conflict detector, no admission control, no "who is blocked on what", no lease/claim primitive. The RFC's `writes=` intent declaration and refuse/queue/warn policies remain unimplemented.
- **Known bug (still open, labels `bug, pending, external`): #6446 — parallel subgraph + parent-node fan-out raises `InvalidUpdateError: At key 'b': Can receive only one value per step` even though the subgraph never writes key `b`. Reproduced by a second commenter on langgraph 1.1.6 (2026-04-04) under `astream_events(version="v2")` with two compiled subgraphs sharing a state key; workaround is to wrap the compiled subgraph in a function node.** https://github.com/langchain-ai/langgraph/issues/6446 — fetch 2026-10-20 — primary
- **Related separate error `MULTIPLE_SUBGRAPHS` (calling the same checkpointed subgraph multiple times in one node) has three documented opt-outs: `checkpointer=False`; default inherited mode (each invocation gets a unique namespace → parallel execution works, starts fresh, can still `interrupt()`); `checkpointer=True` (position-based namespace suffix `calling_node`, `calling_node|1`).** https://docs.langchain.com/oss/python/langgraph/errors/MULTIPLE_SUBGRAPHS — fetch 2026-10-20 — primary

### Reducers vs. overwrite

- **Each state key has an independent reducer; "If no reducer function is explicitly specified then it is assumed that all updates to the key should override it." Default reducer discards left (current state) and keeps right (node update).** https://docs.langchain.com/oss/python/langgraph/graph-api — fetch 2026-10-20 — primary
- **`Overwrite` bypasses a reducer; documented constraint: "When nodes execute in parallel, only one node can use `Overwrite` on the same state key in a given super-step. If multiple nodes attempt to overwrite the same key in the same super-step, an `InvalidUpdateError` will be raised."** https://docs.langchain.com/oss/python/langgraph/use-graph-api — fetch 2026-10-20 — primary
- **With a merging reducer, returning an empty value does NOT clear the field (empty right-arg is merged in); clearing requires `Overwrite([])`.** https://docs.langchain.com/oss/python/langgraph/graph-api — fetch 2026-10-20 — primary
- **`messages` is the canonical shared key; `add_messages` reducer is prebuilt (`MessagesState`), and it is "vital to telling the graph how to update the list" — without it, every state update overwrites.** https://docs.langchain.com/oss/python/langgraph/graph-api — fetch 2026-10-20 — primary
- **Reducers are per-key binary functions `(left=current_state[key], right=node_update[key])`; left always from accumulated state, right always from the latest node update.** https://docs.langchain.com/oss/python/langgraph/graph-api — fetch 2026-10-20 — primary

### Supersteps, parallelism, ordering — the explicit non-guarantees

- **"Importantly, updates from a parallel superstep may not be ordered consistently. If you need a consistent, predetermined ordering of updates from a parallel superstep, you should write the outputs to a separate field in the state together with a value with which to order them."** (exact wording from the parallelization section of Use the graph API) https://docs.langchain.com/oss/python/langgraph/use-graph-api — fetch 2026-10-20 — primary
- **Supersteps are transactional: "If any of these branches raises an exception, none of the updates are applied to the state (the entire superstep errors)." With a checkpointer, successful nodes' results within the failed superstep are saved and are not repeated on resume.** https://docs.langchain.com/oss/python/langgraph/use-graph-api — fetch 2026-10-20 — primary
- **LangGraph's own design post claims deterministic application order that does not depend on which node started/finished first — "it applies updates from nodes in an order which doesn't depend on which one started or finished first (as that can change between executions). This ensures that the execution order and latency of each node never influences the final output of the agent."** https://www.langchain.com/blog/building-langgraph — fetch 2026-10-20 — primary
  - **Conflict:** the blog says update application order is deterministic and latency-independent; the docs say parallel-superstep updates "may not be ordered consistently" and you must add your own ordering field. Reconciliation: the *runtime* application order is deterministic (no data race), but the *order of values inside a merged list* is not a documented, user-visible guarantee. Users must sort explicitly.
- **Fan-in semantics are explicit and differ by edge form: (a) list-form `add_edge(["b_2","c"], "d")` runs `d` once after all listed nodes complete — but if one never runs, `d` never runs and no error is raised, and completed-branch updates stay in state unconsumed; (b) separate edges run `d` once per superstep in which any incoming branch completes (so with unequal branch lengths, `d` runs more than once); (c) `defer=True` runs `d` once after every selected branch completes, and postpones it until no tasks are pending anywhere in the graph, not just its feeders — a `Send` addressed to that node still invokes it separately.** https://docs.langchain.com/oss/python/langgraph/use-graph-api — fetch 2026-10-20 — primary
- **`Send` is the map-reduce / dynamic fan-out primitive: a conditional edge returns `[Send("generate_joke", {"subject": s}) for s in state["subjects"]]` to dispatch N parallel tasks with per-task input.** https://docs.langchain.com/oss/python/langgraph/use-graph-api — fetch 2026-10-20 — primary
- **Fault-tolerance layer (langgraph>=1.2): per-node `retry_policy=RetryPolicy(max_attempts=3)` (default retries any exception except ValueError/TypeError/OSError-family/etc.; 5xx for requests/httpx), per-node `timeout=` (async only; `run_timeout` wall clock, `idle_timeout` progress-resetting, with `runtime.heartbeat()` manual reset), and `error_handler` receiving a `NodeError(node, error)` and returning a `Command` to route to a recovery branch. Compose order: retry first, then handler, then bubble.** https://docs.langchain.com/oss/python/langgraph/fault-tolerance — fetch 2026-10-20 — primary
- **`NodeTimeoutError` is retryable by default and writes from the timed-out attempt are cleared before retry; `Send` can carry a per-dispatch timeout override.** https://docs.langchain.com/oss/python/langgraph/fault-tolerance — fetch 2026-10-20 — primary
- **Parallel node failure semantics are documented as a superstep-wide transaction; per-node error handlers (`langgraph>=1.2`) are the escape hatch for recovering one branch without aborting the superstep.** https://docs.langchain.com/oss/python/langgraph/fault-tolerance + use-graph-api — fetch 2026-10-20 — primary

### Checkpointing / durable execution

- **Three durability modes, least→most durable: `"exit"` (persist only on exit — "you cannot recover from system failures (like process crashes) mid-execution"), `"async"` (persist while next step executes — "small risk that LangGraph does not write checkpoints if the process crashes"), `"sync"` (persist synchronously before next step starts; highest durability, performance overhead).** https://docs.langchain.com/oss/python/langgraph/checkpointers — fetch 2026-10-20 — primary
- **Checkpoint is written at each super-step boundary (a super-step = one tick where all nodes scheduled for that step execute, potentially in parallel); per-task writes are ALSO persisted to `checkpoint_writes` as each node finishes, enabling "pending writes" recovery — if a peer node fails in the same superstep, successful nodes are not re-run on resume. Full `StateSnapshot` is committed only when the superstep completes.** https://docs.langchain.com/oss/python/langgraph/checkpointers — fetch 2026-10-20 — primary
- **Threads are the unit of isolation: `thread_id` is the checkpointer primary key; "threads are completely independent, and each invocation only touches a single one." Cross-thread data goes through Stores, not checkpointers.** https://docs.langchain.com/oss/python/langgraph/checkpointers — fetch 2026-10-20 — primary
- **Checkpoint namespaces scope subgraphs: `""` = root graph, `"node_name:uuid"` = subgraph invoked as that node, nested joined with `|`.** https://docs.langchain.com/oss/python/langgraph/checkpointers — fetch 2026-10-20 — primary
- **Documented limitation: "When a subgraph updates state, the parent graph may not see the changes immediately. This is because each subgraph manages its own checkpoint namespace." Fix: shared state via Store, or configure the subgraph to write to the parent checkpoint.** https://docs.langchain.com/oss/python/langgraph/persistence — fetch 2026-10-20 — primary
- **Checkpoint storage grows unboundedly for long conversations (full value of every channel per super-step) → prune or set retention. `DeltaChannel` (langgraph>=1.2, beta) stores incremental deltas instead of full accumulated values.** https://docs.langchain.com/oss/python/langgraph/checkpointers — fetch 2026-10-20 — primary
- **Design rationale (first-party): BSP/Pregel chosen because it "provides deterministic concurrency, with full support for loops"; nodes run with independent copies of channel values so they don't affect each other while running; updates applied after all nodes finish, in deterministic order — "this is what guarantees no data races".** https://www.langchain.com/blog/building-langgraph — fetch 2026-10-20 — primary
- **Six features the design targets: parallelization, streaming, task queue, checkpointing, human-in-the-loop, tracing. Note the scoping: "Task queue. This was out of scope for a Python library such as LangGraph, so we ended up creating LangGraph Platform to answer this need."** https://www.langchain.com/blog/building-langgraph — fetch 2026-10-20 — primary
- **Design philosophy: "We don't know what the future holds for AI" + "It should feel like writing code"; each of the six features is opt-in building blocks, not a mandatory abstraction.** https://www.langchain.com/blog/building-langgraph — fetch 2026-10-20 — primary

### Interrupts / human-in-the-loop

- **`interrupt()` is dynamic (placeable anywhere, conditional), saves state via the checkpointer, and "waits indefinitely until you resume execution"; requires (1) a checkpointer (durable in production), (2) a `thread_id` in config, (3) a JSON-serializable payload.** https://docs.langchain.com/oss/python/langgraph/interrupts — fetch 2026-10-20 — primary
- **Critical re-execution semantics: "The node restarts from the beginning of the node where the `interrupt()` was called when resumed, so any code before the `interrupt()` runs again."** This is the single most load-bearing non-guarantee for HITL: side effects before the interrupt replay. https://docs.langchain.com/oss/python/langgraph/interrupts — fetch 2026-10-20 — primary
- **Resume must use the same `thread_id`; `Command(resume=...)` is the ONLY Command pattern valid as invoke/stream input (passing `Command(update=...)` as input is documented as wrong).** https://docs.langchain.com/oss/python/langgraph/interrupts — fetch 2026-10-20 — primary
- **Multiple simultaneous interrupts (parallel branches each interrupting) must be resumed in one invocation using a `{interrupt_id: value}` map so each response pairs with the right interrupt.** https://docs.langchain.com/oss/python/langgraph/interrupts — fetch 2026-10-20 — primary
- **Typed resume via `interrupt(..., response_schema=...)` requires `langgraph>=1.2.12`; invalid input raises `pydantic.ValidationError` and can be retried with the same thread_id.** https://docs.langchain.com/oss/python/langgraph/interrupts — fetch 2026-10-20 — primary
- **Interrupt payloads surface via `stream.interrupts` / `stream.interrupted` under the v3 event-stream API, or `result["__interrupt__"]` under `invoke()`.** https://docs.langchain.com/oss/python/langgraph/interrupts — fetch 2026-10-20 — primary

### Subgraphs as teams; how teams are actually modeled

- **Two documented subgraph wiring patterns: (a) call a subgraph inside a node when parent and subgraph have DIFFERENT state schemas — you write a wrapper that maps parent state → subgraph input and subgraph output → parent state; (b) add a compiled subgraph directly as a node when they SHARE state keys — no wrapper, it reads/writes the parent's channels.** https://docs.langchain.com/oss/python/langgraph/use-subgraphs — fetch 2026-10-20 — primary
- **Subgraphs' stated purpose: building multi-agent systems, reusing node sets across graphs, and "Distributing development: ... different teams to work on different parts of the graph independently, as long as the subgraph interface (the input and output schemas) is respected."** https://docs.langchain.com/oss/python/langgraph/use-subgraphs — fetch 2026-10-20 — primary
- **Cross-graph navigation: `Command(goto=..., graph=Command.PARENT)` navigates to the closest parent graph relative to the subgraph. Documented constraint: "When you send updates from a subgraph node to a parent graph node for a key that's shared by both parent and subgraph state schemas, you must define a reducer for the key you're updating in the parent graph state."** https://docs.langchain.com/oss/python/langgraph/use-graph-api — fetch 2026-10-20 — primary
- **Current official multi-agent pattern set (LangChain docs, "Multi-agent" index): Subagents, Handoffs, Skills, Router, Custom workflow. The docs also say: "not every complex task requires this approach — a single agent with the right (sometimes dynamic) tools and prompt can often achieve similar results."** https://docs.langchain.com/oss/python/langchain/multi-agent — fetch 2026-10-20 — primary
- **Subagents pattern (the current "team" model): a central main agent (supervisor) calls subagents AS TOOLS. Key characteristics: centralized control (all routing passes through the main agent), no direct user interaction, subagents invoked via tools, main agent can invoke multiple subagents in a single turn. Subagents are STATELESS by default — all conversation memory is held by the main agent.** https://docs.langchain.com/oss/python/langchain/multi-agent/subagents — fetch 2026-10-20 — primary
- **Two tool shapes for subagents: "Tool per agent" (fine-grained input/output control) vs "Single dispatch tool" (a `task(agent_name, description)` tool with a registry) — the latter is described as supporting "Team distribution: Different teams can develop and deploy agents independently" and "Agent discovery ... via system prompt ... or through progressive disclosure".** https://docs.langchain.com/oss/python/langchain/multi-agent/subagents — fetch 2026-10-20 — primary
- **Official guidance to use interrupts inside a subagent for user interaction, while the main agent remains the orchestrator.** https://docs.langchain.com/oss/python/langchain/multi-agent/subagents — fetch 2026-10-20 — primary
- **Handoffs pattern: tools update a state variable (`current_step`/`active_agent`) that persists across turns and switches agent or config. Term "handoffs" credited to OpenAI. Two implementations: single agent with middleware (recommended for most cases) or multiple agent subgraphs using `Command.PARENT`.** https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs — fetch 2026-10-20 — primary
- **Handoff correctness requirement (a coordination invariant enforced only by convention): the handoff must include BOTH the `AIMessage` carrying the tool call AND a matching `ToolMessage` ("without this pairing, the receiving agent will see an incomplete conversation and may produce errors or unexpected behavior").** https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs — fetch 2026-10-20 — primary
- **Router pattern: a dedicated routing step classifies input and dispatches to zero or more agents in parallel, results synthesized. Stateless by default; `Command` for single-agent routing, `Send` for parallel fan-out.** https://docs.langchain.com/oss/python/langchain/multi-agent/router — fetch 2026-10-20 — primary
- **Documented router warning: "Stateful routers require custom history management ... With parallel invocation, you'll need to maintain history at the router level."** https://docs.langchain.com/oss/python/langchain/multi-agent/router — fetch 2026-10-20 — primary
- **Skills pattern: a single agent loads specialized prompts/knowledge on demand via a `load_skill` tool — "progressive disclosure"; also supports dynamic tool registration and hierarchical skills.** https://docs.langchain.com/oss/python/langchain/multi-agent/skills — fetch 2026-10-20 — primary
- **Superseded first-party libraries: `langgraph-supervisor` README now opens "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases"; `langgraph-swarm` still ships `create_swarm`/`create_handoff_tool` with a `default_active_agent` router that remembers the last active agent.** https://raw.githubusercontent.com/langchain-ai/langgraph-supervisor-py/main/README.md, https://raw.githubusercontent.com/langchain-ai/langgraph-swarm-py/main/README.md — fetch 2026-10-20 — primary
- **2024 first-party framing of multi-agent on LangGraph: "multiple independent actors powered by language models connected in a specific way"; each agent = a node, connections = edges, "they communicate by adding to the graph's state"; named examples: Multi-Agent Collaboration (shared scratchpad), Agent Supervisor (private scratchpads + global scratchpad), Hierarchical Agent Teams (subagents are themselves LangGraph graphs).** https://www.langchain.com/blog/langgraph-multi-agent-workflows — fetch 2026-10-20 — primary

### What LangGraph explicitly does NOT provide

- **No shared task list / no cross-agent board. The Deep Agents `write_todos` tool "maintains a task list in the current agent's state" — per-agent, not shared across agents or subagents; docs describe it as an opt-in planning tool for the main agent.** https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/overview.mdx (source: "Tasks support status tracking ('pending','in_progress','completed') and are persisted in agent state") + https://docs.langchain.com/oss/python/deepagents/subagents ("Subagents are stateless and cannot send multiple messages back") — fetch 2026-10-20 — primary
- **No multi-hop / no agent-to-agent initiative in the default patterns: the multi-agent index's capability matrix rates Handoffs as "—" for Parallelization, and Router as "—" for Multi-hop. Parallelization exists only as "the main agent can invoke multiple subagents in a single turn" (fan-out) or router parallel dispatch.** https://docs.langchain.com/oss/python/langchain/multi-agent — fetch 2026-10-20 — primary
- **No ordering guarantee for parallel results, no conflict detection beyond the channel-level error, no admission control, no leases/claims, no "blocked on what" graph, no per-agent budgets, no chatter backpressure.** Derived from the exhaustive error-code enum (5 codes, none about leases/conflicts/budgets) + docs' explicit "may not be ordered consistently" + issue #7907's unanswered admission-control RFC. https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/errors.py, https://docs.langchain.com/oss/python/langgraph/use-graph-api, https://github.com/langchain-ai/langgraph/issues/7907 — fetch 2026-10-20 — primary
- **Sync subagents explicitly block the supervisor and cannot be steered mid-flight: "Inline subagents block your supervisor agent for the duration of the task ... the supervisor can't respond to users, coordinate other work, or course-correct until the subagent finishes"; "Subagents can't run concurrently, so there's no cross-pollination of results. And subagent turns are all-or-nothing."** https://www.langchain.com/blog/running-subagents-in-the-background — fetch 2026-10-20 — primary
- **The async-subagent escape hatch is explicitly out-of-band process machinery, not a graph primitive: five supervisor tools (`start_async_task`, `check_async_task`, `update_async_task`, `cancel_async_task`, `list_async_tasks`), built on the Agent Protocol spec so subagents "run as fully separate agents with their own process and state". The `task_id` IS the subagent's thread id; task metadata lives in a dedicated `async_tasks` state channel so it survives message-history compaction.** https://docs.langchain.com/oss/python/deepagents/async-subagents — fetch 2026-10-20 — primary
- **Async subagent limitations: the supervisor "cannot answer or approve on the user's behalf" for a subagent waiting on input ("The request is for the user"); `update_async_task` restarts the subagent with full history plus new instructions (previous run is interrupted); fork mode is "experimental" and Python-only; task notifications require `deepagents>=0.7.26` and are beta.** https://docs.langchain.com/oss/python/deepagents/async-subagents — fetch 2026-10-20 — primary
- **Handoff/swarm pattern shares ONE `messages` list by default — "messages from all of the agents will be combined into a single, shared list of messages" — and the library docs flag that this may be undesirable, requiring a custom state key per agent plus a state-transform wrapper.** https://raw.githubusercontent.com/langchain-ai/langgraph-swarm-py/main/README.md — fetch 2026-10-20 — primary
- **LangGraph the library does not provide a task queue / durable job execution; that was moved to LangGraph Platform / Agent Server.** https://www.langchain.com/blog/building-langgraph — fetch 2026-10-20 — primary

### Deployment / platform coordination semantics (Agent Server)

- **Runs are enqueued, not executed on demand: "When a client creates a run, the API server enqueues it and a queue worker picks it up for execution." Redis carries wake-up/cancel/stream signals only — run data lives in PostgreSQL.** https://docs.langchain.com/langsmith/agent-server — fetch 2026-10-20 — primary
- **Concurrency bound: "Each worker executes up to `N_JOBS_PER_WORKER` runs concurrently (default: 10) ... This bounds concurrent run execution, not the number of API requests the deployment can serve."** https://docs.langchain.com/langsmith/agent-server — fetch 2026-10-20 — primary
- **Autoscaling: on self-hosted with KEDA, queue workers scale on pending+running runs; "The KEDA backlog target is 75% of the configured jobs per worker, rounded down to at least 1." CPU target is 50% of the CPU limit for both worker tiers.** https://docs.langchain.com/langsmith/data-plane — fetch 2026-10-20 — primary
- **Run retry policy: "Runs in an Agent Server may be retried for specific failures (currently only for transient PostgreSQL errors encountered during the run)", limited to 3 attempts per run.** https://docs.langchain.com/langsmith/data-plane — fetch 2026-10-20 — primary
- **Distributed runtime exists for "large-scale deployments with high concurrency requirements": one process for orchestration, one for execution.** https://docs.langchain.com/langsmith/agent-server — fetch 2026-10-20 — primary
- **Per-thread run-conflict policy exists at the platform level as `multitask_strategy` (reject / enqueue / interrupt / rollback), distinct from in-graph `interrupt()`. NOTE: the `langchain-ai.github.io/langgraph/concepts/double_texting/` page now meta-redirects to `docs.langchain.com/oss/python/langgraph/graph-api`; the strategy list is corroborated by the SDK reference and the Managed Deep Agents "Create a thread run" API page.** https://reference.langchain.com/python/langgraph-sdk/schema/MultitaskStrategy ; https://docs.langchain.com/langsmith/managed-deep-agents-api/runs/create-thread-run — fetch 2026-10-20 — primary

### Official cost / coordination guidance (numbers only where sourced)

- **Official performance comparison (docs "Multi-agent" → Performance comparison) gives model-call counts and token totals for three scenarios.** One-shot "buy coffee": Subagents 4 calls, Handoffs 3, Skills 3, Router 3. Repeat request (turn 2 + total): Subagents 4 / 8 total, Handoffs 2 / 5 total, Router 3 / 6 total, Skills 2 / 5 total. Multi-domain (Python/JS/Rust, ~2000 tokens of docs per language): Subagents 5 calls / ~9K tokens, Handoffs 7+ calls / ~14K+ tokens, Skills 3 calls / ~15K tokens, Router 5 calls / ~9K tokens. Documented insights: "Subagents adds one extra call because results flow back through the main agent"; "Stateful patterns (Handoffs, Skills) save 40-50% of calls on repeat requests"; "Subagents processes 67% fewer tokens overall [than Skills] due to context isolation"; "Handoffs is inefficient here — it must execute sequentially and can't leverage parallel tool calling." https://docs.langchain.com/oss/python/langchain/multi-agent — fetch 2026-10-20 — primary
- **The same numbers are repeated in the first-party blog "Choosing the Right Multi-Agent Architecture" (Sydney Runkle, Jan 14 2026), plus the framing "Adds one extra model call per interaction because results must flow back through the main agent. This overhead provides centralized control and context isolation, but costs latency and tokens."** https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture — fetch 2026-10-20 — primary
- **Pattern-selection guidance, official: Subagents for "multiple distinct domains ... need parallel execution"; Skills for "single agent with many possible specializations"; Handoffs for "sequential workflow with state transitions"; Router for "distinct verticals, query multiple sources in parallel and synthesize results".** Same URL — primary

## Conflicting evidence
- **Update ordering.** LangGraph's design blog asserts update application order is deterministic and never influenced by which node started/finished first (https://www.langchain.com/blog/building-langgraph); the current docs say parallel-superstep updates "may not be ordered consistently" and require the user to add an ordering value (https://docs.langchain.com/oss/python/langgraph/use-graph-api). Both are first-party. Resolution: runtime determinism ≠ user-visible ordering guarantee; treat docs as binding.
- **Two different "subagent" lineages.** The LangGraph multi-agent docs (2026) define subagents as *tool calls* by a supervisor, stateless, sync by default; Deep Agents' `async-subagents` docs describe agents with their own processes, threads, steering and cancellation via Agent Protocol. The Deep Agents blog explicitly frames inline subagents as a pattern that "has started to break down" for long tasks. Do not conflate the two when characterizing "LangGraph multi-agent".
- **`langgraph-supervisor` deprecation.** The library still ships and works, but its own README now steers users to the tool-based supervisor pattern. Treat supervisor-library examples as legacy.
- **Legacy docs URLs.** `langchain-ai.github.io/langgraph/*` meta-redirects to `docs.langchain.com/oss/python/langgraph/graph-api`, so old-blog citations (e.g. the `double_texting` multitask-strategy page) no longer render at their old path; the SDK reference and Managed Deep Agents API pages corroborate the strategy list.
- **Conflict detection.** RFC #7907 argues reducers "can't catch" logically-exclusive parallel updates and proposes admission control; the LangChain maintainer answered that `InvalidUpdateError` already covers it. The RFC was closed with that reply; no admission-control feature exists in the codebase (only 5 error codes, no conflict-related code path found in `errors.py`).

## Gaps
- **No official LangGraph-native primitive for: leases/claims on a resource, dependency ordering between claims, shared task lists across agents, "who is blocked on what", chatter budgets/backpressure, escalation paths, per-agent cost budgets, or retrieval of coordination literature.** Verified against: the complete `ErrorCode` enum (5 members), the LangGraph docs page inventory (`_llms/agent-development-lifecycle/build/python.txt`), and issue #7907 (admission control unimplemented). No lease/lock RFC exists in the tracker beyond #7907's explicit "not a distributed lock".
- **#6446 (parallel subgraph + shared key raising InvalidUpdateError) is still open and unfixed as of the fetch.** This is a live correctness hazard for exactly the "parallel teams writing a shared state" pattern our plugin emulates.
- **No primary source found quantifying LangGraph multi-agent coordination quality** (task-completion rates, deadlock rates, duplicate-work rates). The only numbers are call-count/token tables (deterministic, architecture-derived) and Anthropic's internal eval (not reproducible, different stack). "Unverified" for any claim about how well LangGraph swarms coordinate.
- **`multitask_strategy` is not documented on a live OSS LangGraph page** (the legacy `double_texting` page now redirects). The four strategies are corroborated only by the SDK reference schema and the Managed Deep Agents API docs — usable but not a first-class OSS doc statement.
- **Deep Agents `write_todos` non-sharing** is asserted in docs prose ("persisted in agent state") but there is no explicit sentence "not shared across subagents"; the negative claim is inferred from the docs' per-agent framing plus the absence of any shared-board statement. Confidence: primary but inferential.
