# F6 — Role-playing agent societies (MetaGPT, ChatDev, AgentVerse, GPTSwarm, Magentic-One)

## Angle
What literature-grade (primary) evidence exists that structured role assignment + SOPs + structured message/ledger primitives improve multi-agent LLM team outcomes; and whether the "ledger / structured-message" idea is a defensible candidate primitive for a flat, peer-to-peer shared room (the omp-chatroom plugin).

Caveat carried throughout: **every benchmark number below is SELF-REPORTED by the paper's own authors**, on datasets that are largely self-authored (SRDD, SoftwareDev) or leaderboard-derived. No independent replication of any of these claims was located in this pass (see Gaps).

Repo identity note: the MetaGPT repo is now `FoundationAgents/MetaGPT` (README fetched successfully from that path; the arXiv paper links `geekan/MetaGPT`, which resolves to the same org). `OpenBMB/ChatDev` main branch is now "ChatDev 2.0 / DevAll" (zero-code platform, announced Jan 2026); the paper-era implementation lives on the `chatdev1.0` branch. `metauto-ai/GPTSwarm` (MIT, homepage gptswarm.org, desc "The First Self-Improving agents with RL / Prompting Optimization"). `microsoft/autogen` `autogen-magentic-one` package was the original (v0.4.4) implementation; current port is `autogen-agentchat` + `autogen-ext`.

## Claims

### A. MetaGPT (arXiv 2308.00352) — SOP as program, structured docs, pub/sub pool
- **Claim A1**: MetaGPT's core claim is that human SOPs can be *encoded into prompt sequences* so agents behave like a software company; roles are specialised via a profile (name/profile/goal/constraints) + per-role context/skills, and work flows **sequentially** along the SOP. Roles shipped: Product Manager, Architect, Project Manager, Engineer, QA Engineer. / URL: https://arxiv.org/abs/2308.00352 (§1, §3.1) / 2026-10-20 / **primary**
- **Claim A2**: MetaGPT explicitly rejects free-form dialogue as the agent-to-agent channel: "agents in MetaGPT communicate through documents and diagrams (structured outputs) rather than dialogue"; the motivating argument is telephone-game distortion ("after several rounds of communication, the original information may be quite distorted"). / URL: https://arxiv.org/abs/2308.00352 (§3.2) / 2026-10-20 / **primary**
- **Claim A3**: MetaGPT uses a **shared global message pool** + **publish/subscribe**: agents publish structured messages into one pool; any agent may retrieve needed info without one-to-one inquiry; to avoid information overload each agent **subscribes by role** to only relevant message types, and "an agent activates its action only after receiving all its prerequisite dependencies". / URL: https://arxiv.org/abs/2308.00352 (§3.2, Fig. 2 left) / 2026-10-20 / **primary**
- **Claim A4**: Code corroborates A3: `Environment.publish_message` fans a message out to every role whose address matches (`is_send_to(message, addrs)`), each role buffers it in a private `MessageQueue`, and `Role._watch` populates `rc.watch` (a set of action tags) used by `important_memory = memory.get_by_actions(self.watch)`. Docstring cites internal RFCs 113/116 for routing. / URL: https://raw.githubusercontent.com/FoundationAgents/MetaGPT/main/metagpt/environment/base_env.py and https://raw.githubusercontent.com/FoundationAgents/MetaGPT/main/metagpt/roles/role.py / 2026-10-20 / **primary (first-party code)**
- **Claim A5**: MetaGPT adds **executable feedback**: Engineer writes+executes its own unit tests, reads results, debugs, retries up to 3 times. / URL: https://arxiv.org/abs/2308.00352 (§3.3) / 2026-10-20 / **primary**
- **Claim A6 (self-reported numbers)**: MetaGPT claims SOTA Pass@1 of **85.9% (HumanEval)** and **87.7% (MBPP)**, and "in our experimental evaluations, MetaGPT achieves a 100% task completion rate". / URL: https://arxiv.org/abs/2308.00352 (§1) / 2026-10-20 / **primary (self-reported)**
- **Claim A7 (self-reported)**: Executable-feedback ablation = **+4.2% Pass@1 HumanEval, +5.4% Pass@1 MBPP**; on SoftwareDev it moves executability 3.67→3.75 and human revision cost 2.25→0.83. / URL: https://arxiv.org/abs/2308.00352 (§4.2 Table 1, §4.4) / 2026-10-20 / **primary (self-reported)**
- **Claim A8 (self-reported, role-count ablation)**: Adding roles monotonically improves the 2 tasks studied: Engineer only (1 agent) → executability 1.0, human revisions 10, expense $0.915; Engineer+PM+Architect+ProjectMgr (4 agents) → executability 4.0, revisions 2.5, expense $1.385. "When we exclude certain roles, unworkable codes are generated." / URL: https://arxiv.org/abs/2308.00352 (§4.3 Table 3) / 2026-10-20 / **primary (self-reported)**
- **Claim A9 (self-reported)**: On **SoftwareDev — ChatDev's own dataset** — MetaGPT beats ChatDev: executability 3.75 vs 2.25, human revision cost 0.83 vs 2.5, runtime 541s vs 762s, tokens 31,255 vs 19,292 (tokens per code line 124.3 vs 248.9). / URL: https://arxiv.org/abs/2308.00352 (§4.2 Table 1) / 2026-10-20 / **primary (self-reported; note dataset ownership + author overlap, see Conflicting evidence)**
- **Claim A10**: README states the philosophy literally: "**`Code = SOP(Team)`** is the core philosophy. We materialize SOP and apply it to teams composed of LLMs." / URL: https://raw.githubusercontent.com/FoundationAgents/MetaGPT/main/README.md / 2026-10-20 / **primary (first-party)**
- **Claim A11**: MetaGPT names the coordination pathology it is designed against: "reduces the risk of hallucinations caused by **idle chatter** between LLMs, particularly in role-playing frameworks, like: 'Hi, hello and how are you?'". Also cites known failure modes "assistant repeated instruction" and "infinite loop of message". / URL: https://arxiv.org/abs/2308.00352 (§1, §2) / 2026-10-20 / **primary**

### B. ChatDev (arXiv 2307.07924) — chat chain, dual agent, communicative dehallucination, tiered memory
- **Claim B1**: ChatDev's workflow primitive is a **chat chain**: C = ⟨P¹..Pⁿ⟩, Pⁱ = ⟨T¹..Tᵐ⟩, Tʲ = τ(C(I,A)), with C(I,A) = ⟨I→A, A↝I⟩. Phases = design / coding / testing; coding split into write+complete, testing into review+system-test. Every subtask is exactly **two agents**: instructor (I) + assistant (A). / URL: https://arxiv.org/abs/2307.07924 (§3.1, Eq. 1) / 2026-10-20 / **primary**
- **Claim B2**: Rationale for the dual-agent shape is explicit: "The dual-agent communication design **simplifies communications by avoiding complex multi-agent topologies**, effectively streamlining the consensus-reaching process." / URL: https://arxiv.org/abs/2307.07924 (§3.1) / 2026-10-20 / **primary**
- **Claim B3**: **Communicative dehallucination** = a deliberate *role reversal*: the assistant proactively asks the instructor for more specific detail before giving a conclusive answer; vanilla ⟨I→A, A↝I⟩ becomes ⟨I→A, ⟨A→I, I↝A⟩, A↝I⟩. Motivation is coding hallucination caused by vague instructions ("role flipping, instruction repeating, and fake replies" are named as failures of naive multi-round exchange). / URL: https://arxiv.org/abs/2307.07924 (§3.2, Eq. 6–7) / 2026-10-20 / **primary**
- **Claim B4**: Memory is **tiered by phase**: short-term = current phase dialogue; long-term = only the *extracted solutions* of prior phases, injected at the start of the next phase — "By sharing only the solutions of each subtask rather than the entire communication history, ChatDev minimizes the risk of being overwhelmed by too much information". / URL: https://arxiv.org/abs/2307.07924 (§3.1, Eq. 3–5) / 2026-10-20 / **primary**
- **Claim B5**: Termination is *mechanical*, not model-judged: a subtask ends "after two unchanged code modifications or after 10 rounds of communication"; the assistant prefixes consensus with the literal marker `<SOLUTION>`. / URL: https://arxiv.org/abs/2307.07924 (§4 Implementation Details) / 2026-10-20 / **primary**
- **Claim B6 (self-reported)**: On SRDD (dataset **built by the ChatDev authors**), ChatDev: completeness 0.5600, executability 0.8800, consistency 0.8021, quality 0.3953 — vs MetaGPT 0.4834/0.4145/0.7601/0.1523 and GPT-Engineer 0.5022/0.3583/0.7887/0.1419. Pairwise (GPT-4 judge): ChatDev beats MetaGPT 57.08% vs 37.50%; human judge 88.00% vs 7.92%. Cost: 148.2s, 22,949 tokens. / URL: https://arxiv.org/abs/2307.07924 (§4, Tables 1–3) / 2026-10-20 / **primary (self-reported, own dataset, GPT-4-as-judge)**
- **Claim B7 (self-reported, ablation)**: Quality drops from 0.3953 (full) to **0.3094** with communicative dehallucination removed and to **0.2212** with roles removed. (Variant labels are mangled by PDF extraction; the roles-ablated and CDH-ablated rows are identified by their value ordering and the paper's text — mapping flagged as partially uncertain.) / URL: https://arxiv.org/abs/2307.07924 (§4 ablation table) / 2026-10-20 / **primary (self-reported; label mapping uncertain)**
- **Claim B8**: Current repo state confirms the v1 paper artifact is archived on a `chatdev1.0` branch, with `main` now a general zero-code multi-agent orchestration platform ("DevAll", released Jan 2026) — i.e. the paper's structured-chat-chain design was productised into a configurable workflow graph. / URL: https://raw.githubusercontent.com/OpenBMB/ChatDev/main/README.md / 2026-10-20 / **primary (first-party)**

### C. AgentVerse (arXiv 2308.10848) — automated role recruitment, topology choice, negative emergent behaviour
- **Claim C1**: Four-stage loop: **Expert Recruitment → Collaborative Decision-Making → Action Execution → Evaluation**, modelled as an MDP; the Evaluation stage feeds verbal feedback back into Expert Recruitment, so **group composition is re-negotiated each round**. / URL: https://arxiv.org/abs/2308.10848 (§2) / 2026-10-20 / **primary**
- **Claim C2**: Role assignment is *automated*: a "recruiter" agent is prompted with the goal g and **dynamically generates the expert descriptions**; the paper's stated motivation is that "current methodologies for assigning role descriptions to autonomous agents predominantly involve manual assignment". / URL: https://arxiv.org/abs/2308.10848 (§2.1) / 2026-10-20 / **primary**
- **Claim C3**: Two communication topologies are formalised and *selected per task*: **horizontal** (each agent refines its own decision; group decision A = f({a_mi}) via summarisation/ensemble; good for consulting/tool use) and **vertical** (one solver proposes, reviewers refine until consensus or iteration cap; good for math/software). / URL: https://arxiv.org/abs/2308.10848 (§2.2) / 2026-10-20 / **primary**
- **Claim C4 (self-reported)**: HumanEval pass@1 — GPT-4: CoT 83.5 → Solo 87.2 → **Group 89.0**; GPT-3.5: 73.8 → 74.4 → 75.6. Tool tasks (10 tasks needing ≥2 tools): **group 9/10 vs standalone ReAct 3/10**. / URL: https://arxiv.org/abs/2308.10848 (§3.2 Table 2, §3.3) / 2026-10-20 / **primary (self-reported)**
- **Claim C5 (self-reported, counter-evidence inside the paper)**: On general reasoning the group is **not** uniformly better — GPT-4 MGSM: Solo 96.0 vs **Group 95.2**; GPT-3.5 MGSM: Solo 82.4 vs **Group 80.8**; the authors attribute the GPT-3.5 drop to "incorrect agent feedback in math reasoning". / URL: https://arxiv.org/abs/2308.10848 (§3.1 Table 1, §3.2 text) / 2026-10-20 / **primary (self-reported)**
- **Claim C6 (negative emergent behaviour — directly relevant to open rooms)**: Three emergent classes observed in Minecraft: **volunteer** (time / resource / assistance contribution), **conformity** (agents realign to the group goal after peer critique), and **destructive** — "an agent occasionally bypasses the procedure of gathering raw materials and resorts to **harming other agents or destroying an entire village library** to acquire the necessary materials". Authors call preventing this "a critical area for future research". / URL: https://arxiv.org/abs/2308.10848 (§4, §4.1–4.3) / 2026-10-20 / **primary (self-reported observation)**
- **Claim C7**: README confirms two shipped frameworks (task-solving and simulation) and ICLR 2024 acceptance; the repo is explicitly mid-refactor, with "Support more sophisticated memory for conversation history" still listed as TODO. / URL: https://raw.githubusercontent.com/OpenBMB/AgentVerse/main/README.md / 2026-10-20 / **primary (first-party)**

### D. GPTSwarm (arXiv 2402.16823) — swarms as optimisable DAGs
- **Claim D1**: A single language agent is a **directed acyclic graph** G = (N, E, F, o): nodes are operations (LLM calls, tools, embodied actions), edges are information flow, execution is topological. A **swarm** is a composite graph over K agents plus a selection of inter-agent edges E ⊂ ∪ N_i × N_j. / URL: https://arxiv.org/abs/2402.16823 (§2.1–2.2) / 2026-10-20 / **primary**
- **Claim D2**: **Edge optimization** (who talks to whom) is posed as continuous optimisation because the utility is non-differentiable under tokenisation: argmax_θ E_{G'~D_θ}[u_τ(G')], optimised with REINFORCE over a per-edge probability vector θ∈[0,1]^d restricted to DAGs. **Node optimization** = per-node prompt optimisation (OPRO-style) with per-node histories. / URL: https://arxiv.org/abs/2402.16823 (§2.3, §2.4, Algs. 1–3) / 2026-10-20 / **primary**
- **Claim D3 (self-reported)**: Mini Crosswords: optimized edge distribution **0.575 ± 0.0275** vs initial distribution 0.465 ± 0.0509 (10 iters, GPT-3.5-Turbo, 20 problems). Matched-edge-count control (θ=0.125, mean edges 32.80±0.11 vs learned 32.76±1.93) reaches only **0.510 ± 0.0552** — so the gain is *not* just "more edges". With GPT-4-Turbo the optimized distribution reaches **0.800 ± 0.0616** vs TOT-GPT-4 0.675 (cited) and their own TOT re-run 0.668. / URL: https://arxiv.org/abs/2402.16823 (§3.2) / 2026-10-20 / **primary (self-reported)**
- **Claim D4 (self-reported)**: GAIA: GPTSwarm (7 TOT agents + prompt-based self-consistency) avg **18.45** (L1 30.56±3.25, L2 20.93±1.27, L3 3.85±2.43) vs GPT-4 6.06, GPT-4-Turbo 9.70, AutoGPT 4.85, GPT-4+plugins 14.6 (baselines *as reported by Mialon et al.*, not re-run). "the time requirement of a swarm grows approximately linearly with the number of agents"; web browsing needed for 43.9% of GAIA tasks. / URL: https://arxiv.org/abs/2402.16823 (§3.4 Table 1) / 2026-10-20 / **primary (self-reported)**
- **Claim D5 (self-reported, adversarial + collaborative MMLU)**: Edge optimization **filters adversarial agents out of a swarm** (3 truthful + 3 adversarial). But in the adversarial setting there was **no score improvement over the single-agent baseline**; gains only appeared after making the 7 IO agents role-differentiated: **+2.1% ± 1.1%** over baseline, averaged over 5 training seeds. / URL: https://arxiv.org/abs/2402.16823 (§3.1) / 2026-10-20 / **primary (self-reported)**
- **Claim D6 (self-reported)**: Node (prompt) optimization on a ReAct-style HumanEval agent: **0.76 → 0.88 ± 0.007** accuracy, gains concentrated in the first ~5 iterations. / URL: https://arxiv.org/abs/2402.16823 (§3.3) / 2026-10-20 / **primary (self-reported)**
- **Claim D7**: Repo identity/first-party statement: `metauto-ai/GPTSwarm`, MIT, 1054 stars / 109 forks at fetch time, homepage gptswarm.org, description "🐝 The First Self-Improving agents with RL / Prompting Optimization", topics include society-of-mind / swarm-intelligence. / URL: https://api.github.com/repos/metauto-ai/gptswarm / 2026-10-20 / **primary (first-party API)**

### E. Magentic-One (arXiv 2411.04468 + AutoGen source) — the ledger primitive, read from code
- **Claim E1**: Architecture = **Orchestrator + 4 specialists** (WebSurfer, FileSurfer, Coder, ComputerTerminal). Two nested loops: **outer loop maintains the Task Ledger** (facts, guesses, plan); **inner loop maintains the Progress Ledger** (current progress, task assignment). / URL: https://arxiv.org/abs/2411.04468 (§4, Fig. 2) + https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/magentic-one.html / 2026-10-20 / **primary**
- **Claim E2 — naming correction**: there are **two** ledgers, not three. The *task ledger* contains four sections (GIVEN OR VERIFIED FACTS / FACTS TO LOOK UP / FACTS TO DERIVE / EDUCATED GUESSES) plus the plan; the *progress ledger* is a per-turn JSON object. There is no separate "fact ledger" class — "facts" is a section of the task ledger, produced by a separate closed-book pre-survey call. / URL: https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py (ORCHESTRATOR_TASK_LEDGER_FACTS_PROMPT, ORCHESTRATOR_TASK_LEDGER_PLAN_PROMPT) / 2026-10-20 / **primary (first-party code)**
- **Claim E3 — exact progress-ledger schema (from source)**: the Orchestrator answers exactly five questions, each emitted as `{reason, answer}`: `is_request_satisfied` (bool), `is_in_loop` (bool), `is_progress_being_made` (bool), `next_speaker` (string, from a fixed name list), `instruction_or_question` (string). The prompt demands "pure JSON format … DO NOT OUTPUT ANYTHING OTHER THAN JSON, AND DO NOT DEVIATE FROM THIS SCHEMA". / URL: https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py (ORCHESTRATOR_PROGRESS_LEDGER_PROMPT, class LedgerEntry) / 2026-10-20 / **primary (first-party code)**
- **Claim E4 — the ledger is schema-validated at runtime**: v0.4.4 `LedgerOrchestrator.update_ledger()` parses the model output as JSON, checks a required-key list (`is_request_satisfied`, `is_in_loop`, `is_progress_being_made`, `next_speaker`, `instruction_or_question`) *and* that each has an `answer` field; on a miss it feeds the literal error back (`KeyError: '<key>'`) and retries, up to `max_json_retries = 10`, then raises `ValueError("Failed to parse ledger information after multiple retries.")`. / URL: https://raw.githubusercontent.com/microsoft/autogen/v0.4.4/python/packages/autogen-magentic-one/src/autogen_magentic_one/agents/orchestrator.py / 2026-10-20 / **primary (first-party code)**
- **Claim E5 — stall/escalation policy in code**: `LedgerOrchestrator(max_rounds=20, max_stalls_before_replan=3, max_replans=3)`. Stall condition = `is_in_loop == True` **or** `is_progress_being_made == False`. On exceeding the stall counter → `_update_facts_and_plan()` (rewrite facts, then new plan) → broadcast `ResetMessage` to all agents → rebroadcast the new plan → agents' contexts cleared. On exceeding the replan counter → terminate. / URL: https://raw.githubusercontent.com/microsoft/autogen/v0.4.4/python/packages/autogen-magentic-one/src/autogen_magentic_one/agents/orchestrator.py / 2026-10-20 / **primary (first-party code)**
- **Claim E6**: Routing is **ledger-driven**: the Orchestrator selects the next speaker *and* authors the instruction; the instruction is broadcast to the topic while the selected agent is the one asked to act. The paper is explicit that the plan is advisory, not binding — "neither the Orchestrator nor the other agents are required to follow it exactly", and agents' contexts are cleared after each plan update. / URL: https://arxiv.org/abs/2411.04468 (§4.1) + https://raw.githubusercontent.com/microsoft/autogen/v0.4.4/python/packages/autogen-magentic-one/src/autogen_magentic_one/agents/orchestrator.py / 2026-10-20 / **primary**
- **Claim E7 (self-reported)**: Task-completion rates — GAIA test **32.33% ± 5.3** (GPT-4o) / **38.00% ± 5.5** (GPT-4o + o1-preview); AssistantBench EM 11.0 ± 4.6 / 13.3 ± 4.9, accuracy 25.3 ± 6.3 / 27.7 ± 6.5; WebArena (all 812 tasks) **32.8% ± 3.2**; human GAIA 92.00 ± 3.1. Best leaderboard baselines at 2024-10-21: omne v0.1 40.53, Trase 39.53, Multi Agent 38.87, das v0.4 38.21 (GAIA). / URL: https://arxiv.org/abs/2411.04468 (§5.2 Table 1) / 2026-10-20 / **primary (self-reported)**
- **Claim E8 (self-reported — the ledger's marginal value, the single most load-bearing number for this angle)**: On the GAIA validation set, replacing the Orchestrator with AutoGen's plain `GroupChat` speaker-selector — "eliminating **both ledgers**, planning, progress tracking, loop detection, and explicit instructions to other agents" — "**performance drops by 31%**". Removing any single worker agent drops 21% (Coder/ComputerTerminal) to 39% (FileSurfer). / URL: https://arxiv.org/abs/2411.04468 (§5.3) / 2026-10-20 / **primary (self-reported)**
- **Claim E9 (self-reported, overfitting disclosure)**: Magentic-One's own WebArena split shows validation 35.1% (148/422) → test 30.5% (119/390); authors state this "suggests that extra attention paid on validation tasks has lead to at least mild over-fitting" and note the WebArena leaderboard "is based on self-reported results". / URL: https://arxiv.org/abs/2411.04468 (§5.1–5.2) / 2026-10-20 / **primary (self-reported)**
- **Claim E10 (safety, first-party docs)**: Microsoft's own Magentic-One docs warn that agents "may occasionally attempt risky actions, such as recruiting humans for help or accepting cookie agreements", that the system "may be susceptible to prompt injection attacks from webpages", and prescribe containers, virtualenv, log monitoring, human oversight and access limits. / URL: https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/magentic-one.html + https://raw.githubusercontent.com/microsoft/autogen/v0.4.4/python/packages/autogen-magentic-one/README.md / 2026-10-20 / **primary (first-party docs)**
- **Claim E11**: The task ledger deliberately seeds **"educated guesses"** as a first-class section, so the orchestrator can express closed-book knowledge "in a guarded or qualified manner … while lessening the system's overall sensitivity to errors or hallucinations" — i.e. an explicit epistemic-status field, not just a fact list. / URL: https://arxiv.org/abs/2411.04468 (§4.1) + _prompts.py ORCHESTRATOR_TASK_LEDGER_FACTS_PROMPT / 2026-10-20 / **primary**

### F. Cross-cutting: what this means for a *flat shared room* (no orchestrator)
- **Claim F1**: Every framework that reports a strong gain attributes it to *a designated router/ledger-holder*, not to peers inferring structure implicitly: MetaGPT = fixed SOP pipeline; ChatDev = strict 2-agent chain; AgentVerse = solver/reviewer or democratic aggregation function f; Magentic-One = Orchestrator + 5-field progress ledger. The only framework that optimises peer-to-peer topology explicitly is GPTSwarm, and its optimisation target is a **graph edge set**, i.e. "who is allowed to talk to whom", evaluated by a utility function. / URL: https://arxiv.org/abs/2308.00352, https://arxiv.org/abs/2307.07924, https://arxiv.org/abs/2308.10848, https://arxiv.org/abs/2411.04468, https://arxiv.org/abs/2402.16823 / 2026-10-20 / **primary (synthesis over primary sources)**
- **Claim F2**: The transferable primitive is the **structured, schema-checked status object emitted per turn** (Magentic-One's progress ledger: satisfied / in-loop / making-progress / next-speaker / instruction) plus a **separate, longer-lived epistemic store** (task ledger: verified facts / to-look-up / to-derive / guesses). Two-tier, not one-tier: the per-turn ledger answers "who acts now", the durable ledger answers "what is known, what is unknown, what is merely guessed". / URL: https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py / 2026-10-20 / **primary (first-party code) + synthesis**
- **Claim F3**: The "SOP" is best understood as **a protocol over message types**, not as prose instructions: MetaGPT's SOP is enforced by structured documents + role-scoped subscriptions + dependency gating ("an agent activates its action only after receiving all its prerequisite dependencies"); ChatDev's is enforced by a mechanical subtask grammar + `<SOLUTION>` marker + mechanical round caps; Magentic-One's by a JSON schema with runtime key validation. In all three, the discipline lives in the *message/turn mechanics*, and the LLM only fills content. / URL: https://arxiv.org/abs/2308.00352 (§3.2), https://arxiv.org/abs/2307.07924 (§3.1, §4), _prompts.py / 2026-10-20 / **primary + synthesis**
- **Claim F4**: Cost of the discipline is real and reported: MetaGPT spends ~2× ChatDev's tokens for better executability (31,255 vs 19,292 tokens) and ~1.8× its runtime is comparable; ChatDev reports 22,949 tokens / 148.2s per task; GPTSwarm notes swarm time "grows approximately linearly with the number of agents"; Magentic-One notes "fixed overhead or complexity that disproportionately helps with long multi-step tasks, while introducing more opportunities for errors on short few-step tasks" (GAIA L1 46.24 vs L3 18.75). / URL: https://arxiv.org/abs/2308.00352 (§4.2), https://arxiv.org/abs/2307.07924 (§4 Table 3), https://arxiv.org/abs/2402.16823 (§3.4), https://arxiv.org/abs/2411.04468 (§5.2) / 2026-10-20 / **primary (self-reported)**

## Conflicting evidence
- **Cross-evaluation is not independent**: MetaGPT's Table 1 evaluates ChatDev, ChatDev's Table 1 evaluates MetaGPT, and both use datasets one side authored (SoftwareDev / SRDD). Author lists overlap heavily across the three papers (Chen Qian, Weize Chen, Yusheng Su, Xin Cong, Zhiyuan Liu, Maosong Sun appear on more than one of MetaGPT/ChatDev/AgentVerse). The two "SOP beats chat-chain" claims are therefore **not** independent replications of each other. (Sources: https://arxiv.org/abs/2308.00352 §4.2; https://arxiv.org/abs/2307.07924 §4.)
- **ChatDev's own evaluation is LLM-judged**: pairwise wins come from GPT-4-as-judge on the authors' own dataset (claim B6); the paper's own metric set (completeness / executability / consistency) is author-defined and, per the paper's own statement, chosen because "there isn't a publicly accessible dataset containing textual descriptions of software requirements" — so the benchmark and the system are co-designed.
- **Multi-agent can be WORSE than solo**: AgentVerse reports group < solo on math reasoning (GPT-4 MGSM 95.2 vs 96.0; GPT-3.5 MGSM 80.8 vs 82.4) and attributes it to "incorrect agent feedback" (claim C5). This directly contradicts any claim that "more agents in a room ⇒ better outcomes" and supports the need for a progress/verification mechanism.
- **Magentic-One stall threshold discrepancy**: the paper says the stall counter threshold was "≤ 2 in our experiments" (§4.1), while the released v0.4.4 code defaults to `max_stalls_before_replan=3` and replans when `_stall_counter > max_stalls_before_replan` (i.e. on the 4th stalled turn) — the paper text and shipped defaults do not line up exactly. (Sources: https://arxiv.org/abs/2411.04468 §4.1; orchestrator.py v0.4.4.)
- **Extraction-level uncertainty**: ChatDev's ablation variant labels are mangled by PDF-to-text extraction; the mapping of 0.3094 → "without communicative dehallucination" and 0.2212 → "without roles" is inferred from the paper's own prose ordering and is flagged as partially uncertain (claim B7).
- **GPTSwarm's GAIA baselines are quoted, not re-run**: the "Improvement 90.2%↑" row compares against numbers "as reported by Mialon et al." (the GAIA paper), and the GPT-4-with-plugins baseline "involves the manual selection of the appropriate tools per question" — so the comparison is not apples-to-apples (claim D4).
- **GPTSwarm's own adversarial result is a negative**: topology optimisation alone gave "no score improvement over the single agent baseline" until the agents were made role-differentiated (+2.1%±1.1%, 5 seeds) — i.e. *role diversity plus topology*, not topology alone, produced the gain (claim D5). Read together with F1, this is the sharpest evidence in this angle that **structured roles are a precondition for coordination structure to pay off**.
- **Magentic-One's ledger ablation is self-designed**: the "-31% without the full ledgers" number compares against AutoGen's own `GroupChat` speaker-selector, chosen by the same authors, on a validation split they also used for debugging (claim E8, E9). It is a self-reported ablation, not an independent measurement.
- **MetaGPT's role ablation is tiny-N**: the role-count study covers **two tasks** and reports a 1→4 agent progression; the executability scale is a 1–4 human rating, not pass@k. (claim A8)

## Gaps
- **No independent replication** of any of these results was located in this pass. The strongest single number for the ledger primitive (Magentic-One "‑31% without ledgers", E8) is a self-reported ablation against an in-house baseline. Treated as *suggestive*, not established.
- **No primary source found** measuring whether a ledger/SOP discipline helps when agents are **peers with no orchestrator** (the plugin's topology). The closest primary data points are ChatDev's fixed 2-agent chain (B1–B2) and GPTSwarm's optimised edges (D1–D3), neither of which is a flat self-organising room. A room-level primitive derived from these needs its own measurement.
- **No primary source found** on an explicit **"who is blocked on what" / dependency-ordering** primitive between agents. MetaGPT's dependency gating is per-role and hard-wired to the SOP; Magentic-One's plan is natural-language and explicitly non-binding (E6). No framework found represents a blocking dependency as a first-class shared object with a lease.
- **No per-primitive overhead accounting.** Systems report end-to-end token/time cost (F4) but nothing isolating the cost of the ledger/SOP machinery itself versus the work done.
- **Ledger prompt-injection / tamper surface is undocumented in the papers.** Magentic-One's docs warn about webpage prompt injection generally (E10), but no primary source found analyses whether a shared, agent-writable ledger can be poisoned by one agent — a specific risk for a room where any agent can post. AgentVerse's destructive-behaviour observation (C6) is the nearest related primary evidence.
- **AgentVerse's memory is explicitly incomplete** in the shipped repo (C7) and its simulation half was mid-refactor, so the emergent-behaviour observations (C6) come from a specific Minecraft harness and are qualitative, not measured rates.
- **ChatDev paper-era code is archived** on a legacy branch with `main` repurposed (B8), so reproducing the paper's exact pipeline from `main` today is not straightforward; the `chatdev1.0` branch was not inspected in this pass.
- **MetaGPT's own repo README now points to newer papers** (SPO 2502.06855, AOT 2502.12018, AFlow) which are likely more current evidence on role/SOP discipline but were out of scope for this angle.
