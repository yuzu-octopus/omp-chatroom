# F14 — MEASUREMENT: what instruments and metrics exist for swarm effectiveness, and which fit an in-process room

## Angle

F14 — MEASUREMENT. Question: what instruments/metrics actually exist for measuring multi-agent (LLM) swarm effectiveness, and which of them are computable from OUR append-only JSONL room log (records carry `v, seq, ts, id, kind, from`; `msg{topic, body, to?, mention?, replyTo?, threadRoot?, performative?, replyWith?, replyBy?}`; `claim{resource, ttlMs}`; `release{resource, reason∈released|expired|reclaimed|aborted, prevHolder}`; `note{topic, body}`; `member{action∈join|leave}`; `gap{skipped, reason∈retention|invalid|corrupt}`; derived `acquiredAt = claim.ts`, `expiresAt = claim.ts + claim.ttlMs`)?

Deliverable: concrete metric definitions with primary URLs, plus a per-metric verdict of COMPUTABLE / NOT COMPUTABLE from the room JSONL alone, with the formula and the log field it needs. Target areas: (a) multi-agent benchmark suites and their reported metrics, (b) METR/agent-eval primary work on human-equivalent runtime and "agent time" vs wall-clock, (c) coordination-overhead measurement (token/cost), (d) observability standards for LLM agents, (e) SE metrics that map onto swarm health.

All fetch dates 2026-10-20.

## Claims

### (a) Benchmark suites for multi-agent / agent evaluation and their metric definitions

- **AgentBench overall score (OA) is a weighted average with weights = reciprocal of each environment's mean score across evaluated models**: `OA_m = (1/8)·Σ_i s_{m,i}·w_i`, `w_i = 1/mean_i(s_·,i)`. Per-environment task metrics differ (success rate, F1, reward, game progress), so OA is a normalized composite, not a percentage. Source: https://proceedings.iclr.cc/paper_files/paper/2024/file/e9df36b21ff4ee211a8b71ee8b7e9f57-Paper-Conference.pdf (arXiv:2308.03688, ICLR 2024). Confidence: primary.
- **SWE-bench = 2,294 real GitHub issues across 12 Python repos; "resolved" = tests pass; the original best model (Claude 2) solved 1.96%**. Source: https://arxiv.org/abs/2310.06770. Confidence: primary.
- **τ-bench introduces pass^k = probability that ALL k i.i.d. trials succeed**, with unbiased estimators `pass^k = E_task[ C(c,k)/C(n,k) ]` and `pass@k = 1 − E_task[ C(n−c,k)/C(n,k) ]` (c = successes of n trials). Reward is `r = r_action × r_output` (database state identical to the single annotated ground truth AND all required numbers present in the user-facing replies). Reported: gpt-4o function-calling `pass^1` = 61.2% τ-retail / 35.2% τ-airline, falling to `pass^8` < 25% on retail; cost $0.38 agent + $0.23 user simulation per task, of which input prompt = 95.9% of price. Source: https://arxiv.org/html/2406.12045v1 (arXiv:2406.12045). Confidence: primary.
- **τ²-bench (successor) is cited by Anthropic as one of the two benchmarks with multidimensional success** (state check + turn constraint + LLM rubric). Source: https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents. Confidence: primary (vendor's own doc about their system/usage).
- **GAIA: 3 difficulty levels keyed to annotator step/tool count (L1 ≈ ≤1 tool/≤5 steps; L2 ≈ 5–10 steps; L3 longer), metric = type-normalized quasi-exact-match accuracy on a short ground-truth answer.** Source: https://arxiv.org/abs/2311.12983. Confidence: primary.
- **MLE-bench: 75 Kaggle competitions; metric = "Any Medal" rate = share of competitions whose submission reaches ≥ bronze medal threshold; headline o1-preview + AIDE = 16.9%.** Official repo README later lists 35.91±1.86% Low / 8.45±0.43% Medium / 11.67±1.27% High / 17.12±0.61% All. Source: https://arxiv.org/abs/2410.07095 and https://github.com/openai/mle-bench/blob/main/README.md. Confidence: primary.
- **WorkArena/BrowserGym: metric is task success rate = fraction of instances where the task validator returns reward == 1** (not a graded partial-credit score). Repo: 33 WorkArena-L1 task types, 19,912 instances; showcased top GPT-4 config 42.7% success, Llama 3 70B 17.9%. Source: https://github.com/ServiceNow/WorkArena and https://servicenow.github.io/WorkArena/ (ICML 2024, PMLR v235/drouin24a). Confidence: primary.
- **MultiAgentBench's coordination KPI is a MILESTONE-CONTRIBUTION ratio, and this is the single most transferable metric definition found for our plugin**: for each agent j, `n_j` = number of milestones agent j contributed to; `KPI_j = n_j / M`; `KPI_overall = (1/N)·Σ_j KPI_j = (1/(N·M))·Σ_j n_j`. Coordination Score `CS = mean(Communication Score, Planning Score)`, each a 5-point LLM-judged scale (C=0 if no communication); scores in the paper are ×20. Four findings from its ablations that map onto our room: (i) protocol comparison reports TOKEN USAGE alongside task/coordination scores (scaled 0–100) — graph best, tree worst (high token consumption, lowest TS and CS); (ii) agent-count ablation 1→3→5→7: overall KPI DECREASES with more agents while coordination score improves most from 1→3, then degrades; (iii) iteration ablation: TS and CS rise from 1 to 7 iterations then drop sharply at 10, and CS is nearly unchanged beyond 7 — the paper attributes this to "communication overhead or conflicting directives emerging over prolonged interactions"; (iv) cognitive-planning improves milestone achievement by 3%; group discussion scored worst on all metrics. Source: https://arxiv.org/html/2503.01935v1 (ACL 2025, PMLR/aclanthology 2025.acl-long.421). Confidence: primary.
- **LLM-Coordination benchmark: two tasks — Agentic Coordination in four pure-coordination games, and CoordQA = 198 multiple-choice questions over three abilities (Environment Comprehension, ToM Reasoning, Joint Planning); zero-shot coordination shows robustness to unseen partners.** Source: https://arxiv.org/abs/2310.03903 (also https://aclanthology.org/2025.findings-naacl.448/). Confidence: primary.
- **MAST (Multi-Agent System Failure Taxonomy): 14 failure modes in 3 categories from 1,642 annotated traces across 7 MAS frameworks; taxonomy built on 150 traces with Cohen's κ = 0.88, LLM-as-judge annotator (o1 few-shot) accuracy 0.94 / κ = 0.77.** Category 2 "Inter-Agent Misalignment" mode prevalences: conversation reset 2.20%, proceeded with wrong assumptions instead of seeking clarification 6.80%, task derailment 7.40%, information withholding 0.85%, ignoring another agent's input 1.90%, reasoning/action mismatch 13.20%. Category 1: fails to follow task requirements 11.8%, fails to follow assigned role 1.5%, repeats steps 15.7%, loses context 2.80%, fails to recognize task completion 12.4%. Category 3: premature termination 6.20%, no/incomplete verification 8.20%, incorrect verification 9.10%. Evaluated systems' failure rates ranged 41%–86.7%. MAST-guided interventions: role-spec fix +9.4% success (ChatDev), high-level objective verification +15.6% (ChatDev). Source: https://arxiv.org/html/2503.13657v3 (NeurIPS 2025). Confidence: primary.
- **Who&When: failure-attribution dataset of 127 multi-agent systems with agent + decisive-step labels; best automated method 53.5% accuracy at identifying the responsible agent but only 14.2% at the step, with some methods below random — "even SOTA reasoning models fail to achieve practical usability" for step-level attribution.** Source: https://arxiv.org/abs/2505.00212 (ICML 2025, Spotlight). Confidence: primary.
- **TeamBench: OS-enforced role separation (Planner/Executor/Verifier in isolated containers), 851 templates → 931 seeded instances, 19 categories, 5 ablation conditions.** Key metrics/numbers: Teamwork Necessity Index `TNI = (S_team − S_restricted) / max(ε, S_oracle − S_restricted)` (1.0 = full recovery of the withheld information, >1.0 = team exceeds the oracle ceiling); LLM Verifiers approve **49.4%** of submissions that FAIL the deterministic grader (Wilson 95% CI [45.9, 52.9], n=1,083; 33.6% conservative lower bound counting missing verdicts as failures; 38.7% on the audited subset); prompt-only teams reach statistically indistinguishable pass rates to sandbox-enforced ones but produce **3.6× more** cases where the Verifier rewrites the Executor's code ("role collapse"); team uplift is conditional — lowest-Solo-score quintile gains **+15.7 points** while the top quintile LOSES points to coordination overhead, mean team-vs-Solo uplift +0.5 points (p = 0.20); adding a Planner to a No-Plan team = +2.4 points; team pipeline uses **2–3× more LLM calls** than the oracle; mixed-provider PGEAVA reaches 26.7% at $20.52 vs all-Anthropic 22.7% at $39.58. Source: https://arxiv.org/abs/2605.07073 and https://teambench.github.io/. Confidence: primary.
- **CoCoBench: construct-level scoring for embodied multi-agent coordination — 897 oracle-validated instances over FOUR constructs: task allocation, sequential ordering, mutual exclusion, and handoff coordination.** The stated motivation is exactly the failure surface a room must avoid: "coordination failures such as duplicated work, violations of ordering constraints, resource contention, and desynchronized handoffs"; 11 MLLMs evaluated across coordination modes, observation inputs, and agent counts; "coordination ability is highly construct-specific" (strong overall performance ≠ balanced competence). Source: https://arxiv.org/abs/2608.28266. Confidence: primary.
- **ProtocolBench compares agent protocols (A2A, ACP, ANP, Agora) on FOUR measurable axes: task success, end-to-end latency, message/byte overhead, and robustness under failures.** Streaming Queue: overall completion time varies up to **36.5%** across protocols, mean end-to-end latency differs by **3.48 s**; Fail-Storm Recovery differs consistently; ProtocolRouter cuts Fail-Storm recovery time up to 18.1%. Source: https://proceedings.mlr.press/v306/du26l.html (ICML 2026). Confidence: primary.
- **"Towards a Science of Scaling Agent Systems": 260 configurations × 6 benchmarks × 5 architectures × 3 LLM families; predictive model with cross-validated R² = 0.373 (0.413 with a task-grounded capability metric); picks the best architecture for 87% of held-out configurations.** Findings: (i) **capability saturation** — coordination yields diminishing (or negative) returns once single-agent baselines exceed a threshold; (ii) **tool-heavy tasks incur multi-agent overhead**; (iii) architectures without centralized verification propagate errors more; (iv) relative performance vs single-agent ranges **+80.8%** (decomposable financial reasoning) to **−70.0%** (sequential planning). Source: https://arxiv.org/abs/2512.08296. Confidence: primary.
- **"The Collaboration Tax" (EMNLP 2026 Main) defines coordination cost as a score gap and decomposes it into a 4-stage conversational cascade**: `tax(M,T) = s_solo-full(M,T) − s_homo(M,T)` (ratio variant `tax/s_solo-full`); 32 solo-tractable tasks (Spatial / Relational / CSP grounding-friction families), 11 models from 7 providers, 50 rollouts/cell, continuous [0,1] deterministic graders. Findings: weakest models lose roughly HALF their solo success to coordination; ordering Spatial ≻ Relational ≻ CSP holds for every model; the mechanism is a cascade — **L1 Grounding** (ungrounded claims, strict necessary condition), **L2 Querying** (did not ask the partner), **L3 Integration** (no explicit combined-state message; strongest single predictor of the tax and the only stage with positive marginal regression weight), **L4 Re-derivation** (accepted the answer without recomputation). A single prompt intervention adding one clause per stage closes **+0.079 ± 0.031** of homogeneous success, i.e. **38.3% ± 14.1%** of the tax, with per-category bottlenecks differing (dropping L4 hurts Spatial, dropping L1 hurts Relational, dropping L2 hurts CSP). Judge validated: expert re-annotation Fleiss κ ∈ [0.40, 0.69]; judge-vs-expert Cohen κ ∈ [0.67, 0.73] on L1–L3, 0.51 on L4. Out-of-fold R² = 0.475, Spearman ρ = 0.760. In heterogeneous pairs EVERY pair violates max-superadditivity and every member's Shapley value falls below its singleton payoff (φ₁ = ½(v({1}) + v({1,2}) − v({2}))). Source: https://arxiv.org/html/2608.22152v2. Confidence: primary.
- **"The Collaboration Gap" (COLM 2026): 32 models, solo / homogeneous / heterogeneous pairings on an unconstrained collaborative maze benchmark — "models that perform well solo often degrade substantially when required to collaborate"; a relay-inference nudge (stronger agent leads, then hands off to weaker) closes much of the gap.** Source: https://arxiv.org/abs/2511.02687. Confidence: primary.

### (b) METR / agent-eval: human-equivalent runtime, and "agent time" vs wall-clock

- **METR's 50%-task-completion time horizon = the task duration (measured in HUMAN EXPERT time) at which an agent is predicted to succeed 50% of the time.** Method: estimate human-expert completion time per task (contracted humans, geometric mean of successful completion times; SWE-bench Verified human-time estimates used for their own tasks); fit a logistic curve of success rate against human time; read off the duration at 50%/80% success. Result: Claude 3.7 Sonnet ≈ 50 minutes; time horizon doubling ≈ every 7 months since 2019 (191-day fit on 2023–2025 models; 212 days over 2019–2025 incl. the SWAA suite); 2019–2025 model success rate vs log human time fits an exponential with R² ≈ 0.83. Source: https://arxiv.org/abs/2503.14499 and https://metr.org/time-horizons/. Confidence: primary.
- **METR explicitly refuses to publish an agent wall-clock metric**: "We don't report the exact time it takes an AI agent to complete a task because it varies greatly by inference provider and exact agent setup"; agents are "typically several times faster than humans" on tasks they complete successfully, but "time horizon … is a measure of the difficulty of a task, rather than the time an AI spends to complete the task." METR also reports the human time horizon empirically as ≈1.5 h (not the 8 h the baseliner contract would imply). Source: https://metr.org/time-horizons/ (FAQ). Confidence: primary. **Implication for us: "agent time" as a metric name is not a settled primary concept; the primary is HUMAN-EQUIVALENT task duration, and any wall-clock claim must be reported with provider+scaffold, or not at all.**
- **METR's own task-suite design principle is directly a coordination-metric warning**: tasks are "coherent, self-contained units of work that can't be trivially split into independent pieces"; solving 1,000 separate 1-hour math problems in a row is "a 1-hour task done 1,000 times", because "you could easily split the work between many people working in parallel". A swarm that parallelizes trivially-splittable work is measuring a DIFFERENT quantity from one that does not. Source: https://metr.org/time-horizons/ (FAQ "What does METR mean by a task?"). Confidence: primary.
- **Anthropic's eval doctrine is transcript/outcome separation and end-state grading**: task / trial / grader (+assertions) / transcript (=trace=trajectory) / outcome (=final environment state) / eval harness / agent harness / eval suite. Tracked metrics they name for coding and conversational agents: `n_turns`, `n_toolcalls`, `n_total_tokens` (transcript) and `time_to_first_token`, `output_tokens_per_sec`, `time_to_last_token` (latency). They warn that checking specific step sequences is "too rigid and results in overly brittle tests" and prefer grading the produced outcome with partial credit for partially-correct multi-component tasks. Source: https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents. Confidence: primary.

### (c) Coordination-overhead measurement (tokens, cost, wall-clock)

- **Anthropic (Jun 2025) measured multi-agent overhead at ≈15× chat tokens**: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats"; on BrowseComp, three factors explained **95% of performance variance**, with **token usage alone explaining 80%**; the multi-agent system (Opus 4 lead + Sonnet 4 subagents) beat single-agent Opus 4 by **90.2%** on an internal research eval; parallel tool calling "cut research time by up to 90% for complex queries"; the lead agent "spins up 3-5 subagents in parallel"; they also observed agents "spawning 50 subagents for simple queries" and "distracting each other with excessive updates" as early failure modes. Source: https://www.anthropic.com/engineering/multi-agent-research-system. Confidence: primary.
- **Anthropic (Jan 2026) restates overhead as 3–10× tokens and, critically, separates THOROUGHNESS from SPEED**: "multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks … This overhead stems from duplicating context across agents, coordination messages between agents, and summarizing results for handoffs"; "The primary benefit of parallelization is thoroughness, not speed … multi-agent systems often take longer overall than single-agent systems because of the sheer increase in total computation"; "most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time" (from the 2025 post). Source: https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them. Confidence: primary.
- **AgentPrune is the primary source that formally defines and measures "communication redundancy"**: one-shot pruning of the spatial-temporal message-passing graph; reports **$5.6 vs $43.7** cost at comparable performance, **28.1%–72.8% fewer tokens** when integrated into existing frameworks, and 2–11.8× token usage for some communication setups relative to a simple chain. Source: https://arxiv.org/abs/2410.02506. Confidence: primary.
- **The noise-floor protocol (KDD 2026 Workshop on Agentic AI Evaluation and Trustworthiness) is the single most important cautionary result for OUR report**: with configuration-equivalent protocols (matched by code inspection + SHA-256 byte audits) on τ²-bench retail / Claude Haiku 4.5 / n=100 × 2 trials, the observed paired gap between protocols whose coordination mechanism is INERT spans **[−3, +18] pp across two seeds** (pooled clean-contrast CI [−2, +12] pp; largest pooled upper Wilson CI ≈ 15 pp), and **7 of 10 recent multi-agent coordination papers report headline gains below this envelope** (one more sits inside it). Their proposed reporting metric is **coordination-active pass^k** = pass^k restricted to trials where the coordination mechanism is logically active. Their own +18 pp, p_corr = 0.012 result did not replicate (became −3 pp, p_corr = 1.0) and was retracted. Release gate at α = 0.05, power 0.80, baseline p₁ = 0.50, p_d = 0.32: 114-task τ²-retail can detect only Δ ≥ 20 pp with independent arms or Δ ≥ 15 pp paired; "Effects the size most coordination papers report (+1 to +11 pp) need hundreds to thousands of paired tasks to separate from the floor." Their three failure modes of coordination itself are directly ours: M1 writer mis-attribution (LLM-judge audit: 77% of 30 analyzable failures were rated upstream, single judge = hypothesis only), M2 per-match injection noise (mean 2.77 injected events per trial, max 8; every matching call fires a separate warning), M3 brittle literal keying (`cancel_order(#W123)` does not match `cancel_order(#W456)`). Their three shipped runtime alarms are directly copyable: (R1) CUSUM on coordination-active pass^k over a golden-task set, alarm at ±1.5σ_floor; (R2) rolling-N 95th-percentile injection-event count, alarm at ≥50% above release baseline; (R3) **coordination-key collision rate, alarm at >0.5%**. Source: https://github.com/abekek/coordination-noise-floor-protocol and https://abekek.github.io/coordination-noise-floor-protocol/. Confidence: primary.
- **Aider's first-party leaderboard is the model for a per-run cost dashboard**: each row reports percent correct, total cost, and a detail block with test cases (225), **Pass rate 1 and Pass rate 2** (pass@1 / pass@2), percent cases well formed, error outputs, num malformed responses, **User asks** (how many times the agent had to ask the user), prompt tokens, completion tokens, **Seconds per case**, and total cost. Example (gpt-5 high): 88.0% correct, $29.08 total, 194.0 s/case, 2,675,561 prompt + 2,623,429 completion tokens, 96 user asks, pass rate 1 = 52.0%. Source: https://aider.chat/docs/leaderboards/. Confidence: primary.
- **OpenHands SDK first-party cost metric**: `conversation.conversation_stats.get_combined_metrics()` → `accumulated_cost`, `accumulated_token_usage` (prompt/completion, plus cached and reasoning tokens when the provider reports them); per-LLM `llm.metrics.accumulated_cost`; per-usage-id via `stats.usage_to_metrics` / `get_metrics_for_usage("agent")`. The conversation aggregate includes the primary agent AND auxiliary LLMs such as the context condenser — i.e. the tool/overhead traffic is counted as part of the same session. Source: https://github.com/OpenHands/docs/blob/main/llms.txt. Confidence: primary.
- **Letta first-party usage/cost surface**: per-interaction usage stats (prompt, completion, total, cached-input, reasoning tokens where reported) plus step-level provider traces carrying agent and run IDs and LLM-request cost/billing context; a hosted Usage page for usage-based billing, while BYO-key requests are billed by the provider. Source: https://docs.letta.com/api/resources/agents and https://docs.letta.com/api/python/resources/steps. Confidence: primary.

### (d) Observability standards for LLM agents

- **The OpenTelemetry GenAI semantic conventions have MOVED out of the core semconv repo into a dedicated repo** (`open-telemetry/semantic-conventions-genai`); the opentelemetry.io pages are now "Moved" stubs and are no longer maintained there. Source: https://opentelemetry.io/docs/specs/semconv/gen-ai/ and https://github.com/open-telemetry/semantic-conventions-genai. Confidence: primary.
- **OTel defines agent/framework spans: `create_agent`, `invoke_agent` (client + internal), `invoke_workflow`, `plan`, `execute_tool`**, all with `gen_ai.operation.name` (required) and `gen_ai.provider.name` (required); agent spans carry `gen_ai.agent.id` / `gen_ai.agent.name` / `gen_ai.agent.version` (conditionally required) and `gen_ai.conversation.id` for correlation. `gen_ai.agent.id` SHOULD be a stable provider-assigned id and it is NOT RECOMMENDED to record transient in-memory agent instance ids. Source: https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-agent-spans.md. Confidence: primary.
- **OTel defines the exact agent-side metrics our room would need to emulate**: `gen_ai.invoke_agent.duration` (Histogram, unit `s`, buckets [0.1 … 409.6]) = "end-to-end duration of a single in-process agent invocation, from the moment the invocation starts until the agent emits the last chunk of its final response or terminates with an error"; `gen_ai.invoke_agent.inference_calls` (Histogram, unit `{inference_call}`) = "number of inference (model) calls a GenAI agent makes during a single invocation"; `gen_ai.invoke_agent.tool_calls` (Histogram, unit `{tool_call}`) = "number of tool calls a GenAI agent makes during a single invocation". Also `gen_ai.client.operation.duration` (Histogram `s`, buckets [0.01 … 81.92]), `gen_ai.execute_tool.duration`, and inference token metrics `gen_ai.client.inference.usage.input_tokens` / `output_tokens` / `cache_read.input_tokens` / `cache_write.input_tokens` / `reasoning.output_tokens` (Counters) and `gen_ai.client.inference.operation.input_tokens` / `output_tokens` (Histograms). Source: https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-metrics.md and .../gen-ai-token-metrics.md. Confidence: primary.
- **A2A telemetry conventions are a PROPOSAL, not a spec** (open issue in the OTel GenAI repo). Proposed `a2a.*` namespace: `a2a.method.name`, `a2a.protocol.version`, `a2a.protocol.binding`, `a2a.message.id`, `a2a.message.referenced_task_ids`, `a2a.task.id`, `a2a.task.state` (submitted|working|input-required|completed|failed), `a2a.task.artifact_ids`, `a2a.agent.card.url`. Proposed metrics: `a2a.client.operation.duration`, `a2a.server.operation.duration`, `a2a.server.task.duration`, `a2a.server.task.in_progress` (UpDownCounter), `a2a.server.task.artifacts_count`, and **`a2a.server.task.message_count`** ("Number of communication messages exchanged over the course of a task"). Explicit cardinality rule: task/message ids MUST NOT be metric attributes. Source: https://github.com/open-telemetry/semantic-conventions-genai/issues/254. Confidence: primary (status: proposal).
- **OpenAI Agents SDK ships first-party swarm tracing**: agent runs and handoffs are traced automatically; `custom_span(name, data=...)` context manager attaches to the current trace and nests under the current span; `handoff_span(from_agent=…, to_agent=…)` is a built-in span type. Source: https://openai.github.io/openai-agents-python/tracing/ and https://openai.github.io/openai-agents-python/ref/tracing/create/. Confidence: primary.
- **Arize Phoenix (open source) is the reference open observability shape**: a TRACE = one run; SPANS nest inside it; OpenInference span kinds include **Agent, Tool, LLM, Chain, Retriever, Reranker, Embedding**; spans arrive over OTLP; Langfuse is the parallel product (nested observations, agent-graph views). Source: https://arize.com/docs/phoenix/learn/tracing and https://arize.com/docs/phoenix/tracing/concepts-tracing/how-does-tracing-work and https://langfuse.com/docs/observability/features/agent-graphs. Confidence: primary.

### (e) SE metrics that map onto swarm health

- **DORA 2024 (primary report PDF) uses FIVE metrics in two factors, not four keys**: software-delivery THROUGHPUT = change lead time, deployment frequency, failed deployment recovery time; software-delivery STABILITY = change failure rate + **rework rate** ("approximately how many deployments in the last six months were not planned but were performed to address a user-facing bug"). Performance-level clusters (elite 19%, high 22%, medium 35%, low 25% of respondents): elite = <1 day lead time, on-demand deploys, 5% change fail rate, <1 hour recovery; vs low performers elite are 127× faster lead, 182× more deployments, 8× lower change failure rate, 2293× faster failed-deployment recovery. Survey base >39,000 professionals. Source: https://dora.dev/research/2024/dora-report/2024-dora-accelerate-state-of-devops-report.pdf. Confidence: primary.
- **DORA 2024's headline AI finding is a NEGATIVE throughput/stability result**: "our findings indicate that AI adoption is negatively impacting software delivery performance … an estimated 1.5% reduction [in delivery throughput] for every 25% increase in AI adoption. The negative impact on delivery stability is larger (an estimated 7.2% reduction for every 25% increase in AI adoption)", while AI improved code quality, docs and review processes — i.e. more AI-generated change volume with lower delivery stability. Source: same PDF (Exploring the downstream impact of AI chapter). Confidence: primary.
- **Google's "What Improves Developer Productivity at Google?" (FSE 2022) defines the review-wait metric exactly and separates ACTIVE from WALL-CLOCK time**: objective per-CL metrics are Total Number of Changelists, Total Lines of Code, **Median Active Coding Time** (active writing time per CL), **Median Wall-Clock Coding Time** (elapsed between starting to write and requesting review), **Median Wall-Clock Review Time** (elapsed waiting for code review per CL), and **Median Wall-Clock Merge Time** (elapsed between approval and actual merge); team-communication metrics include **p50/p90 of code-review rounds** and **p50/p90 of total code-review wait time**. Random-forest model of self-rated productivity from these metrics: 83% precision, 99% recall over 1,958 engineer-periods. Crucially, in the causal table the p50/p90 code-review WAIT TIME coefficients are NOT significant (p50 wait time effect −0.0006, p = 0.875; p90 +0.0019, p = 0.625) while self-reported "slow code review" hindrance IS causally linked (effect 0.051, p = 0.004) — i.e. perceived waiting hurts, measured waiting does not. Source: https://storage.googleapis.com/gweb-research2023-media/pubtools/pdf/22106ec30ce8259e6bd195c14a26d27535bbd317.pdf. Confidence: primary.
- **Human merge-conflict rate is measurable and small under PRs**: in the VSS+19 GitHub study, of 3,436 merge scenarios USING pull requests only 7 conflicted (**0.2%**), versus 851 of 3,051 multi-developer scenarios merged WITHOUT pull requests (**27.89%**) — a 139× difference; the authors' framing is that PRs lead to fewer merge conflicts. Source: https://www.se.cs.uni-saarland.de/publications/docs/VSS+19.pdf. Confidence: primary.
- **AI-agent-authored PRs conflict far more: AgenticFlict measured 27.67% conflict rate** over 142K+ Agentic PRs from 59K+ repos, of which 107K+ were processed through deterministic merge simulation, identifying 29K+ conflicted PRs and 336K+ fine-grained conflict regions. Source: https://arxiv.org/abs/2604.03551. Confidence: primary.
- **Co-active AI PRs are the norm and cross-agent pairs conflict more than intra-agent pairs**: using AIDev-pop (33,596 agent PRs in 2,807 repos), exact temporal overlap: **40.2%** of repositories contain co-active agent-authored PR pairs and those pairs are **79.4%** of all agent PRs; within a one-week window: 53.4% and 95.0%; only **0.5%** of co-active pairs are CROSS-agent (122 of 2,807 repos, ~4.3%); replaying actual three-way git merges on 747 co-active pairs, textual conflict was **41.7% for cross-agent pairs vs 19.8% for intra-agent pairs** (non-overlapping 95% CIs); 84.4% of conflicted files were source code, and nearly 42% of conflicts were structural (modify/delete, add/add). Source: https://arxiv.org/abs/2607.04697. Confidence: primary.
- **Duplicate-change / shared-codebase tragedy-of-the-commons is measured in the literature**: "Governing the Commons: Code Ownership and Code-Clones in Large-Scale Software Development" collected change-size and clone-introduction data for TEN TEAMS across EIGHT COMPONENTS of one large industrial system, modelled team behavior with a Multi-Level Generalized Linear Model, and found teams behave differently per component; the proposed remedy is per-team visualizations of clone introduction compared against an average team (avoiding inter-team comparison). Source: https://arxiv.org/abs/2405.15866. Confidence: primary. (NOTE: the well-known "tragedy of the commons" study of shared codebases is NOT a Google study; the Google primaries here are "Advantages and Disadvantages of a Monolithic Codebase" (2018, https://research.google/pubs/advantages-and-disadvantages-of-a-monolithic-codebase/) and "Why Google Stores Billions of Lines of Code in a Single Repository" (2016, https://research.google/pubs/why-google-stores-billions-of-lines-of-code-in-a-single-repository/).)

## Metric catalogue — computable from the append-only room JSONL

Verdict key: **Y** = computable from the JSONL alone (replay the log, group by `seq`/`ts`/`from`/`resource`); **N** = NOT computable from the JSONL alone (needs a state the log does not hold: delivery events, cursors, wait outcomes, model telemetry, or git state); **Y-with-caveat** = computable but only as a proxy or with a known bias.

1. **Duplicate / overlapping-claim rate** — Y-with-caveat. Formula: for each `resource`, collect its `claim` records; a claim pair is OVERLAPPING if their leases `[claim.ts, claim.ts + claim.ttlMs)` intersect and no `release{resource}` for that resource lies between them. `duplicate_claim_rate = (#resources with ≥1 overlapping claim pair) / (#distinct resources claimed)`; `reclaim_rate = #release{reason:"reclaimed"} / #claim`. Fields: `claim{resource, ttlMs, ts, from}`, `release{resource, reason, prevHolder}`. **Caveat, load-bearing:** a FAILED claim appends NOTHING (first-writer-wins: "A loss appends NOTHING: it returns the current holder and expiry"), so contention attempts are INVISIBLE in the log. The room's duplicate-work signal is only visible after the fact, as overlapping leases or a `reclaimed` release — i.e. exactly the failure we want to prevent is under-measured. **Recommendation: add a `contended` record kind** (resource, would-be holder, incumbent holder) so duplicate-work attempts are countable. This is the room's direct analogue of AgenticFlict's 27.67% and the cross-agent 41.7% conflict rate, and of the noise-floor protocol's R3 alarm (coordination-key collision rate, alarm > 0.5%).
2. **Orphan / expired-claim rate** — Y. `expired_rate = #release{reason:"expired"} / #claim`; `orphan_rate = #claims whose holder never emitted release{reason:"released"} for that resource and whose lease lapsed / #claims`. Fields: `claim{from, resource, ts, ttlMs}`, `release{from, resource, reason, prevHolder}`. `release{reason:"expired"}` is written by the 5 s sweep with `from:"system"`. Note the plugin has NO `member{action:"leave"}` record ever appended and no `release{reason:"aborted"}` ever appended (both are in the schema, neither has a call site), so agent death mid-lease is invisible except as a later expiry/reclaim.
3. **Time-to-first-claim (TTFC)** — Y-with-caveat. `TTFC(resource) = min(claim.ts over that resource) − t0`, where `t0` is either the room's first record ts or the ts of the first `msg` mentioning the resource. Fields: `claim{resource, ts}`, `msg{body, ts}`. Caveat: the claiming agent's INTENT (when it decided to claim) is not logged, so TTFC is "time from first mention", not "time from decision to claim".
4. **Resource idle-gap / re-claim latency (the wait-time proxy)** — Y. For consecutive leases on the same resource: `idle_gap = claim₂.ts − release₁.ts` (time the resource sat unheld) and `handover_gap = release₁.ts − claim₁.ts` (time the lease was held past its own release). This is the closest computable analogue of Google's "Median Wall-Clock Review Time" / "Median Wall-Clock Merge Time" pair and of TeamBench's queue-wait. Fields: `claim{resource, ts, ttlMs}`, `release{resource, ts, reason}`.
5. **Wait time per agent (true)** — N. `wait_for_claim` outcomes are tool results, never log records; the waiter queue (`store.waiters`) is in-memory only, and the FIFO promotion path appends only the `claim`. **Recommendation: append a `wait` record** (resource, waiter, enqueue ts, grant ts, outcome∈granted|timeout|aborted) — this is the only way to measure whether `wait_for_claim` is productive or a stall, and it is the room's direct analogue of TeamBench's "Verifier false-accept 49.4%" and the noise-floor protocol's "per-match injection noise (mean 2.77 events/trial)".
6. **Claims-per-post ratio** — Y. `claims_per_post = #claim / #msg` (also per-agent: `#claim{from=a} / #msg{from=a}`). Fields: `claim{from}`, `msg{from}`. Interpretation anchor: MultiAgentBench's protocol ablation showed token usage and task score moving TOGETHER across topologies (graph good, tree bad) — so a claims-per-post ratio that rises while throughput falls is the room's own "coordination tax" signal.
7. **Coordination tokens per turn** — N as stated; Y-proxy. The log stores no token counts and no turn boundaries. Proxy: `coordination_tokens_estimate = Σ over msg records of ceil(len(body)/4)` (the plugin's own estimator, `estimateTokens = ceil(len/4)`) attributed per agent, or per topic, and divided by the number of `turn_start` boundaries (NOT in the log) → fall back to per-wall-clock-minute. **Recommendation: log a per-turn record** (agent, turn id, injected token count, injected record count, digest token count) — this is the OTel `gen_ai.invoke_agent.inference_calls` / `tool_calls` shape, and it is the ONLY way to compute Anthropic's "15× chat tokens" / "3–10× tokens" equivalent for OUR room. Aider's "User asks" counter and "Seconds per case" are the dashboard precedent.
8. **Findings-posted vs findings-read** — posted is Y (`#msg{performative:"inform"}` or a topic convention), **read is N**: there are no read receipts; cursors are in-memory (`store.cursors`) and only the session's own cursor is persisted outside the log (`pi.appendEntry("chatroom:cursor", …)`). The OTel analogue `a2a.server.task.message_count` and Phoenix's trace/span tree both require a delivery-side record. **Recommendation: append a `delivered` record** (target, record seq, tier) — it simultaneously makes tier distribution (T0/T1/T2), per-agent unread lag, and findings-read computable, and it is the room's version of the "coordination-active" filter the noise-floor protocol demands.
9. **Tier distribution (T0/T1/T2) and T0 wake rate** — N. Tier is COMPUTED PER VIEWER at delivery time (`classify(record, viewer)`) and never stored; delivery events are not logged. Needs the same `delivered` record as above (with a `tier` field). This matters because T0 is a wake+steer interrupt: the room's T0 rate IS its interruption budget, and no source we found measures interrupt cost directly — it is a genuine gap (see Gaps).
10. **Coordination-active metric (noise-floor protocol's required protocol)** — Y-with-caveat, once (5) and (8) are instrumented. Definition, adapted: restrict any coordination-effect measurement to intervals where the mechanism was LOGICALLY ACTIVE — for the room: an interval in which a claim was CONTENDED, or a `wait_for_claim` was enqueued, or a T0/T1 record was actually delivered. Today, "contended" and "delivered" are both unlogged, so the room cannot currently produce a coordination-active subset at all. **This is the single highest-value instrumentation change for the report's ranking of build tracks.**
11. **Duplicate-work rate (room's "tragedy of the commons")** — Y-with-caveat via metric 1 plus body-similarity. Fields: `claim{resource, from, ts}`, `msg{from, body, topic, replyTo}`. Cross-agent analogue of AgenticFlict's 41.7% vs 19.8% and of Anthropic's reported failure "one subagent explored the 2021 automotive chip crisis while 2 others duplicated work investigating current 2025 supply chains". Deliberate replication (verification) must be excluded — the Collaboration Tax paper insists useful redundancy is not waste, and the same distinction appears in Google's clone-visualization work.
12. **Rework rate (DORA stability analogue)** — Y. `rework_rate = #resources claimed ≥2 times by the SAME agent / #distinct resources claimed` — a re-claim by the same agent after a release maps to DORA's "deployments that were not planned but were performed to address a user-facing bug". The DORA primary uses exactly this construction (unplanned remediation as the rework signal), so the mapping is definitional, not loose.
13. **Review-wait time (Google analogue)** — Y-proxy, with the DORA/Google caveat attached. The room's review step is a `release` → next `claim` on the same resource; `handover_gap` (metric 4) is the wait. Google's own finding is that measured wait time was NOT causally linked to productivity (p50 p = 0.875) while PERCEIVED slowness was (p = 0.004) — so a room that reports only the wait-time number may be measuring nothing. Report perceived-signal proxies (T0 interrupts to the holder, wait timeouts) alongside.
14. **"Last agent standing" detection** — N as a liveness fact, Y-proxy. No `member{action:"leave"}` record is ever appended (the schema permits it; no call site emits it), so agent exit is invisible in the log. Proxy: for each agent, `last_activity_ts = max(ts of records with from = agent)`; the "last agent standing" is the agent whose last_activity_ts is the maximum, and a "quiet collapse" is detectable as an agent whose last activity precedes the room's final record by more than a threshold while other agents continued. **Recommendation: emit `member{action:"leave"}` on park/abort** — the roster currently reports "N joined" as a monotonic lifetime counter (the plugin's own code comments say so), which is why the digest had to be changed to "1 joined · 32 live".
15. **Conflict/overlap detection on file edits** — N from the room log. The room log records no file paths, no diffs, and no git state. The primaries for this (AgenticFlict 27.67%, 41.7% cross-agent vs 19.8% intra-agent, structural conflicts 42%) are all git-level measurements. To inherit them the plugin would need to carry the touched-file set on a claim (a per-agent "I own these paths" set) — a mechanics change, not a measurement change.
16. **Task-success / outcome metric** — N. The room has no notion of task success; MultiAgentBench's KPI (milestone contributions) and TeamBench's partial score both require an external grader. The room can supply the numerator's inputs (who contributed to which claimed resource) but not the grade.

### Cluster-level implications for the three build tracks (measurement-derived only)

- **MECHANICS wins on measurement grounds, specifically three record kinds**: `contended` (makes duplicate-claim attempts and the noise-floor protocol's R3 collision-rate alarm computable), `delivered` with `tier` (makes T0/T1/T2 distribution, per-agent read lag, findings-read, and the coordination-active subset computable), and `wait` with outcome+grant-ts (makes wait productivity computable). Without these three, the room can measure only what it already writes down, and the most important coordination failure (contention that ends in duplicate work) is structurally unmeasurable.
- **GUIDANCE is cheap to measure but weak as evidence**: the Collaboration Tax paper's own result is that a single system-prompt change (one clause per cascade stage) closes 38.3% ± 14.1% of the tax — a prompt-level fix for a coordination failure, at zero mechanical cost. That is the strongest published evidence FOR the guidance track, and it is a primary, peer-reviewed, EMNLP 2026 Main result. But the same paper's cascade (L1 grounding / L2 querying / L3 integration / L4 re-derivation) is a DYADIC (N=2) result, and the authors explicitly flag N≥3 as unstudied — our room is N=32.
- **Agent-research-retrieval has no supporting measurement evidence at all**, and the nearest signal is a write-conflict surface (a shared catalog that two agents can collide on), consistent with the peer report in F11.

## Conflicting evidence

- **Anthropic's two multi-agent posts disagree on the token multiplier**: 15× chat tokens (Jun 2025) vs 3–10× tokens vs single-agent for equivalent tasks (Jan 2026). Both are first-party; the 2026 post is the later and more general statement, and its 3–10× is vs SINGLE-AGENT while the 2025 15× is vs CHAT — different baselines, so these are not necessarily contradictory, but any report must state the baseline. (Do NOT cite "15×" without saying "vs chat".)
- **Anthropic 2026 says parallelization speeds research up (2025: "cut research time by up to 90%") while also saying multi-agent systems "often take longer overall than single-agent systems"** because of total compute. Both are Anthropic, same corpus. Resolution: the 90% is for parallel tool calls / parallel subagents on research queries; the "longer overall" is total end-to-end elapsed including coordination. The room must decide which it reports — and per Anthropic, "the primary benefit of parallelization is thoroughness, not speed."
- **MAST's inter-agent-misalignment share**: summing the six FC2 mode prevalences from the MAST paper gives 32.35%, while the noise-floor protocol's paper asserts MAST attributes **36.94%** of failures to inter-agent coordination breakdowns. MAST itself does not print a single category-total percentage in the text we read. Treat 36.94% as secondary (a restatement by another paper) and prefer the six primary mode percentages; the "largest category" claim in the noise-floor paper is also NOT supported by MAST's own table, where FC1's modes sum to 44.2% vs FC2's 32.35% — MAST's own framing is that FC1 (system design) dominates, and the noise-floor paper's "single largest category" is therefore a misreading. Do not repeat it.
- **Noise floor vs published gains**: the noise-floor protocol measures a [−3, +18] pp paired gap between CONFIGURATION-EQUIVALENT (coordination-inert) protocols and finds 7 of 10 published coordination gains below the envelope. This directly contradicts the framing of MultiAgentBench, TeamBench, CoCoBench, ProtocolBench and the Collaboration Tax paper — all of which report coordination gains without a paired noise-floor control. The reconciliation offered by the noise-floor authors themselves is that the comparison is heterogeneous (different model/task/metric/n) and "any individual row may be entirely real in its original setting" — but whether it survives a same-model paired replication is untested. **This is the strongest available argument that OUR plugin must report a noise floor, not just a delta.**
- **Merge-conflict rate for humans**: 0.2% (VSS+19, PR-based scenarios) vs 27.67% (AgenticFlict, AI-agent PRs) vs 19.8% intra-agent / 41.7% cross-agent (2026 co-active PR study). These are different populations and different denominators (merge scenario vs PR vs co-active pair). The VSS+19 "0.2%" is the classic number people quote and it is a specific sample/method, not a general rate.
- **DORA 2024 contradicts the intuition that AI-assisted development improves delivery**: AI improved code quality/docs/review processes yet reduced delivery throughput ~1.5% and stability ~7.2% per 25% AI adoption. This is a survey-based, self-reported primary, and it is about organizations adopting AI, not about agent swarms — the mapping to OUR plugin is analogical.
- **Review wait time**: Google's FSE'22 finds measured review wait time NOT causally linked to productivity while perceived slowness IS. So a "review-wait time" metric for a room may be measuring noise, unless paired with a perception/interruption proxy.
- **MultiAgentBench's own coordination score does not track task score** (Llama-3.1-70B: CS 75.00 with TS 0.21 on Minecraft). A coordination metric can be high while the task fails — so a room that reports only coordination health will not predict task success.
- **TeamBench says the Verifier is the binding constraint and removing it IMPROVES mean partial score**, while the paper's own table shows "No-Verify and Full Team tie on average (0.592), with No-Verify outperforming Full Team on most individual tasks" — i.e. the role that was supposed to add quality was adding overhead instead. Directly relevant to whether a room should add a verification/exclusion role at all.

## Gaps

- **No primary source measures the cost of INTERRUPTIONS in an agent swarm** (T0 wake+steer). The closest we found is Anthropic's observation of "distracting each other with excessive updates" (qualitative) and the noise-floor protocol's "per-match injection noise" (2.77 events/trial, every match firing a separate warning) — but nobody has published a metric for "cost per interrupt". Our room's T0 budget is therefore an unmeasured design choice; the report should say so.
- **No primary work measures "agent time" as a distinct quantity from wall-clock.** METR deliberately refuses to report agent completion time; Google distinguishes active vs wall-clock coding time per CL, which is the closest primary construct. Any "agent time" metric in the report must be labeled as our construction, and should adopt Google's active/wall-clock split.
- **The Collaboration Tax framework is dyadic (N=2) and its own authors state N≥3 is unstudied** (the partition structure and multi-party floor management "change qualitatively"). Our room is N=32, so the cascade's applicability to a bus with 32 participants is an extrapolation, not a finding.
- **The Collaboration Tax cascade labels are LLM-judged**, with expert-judge agreement only moderate on L4 (κ = 0.51) and Fleiss κ ∈ [0.40, 0.69] across stages. Any room metric modeled on L1–L4 inherits that judge reliability, and the room has no judge at all today.
- **MAST's LLM annotator recall is 0.77 / F1 0.80** (o1 few-shot), i.e. it misses ~23% of failure modes it was trained to find — so "we have no MAST failures" would be weak evidence.
- **Nobody publishes a benchmark for a room/bus-shaped coordination substrate** (append-only log + claim leases + tiered delivery). Every coordination benchmark we found assumes a turn-taking, message-addressed, or container-isolated substrate. The nearest structural analogue is the ET-MCP negative-knowledge store in the noise-floor protocol (a task-scoped store with typed failure events) — itself unpublished outside that workshop.
- **Duplicate-claim ATTEMPTS are unlogged in our room** (first-writer-wins appends nothing on a loss), and **wait outcomes, delivery events, tier assignments, cursors, and member leave are all unlogged**. Until `contended` / `delivered` / `wait` / `member{leave}` exist, the room cannot produce: the noise-floor protocol's coordination-active subset, its R3 collision-rate alarm, per-agent wait productivity, findings-read, tier distribution, or true last-agent-standing. This is the largest measurement gap and it is a MECHANICS gap, not a guidance gap.
- **Unverified:** the exact "150 minutes"-style figures I quote are all traceable to their primaries; I did NOT verify DORA's 2025 edition, MLE-bench's current leaderboard beyond the README values, WorkArena+"WorkArena++" numbers, Terminal-Bench, SWE-bench Verified's current resolution rates, or the "coordinated-duplicate-work" claim in the 21-agent DEV report (that one is from a practitioner report, cross-checked in F11). "42.7% WorkArena success" and "17.9% Llama 3 70B" are the showcased project-page numbers for specific configurations, not a current leaderboard.
- **Not searched to primary:** McKinsey's "cutting the coordination tax" and other vendor/consultancy framings of coordination cost — deliberately excluded as secondary. Letta's and OpenHands' per-agent cost dashboards were confirmed to exist but their CONTENT was not read beyond the API surface; treat the numbers as unverified.
