# F5 — smolagents + Letta: coordination and memory primitives for long-running agent teams

## Angle

Two framework families that ship *agent-to-agent* primitives rather than single-agent loops.

- **smolagents (HuggingFace)** — `managed_agents`: a manager agent calling specialized sub-agents *as tools*. Hierarchy is hard-wired manager→worker, one level of "team member" per manager (the sub-agent is exposed as a Python function `def <name>(task, additional_args) -> str` in the manager's code sandbox). Memory is per-agent (`AgentMemory` = flat list of steps) with no shared substrate; the only documented way to move knowledge between agents is *manual copy of another agent's `memory.steps`*. Notably: there is no first-party "agentic memory" feature under that name — the term in the assignment brief does not correspond to a shipped smolagents feature (see Gaps).
- **Letta (formerly MemGPT)** — the deepest shipping of a *blackboard*: **memory blocks** (in-context, always-visible, character-limited, agent-editable sections of the system prompt) that can be **attached to multiple agents at once** = a shared, contended, last-writer-wins scratchpad. Plus **sleeptime compute** (a second background agent that owns memory editing while the primary agent answers), **agent-as-tool** (send-message tools), **groups** (round-robin / supervisor / dynamic / sleeptime managers, v1 API, now archived), **shared memory repositories** (git-backed multi-agent file sharing, the current successor to shared blocks), **dynamic workflows** (agent-written JS fanning out to many subagents with pipeline/parallel/decide primitives), and an **MCP interface** in both directions (Letta hosts an MCP server exposing agents; the SDK consumes MCP servers).

Angle relevance to our plugin: Letta's shared block is the closest published analogue of a **blackboard**, and it is *documented as unsafe under concurrency* — the docs give an explicit concurrency table ("`memory_rethink` — full rewrites — **No (last-writer-wins)**") and an explicit anti-pattern ("Multiple agents doing `memory_rethink` on the same block simultaneously leads to lost updates"), plus a recommended mitigation ("Designate one agent … as the 'owner' for heavy edits. Other agents append via `memory_insert`"). That is almost exactly the ownership-vs-lease question our claim board raises, answered by a first-party vendor with a "one owner + append-only others" split. smolagents, by contrast, ships *no* shared substrate at all — coordination is entirely a call/return of a string.

All fetches dated 2026-10-20.

## Claims

### A. smolagents — managed agents = hierarchical manager→worker, agent-as-tool

- **Managed agents are passed to a manager's constructor and appear in its system prompt as callable Python functions.** `managed_agents=[web_agent]`; each sub-agent must have `name` and `description` ("mandatory attributes to make this agent callable by its manager agent"). / https://huggingface.co/docs/smolagents/en/examples/multiagents · https://github.com/huggingface/smolagents/blob/main/docs/source/en/examples/multiagents.md / 2026-10-20 / **primary**
  - The rendered system-prompt fragment (source, `src/smolagents/prompts/code_agent.yaml`, key `managed_agents`): "You can also give tasks to team members. Calling a team member works similarly to calling a tool: provide the task description as the 'task' argument. … You can also include any relevant variables or context using the 'additional_args' argument." Each member is emitted as `def {{ agent.name }}(task: str, additional_args: dict[str, Any]) -> str:` with the agent's `description` as the docstring. / https://github.com/huggingface/smolagents/blob/main/src/smolagents/prompts/code_agent.yaml / 2026-10-20 / **primary**
  - Note the wording defect in that shipped template: "Since this team member is **a real human**, be as detailed and verbose as necessary" — a stale phrase in a template whose members are agents. First-party prompt text; treat as a template artifact, not a design claim. / same URL / **primary**

- **The delegation contract is a fixed report template, not a free-form handoff.** Sub-agent's final answer must contain "### 1. Task outcome (short version): / ### 2. Task outcome (extremely detailed version): / ### 3. Additional context (if relevant)" and "everything that you do not pass as an argument to final_answer will be lost"; the manager receives "Here is the final answer from your managed agent '{{name}}': {{final_answer}}". / https://github.com/huggingface/smolagents/blob/main/src/smolagents/prompts/code_agent.yaml / 2026-10-20 / **primary**
  - There is a `provide_run_summary` flag that appends a `<summary_of_work>` block with the sub-agent's own step summary. / https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py (`MultiStepAgent.__call__`, lines ~868-890) / **primary**

- **Mechanically, a managed agent call is `agent(task, **kwargs)` → `self.run(full_task, **kwargs)` → the sub-agent's `run()` with `reset` defaulting to `True`.** `MultiStepAgent.__call__` calls `self.run(full_task, **kwargs)`; `run(..., reset: bool = True, ...)` calls `self.memory.reset()` and `self.monitor.reset()` when reset is true; `execute_tool_call` passes only `task`/`additional_args` down, so `reset` never reaches `run()`. / https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py / 2026-10-20 / **primary**
  - Consequence, documented upstream as a **bug**: "the sub-agent's memory will be cleared" on every manager→sub-agent call, so "memory being unable to be traced back." / https://github.com/huggingface/smolagents/issues/1695 (open, 2025-08-19) / **primary**
  - Proposed fixes, all still open at fetch date: `reset_on_managed_call` parameter / https://github.com/huggingface/smolagents/pull/2023 (open, 2026-03-01, fixes #1695) and https://github.com/huggingface/smolagents/pull/2244 (open) / **primary**
  - **This is the single most load-bearing smolagents fact for our plugin: in stock smolagents a sub-agent is a stateless function call. There is no per-agent durable memory across delegations, let alone shared memory.**

- **Parallel calls to the *same* managed agent in one step collide on shared instance state.** Upstream bug: "calling the same managed agent multiple times **in one step in parallel**, all calls produce identical or very similar results instead of executing independently … all `__call__` methods would be on the same agent instance, therefore sharing and overwriting the agent state." / https://github.com/huggingface/smolagents/issues/1781 (open, 2025-09-22) / **primary**
  - Mechanism confirmed in source: `ToolCallingAgent.process_tool_calls` dispatches multiple tool calls through a `ThreadPoolExecutor(self.max_tool_threads)`, so two calls into the same managed-agent *instance* execute concurrently on one instance. / https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py (lines ~1417-1434) / **primary**

- **A failing sub-agent's failure is laundered into a confident answer.** Upstream issue: "When a sub-agent used as a managed agent hits a tool error and loops, or exhausts `max_steps`, `MultiStepAgent.run()` never raises: it falls back to a best-effort, LLM-generated answer via `provide_final_answer()` … indistinguishable from a genuine, confident answer once it reaches the manager. The manager has no way to tell task completion from task failure." / https://github.com/huggingface/smolagents/issues/2747 (open, 2026-09-04) / **primary**

- **smolagents ships no shared-memory / blackboard primitive.** The only cross-agent memory transfer in the docs is a manual assignment: "# You could modify the memory as needed here by inputting the memory of another agent. # `agent.memory.steps = previous_agent.memory.steps`" (a commented-out line in the "Run agents one step at a time" recipe). / https://huggingface.co/docs/smolagents/en/tutorials/memory · https://github.com/huggingface/smolagents/blob/main/docs/source/en/tutorials/memory.md / 2026-10-20 / **primary**
  - `AgentMemory` itself is a flat list of `MemoryStep` dataclasses (`TaskStep`, `ActionStep`, `PlanningStep`, `SystemPromptStep`, `FinalAnswerStep`) with `reset()`, `get_succinct_steps()`, `get_full_steps()`, `replay()`. No shared store, no TTL, no lease, no claim. / https://github.com/huggingface/smolagents/blob/main/src/smolagents/memory.py / **primary**
  - **No memory consolidation / compaction ships.** Open feature request: "agents maintain a history of every interaction … Over time this results in a growing context size … Other agentic LLM applications like Claude Code deal with this by summarizing the context every few steps … To be able to do appropriate management of memory we would need some memory related tool". / https://github.com/huggingface/smolagents/issues/901 (open, 2025-03-06) / **primary**
  - Release-note scan of the 30 most recent releases shows no memory-consolidation or shared-memory feature; memory-related entries are `AgentMemory.replay` bugfixes, i18n of `memory.md`, GradioUI reset hooks. / https://github.com/huggingface/smolagents/releases / **primary**

- **Token accounting exists but no coordination accounting.** `TokenUsage{input_tokens, output_tokens, total_tokens}` per step/run; `Timing` for wall-clock. There is no per-agent budget, no per-turn spend cap, no backpressure. / https://github.com/huggingface/smolagents/blob/main/src/smolagents/monitoring.py / **primary**

- **smolagents' MCP surface is *inbound* only** (agents consume MCP servers as tools): `MCPClient` supports stdio, Streamable HTTP, legacy SSE, multiple servers at once, and `structured_output=True` for MCP `outputSchema` support. No smolagents-shipped MCP *server* exposing smolagents agents to other agents. / https://huggingface.co/docs/smolagents/en/tutorials/tools · https://github.com/huggingface/smolagents/blob/main/src/smolagents/mcp_client.py / 2026-10-20 / **primary**

- **Measured multi-agent payoff and cost, first-party (HF blog on the GAIA leaderboard run):** the submitted system was a *manager agent + web-search agent* ("This embedding of an agent as a tool is a naive way to do multi-agent orchestration, but we wanted to see how far we could push it"); result "44.2% on the validation set … #1 overall, with 4 points above the second"; test set 33.3%, "#2, in front of Microsoft Autogen's submission". The blog itself labels the orchestration "naive" and names multi-agent orchestration as a *next-steps* improvement axis. / https://huggingface.co/blog/beating-gaia / 2026-10-20 / **primary**
  - Context figures cited there: "GPT-4-Turbo does not reach 7% on average. The top submission is (was) an Autogen-based solution with a complex multi-agent system … it reaches 40%."
  - Cost note (HF's own framing, attributing the number to the CodeAct paper): "the paper shows that Code actions require 30% fewer steps than JSON … your agent system runs are ~30% cheaper." The underlying primary source is the CodeAct paper: "CodeAct achieves up to a 20% absolute improvement over baselines on the success rate … while requiring **up to 30% fewer actions**." / https://arxiv.org/abs/2402.01030 (Executable Code Actions Elicit Better LLM Agents, 2024-02-01) / **primary**

(The phrase exists in the unrelated research line "A-Mem: Agentic Memory for LLM Agents", which is **not** smolagents.) / searched smolagents source tree, docs tree, and 30 release notes / 2026-10-20 / **primary (absence)** / **speculative** for the A-Mem attribution

### B. Letta — memory blocks as a shared blackboard (the closest published analogue)

- **A memory block is an always-in-context, character-limited, agent-editable section of the system prompt**, rendered as XML-ish markup prepended to the prompt (`<persona><description>…</description><metadata>chars_current/chars_limit</metadata><value>…</value></persona>`). Fields: `label`, `description`, `value`, `limit` (characters); optional `read_only`. / https://docs.letta.com/v1-sdk/memory/memory-blocks/ / 2026-10-20 / **primary**
  - First-party framing of blocks as a coordination primitive: "**Memory blocks aren't just storage - they're a coordination primitive that enables sophisticated agent behavior.**" with listed uses including "Coordinate multi-agent systems: parent agents watch subagent result blocks update in real-time" and "Maintain working memory in a scratchpad block". / same URL / **primary**
  - Origin blog: "Because memory block values are just strings, you can store more complex data structures like lists or dictionaries in blocks" and the multi-agent use cases "Shared knowledge bases", "Sleep-time compute: Background agents updating the memory of primary agents", "Collaborative memory: Teams of agents maintaining a shared understanding". / https://www.letta.com/blog/memory-blocks (2025-05-14) / **primary**

- **A block attached to multiple agents IS shared memory, with immediate visibility.** "When one agent updates the block, all others see the change immediately. This enables real-time coordination without explicit agent-to-agent messaging." Diagram shows a Supervisor and a Worker both holding an `Organization: Letta` block. Attach with `block_ids=[shared_block.id]`; detach removes access without deleting the block; `client.blocks.agents.list(block_id=...)` enumerates holders. / https://docs.letta.com/v1-sdk/memory/shared-memory/ / 2026-10-20 / **primary**
  - The legacy page's own warning: "Memory blocks may be deprecated in the future. We do not recommend building on memory blocks anymore. Use shared memory repositories instead, and make a best effort to migrate agents to MemFS."

- **The documented concurrency semantics of the shared blackboard (verbatim table) — this is the highest-value primary evidence in this file for our claim/lease design:**
  | Operation | Use when | Concurrent-safe? |
  |---|---|---|
  | `memory_insert` | Appending new info | **Yes (append-only)** |
  | `memory_replace` | Targeted edits | **Mostly (fails if target string changed)** |
  | `memory_rethink` | Full rewrites | **No (last-writer-wins)** |
  / https://docs.letta.com/v1-sdk/memory/shared-memory/ / 2026-10-20 / **primary**
  - Mitigation guidance, verbatim: "Designate one agent (or sleep-time memory) as the 'owner' for heavy edits. Other agents append via `memory_insert`."
  - Named anti-pattern, verbatim: "**Anti-pattern**: Multiple agents doing `memory_rethink` on the same block simultaneously leads to lost updates."
  - Race-condition advice: "Design blocks so each agent updates their own section. Use timestamps and agent IDs in content. Consider separate blocks for high-contention data." Also: "`blocks.update()` **replaces** the entire block content - it does not append. All agents with access see changes immediately."
  - Troubleshooting entry: "Agent can't see updates — Verify both agents have the same `block_id` attached. Check that updates completed (agent finished its turn). Ensure character limit wasn't exceeded." — note the visibility is **turn-boundary** ("agent finished its turn"), not write-boundary.

- **Read-only is per-block, not per-agent.** "Read-only applies to the entire block, not per-agent. You cannot make a block read-only for some agents but writable for others." / https://docs.letta.com/v1-sdk/memory/shared-memory/ / **primary**
  - Documented use: "Share read-only policies across all agents from a central source" (legacy blocks page).

- **Published coordination patterns over a shared block (a first-party catalogue of blackboard patterns)** — `/ https://docs.letta.com/v1-sdk/memory/shared-memory/ / **primary**`:
  - "**Supervisor/Worker State** — Block: `task_queue` — Attached to: Supervisor + all workers — Pattern: Supervisor writes tasks, workers read and update status"
  - "**Shared Knowledge Base** — Block: `domain_knowledge` — Pattern: Any agent can append learnings, all benefit"
  - "**Coordination/Handoff** — Block: `handoff_context` — Attached to: Agent A + Agent B — Pattern: Agent A writes before handoff, Agent B reads on pickup"
  - "**Global Config** — Block: `system_config` (read-only)"
  - Note the "Supervisor/Worker State" pattern is a **shared task list over a shared string**, with no ordering, no lease, no TTL — i.e. exactly the blackboard-only tier of our design, minus ownership enforcement.

- **Shared memory blocks are now legacy; the current mechanism is a git-backed shared repository (MemFS).** "Each shared memory repository is a Git repository hosted in Letta Cloud and owned by your organization." Agents read/edit with normal file and Git tools; "The agent must commit and push its changes. Other agents can then pull those commits into their own checkouts." Letta Code clones at `$MEMORY_DIR/../<repository-name>/`; later syncs fast-forward the local checkout. / https://docs.letta.com/concepts/shared-memory/ / 2026-10-20 / **primary**
  - Memory vs shared ownership table (verbatim): MemFS = "One agent" / "Store the agent's identity, skills, and long-term memory"; Shared memory repository = "Your organization" / "Share knowledge and working files between agents".
  - **Conflict resolution is delegated to git.** "Every memory edit is committed to the MemFS git repository. This provides version history, conflict resolution, and a clear boundary between saved memory and uncommitted changes." / https://docs.letta.com/concepts/memfs/ / **primary**
  - Concurrent background editing uses **git worktrees**: "Memory subagents such as dreaming and memory doctor use git worktrees so they can update memory concurrently without blocking the main agent." / same URL / **primary**
  - Shared memory repos require cloud hosting; "Local agents use their own MemFS and project files."

- **Agent-owned memory files (MemFS) are projected onto the machine and tiered by directory.** Memory labels become paths (`persona` → `persona.md`); root files are in the system prompt every turn; subdirectories with their own `MEMORY.md` index stay out of context until read. "MemFS does not include a semantic or vector index by default. Agents find memory in its Markdown files with normal file-search and read tools." (Optional MemFS Search mod adds keyword/semantic/hybrid search.) / https://docs.letta.com/concepts/memfs/ / **primary**

### C. Letta — sleeptime compute / dreaming (off-hours self-improvement)

- **The architectural claim (first-party blog):** a sleep-time-enabled agent "actually creates two agents under the hood: a primary agent and a sleep-time agent. The primary agent … is **not provided with tools to edit its core memory**, which is the memory stored in-context composed of memory blocks. These tools are attached to the sleep-time agent, which has the ability to manage *both* the in-context memory of the primary agent as well as its own in-context memory." / https://www.letta.com/blog/sleep-time-compute (2025-04-21) / 2026-10-20 / **primary**
  - Stated rationale: "In MemGPT, memory management, conversation, and other tasks are all bundled into a single agent, which means the agent may be slower … and potentially less reliable … Offloading memory to a sleep-time agent allows memory management to happen asynchronously. Memory formation in MemGPT is incremental, so memories may become messy and disorganized over time."
  - Latency/cost knob: primary and sleep-time agents "can be configured independently with different underlying models … the conversational primary agent can use a fast model like gpt-4o-mini, while the sleep-time agent can use a larger and slower model like gpt-4.1 or Sonnet 3.7. Sleeptime agents can also be configured to run at different frequencies. **The higher the frequency setting, the more tokens your agent will use**: but the more time the agent will have to revise its learned context."
  - "the sleep-time agent modifies the memory in an 'anytime' fashion - so the primary agent can read from this memory whenever, without having to wait for the sleep-time agent to finish its reasoning." — i.e. read-while-write, no lock.
  - Shipped "as part of Letta 0.7.0" (blog).

- **The peer-reviewed numbers (paper):** sleep-time compute "can reduce the amount of test-time compute needed to achieve the same accuracy by **~ 5x** on Stateful GSM-Symbolic and Stateful AIME" and "by scaling sleep-time compute we can further increase accuracy by **up to 13% on Stateful GSM-Symbolic and 18% on Stateful AIME**"; on Multi-Query GSM-Symbolic (multiple related queries per context) "we can decrease the average cost per query by **2.5x**" by amortizing sleep-time compute across related queries about the same context. Also: "the predictability of the user query is well correlated wi…" (truncated in the HTML abstract) with effectiveness. / https://arxiv.org/abs/2504.13171 (Sleep-time Compute: Beyond Inference Scaling at Test-time, 2025-04-17) / 2026-10-20 / **primary**
  - These are **math-benchmark** numbers on *one agent's own* memory, not multi-agent coordination numbers.

- **Current Letta product name for the same idea: "dreaming".** "Dreaming uses background subagents to review recent conversations, consolidate useful lessons, and update memory without interrupting your active work. Configure dreaming with `/sleeptime` in the CLI or Dream settings in the app. Choose when it runs: after a set number of completed agent steps or when the context window is compacted." Optional "Agent reviews before applying" second pass: "This uses more model tokens and does not ask you for approval." / https://docs.letta.com/configuration/memory/ / 2026-10-20 / **primary**
  - SDK surface: `dreaming: { trigger: "off" | "step-count" | "compaction-event", behavior: "reminder" | "auto-launch", stepCount: 25 }`; `behavior` is settable only at agent creation; sessions may override `trigger` and `stepCount`. / https://docs.letta.com/agent-sdk/memory/ / **primary**
  - Built-in subagent catalogue includes `reflection` — "Background 'sleep-time' memory consolidation from recent conversations" — and `memory` — "Reorganize memory blocks into a cleaner hierarchy with less redundancy". / https://docs.letta.com/configuration/subagents/ / **primary**
  - Cost documentation (memory-side): "The memory workflow **backs up the current repository before splitting large files, merging duplicates, or restructuring the hierarchy**." / https://docs.letta.com/configuration/memory/ / **primary**

- **Letta Code's reflection subagent is a genuinely separate agent process with a restricted toolset** — the primary agent's memory is edited by a background worker under git rules: "You are NOT the primary agent. You're reviewing conversations that already happened"; tools are only `Bash` and `Edit`; "All filesystem writes under the memory repo"; "Do not push: the harness handles normal sync after you finish." / https://github.com/letta-ai/letta-code/blob/main/src/agent/subagents/builtin/reflection.md / 2026-10-20 / **primary**
  - The `memory` subagent prompt adds the concurrency rule a blackboard needs: "For a memory update it is a **private worktree** of the agent's memory: the harness merges your commits into the main checkout when you finish, and anything left uncommitted is discarded." and "stage them by explicit path, never with `git add -A` or `git add .`, because the primary agent may be editing other files in this checkout at the same time." / https://github.com/letta-ai/letta-code/blob/main/src/agent/subagents/builtin/memory.md / **primary**
  - Reflection startup context is budgeted: `REFLECTION_STARTUP_CONTEXT_TOKEN_LIMIT = 16_000`, `REFLECTION_PARENT_MEMORY_SNAPSHOT_CHAR_LIMIT = 40_000`, chars-per-token estimate 4, with a truncation notice telling the subagent to "read files directly from MEMORY_DIR if needed". / https://github.com/letta-ai/letta-code/blob/main/src/agent/subagents/context-budget.ts / **primary**

- **The v1 API also shipped a dedicated sleep-time *agent type* and a sleep-time *group manager*** — `AgentType.sleeptime_agent = "sleeptime_agent"`, `AgentType.voice_sleeptime_agent`, `enable_sleeptime` flag ("If set to True, memory management will move to a background agent thread"), `ManagerType.sleeptime` with `sleeptime_agent_frequency`, and a dedicated system prompt "You are Letta-Sleeptime-Memory" that gives the background agent narrow vs broad memory-edit tools ("Use your precise tools to make narrow edits … you can use your `rethink` tool to reorganize the entire memory block at a single time") and instructs it to "call the finish tool directly" when there is nothing to record. / https://github.com/letta-ai/letta/blob/archive/letta/schemas/agent.py · https://github.com/letta-ai/letta/blob/archive/letta/schemas/group.py · https://github.com/letta-ai/letta/blob/archive/letta/prompts/system_prompts/sleeptime_v2.py / 2026-10-20 / **primary** (note: `letta-ai/letta` main branch now contains only docs — the V1 server lives on the `archive` branch: "The `archive` branch contains the retired Letta V1 API server.")

### D. Letta — groups, agent-as-tool, and the MCP surface

- **Letta v1 shipped groups with pluggable manager types** — `ManagerType` = `round_robin`, `supervisor`, `dynamic`, `sleeptime`, `voice_sleeptime`, `swarm`. Group fields include `agent_ids`, `manager_agent_id`, `termination_token`, `max_turns`, `sleeptime_agent_frequency`, `turns_counter`, `last_processed_message_id`, `max_message_buffer_length`/`min_message_buffer_length`, and a deprecated `shared_block_ids`. / https://github.com/letta-ai/letta/blob/archive/letta/schemas/group.py / 2026-10-20 / **primary**
  - The `dynamic` manager is a real conversation-level protocol: it loads all participant agents, keeps a `message_index` per agent, and terminates on a `termination_token` (default `"DONE!"`) or `max_turns` (default = number of agents). / https://github.com/letta-ai/letta/blob/archive/letta/groups/dynamic_multi_agent.py / **primary**
  - The `supervisor` manager's actual body is **entirely commented out** in the archived source, with a `send_message_to_all_agents_in_group` tool sketched in comments — i.e. the supervisor pattern was scaffolded, not finished. / https://github.com/letta-ai/letta/blob/archive/letta/groups/supervisor_multi_agent.py / **primary**
  - **`swarm` is declared in the enum but has no implementation**: `letta/groups/helpers.py` dispatches only round_robin / dynamic / supervisor / sleeptime, and falls through to `raise ValueError(f"Type {group.manager_type} is not supported.")`. There is no `swarm.py` in the tree. / https://github.com/letta-ai/letta/blob/archive/letta/groups/helpers.py / **primary**
  - The v1 API server is retired; the live product is `letta-ai/letta-code` ("Letta Code"), with the V1 server on the `archive` branch. / https://github.com/letta-ai/letta (README) / **primary**

- **Agent-as-tool / agent-to-agent messaging, v1 (archived source):** three builtin tools in the multi-agent function set — `send_message_to_agent_and_wait_for_reply(message, other_agent_id)` (blocking, two-way, sender identity auto-injected as an `[Incoming message from agent with ID '…']` prefix), `send_message_to_agent_async(message, other_agent_id)`, and `send_message_to_agents_matching_tags(message, match_all, match_some)` (tag-directed broadcast). / https://github.com/letta-ai/letta/blob/archive/letta/functions/function_sets/multi_agent.py / 2026-10-20 / **primary**
  - Note the failure of the broadcast API to actually reach an agent: the code appends the original message **plus a lowercased copy** of it ("to make downstream matching deterministic across LLM capitalization choices") — a workaround for non-deterministic routing, i.e. a documented-but-hacky addressing mechanism.
  - All three are **request/response or fire-and-forget with no shared history, no queue, no TTL, no delivery guarantee, and no "who is blocked on what"**.

- **Agent-as-tool, current Letta Code:** `SendAgentMessage` tool with `message` (required), `agent_id` (start a new conversation with a stateful agent), `conversation_id` (continue an existing `conv-…` thread; a subagent that omits both messages its parent), and `computer` (execution destination). Schema description: "An agent shares its identity and memory across conversations." / https://github.com/letta-ai/letta-code/blob/main/src/tools/schemas/SendAgentMessage.json · https://github.com/letta-ai/letta-code/blob/main/src/backend/api/agent-message.ts / 2026-10-20 / **primary**
  - The injected recipient-side reminder is a hard guidance line (comparable to our T0/T1 routing rule): "The sender will only see the final message you generate (not tool calls or reasoning). Include your answer in your final response." and "Ordinary assistant output is not forwarded to the sender." / same URLs / **primary**
  - **Nested delegation is depth-capped**: `MAX_SUBAGENT_DEPTH = 2` — "the root agent is depth 0 and each Agent launch adds one. Agent is attached below MAX_SUBAGENT_DEPTH, so a root's child may launch one more layer and that grandchild is a leaf." Memory-profile workers (reflection/memory/init) are excluded from getting `Agent` or `SendAgentMessage` at all: "they maintain the parent's memory in a confined process and must not message or launch agents." / https://github.com/letta-ai/letta-code/blob/main/src/agent/subagents/subagent-depth.ts / **primary**

- **A shared task board with dependency edges — Letta Code's `Task*` family (closest shipping analogue to a claim board + dependency ordering).** `TaskRecord` has `taskId`, `subject`, `description`, `status` (`pending` | `in_progress` | `completed` | `deleted`), optional `owner`, **`blocks: string[]`** ("IDs of tasks this task blocks (i.e. those tasks can't start until this one finishes)"), **`blockedBy: string[]`**, a free-form `metadata` bag, and timestamps. Tools: `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate` (`addBlocks`, `addBlockedBy`, `owner`, `status`). / https://github.com/letta-ai/letta-code/blob/main/src/tools/impl/tasks/store.ts · https://github.com/letta-ai/letta-code/blob/main/src/tools/schemas/TaskUpdate.json / 2026-10-20 / **primary**
  - **Critical scope caveat, verbatim from the source**: "Scope: process-lifetime. Same model as `process_manager.ts`'s background task registry. A future follow-up may scope per-conversation." — the store is an in-memory `Map`, so it is **not** durable, **not** shared across processes/machines, and **has no lease/TTL/atomic-claim semantics**. `owner` is a free-form string, not enforced.
  - This is still notable: it shows a mainstream vendor shipping *dependency edges + owner* on a task board, i.e. the data model our MECHANICS track proposes — with the enforcement left to conventions.

- **Dynamic workflows: the strongest shipped fan-out primitive in either family.** An agent writes a small JS script with primitives `agent()`, `parallel()`, `pipeline()`, `decide()`; each `agent()` call is one subagent. Documented hard limits: "Subagents running at once — **16 by default**; the rest queue"; "Subagents per run — **1,000**"; "Per subagent — **10 minutes, 1,000 tool calls, stopped after 3 identical calls in a row**"; "Items per fan-out stage — **4,096**". / https://docs.letta.com/configuration/workflows/ / 2026-10-20 / **primary**
  - **Explicitly no inter-agent channel, verbatim**: "Subagents cannot see each other or each other's conversations. Results move between stages through the script alone: what one stage returns becomes part of the next stage's prompt. **There is no shared scratchpad and no way for two subagents to message each other.**" — a direct first-party statement that fan-out has *no* blackboard.
  - Also: "Each subagent starts with only the prompt the script gives it: no memory, no conversation history, no skills." and "Subagents get read-only tools (`Read`, `Grep`, `Glob`) by default, so say when a stage must write files or run commands."
  - Cost guidance: "One run can spawn dozens of subagent sessions, each with its own context window. Try a new workflow on one directory with a handful of agents before turning it loose on a repository." and "your agent can also call specific models and mix and match models within the same workflow … use cheaper models for easier tasks".
  - Run persistence: each run gets a directory with `script.js`, `args.json`, and a **JSONL journal** with one line per completed subagent call plus `tool_call` and `decision` entries (model, cost, calibrated, valid, totalTokens). "The journal is a debugging record (what each agent actually returned); nothing replays from it." / https://github.com/letta-ai/letta-code/blob/main/src/tools/workflow/journal.ts / **primary**
  - First-party blog confirms and quantifies the per-call cost concern: "Dynamic workflows can spawn many subagents, so per-call cost adds up fast. Low-cost models with strong coding ability, such as DeepSeek V4.1 Flash and GPT-6 Luna, make large fan-outs practical." / https://www.letta.com/blog/dynamic-workflows/ (2026-09-28) / **primary**

- **Letta hosts an MCP server so *other* agents can create and message Letta agents — the "agent-as-tool over MCP" surface.** Endpoint `https://api.letta.com/mcp`, bearer-token auth (OAuth-only clients unsupported). Tools: `list_agents`, `list_models`, `create_agent`, `send_agent_message`, `get_run`, `get_reply`. "Letta agents keep their memory across every conversation, so the calling agent does not need to resend context." / https://docs.letta.com/platform/hosted-mcp/ / 2026-10-20 / **primary**
  - **Documented wait semantics (directly comparable to our blocking waits):** "A call waits up to **110 seconds** for a reply. Longer work keeps running; use `get_reply` with the returned IDs rather than resending." Return statuses: `completed` (reply included), `queued` (accepted; did not wait), `wait_failed` (accepted, waiting timed out → call `get_reply`), `acceptance_unknown` (may have been accepted → check the conversation before resending), `submission_failed` (not accepted).
  - Also: "Messages run on a Cloud computer in unrestricted permission mode: the agent executes tools without approval prompts."
  - Direction reversed: the Agent SDK consumes stdio/HTTP/SSE MCP servers as tools, and those tools "are not persisted on the Letta agent: their implementations, processes, credentials, and filesystem access belong to the application hosting the session." / https://docs.letta.com/agent-sdk/mcp/ / **primary**

- **Background subagents = the current async-delivery primitive.** "By default, launching a subagent blocks: the subagent tool does not return until the subagent finishes. Background subagents flip this around: the main agent can call subagents in 'background mode' … When the subagent finishes, a completion notification is automatically injected into the conversation, and the main agent can read the result." / https://docs.letta.com/configuration/subagents/ / **primary**
  - Letta Code blocks foreground polling: `FOREGROUND_SLEEP_BLOCKED_MESSAGE` = "Foreground `sleep` is blocked. If you are waiting on a task you already started, its completion notification will arrive on its own; keep working or end your turn." / https://github.com/letta-ai/letta-code/blob/main/src/tools/impl/foreground-sleep.ts / **primary**
  - Subagent types and access: `fork` (inherits full context+tools), `general-purpose`, `history-analyzer`, `init`, `memory`, `recall` (read-only), `reflection`; access column is Read/write except `recall` = Read-only. Custom subagents are Markdown+YAML in `.letta/agents/` with `tools`, `model`, `memoryBlocks` ("Which memory blocks the subagent can access: specific list, `all`, or `none`. Defaults to `all`"), `skills`. / https://docs.letta.com/configuration/subagents/ / **primary**
  - **The memoryBlocks frontmatter field is a per-subagent capability grant on shared memory** — i.e. Letta's answer to "who may write the blackboard" is *capability scoping at spawn time*, not runtime locking.

- **Deployment of an existing agent as a subagent** = "agent-as-tool" with state: "It is also possible to deploy an arbitrary Letta agent as a subagent by specifying its `agent_id` … This lets your main agent invoke other agents—with their own rich memories, personalities, and skillsets—as subagents". Constraint: "When deploying an existing agent (via `agent_id`), `subagent_type` must currently be `general-purpose`." / https://docs.letta.com/configuration/subagents/ / **primary**

### E. Documented cost of the blackboard / shared-memory approach

- **Storage cost of shared memory is priced and small.** "The Free plan includes **5 MiB per memory repository**; Pro includes **50 MiB per memory repository**. This counts the files in each branch or tag's latest snapshot, not Git history. The allowance applies separately to each repository, including shared memory." / https://docs.letta.com/configuration/memory/ / 2026-10-20 / **primary**
  - Plan prices: Free $0/month; Pro $20/month (up to 20 stateful agents, 50 MiB/memory repo); API plan $20/month (unlimited agents, usage-based); "LLM usage is charged based on the underlying token costs of the model used." Free plan limited to 3 stateful agents. / https://docs.letta.com/pricing/ / **primary**

- **Context cost of a shared block is a per-agent charge.** A block is *always in the context window* of every attached agent, so attaching a block to N agents multiplies its token cost by N. Blocks are limited in **characters** (`limit`, e.g. 5000), and the docs' own remediation for overflow is: "Increase limit … Archive old content to a separate block. Have an agent periodically summarize." / https://docs.letta.com/v1-sdk/memory/memory-blocks/ · /https://docs.letta.com/v1-sdk/memory/shared-memory/ / **primary**

- **Sleep-time compute's cost is explicitly a token-frequency dial**: "The higher the frequency setting, the more tokens your agent will use" (blog); "Agent reviews before applying … uses more model tokens" (dreaming docs). The paper's counter-measure is amortization: ~5x less test-time compute, 2.5x lower average cost per query when one context serves multiple related queries. / https://www.letta.com/blog/sleep-time-compute · https://docs.letta.com/configuration/memory/ · https://arxiv.org/abs/2504.13171 / **primary**

- **Fan-out cost is documented as the thing that breaks.** Workflow limits (16 concurrent, 1,000/run, 10 min + 1,000 tool calls per subagent) and the guidance "One run can spawn dozens of subagent sessions, each with its own context window" + "Dynamic workflows can spawn many subagents, so per-call cost adds up fast." / https://docs.letta.com/configuration/workflows/ · https://www.letta.com/blog/dynamic-workflows/ / **primary**

- **smolagents' only first-party cost figure is the ~30%-fewer-actions code-vs-JSON property of CodeAct**, quoted in the GAIA blog; it is not an orchestration cost multiplier. No published multi-agent-vs-single-agent cost ratio exists for smolagents in the sources read (unverified elsewhere). / https://huggingface.co/blog/beating-gaia · https://arxiv.org/abs/2402.01030 / **primary** (for the claim's origin) / **unverified** (for any multi-agent cost ratio)

## Conflicting evidence

- **The assignment brief's arXiv IDs are wrong.** 2502.04038 (offered as "Letta / Sleep-time compute") is a neural-network language-learning paper; 2504.09713 (offered as "the Letta OS paper") is a ferroelectric-materials paper; 2402.04445 (offered as "smolagents arXiv") is a solar-flare physics paper. The actual primary papers are: sleep-time compute = **arXiv:2504.13171** (Letta, 2025-04-17); the smolagents-lineage primary paper = **arXiv:2402.01030** (CodeAct, 2024-02-01), which the HF GAIA blog cites for its 30%-fewer-actions claim; Letta's own lineage paper is **arXiv:2310.08560** (MemGPT, 2023). There is **no arXiv paper titled "Letta OS"**; Letta's OS framing lives in the Agent File blog post (2025-04-02) and the Context Constitution (2026-04-02).
- **"Letta OS" is a marketing/OS-metaphor, not a research artifact** — the assignment's framing as an arXiv paper does not resolve to any primary source. The nearest primary sources are the Letta research page (https://www.letta.com/research/) and the Context Constitution repo (https://github.com/letta-ai/context-constitution).
- **smolagents' own docs contradict the multi-agent framing on capability**: the shipped prompt says a managed agent is "a real human", while the same file's contract treats it as a stateless function returning a string; and `agent.memory.steps = previous_agent.memory.steps` is *commented out* in the docs, i.e. the "share memory between agents" recipe is presented as a manual hack, not a supported feature.
- **Letta's shared-block blackboard is documented as unsafe, yet Letta simultaneously markets it as enabling coordination.** The same legacy page that says "This enables real-time coordination without explicit agent-to-agent messaging" also carries the concurrency table ("`memory_rethink` … No (last-writer-wins)") and the anti-pattern ("lost updates"), and marks the whole mechanism `status: legacy` with "We do not recommend building on memory blocks anymore."
- **Letta's "swarm" manager type is a declared-but-unimplemented enum member** (`ManagerType.swarm` exists; no implementation; dispatch raises `ValueError`). Any claim that Letta ships a swarm coordinator would be wrong on the archived source.
- **The v1 "supervisor" group manager is commented-out scaffolding**, not an implementation — so "Letta ships a supervisor pattern" overstates the archived code.
- **Two Letta products, two different "sleep-time" mechanisms**: v1 shipped a *dedicated agent type* (`AgentType.sleeptime_agent`, `enable_sleeptime` → "background agent thread") with a `sleeptime_agent_frequency` dial and a group manager; the current product ships *background subagents* (`reflection` / `memory`) launched by "dreaming" triggers (`step-count`, `compaction-event`). The blog's "two agents under the hood" framing describes the v1 shape. Cite the era-appropriate source.
- **Letta's *current* shared-memory answer (git repos + worktrees + commit/push/pull) deliberately trades "real-time" for durability**: the legacy block path is "real-time coordination" but legacy and last-writer-wins; the current path is versioned and conflict-resolved but requires explicit commit+push and explicit pull by other agents — i.e. **eventually consistent, not immediately consistent**. Two agents editing the same shared repo concurrently rely on git merge semantics, not on coordination primitives.
- **Letta's fan-out explicitly has no shared scratchpad and no inter-subagent messaging** — which conflicts with the marketing that dynamic workflows "orchestrate many subagents" and, per the F11 practitioner evidence, is the exact seam where duplication and lost updates appear.
- **smolagents' parallelism can be actively harmful**: the same managed agent called twice in one step shares instance state (issue #1781) and can return duplicate results — a *silent* coordination defect, not a loud failure.

## Gaps

- **No published cost ratio for multi-agent vs single-agent in either family.** smolagents' only cost figure (~30% cheaper) is a code-vs-JSON action property from the CodeAct paper; Letta's figures are per-subagent token/frequency dials and workflow caps. Any "multi-agent costs Nx" claim would be unverified. (Anthropic's 15x figure, from F4, is the only sourced multiplier in this cluster.)
- **No measured evidence that a shared memory block improves swarm outcome quality.** The blocks docs assert capability ("sophisticated agent behavior") but publish no ablation. The only Letta memory benchmarks found are agent-memory benchmarks (Letta Leaderboard, Context-Bench, LoCoMo filesystem result 74.0%) — i.e. *single-agent* memory, not multi-agent coordination.
- **No sleep-time/multi-agent interaction study.** The sleep-time compute paper measures a single agent's own offline pre-computation on math benchmarks (Stateful GSM-Symbolic, Stateful AIME); it does not evaluate shared blocks, groups, or contention.
- **Letta v1 "groups" has no public usage numbers, no failure post-mortem, and the whole V1 server is archived.** Any claim about groups' effectiveness is unverified.
- **The current Letta Code task-board (`Task*`) has no documented multi-agent semantics beyond "owner is a free-form string" and "scope: process-lifetime"** — the dependency edges (`blocks`/`blockedBy`) are stored but no first-party doc states that any agent or the harness *enforces* them. Whether they are advisory is unverified from source (the store exposes no enforcement code, but no doc says so either).
- **smolagents has no first-party guidance/playbook layer** for delegation — only the prompt templates. No "when to delegate / when to wait / how to hand off" protocol document exists (the "hierarchical" claim in the brief maps only to `managed_agents` + `planning_interval`).
- **No retrieval-over-coordination-literature tool exists in either family** (relevant to track (c)): smolagents' `MCPClient` is a generic tool bridge and Letta's MCP server exposes agents, not literature search. Absence established for these two frameworks only.
- **Whether Letta Code's `MessageChannel` tool provides any cross-agent messaging** (as opposed to human channels like Slack/Telegram) is unverified — the implementation file resolves *channel plugins* for messaging platforms; it is not an agent-to-agent bus.
- **The "agentic memory" term in the brief could not be grounded in any smolagents primary source** (source tree, docs tree, 30 release notes all checked). If the brief meant the research line "A-Mem: Agentic Memory for LLM Agents", that is a separate paper — unverified here, and **not** a smolagents feature.
