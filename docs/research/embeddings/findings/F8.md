# F8 — Counter-angle: lexical/BM25 vs dense for identifier-heavy technical content

## Angle

Evidence AGAINST dense embeddings for a CPU-only, text-only retrieval layer over
agent-chatter containing file paths, code symbols, version strings, error codes,
hashes. Sub-questions: (1) where lexical/BM25 beats dense (published), (2) hybrid
BM25+dense measured deltas, (3) dense failure modes on exact identifiers/code,
(4) domain-shift robustness. All fetch dates 2026-10-07 unless noted.
Confidence scale: primary > secondary > speculative. Vendor first-party benchmarks
are tagged `primary (vendor)` — the vendor measured its own system; not independent.

---

## Claims

### A. Lexical/BM25 vs dense — head-to-head published evidence

**A1. BEIR's headline finding is that BM25 is a robust zero-shot baseline and
dense/sparse bi-encoders often underperform it out-of-distribution.** 18 datasets,
10 systems. Average nDCG@10 performance *relative to BM25*: DPR −47.7%, ANCE
−7.4%, TAS-B −2.8%, GenQ −3.6%, docT5query +1.6%, ColBERT +2.5%, BM25+CE +11%.
Dataset: BEIR (zero-shot), snapshot = arXiv v4, 21 Oct 2021 (NeurIPS 2021 D&B).
Source: https://arxiv.org/html/2104.08663v4 (Table 2) | fetch 2026-10-07 | **primary**

**A2. In-domain performance does not predict out-of-domain performance; BM25
underperforms neural by 7–18 points on in-domain MS MARCO yet beats many of them
zero-shot.** E.g. MS MARCO nDCG@10: BM25 0.228 vs TAS-B 0.408; TREC-COVID: BM25
0.656 vs DPR 0.332, TAS-B 0.481. Source: same BEIR v4 §5 + Table 2 | fetch
2026-10-07 | **primary**

**A3. Dense retrievers are observed to underperform BM25 specifically on datasets
with large domain shift (BioASQ) or task shift (Touché-2020).** Source:
https://arxiv.org/html/2104.08663v4 §5 finding 3 | fetch 2026-10-07 | **primary**

**A4. Contriever authors state dense retrievers "do not transfer well to new
applications with no training data, and are outperformed by unsupervised
term-frequency methods such as BM25."** Their unsupervised model beats BM25 on
11/15 datasets for Recall@100 (not nDCG@10). arXiv 2112.09118, 16 Dec 2021.
Source: https://arxiv.org/abs/2112.09118 | fetch 2026-10-07 | **primary**

**A5. Dense performance "severely degrades under a domain shift" (stated as
established prior work by the GPL authors); unsupervised domain adaptation
recovers up to 9.3 nDCG@10 points on six domain-specialized datasets.** arXiv
2112.07577, 14 Dec 2021. Source: https://arxiv.org/abs/2112.07577 | fetch
2026-10-07 | **primary**

**A6. HyDE exists because fully zero-shot dense retrieval without relevance
labels is hard; it requires an instruction-following LLM to generate a
hypothetical document to reach competitive quality.** arXiv 2212.10496, 20 Dec
2022. Source: https://arxiv.org/abs/2212.10496 | fetch 2026-10-07 | **primary**

### B. Theory: dense fixed-vector capacity and large-index failure

**B1. Probability of dense false positives increases with index size and
decreases with embedding dimensionality (proved analytically, spherical-cap
argument).** Reimers & Gurevych, ACL 2021, arXiv 2012.14210. Source:
https://arxiv.org/html/2012.14210v2 §3 | fetch 2026-10-07 | **primary**

**B2. Measured: dense 768-dim (no hard negatives) MRR@10 88.99 at 10k index →
17.34 at 8.8M index, *falling below* BM25 at 8.8M (17.56).** MS MARCO passage,
8.8M docs. Source: https://arxiv.org/html/2012.14210v2 Table 1 | fetch
2026-10-07 | **primary**

**B3. BM25 ranked a randomly generated noise passage above the relevant passage
for 0.00% of queries at every index size (100k/1M/10M/100M); dense 128-dim did so
for up to 9.73%.** MS MARCO/NQ. Source: same paper Table 3 | fetch 2026-10-07 |
**primary**

**B4. DPR retrieved a random-string passage above the relevant passage for up to
12.08% of questions when the index contained 100M entries with real Wikipedia
titles + random paragraphs.** Source: same paper Table 3 | fetch 2026-10-07 |
**primary**

**B5. Dual-encoder capacity is bounded by encoding dimension, margin between gold
and lower-ranked docs, and document length — a limitation for precise retrieval of
long documents; sparse-dense hybrids are proposed to "capitalize on the precision
of sparse retrieval."** Luan et al., TACL 2021, arXiv 2005.00181. Source:
https://arxiv.org/abs/2005.00181 | fetch 2026-10-07 | **primary**

### C. Exact identifiers, entities, and code-specific failures

**C1. Dense retrievers "drastically underperform sparse methods" on simple,
entity-rich questions (EntityQuestions); they generalize only to common entities
unless the question pattern was seen in training, and data augmentation does not
fix it.** Sciavolino et al., arXiv 2109.08535, 17 Sep 2021. Source:
https://arxiv.org/abs/2109.08535 | fetch 2026-10-07 | **primary**

**C2. "Token amnesia": dense retrievers' inability to handle tail entities
correlates with the token distributions forgetting entity tokens; injecting
lexical information at inference improves zero-shot retrieval, specifically on
BEIR.** "What Are You Token About?" ACL 2023. Source:
https://aclanthology.org/2023.acl-long.140.pdf (also https://belinkov.com/assets/pdf/acl2023-token.pdf)
| fetch 2026-10-07 | **primary**

**C3. CoIR (code retrieval) headline: "even state-of-the-art models struggle in
code retrieval"; models that top text leaderboards do not transfer — GTE-Base
ranks 2nd on BEIR but 6th on CoIR.** CoIR, ACL 2025, arXiv 2407.02883v3.
Source: https://arxiv.org/html/2407.02883v3 §5.4 Table 6 | fetch 2026-10-07 |
**primary**

**C4. On CoIR, BM25 average nDCG@10 = 29.79 vs dense/code models: Contriever
36.40, GTE-Base 36.75, UniXcoder 37.33, BGE-M3 39.31, BGE-Base 42.77,
OpenAI-Ada-002 45.59, E5-base 50.90, E5-Mistral 55.18, Voyage-Code-002 56.26.**
Counter-evidence: dense generally beats BM25 on code retrieval. Source:
https://arxiv.org/html/2407.02883v3 Table 3 | fetch 2026-10-07 | **primary**

**C5. CoIR explicitly lists as a benchmark limitation that real code needs
meta-data (programming-language / library *versioning* materially changes whether
a snippet works) and that its queries are purely semantic/textual.** Directly
relevant: version strings are not covered by any benchmark. Source:
https://arxiv.org/html/2407.02883v3 §7 Limitations | fetch 2026-10-07 | **primary**

**C6. BM25's weakness on code is largely an *IDF/tokenization* problem, not a
lexical-vs-dense problem: replacing BM25's log RSJ-odds IDF with a q-log lifted
CoIR CodeSearchNet-Go nDCG@10 from 0.2575 → 0.4874 (+89.3%, p≤1e-4), and an
identifier-aware tokenization ablation "largely removes the incremental gain."**
arXiv 2605.18561, 18 May 2026. Source: https://arxiv.org/abs/2605.18561 | fetch
2026-10-07 | **primary**

**C7. CodeSearchNet Challenge defines the code-search task precisely as needing
to "bridge the gap between the language used in code (often abbreviated and highly
technical) and natural language" — i.e. queries and corpus are lexically
different by construction.** 6M functions, 6 languages, 99 expert-annotated
queries. arXiv 1909.09436. Source: https://arxiv.org/abs/1909.09436 | fetch
2026-10-07 | **primary**

**C8. CodeRAG-Bench counter-finding: dense embedding models frequently surpass
BM25 on code retrieval, because competitive retrievers are trained on code data;
Jina-v2-code beats GIST-base and BGE-base by 7.4 and 6.6 average nDCG@10.** arXiv
2406.14497, NAACL 2025 Findings. Source: https://arxiv.org/html/2406.14497v2 §3.2
| fetch 2026-10-07 | **primary**

**C9. BRIGHT: the then-top MTEB retriever (SFR-Embedding-Mistral) scored 59.0
nDCG@10 on MTEB but only 18.3 on BRIGHT — reasoning-intensive queries (incl.
coding) collapse retrieval quality.** arXiv 2407.12883, 16 Jul 2024. Source:
https://arxiv.org/abs/2407.12883 | fetch 2026-10-07 | **primary**

### D. Hybrid (BM25 + dense) — measured deltas

**D1. Reciprocal Rank Fusion (RRF) "consistently yields better results than any
individual system" across TREC experiments; rank-based, needs no score
calibration; k=60 default.** Cormack, Clarke & Buettcher, SIGIR 2009, pp. 758–759,
DOI 10.1145/1571941.1572114. Source:
https://dl.acm.org/doi/pdf/10.1145/1571941.1572114 (abstract confirmed via
https://scholar.google.com/citations?view_op=view_citation&user=TkVleDIAAAAJ&citation_for_view=TkVleDIAAAAJ%3A7PzlFSSx8tAC)
| fetch 2026-10-07 | **primary**

**D2. Elastic first-party: RRF (k=20, N=1000) raises average NDCG@10 by 1.4%
over ELSER alone and 18% over BM25 alone on a 9-dataset BEIR subset; result is
better-or-equal to BM25 alone on all test datasets.** Blog dated 20 Jul 2023.
Source: https://www.elastic.co/search-labs/blog/improving-information-retrieval-elastic-stack-hybrid
| fetch 2026-10-07 | **primary (vendor)**

**D3. Elastic: picking the best method per dataset gives +3% (over ELSER) and
+20% (over BM25) — the ceiling hybrid tuning chases; linear score combination
needs ~40 annotated queries to beat RRF and is not "plug and play".** Source:
same Elastic blog | fetch 2026-10-07 | **primary (vendor)**

**D4. Vespa first-party BEIR (13 datasets, nDCG@10): Vespa BM25 avg 0.453,
Vespa ColBERT avg 0.363, Vespa hybrid ColBERT+BM25 avg 0.481 — hybrid best on
12 of 13 datasets.** ColBERT in-domain MS MARCO 0.401 vs BM25 0.228, but ColBERT
underperforms BM25 out-of-domain (e.g. CLIMATE-FEVER 0.067 vs 0.207). Blog dated
09 Jan 2023. Source: https://blog.vespa.ai/improving-zero-shot-ranking-with-vespa-part-two/
| fetch 2026-10-07 | **primary (vendor)**

**D5. BEIR SIGIR-2024 resource paper: hybrid (Contriever + SPLADE fusion) gives
"more than a six-point gain on average" over the best individual model, with
gains "consistent"; four exceptions: BioASQ, Touché-2020, ArguAna, Quora.** arXiv
2306.07471, 13 Jun 2023. Source: https://arxiv.org/html/2306.07471v1 | fetch
2026-10-07 | **primary**

**D6. Qdrant first-party: across five BEIR-style datasets, default RRF beat the
stronger individual retriever on 4/5. CodeSearchNet: dense 0.6299, sparse 0.5126,
hybrid 0.6555 nDCG@10 (+0.0256). SciFact 0.6886→0.7175; ArguAna 0.4905→0.5216;
WANDS 0.7098→0.7254; DBPedia-entity exception (hybrid 0.4638 < dense 0.4677).**
Source: https://qdrant.tech/documentation/search-tuning/hybrid-search/ | fetch
2026-10-07 | **primary (vendor)**

**D7. Fusion only reorders the union of the two retrievers' candidates — "a
document neither one found cannot appear anywhere in the results."** Source:
same Qdrant doc | fetch 2026-10-07 | **primary (vendor)**

**D8. SPLADE (learned sparse) keeps exact term matching + inverted index, gains
>9% NDCG@10 on TREC DL 2019 over prior SPLADE and reaches SOTA on BEIR;
SPLADE++ reaches 38.3 MRR@10 on MS MARCO dev.** arXiv 2107.05720 (SIGIR'21),
2109.10086 (v2), 2205.04733 (SPLADE++); official repo
https://raw.githubusercontent.com/naver/splade/main/README.md | fetch 2026-10-07
| **primary**

**D9. Efficient SPLADE achieves latency "less than 4ms difference" from BM25
under the same compute constraints while keeping within 10% MRR@10 of the
state-of-the-art single-stage neural ranker (in-domain).** Lassance & Clinchant,
SIGIR 2022, DOI 10.1145/3477495.3531833, cited in official repo | fetch 2026-10-07
| **primary**

**D10. WANDS e-commerce: BM25 0.6983, pure KNN 0.6953, basic RRF 0.7068,
field-boosted hybrid 0.7497 mean nDCG — BM25 and dense statistically
indistinguishable, fusion reliably above both.** Turnbull study, March 2025;
reported via third-party write-up (softwaredoug.com primary not fetched).
Source: https://www.digitalapplied.com/blog/hybrid-search-bm25-vector-reranking-reference-2026
| fetch 2026-10-07 | **secondary**

### E. Retrieval-to-context: ordering and context limits

**E1. "Lost in the Middle": LLM performance is highest when relevant information
sits at the beginning or end of the input context and degrades significantly when
it must be found in the middle — so even correctly-retrieved evidence can be
wasted.** arXiv 2307.03172, 6 Jul 2023. Source:
https://arxiv.org/abs/2307.03172 | fetch 2026-10-07 | **primary**

**E2. Cost/size asymmetry (CPU-relevant): BEIR 1M-doc DBPedia index — BM25
0.4GB / 20ms CPU vs dense 768-dim 3GB / 125–275ms CPU vs ColBERT 20GB.** On
BioASQ (~15M docs) ColBERT needs ~900GB vs BM25 18GB. Source:
https://arxiv.org/html/2104.08663v4 §5.1 Table 3 | fetch 2026-10-07 | **primary**

**E3. CoIR efficiency on CodeFeedBack-ST (156k corpus, 31k queries): embedding
latency per sample 7.4–7.8ms for 768-dim base models, 31.4ms for BGE-M3 (1024),
1840ms for E5-Mistral (7B); index sizes 0.3GB–2.3GB.** Source:
https://arxiv.org/html/2407.02883v3 Table 4 | fetch 2026-10-07 | **primary**

## Conflicting evidence

**K1. Dense vs BM25 on code — direct conflict.**
- F8-C4 (CoIR, ACL 2025): BM25 29.79 avg nDCG@10, beaten by most dense models
  (E5-Mistral 55.18).
- F8-C8 (CodeRAG-Bench, NAACL 2025): "dense embedding models frequently surpass
  BM25" on code; code-specific models win by 6.6–7.4 nDCG@10.
- F8-A1/A2/A3 (BEIR, 2021): dense bi-encoders underperform BM25 out-of-domain.
Reconciliation: the BEIR result is for **general-domain** encoders on
**natural-language** corpora; CoIR/CodeRAG-Bench use **code-trained or
multi-domain-trained** encoders on **code** corpora. Where the encoder has been
trained on code, dense wins on code; where it has not (and the domain shifts),
BM25 wins. CoIR's own §5.4 (F8-C3) shows the same model ranking differently
between BEIR and CoIR. → **Carry forward:** for a *general* small local embedding
model on agent chatter (mixed prose + identifiers), BEIR is the closer analogue;
for a *code-trained* model on code, dense can win. Which regime applies depends
on model choice, not on "embeddings vs BM25" in the abstract.

**K2. BEIR itself is biased against dense — an important caveat that weakens
A1/A2 as pure anti-dense evidence.**
- F8-A1: dense underperforms BM25 on BEIR.
- BEIR §6 (same paper): many BEIR datasets were annotated from lexical retrieval
  pools (lexical bias). Hole@10: BM25 6.4%, docT5query 2.8% vs TAS-B 31.8%, ANCE
  14.4%, DPR 30.6%. After manually annotating the holes on TREC-COVID, ANCE went
  0.654 → 0.735 (6.7 points *above* BM25), ColBERT 0.677 → 0.735.
Reconciliation: BEIR's own authors state the benchmark "can give an unfair
disadvantage to non-lexical approaches." Both claims are true: BM25 wins on BEIR
as scored, *and* BEIR's scoring penalises dense. → **Carry forward:** do not treat
BEIR aggregate gaps as ground truth for a new domain; the direction (BM25 robust
zero-shot) survives, the magnitude does not. Source:
https://arxiv.org/html/2104.08663v4 §6 Table 4 | fetch 2026-10-07 | **primary**

**K3. Hybrid gains are real but not universal.**
- F8-D2/D4/D5/D6: hybrid beats both parents on most datasets.
- F8-D5: four BEIR exceptions (BioASQ, Touché-2020, ArguAna, Quora).
- F8-D6: DBPedia-entity exception, hybrid 0.4638 < dense 0.4677.
- F8-D4: on in-domain MS MARCO, adding BM25 *hurt* ColBERT (0.401 → 0.344),
  because fusing a much weaker retriever degrades a strong one.
Reconciliation: fusion helps when the two retrievers have comparable strength and
complementary errors; it hurts when one is far weaker (Elastic §: "hybrid search
performs strongly when both methods have similar overall accuracy"). → **Carry
forward:** the hybrid gain is conditional on relative retriever quality, not
automatic.

**K4. Dense retrieval can be improved rather than replaced.**
- F8-C2: lexical enrichment at inference improves dense on BEIR.
- F8-A5/F8-D8: domain adaptation (GPL) and learned sparse (SPLADE) close gaps.
- F8-C6: BM25's code weakness is fixable by IDF/tokenization changes.
Reconciliation: "lexical vs dense" is not the only axis; both sides have
fixable failure modes. → **Carry forward:** the honest counter-argument is not
"embeddings are useless" but "a plain general-purpose dense model with no lexical
channel is the wrong default for identifier-heavy text."

## Gaps

1. **No published benchmark on agent/LLM chat-log retrieval.** No paper found
   measuring retrieval over agent transcripts, tool-call logs, or chatroom
   chatter. All identifier-heavy evidence is proxied from code retrieval (CoIR,
   CodeSearchNet, CodeRAG-Bench) and entity retrieval (EntityQuestions). This is
   the single largest gap for the repo's actual corpus.
2. **No head-to-head BM25 vs dense on error codes / hashes / version strings.**
   Failure-mode claims (B1–B4, C1) are on entities, product codes, and random
   strings; error-code and hash tokens specifically are asserted by practitioner
   sources only (e.g. the `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` example at
   https://tianpan.co/blog/2026/04/12/hybrid-search-production-bm25-dense-embeddings
   — **secondary**, not fetched as primary).
3. **BEIR official leaderboard (eval.ai challenge 1897) is JS-rendered and
   returned empty on fetch.** Current SPLADE/BM25 leaderboard numbers could not
   be verified from the primary leaderboard; only the 2021 paper and the 2023
   SIGIR resource paper were readable. Any "current BEIR average" figure should
   be treated as unverified.
4. **No CPU-specific dense-vs-BM25 latency benchmark for the target hardware
   class (4c/8t, no CUDA, 15GB).** BEIR reports CPU latency on an 8-core Xeon
   Platinum 8168 (E2); CoIR reports GPU embedding latency (E3). Extrapolation to
   i5-1135G7 is inference, not measured.
5. **SPLADE/BGE-M3 hybrid deltas on code not measured.** CoIR (F8-C4) evaluates
   BM25 and dense but not hybrid; CodeRAG-Bench adds a BGE reranker but the
   hybrid-vs-parents delta for code is not reported as a single nDCG@10 figure.
6. **WANDS numbers (F8-D10) are secondary** — the underlying Turnbull study
   (softwaredoug.com, March 2025) was not fetched; treat as indicative only.
