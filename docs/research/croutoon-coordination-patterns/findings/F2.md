## Angle
Claims/leases/fencing: TTL leases, fencing epochs/tokens, lease renewal/heartbeat, claim expiry/reclaim. Evidence from etcd/Zookeeper lease+fencing-token docs, contract-net protocol, work-stealing schedulers, and LLM claim-board implementations.

## Claims
- etcd LeaseGrant TTL advisory, server selects actual TTL >= requested; no keepalive within TTL -> lease expires, attached keys deleted. Source: https://etcd.io/docs/v3.7/learning/api/ — fetch 2026-11-09 — confidence: primary (official etcd docs, Lease API section: "Leases are a mechanism for detecting client liveness... lease expires if etcd does not receive a keepAlive within a given TTL period... When a lease expires or is revoked, all keys attached deleted").
- etcd LeaseKeepAlive bidirectional stream refreshes lease, response returns ID + remaining TTL. Source: https://etcd.io/docs/v3.7/learning/api/ — fetch 2026-11-09 — confidence: primary (same page, Keep alives section).
- etcd fencing token = key creation revision (create_revision), 64-bit cluster-wide counter incremented on every keyspace modification; distributed lock in etcd client uses creation revision as ordering. Source: https://etcd.io/docs/v3.7/learning/api/ — fetch 2026-11-09 — confidence: primary (Key-Value pair / Revisions section: "create_revision... etcd client's distributed shared locks use creation revision... revision serves as global logical clock").
- Lease alone != mutual exclusion for external resources; paused/partitioned former holder can still act after lease expires unless protected resource validates fencing token. Source: https://etcd.io/docs/v3.5/learning/why/ (secondary capture via search, etcd docs) + Kleppmann primary for full argument — fetch 2026-11-09 — confidence: primary (etcd docs) corroborated by Kleppmann 2016.
- Kleppmann fencing pattern: strictly monotonically increasing token per lock acquisition; client includes token with every write; resource remembers highest accepted token, rejects lower. Client-side check/heartbeat alone insufficient — GC pause can occur between last check and write. Source: https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html — fetch 2026-11-09 — confidence: primary-authority (Kleppmann, distributed locking, citing Gray-Cheriton 1989 leases + Chubby 2006). Example: A token 33 pauses, lease expires, B gets 34 writes, A resumes with 33 -> rejected.
- Kleppmann: UUID/random token insufficient; storage cannot distinguish unseen-but-stale UUID from legitimate new holder without monotonic ordering. Source: same Kleppmann page, comments + main text "Redlock does not have facility for generating fencing tokens... unique random value does not provide monotonicity" — fetch 2026-11-09 — confidence: primary-authority, author answer in comments.
- ZooKeeper session expiry decided by cluster, not client; negotiated session timeout + missed heartbeats (PING). On expiry cluster deletes session ephemeral znodes. Partitioned client learns expiry only on reconnect. Source: https://zookeeper.apache.org/doc/current/zookeeperProgrammers.html — fetch 2026-11-09 — confidence: primary (Apache official programmer guide, Sessions section).
- ZK zxid = total ordering of all state changes; each change unique zxid, smaller zxid happened before. version/cversion/aversion per znode. Source: same ZK programmers guide, Time in ZooKeeper section — fetch 2026-11-09 — confidence: primary.
- ZK lock recipe: ephemeral sequential nodes; lowest sequence number holds lock; single-watcher avoidance of herd effect; no polling/timeouts in recipe. Ambiguity: create() can succeed server-side but client never learns node name (server crash before return) — must handle via GUID. Source: https://zookeeper.apache.org/doc/r3.9.3/recipes.html — fetch 2026-11-09 — confidence: primary (Apache recipes doc).
- ZK TTL nodes (3.5.3+): PERSISTENT/PERSISTENT_SEQUENTIAL with TTL ms; unmodified + no children -> candidate for deletion at some future point; disabled by default via system property. Source: ZK programmers guide, TTL Nodes — fetch 2026-11-09 — confidence: primary.
- Chubby master lease: master must obtain majority votes + promises not to elect different master for "few seconds" interval = master lease; periodically renewed if master keeps winning majority. Source: https://www.usenix.org/legacy/events/osdi06/tech/full_papers/burrows/burrows.pdf (Burrows OSDI 2006) — fetch 2026-11-09 — confidence: primary (peer-reviewed paper).
- Chubby session KeepAlive: client session lease extends into future; master advances timeout only forward (creation, failover, KeepAlive response). Master blocks KeepAlive RPC until previous lease close to expiring, then returns new timeout; default extension 12s, overloaded master up to ~60s. Client keeps local conservative approx of master timeout (accounts in-flight time + clock rate), jeopardy -> grace period 45s default, blocks app calls, then expires. Source: same Chubby paper §2.8 — fetch 2026-11-09 — confidence: primary.
- Chubby sequencer = fencing token equivalent: GetSequencer returns opaque byte-string (lock name, mode, lock generation number); client passes to file server, recipient tests validity via Chubby cache or most recent sequencer observed, rejects if invalid/wrong mode. Lock-delay (up to 1 min) protects servers not supporting sequencers. Source: same Chubby paper §2.4 — fetch 2026-11-09 — confidence: primary.
- Chubby lock-generation number increases free->held; instance/content/ACL generation numbers monotonically increasing 64-bit. Source: same paper §2.3 — fetch 2026-11-09 — confidence: primary.
- Chubby failover: new master picks new client epoch number, rejects calls with older epoch, rebuilds sessions from DB + conservative lease extension, waits for each session to ack fail-over event or expire. Source: same paper §2.9 — fetch 2026-11-09 — confidence: primary.
- Gray-Cheriton 1989 leases: lease correctness depends on synchronized clocks / bounded clock drift; clock-rate errors cause holder/server disagreement on expiry. Source: https://www.cs.cmu.edu/afs/cs.cmu.edu/academic/class/15712-s12/www/papers/gray89.pdf — fetch 2026-11-09 — confidence: primary (SOSP paper; PDF text extraction incomplete, exists as citation in Kleppmann refs; claim restated from Kleppmann citing it — marked primary-paper / secondary-capture).
- K8s Lease object: spec.holderIdentity, spec.renewTime (last update), spec.leaseDurationSeconds (wait to force-acquire measured against renewTime), spec.leaseTransitions (count of holder transitions), spec.acquireTime. Node heartbeats = update renewTime; control plane uses timestamp for availability. Source: https://kubernetes.io/docs/concepts/architecture/leases/ + https://kubernetes.io/docs/reference/kubernetes-api/coordination/lease-v1/ — fetch 2026-11-09 — confidence: primary (official k8s docs/API reference).
- K8s coordinated leader election: candidates use LeaseCandidate objects + Lease; holderIdentity must equal elected LeaseCandidate name. Source: https://kubernetes.io/docs/concepts/architecture/leases/ — fetch 2026-11-09 — confidence: primary.
- Martin Fowler Lease pattern: time-bound lease for cluster nodes, TTL associated; holder responsible for periodic refresh; HeartBeat used to refresh TTL in consistent core. Source: https://martinfowler.com/articles/patterns-of-distributed-systems/lease.html — fetch 2026-11-09 — confidence: secondary-synthesis (book chapter summary, points to oreilly ch26; no primary code/spec).
- Contract-Net Protocol (Smith IEEE TC C-29 Dec 1980, pp 1104-1113): task announcement with slots eligibility-spec, task-abstraction, bid-spec, expiration-time (deadline for bids). Nodes rank announcements, submit bids; manager evaluates bids, may award before expiration if satisfactory else on expiration may award best acceptable / reannounce / wait. Award via announced-award message with task-specification. Sources: https://www.reidgsmith.com/The_Contract_Net_Protocol_Dec-1980.pdf — fetch 2026-11-09 — confidence: primary (author-hosted original paper).
- Contract-Net extensions relevant to claims: directed contracts (skip announcement/bid, send directed award + acceptance/refusal with justification INELIGIBLE/NO TEMPLATE), node-available messages (invert: idle node broadcasts availability with eligibility-spec + expiration, manager sends directed award), immediate-response bids (BUSY/INELIGIBLE/LOW-RANKING). Source: same Smith paper §IV-B — fetch 2026-11-09 — confidence: primary.
- Work stealing (Cilk): workers keep local pools; idle worker picks victim (randomly) and steals. Theoretical bound: T_P <= T_1/P + O(T_inf) where T_1 work, T_inf span. Source: https://cilk.mit.edu/runtime/ — fetch 2026-11-09 — confidence: primary (MIT Cilk project docs).
- Java ForkJoinPool: work-stealing executor; all threads attempt to find/execute tasks submitted to pool or created by other active tasks, eventually block waiting for work. getStealCount() is estimate, not exact while pool busy. Source: https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/concurrent/ForkJoinPool.html — fetch 2026-11-09 — confidence: primary (Oracle JDK API docs).
- byzantine-lease (LLM swarm): in-memory DistributedLeaseManager; acquire_lease TTL default 15.0s, on free/expired increments highest fencing token (+1), issues LeaseRecord; renew_heartbeat requires matching agent_id + fencing_token and now <= expires_at else marks EXPIRED returns false; verify_write rejects submitted_token < highest_token as FencingTokenStale, also rejects if no matching active lease or expired. Source: https://github.com/AAH20/byzantine-lease + raw lease_manager.py — fetch 2026-11-09 — confidence: primary (source code, MIT, 0 stars — single implementation, not established standard).
- dibs (parallel coding agents, Go, MIT): file claims = leases with TTL; default 30m, max 24h; claim JSON with id/agent/patterns/reason/created/expires/renewals; expiry evaluated lazily at read; expired pruned under advisory lock (flock) and journaled as expire; renew extends all own leases from now; re-claiming own identical pattern set renews in place. Conflict check before edit + optional Claude Code PreToolUse hook blocks colliding edits. Source: https://github.com/polymatx/dibs + raw internal/coord/lease.go — fetch 2026-11-09 — confidence: primary (source code).
- llm-bus (MCP coordination, TS, AGPL): atomic gap-free claim via single SQL upsert (INSERT...ON CONFLICT DO UPDATE current+1 RETURNING) + ledger event in same tx, proven 500 concurrent claims; advisory file leases report contention, do not block filesystem (fail-open, never deadlock). Source: https://github.com/danieldoderlein/llm-bus + docs/coordination-layer.md — fetch 2026-11-09 — confidence: primary (source docs, self-reported dogfooding 8 days, 591 events).
- Waymark (Claude Code blackboard, Python stdlib + SQLite): intent leases, reason leases, heartbeats, release counts, abandonment, lazy expiry; SQLite transactions prevent double-claims; CLI + sqlite = authority. Source: https://github.com/Y4tacker/Waymark — fetch 2026-11-09 — confidence: primary (repo README); fencing tokens NOT documented.

## Conflicting evidence
- Lease TTL semantics: etcd LeaseGrant TTL = "advisory, server selects actual TTL >= requested" (etcd docs) vs dibs LLM-board TTL = exact client-chosen 30m default clamped to 24h max, expiry = ExpiresAt.After(now). No conflict — different layers (distributed KV vs local file board). Reconciliation: etcd TTL not precise deadline; dibs is local-clock wall time, no clock-skew handling.
- Fencing enforcement location: Kleppmann/Chubby require protected resource itself check token (file server checks sequencer). byzantine-lease verify_write() is a separate manager call, not enforced by storage — client must call it before writing; if client skips verify, stale write passes. dibs/llm-bus leases are advisory — enforcement is hook/protocol, not resource. Conflict between "lease = claim board advisory signal" (LLM boards) vs "lease+token = safety boundary" (Kleppmann/Chubby/etcd). Reconciliation: LLM boards accept best-effort collision prevention; Kleppmann safety requires resource-side check — boards do not provide it.
- Clock model: Gray-Cheriton/Chubby/Kleppmann require bounded clock drift for lease safety; etcd/K8s lease docs do not state clock assumption (they use server-side expiry / renewTime timestamps). LLM boards use naive local time.time()/time.Time with no skew bound. Reconciliation: production KV leases rely on server clock single source; local boards have no distributed clock — expiry is heuristic only.
- Contract-Net vs lease claim: Contract-Net is negotiation (announce->bid->award) with expiration-time deadline for bids, no fencing token; lease systems are exclusive hold + TTL. Not contradictory — CNP solves allocation among many bidders; lease solves single-holder exclusion. CNP expiration != lease TTL (bid deadline vs hold duration).
- Work-stealing vs claim board: work-stealing has no leases/TK/TTL at all — tasks are movable via stealing, no exclusive claim. Contrasts with claim-board model where resource is locked until TTL. Relevance: work-stealing avoids claim expiry problem by making work stealable/idempotent, not exclusively leased. No conflict, different tradeoff (stealable tasks vs exclusive claims).
